# TELME 백엔드 문서

서비스의 공통 기준, 채팅 처리 흐름, 독립 기능, 품질 평가, 운영 절차를 안내한다. 기존 문서는 작성 당시의 조건과 결론을 보존한다. 폴더 이동이나 파일명 통일은 과거 실험의 운영 적용 또는 최신성 확인을 의미하지 않는다.

## 분류 원칙

- `00-overview`: 서비스 정책과 FAQ 분류 등 공통 기준.
- `01-pipeline`: 채팅 처리 단계와 그 단계의 기술 결정·실험. 여러 단계에 걸친 복합 상담 문서는 파이프라인 최상위에 둔다.
- `02-features`: 매장·요금제 등 독립 기능. 해당 기능에만 필요한 운영 지식은 기능 문서 옆에 둔다.
- `03-evaluation`: 파이프라인 전체의 평가 기준·Judge·여러 호출을 함께 비교한 결과. 검색 전용 평가셋과 실험은 검색 단계에 둔다.
- `04-operations`: DB 마이그레이션, 전체 모델 전환 설정, 장애 대응, 서빙과 관측.
- 벤치마크는 검증하는 설계 가까이에 둔다. 측정 문서라는 이유만으로 공통 평가 폴더에 모으지 않는다.

## 파일명과 문서 작성 기준

### 이름과 경로

- 일반 문서는 소문자 `kebab-case.md`를 사용한다. 각 묶음의 진입점은 `README.md`다.
- 번호는 최상위 읽는 순서와 파이프라인 단계에만 사용한다. 모든 파일에 번호를 붙이지 않는다.
- 기존 파일명에서 의미를 보존하고 대소문자·구분자를 통일한다. 날짜가 실험 식별자이면 유지한다.
- `results/`의 실행 폴더·원시 데이터·기존 결과 파일명은 증거 보존을 위해 유지한다. 압축 파일 내부 경로, 과거 커밋 URL, 측정 당시 절대경로도 현재 경로로 바꾸지 않는다.
- `scripts/`의 Python 모듈명과 기존 실행 진입점은 별도다. 문서 컨벤션을 맞추기 위해 스크립트를 일괄 이동하거나 이름을 바꾸지 않는다.

### 본문 형식

모든 문서를 같은 목차로 강제하지 않는다. 다음 항목은 새 문서나 실제 내용 개정 시 필요한 것만 사용한다.

| 문서 성격 | 포함하면 좋은 정보 |
| --- | --- |
| 현재 명세 | 적용 범위, 입력·출력, 처리 규칙, 실패·예외, 설정, 검증·한계 |
| 기술 결정·실험 | 문제, 비교 대안, 코드·환경·평가셋·설정, 결과, 해석·한계, 채택 또는 보류 |
| 검증 기록 | 대상 커밋·경로, 실행 절차, 확인 결과, 미확인 항목 |
| 운영 가이드 | 적용 전제, 절차, 확인 방법, 실패 시 조치·되돌리기, 영향 범위 |

- 제목, 기존 절 번호, 표, 수치, 코드 예시, 결론, 미확인·미적용 표시는 경로 정리를 이유로 바꾸지 않는다.
- `현행`, `후보`, `과거 실험`, `적용 완료`는 코드·배포·측정 근거를 확인한 경우에만 명시한다. 과거 문서의 표현을 현재 동작으로 자동 갱신하지 않는다.
- 내용 개정과 경로 정리는 별도 변경으로 검토한다. 본문 개정 시에는 바꾼 이유와 근거를 함께 남긴다.

### 스크립트와 실험 근거 연결

- 실험 문서에는 실제 존재하는 실행 도구·평가셋·결과 경로를 연결한다. 명령은 저장소 루트에서 실행하는지 별도로 표시한다.
- 도구가 별도 보관되거나 일부 자료가 없으면 재현 가능하다고 표시하지 않는다. [매장 거리 계산 실측](02-features/store/store-nearest-search.md)의 도구 보관 조건처럼 기존 제한을 유지한다.
- 실행 시 외부 모델·API·DB가 필요한지, 호출 비용·데이터 변경이 있는지는 해당 실행 안내에서 확인한다.
- `scripts/README.md`는 실행 목적별 입구이며 문서 트리를 일대일 복제하지 않는다.

## 경로 변경 시 주의

문서는 Markdown 링크 외에도 Python 파서, 생성 도구, Java 테스트와 코드 주석에서 참조된다. 경로를 변경하면 이 참조를 함께 확인한다. 이미 적용된 Flyway SQL은 주석만 바꿔도 체크섬이 달라지므로 수정하지 않는다. 마이그레이션에 남은 과거 문서 경로는 커밋 당시의 참조로 보존한다.

# 단일 FAQ 검색어 보존과 재검색

고객 원문과 검색용 문장을 각각 보존한다. 원문 검색이 0건이고 검색 문장이 다르면, 그때 검색 문장의 의미를 검증해 통과한 문장으로 다시 검색한다. 원문에 없는 조건이나 업무를 추가한 문장, 의미 검증이 실패한 문장은 재검색에 사용하지 않는다.

## 처리 기준

1. 라우터는 구어 표현을 검색에 적합한 같은 뜻의 문장으로 다듬는다. 상황만 말한 질문은 일반적인 처리 안내로 바꾸며 특정 해결책으로 좁히지 않는다.
2. 라우팅은 숫자와 지역의 기존 검증만 하고, 다듬은 문장을 검색 후보로 저장한다. 이 단계에서는 의미 검증 모델을 부르지 않는다.
3. 원문과 검색어가 띄어쓰기만 다르면 원문을 사용한다. 단독 비교 질문은 두 대상을 포함한 원문을 유지한다.
4. 검색은 원문을 먼저 사용한다. 원문에서 후보를 찾으면 추가 검색과 의미 검증을 모두 생략한다.
5. 원문 검색이 0건이고 검색어가 다를 때만 `QueryRoutingService.refinedSearchQuery`로 검색어를 검증한다. 먼저 `SearchTopicPolicy`가 원문에 없는 업무 대상(유심, 번호이동, 명의변경, 해지, 요금제, 청구·납부 등)이 검색어에 새로 생겼는지 본다. 생겼으면 모델을 부르지 않고 거절한다. "번호를 옮기고"와 "번호이동"처럼 같은 대상의 다른 표현은 같은 대상으로 본다. 이 판정을 통과한 문장만 모델로 조건, 부정, 업무 의미를 검증한다. 같은 뜻의 표현은 원문 단어와 일치하지 않아도 유지한다. 통과한 문장으로 `REFINED` 검색을 실행하고, 검증 결과는 실행 trace의 `refinedQueryChecks`에 남긴다.
6. 검증에 실패했고 "싶/하려고/할래"처럼 업무 수행 의사를 밝힌 질문이면, 원문에 있는 단어만 남긴 문장을 만들어 같은 의미 검증을 한 번 더 거친다. 예를 들어 "번호이동하고싶어요"의 후보 "번호이동 방법 및 필요 절차"가 거절되면 "번호이동 방법"을 검증한다. 이 문장도 조건을 빠뜨리면 거절해 재검색하지 않는다.
7. RAG에 전달하는 고객 질문은 원문이다. 검색어를 고객의 확정 조건으로 사용하지 않는다. 이전 대화 복원과 복합 질문별 검색은 기존 경로를 유지한다.

| 원문 | 검색어 | 처리 |
|---|---|---|
| 유심을 잃어버렸어요 | 유심 분실 처리 안내 | 의미가 검증되면 유지 |
| 유심을 잃어버렸어요 | 유심 분실 시 재발급 방법 | 해결책을 재발급으로 좁히므로 거절 |
| 미납 요금이 있는데 번호이동하고 싶어요 | 번호이동 신청 방법 | 미납 조건이 빠졌으므로 거절 |
| 해지는 원하지 않고 요금만 줄이고 싶어요 | 해지 신청 방법 | 부정과 업무 의미가 바뀌므로 거절 |
| 지난달에 한 번 바꿨는데 이달에 또 바꿔도 되는지 궁금합니다 | 동일 기간 내 유심 재발급 가능 여부 | 원문에 없는 유심을 만들었으므로 모델 검증 전에 거절 |

운영 변경은 `QueryRoutingService`의 단일 FAQ 검색어 보존과 재검색 직전 의미 검증, `SearchTopicPolicy`의 업무 대상 판정, `FaqSearchAnswerProvider`의 재검색 문장 선택, 라우팅 프롬프트다. 공개 API, DB 스키마와 검색 임계값은 추가하거나 변경하지 않는다. 검색 후보 문장은 기존 `refinedQuery`와 상담 요청의 `queryText`, 고객 원문은 기존 메시지의 `content`에 저장한다. 저장된 후보는 의미 검증 전 문장이므로 검색 외의 용도로 쓰지 않는다.

기준 커밋은 최신 develop `02f0b3d8`이다. 해당 커밋의 소스를 별도로 빌드한 기준 앱과 수정한 앱에 같은 8개 시나리오, 9개 발화를 보냈다. Docker EXAONE 3.5 7.8B, bge-m3와 독립 PostgreSQL 평가 DB를 사용했다. FAQ와 임베딩은 각각 1,152건이며 이전 평가용 FAQ 2건이 포함되어 있다. QA 임계값 0.72, 질문 벡터 임계값 0.88, 이중 벡터 검색은 유지했다.

| 유심 재발급 서류 | 원문 검색 후 대리인 여부 되묻기 | 같은 흐름, 재검색 없음 |

기준과 수정 앱의 실행은 각각 9건 모두 완료됐다. SSE 완료 메시지 ID와 저장 메시지가 일치했고, 전송된 토큰과 저장 본문도 일치했다. 이는 처리 흐름 검사이며 답변 정확도 100%를 뜻하지 않는다.

이 측정은 의미 검증을 라우팅 단계에서 매번 하던 초기 구현이다. 의미 검증이 5회 추가 호출됐고 호출 시간 중앙값은 390ms, 전체 발화 처리 시간 중앙값은 기준 2,344ms, 수정 3,016ms였다. 원문 검색이 성공한 질문도 검증 비용을 냈기 때문에, 현재 구현은 검증을 원문 검색 0건 이후로 옮겼다.

### 테스트

전체 `gradlew build`는 총 2,673건 중 실패와 오류 0건, 제외 110건으로 통과했다. 단위 테스트는 동의어, 조건 누락, 부정, 잘못된 출력과 호출 실패를 확인한다. 실제 라우터를 사용하는 PostgreSQL API 통합 테스트는 원문 검색 실패 후 재검색, 원문 검색 성공 시 재검색과 의미 검증 생략, 위험한 검색어의 미사용, 원문 및 상담 상태 저장을 확인한다.

## 남은 한계

- 의미 검증은 LLM 판정이므로 잘못 허용하거나 정상 검색어를 거절할 수 있다. 평가셋에서는 원문에 없는 대상(유심)을 만든 문장을 통과시켜, 업무 대상 규칙을 먼저 적용한다. 호출이 실패하면 원문을 유지해 답변 가능성이 낮아지는 쪽으로 처리한다.
- 업무 대상 규칙은 사전에 있는 표현만 판정한다. 사전에 없는 동의어("5G 상품"과 "요금제")는 다른 대상으로 보고 거절할 수 있다. 잘못 거절하면 develop처럼 재검색하지 않을 뿐이다.
- 재검색 결과도 원문 검색과 같은 임계값만 거친다. EVAL-164처럼 찾은 FAQ에 없는 내용을 답한 사례가 있다. 원문 검색 근거에서도 생길 수 있는 기존 한계다. 이를 막는 근거 적합성 판정(`rag.evidence-check`)은 서비스 모델의 판정 정확도 문제로 꺼져 있다([ANSWER_QUALITY.md](ANSWER_QUALITY.md) 7절).
- 관련 FAQ를 찾았어도 최종 답변 품질은 별도 문제다. 일반 유심 분실 질문의 검색 결과에 해외 분실 FAQ `USIM-0040`도 포함되면서 답변에 고객이 말하지 않은 “귀국 후”가 섞였다. 별도 실행에서는 분실 신고 안내가 빠지기도 했다. 질문에 맞는 FAQ 조건 선택과 답변 필수 내용 검증의 보완 대상이다.
- 원문에서 후보가 한 건이라도 나오면 적합성 판단 전에 재검색을 생략하는 기존 정책은 유지한다. 후보가 있다는 이유만으로 질문에 답할 수 있다는 뜻은 아니다.
- 이전 대화의 신청 장소 질문을 검색하지 못한 사례는 기준과 수정 앱 모두에서 확인됐다. 이 변경만으로 모든 후속 질문의 검색 성공을 보장하지 않는다.

## 원시 자료와 재실행

[압축 원시 자료](../scripts/single-faq-search-evaluation/results.json.gz)는 시나리오 확인의 기준 실행, 최종 수정 실행, 개발 확인 실행을 구분해 보관한다. 고객 질문, 기대 동작, 모델 요청과 원시 응답, 코드 해시, 실행 trace, 검색 FAQ, 저장 답변과 SSE를 포함한다. 반복 발화를 독립 문항 수로 합산하지 않는다.

[실행 스크립트](../scripts/single-faq-search-evaluation/run_live.py)는 실제 Spring API를 호출하고 결과를 수집한다. 라우팅과 검색 및 답변 생성은 Spring이 수행한다. `telme_146_`으로 시작하는 독립 평가 DB의 서버가 필요하며, 모델 호출 기록용 로컬 프록시 소스는 압축 원시 자료에 포함되어 있다.

```powershell
python scripts/single-faq-search-evaluation/run_live.py --database telme_146_search_eval --base-url http://localhost:18135 --llm-log .measure/telme146/model-calls.jsonl --output .measure/telme146/new-run.json.gz
```

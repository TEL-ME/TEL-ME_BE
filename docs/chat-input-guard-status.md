# 채팅 입력 제한 상태 조회

## 지원 범위

- 새로고침·재접속 후 현재 회원 또는 게스트의 입력 제한 상태를 조회한다.
- 기존 인증 세션과 게스트 식별 방식을 사용한다. 다른 사용자 ID를 조회 인자로 받지 않는다.
- 현재 제한 여부만 제공한다. 경고 횟수·감지 입력·감지 이력·관리자 검토 정보는 반환하지 않는다.
- 감지 횟수·제한 기간·자동 종료·오탐 처리 등 기존 입력 검사 정책은 변경하지 않는다.
- 조회 API 제공과 실제 브라우저의 안내·전송 잠금 구현은 구분한다.

## 준비 조건

- 기존 입력 검사 기능의 `chat_input_guard_states` 테이블이 적용돼 있어야 한다.
- `guests.merged_user_id`를 통해 회원으로 승계된 게스트를 확인한다.
- 새 테이블은 추가하지 않는다. 승계 게스트 조회 인덱스는 별도 Flyway 마이그레이션으로 추가한다.
- 프런트는 기존 인증 쿠키를 유지하며 같은 사용자·게스트로 요청해야 한다.
- 식별자가 없는 첫 방문은 기존 `GuestIdentityFilter`의 게스트 발급을 따른다.
  이때 게스트 발급과 입력 제한 상태 행 생성은 별개이며, 조회는 제한 상태 행을 만들지 않는다.

## 호출 및 응답

- `GET /api/v1/chat/input-guard/status`
- 채팅 세션 ID·회원 ID·게스트 ID·본문 없이 요청한다.
- HTTP `200`과 기존 `CustomResponse` 형식을 사용한다.
- `Cache-Control: no-store`로 이전 제한 결과의 캐시 재사용을 방지한다.
- 제한 중이면 `Retry-After` 헤더에 `retryAfterSeconds`와 같은 값을 반환한다.
- 조회 오류는 기존 예외 응답으로 전달하며 미제한 성공으로 바꾸지 않는다.

| 필드 | 의미 |
| --- | --- |
| `restricted` | 계산 시각에 제한 종료 시각이 미래이면 `true` |
| `restrictionUntil` | 현재 유효한 제한 종료 시각. 기록 없음·만료 상태는 `null` |
| `retryAfterSeconds` | 남은 시간을 초 단위로 올림한 값. 미제한 상태는 `0` |
| `serverTime` | DB 조회 후 제한 여부와 남은 시간 계산에 사용한 서버 시각 |

시간은 ISO 8601 UTC 형식이다. 응답 예시는 실제 실행 기록이 아닌 계약 예시다.

- 새 제한은 저장 전에 마이크로초 정밀도로 맞추고, 접수 응답·감지 이력·재전송 스냅샷은 실제 DB 저장 시각을 사용한다.
- 조회도 같은 DB 저장 시각을 사용한다. 저장 정밀도 처리로 최초 남은 시간이 제한 기간보다 늘어나지 않도록 한다.
- 과거 전송 응답이나 응답 스냅샷은 소수점 정밀도가 다를 수 있다. 문자열 또는 정확한 시각 동등 비교로 제한을 구분하지 않는다.
- 화면의 현재 제한 여부는 `restricted`, 남은 시간은 `retryAfterSeconds`를 기준으로 사용한다.
  종료 시각은 시각 값으로 파싱하며 서로 비교해야 할 때는 정밀도 처리 기준을 일치시킨다.
- `serverTime`은 계산에 사용한 서버 시각이므로 제한 종료 시각과 소수점 자릿수가 다를 수 있다.

```json
{
  "isSuccess": true,
  "code": "200",
  "message": "OK",
  "result": {
    "restricted": true,
    "restrictionUntil": "2026-10-08T00:01:00Z",
    "retryAfterSeconds": 40,
    "serverTime": "2026-10-08T00:00:20Z"
  }
}
```

기록이 없거나 제한이 만료된 경우:

```json
{
  "isSuccess": true,
  "code": "200",
  "message": "OK",
  "result": {
    "restricted": false,
    "restrictionUntil": null,
    "retryAfterSeconds": 0,
    "serverTime": "2026-10-08T00:01:00Z"
  }
}
```

## 처리 흐름과 상태 선택

`ChatInputGuardController` → `ChatActorProvider` → `ChatInputGuardStatusService`
→ `JdbcInputGuardStatusStore` → 현재 시각 기준 응답 계산

- 저장소는 한 번의 `SELECT`로 현재 식별자의 제한 종료 후보를 읽는다.
- 회원 식별자가 있으면 회원을 우선한다. 게스트만 있으면 승계 회원을 확인한다.
- 미승계 게스트는 자신의 상태만 조회한다.
- 회원 본인의 제한이 아직 유효하면 기존 전송 검사와 같이 해당 제한을 우선한다.
- 회원 본인 제한이 없거나 만료됐으면 승계된 게스트 중 가장 늦게 끝나는 유효한 제한을 사용한다.
- 종료 시각과 현재 시각이 같으면 만료다. 만료된 종료 시각은 현재 유효한 제한으로 반환하지 않는다.
- DB 조회 후 서버 시각을 읽어 조회 지연 중 만료된 제한을 제외한다.

## 승계 게스트 조회 인덱스

- `guests(merged_user_id)`에 `merged_user_id IS NOT NULL` 조건의 B-tree 부분 인덱스를 추가한다.
- 한 회원에게 여러 게스트가 승계될 수 있으므로 비유니크 인덱스로 작성한다.
- `JdbcInputGuardStatusStore.findRestrictionEnds`와 `JdbcInputGuardStore.cohort`의 SQL은 유지한다.
  회원 본인 제한 우선, 승계 제한 선택, 위반 횟수 집계, 중복 요청 처리도 변경하지 않는다.
- 게스트 만료 시각은 인덱스 조건에 포함하지 않는다. 기존 조회가 사용하는 승계 관계를 그대로 인덱싱한다.
- 기존 `idx_guest_expires`와 이미 병합된 마이그레이션은 수정하지 않는다.
- 새 파일은 `V34__add_guest_merged_user_index.sql`이다. 작업 브랜치 푸시는 가능하지만,
  V33을 사용하는 요금제 사용량 PR #142를 먼저 병합한 뒤 이 작업을 `develop`에 병합·DB 적용한다.
  브랜치 게시와 `develop` 병합 직전에 두 마이그레이션 폴더와 열린 PR에서 번호 충돌을 다시 확인한다.
  이번 브랜치에는 PR #142의 코드나 SQL을 포함하지 않는다.
- 일반 `CREATE INDEX`를 사용하므로 인덱스 구축 중 `guests` 쓰기가 대기할 수 있다. 공유 DB 적용 시점은 별도로 조율한다.
  인덱스 추가를 위해 공통 Flyway·JPA 설정을 변경하지 않는다.

## 읽기 전용 계약

- 조회 서비스는 읽기 전용 트랜잭션을 사용한다.
- 기존 입력 검사 저장소의 행 잠금·초기화·제한 승계 저장 메서드를 호출하지 않는다.
- 상태 행 생성·집계 구간 초기화·제한 연장·감지 이력 추가를 하지 않는다.
- 메시지·실행·상담 조건·대기 질문을 생성하거나 변경하지 않는다.
- 만료 정리와 실제 승계 저장은 기존 입력 접수 경로의 정책을 유지한다.
- 조회 직후 새 요청이나 다른 창에서 제한 상태가 바뀔 수 있다.
  `restricted=false` 응답은 다음 입력의 접수를 보장하지 않으며 실제 전송 시 서버가 다시 검사한다.

## 프런트 연결 기준

- 같은 인증 쿠키로 화면 진입·새로고침·재접속 후 조회한다.
- `restricted=true`이면 제한 안내를 표시하고 남은 시간과 종료 시각을 사용한다.
- 클라이언트 시계만으로 서버의 제한 상태를 덮어쓰지 않는다.
- 제한이 끝난 시점 또는 전송 결과가 달라졌을 때 서버 상태를 다시 확인한다.
- 조회 실패를 미제한으로 단정하지 않으며 기존 서버 전송 검사를 유지한다.
- 조회 응답은 답변 생성 접수가 아니다. SSE 구독이나 생성 재시도를 시작하지 않는다.
- 실제 브라우저 표시·전송 잠금·새로고침 복원은 소비 프런트와 별도 검증해야 한다.

## 검증 방법

- 독립 개발 DB에 기존 마이그레이션을 적용한 환경에서 검사한다. 운영·공유 DB는 사용하지 않는다.
- 기록 없음·유효한 제한·지난 제한·정확한 종료 시각·초 미만 올림을 확인한다.
- 회원·미승계 게스트·승계된 게스트와 다른 사용자 정보의 분리를 확인한다.
- 회원 본인 제한 우선과 본인 상태가 없을 때의 승계 제한을 확인한다.
- 반복 조회 전후 상태·감지 이력·상담·메시지·실행 행이 동일한지 대조한다.
- 제한 중 실제 전송은 기존 검사에서 거절되고 제한 종료 시각이 늘어나지 않는지 확인한다.
- `/v3/api-docs`의 응답 필드·헤더·제한 여부별 예시와 실제 응답을 대조한다.
- 소수점 시각으로 새 제한을 만들고 최초 접수·조회·재전송·감지 이력의 종료 시각이 같은지 확인한다.
  최초 남은 시간, 초 경계 직전, 정확한 만료 시각과 조회 전후 저장 내용도 확인한다.
- 실제 모델 호출은 조회 기능의 필수 조건이 아니다. 자동 테스트와 화면 복원 검증은 각각 보고한다.

## 인덱스 검증 결과

- 기준: 2026-10-14, `origin/develop` 커밋 `b1c3dd2`에서 분리한 로컬 작업.
- 게시 전 최신 `develop` 커밋 `82e9f29`를 반영했다. 추가 변경은 평가 문서·스크립트뿐이며,
  앞서 검증한 애플리케이션·DB·Java 테스트·빌드 설정은 동일하다.
- 작업 전용 PostgreSQL 16.15·pgvector·PostGIS에서 실제 Flyway를 사용했다. 운영·공유 DB에는 적용하지 않았다.
- 신규 통합 테스트 3건을 포함해 입력 검사·제한 조회·실제 전송·게스트 승계·운영 Flyway 경로 회귀 181건이 통과했다.
  실패·오류·스킵은 0건이다. 분석·답변 생성 등 모델 호출은 기존 테스트 대역을 사용했다.
- 빈 DB에 V34까지 적용하는 경로와, 별도 V32 DB에 기존 합성 게스트·제한 상태를 넣고 V34만 추가 적용하는 경로를 확인했다.
  기존 데이터 보존, `validate` 성공, 재실행 시 추가 마이그레이션 0건을 확인했고 애플리케이션 패키징도 통과했다.
- 성능 비교는 별도 임시 스키마의 합성 게스트 100,000건, 승계 비율 10%, 회원 1,001명으로 진행했다.
  회원 1,000명에게 승계 관계를 배분하고, 나머지 1명은 실제 회원이지만 승계·제한 이력이 없는 표본으로 사용했다.
  두 저장소의 운영 소스에서 SQL을 읽어 사용했고, 인덱스 전후 동일한 데이터·파라미터·쿼리로 비교했다.
  `ANALYZE` 후 각 조건당 준비 실행 1회와 측정 7회의 중앙값을 사용했다.
- `plan_cache_mode=auto`와 `force_generic_plan` 모두에서 회원·승계 게스트 조회, 제한 승계, 위반 횟수 집계의
  `idx_guest_merged_user` 사용을 실제 실행 횟수로 확인했다. 순차 스캔을 강제로 끄지 않았다.
- 회원·승계 게스트·미승계 게스트·승계 이력이 없는 회원의 조회 결과, 제한 승계 결과, 위반 횟수는 전후 동일했다.
  새 승계 관계 갱신, 한 회원의 다중 게스트 승계, 다른 회원·미승계 게스트 분리는 통합 테스트에서도 확인했다.
- 아래 수치는 `plan_cache_mode=auto`의 DB 실행 시간이며 전체 API 응답 시간이나 운영 성능을 뜻하지 않는다.
  미승계 게스트 경로는 기존 게스트 PK를 사용한다. 해당 경로의 작은 측정 차이는 개선 효과로 해석하지 않는다.

| 경로 | 추가 전 중앙값(ms) | 추가 후 중앙값(ms) |
| --- | ---: | ---: |
| 회원 제한 조회 | 3.105 | 0.675 |
| 승계 게스트 식별자로 제한 조회 | 3.400 | 0.815 |
| 미승계 게스트 제한 조회 | 0.393 | 0.406 |
| 승계 이력이 없는 회원 조회 | 2.859 | 0.345 |

- 이 합성 데이터에서 부분 인덱스 크기는 114,688바이트였다. 실제 데이터 분포에 따라 크기와 실행 계획은 달라진다.
- 실제 로컬 모델 호출·화면·운영 응답 시간은 이번 작업에서 검증하지 않았다. 원격 CI는 게시 전이라 미검증이다.

재현은 마이그레이션을 적용한 작업 전용 로컬 DB에서 실행한다. DB 비밀번호는 `PGPASSWORD`로 제공한다.

```bash
python3 scripts/verify_guest_merged_user_index.py \
  --dsn postgresql://telme@127.0.0.1:55437/telme \
  --output-dir ../outputs/guest-merged-index-20261014/recheck
```

- 스크립트는 실행마다 새 임시 스키마를 만들고 합성 데이터만 사용하며, 종료 시 해당 스키마만 제거한다.
  기존 `public` 스키마의 데이터와 인덱스는 변경하지 않는다.
- 쿼리·실행 계획·결과·측정 조건은 출력 폴더의 `comparison.json`에 저장한다. JSON 산출물을 `docs/`에 넣지 않는다.
- 재검토 시 새 전용 DB에서 자동 테스트 181건을 재실행했고 모두 통과했다.
  원격 URI·접속 주소나 서비스 옵션이 포함된 URI 5건은 DB 접속 전 거부되는지 확인했다.
  `PGHOSTADDR`·`PGSERVICE` 환경 변수가 로컬 URI를 덮어쓰지 않는 상태로 성능 비교도 통과했다.

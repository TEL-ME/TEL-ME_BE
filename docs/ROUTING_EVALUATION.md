# 라우팅 평가 기준

## 검색 라벨과 라우팅 라벨의 차이

검색 평가의 `UNRELATED`는 현재 FAQ에서 답이 되는 근거를 찾을 수 없다는 뜻이다. 라우팅의 `UNKNOWN`은 통신 고객 상담으로 처리할 질문이 아니라는 뜻이다. 두 값은 같은 의미가 아니다.

예를 들어 `eSIM 발급 비용에 부가세가 포함됐나요?`는 현재 FAQ에 정답이 없어 검색 평가에서는 `UNRELATED`지만, 통신 정책 질문이므로 라우팅 기대값은 `FAQ`다. 반면 `내일 서울 날씨가 어떻게 되나요?`는 통신 상담 범위 밖이므로 라우팅 기대값도 `UNKNOWN`이다.

라우팅 기대값은 검색 평가 파일을 수정하지 않고 `scripts/data/eval_routing_intent_labels.json`에서 별도로 관리한다.

## 이번 라우팅 작업에서 추가한 JSON 파일

| 파일 | 문항 수 | 용도 | 평가에서 쓰는 방식 |
| --- | ---: | --- | --- |
| `scripts/data/eval_routing_intent_labels.json` | 180개 라벨 | 기존 검색 평가 질문의 라우팅 정답 intent를 별도 관리 | `eval_questions_130.json`과 `eval_questions_supplement_50.json`의 질문에 정답 intent를 연결한다. 질문 본문은 이 파일에 중복 저장하지 않는다. |
| `scripts/data/eval_routing_cases_32.json` | 32개 | 라우팅 전용 기본 평가셋. FAQ, STORE, BOTH, UNKNOWN 각 8개 | 규칙 보정 전후의 라우팅 결과를 비교한다. |
| `scripts/data/eval_routing_holdout_20.json` | 20개 | 보정 규칙을 만들 때 참고하지 않은 새 질문 평가셋. FAQ, STORE, BOTH, UNKNOWN 각 5개 | 규칙이 새 질문에도 통하는지 별도로 확인한다. 결과를 보고 규칙을 추가하지 않는다. |
| `scripts/data/eval_routing_context_3.json` | 3개 | 이전 상담 요약이 있어야 해석할 수 있는 후속 질문 평가셋 | 단독 질문 평가와 분리해, 이전 맥락이 있을 때 intent가 유지되는지 확인한다. |

위 네 파일은 이번 라우팅 작업에서 추가했다. 기존 질문 원문은 `eval_questions_130.json`과 `eval_questions_supplement_50.json`에 있으며, 180개 정답 intent만 별도 파일로 분리했다. 따라서 JSON 파일별 역할은 **기존 질문의 정답 라벨**, **보정 개발용 평가**, **새 질문 검증**, **이전 맥락 검증**으로 나뉜다.

## 현재 기준

| 문항 | 검색 분류 | 라우팅 기대값 | 이유 |
| --- | --- | --- | --- |
| EVAL-001부터 EVAL-080 | 답변 가능 | FAQ | FAQ 검색으로 처리할 통신 상담 |
| EVAL-081부터 EVAL-096 | UNRELATED | UNKNOWN | 통신과 무관한 외부 질문 |
| EVAL-097부터 EVAL-106 | UNRELATED | FAQ | 근거는 없지만 통신 고객 질문 |
| EVAL-107부터 EVAL-108 | UNRELATED | UNKNOWN | 채용과 대리점 창업은 고객 상담 범위 밖 |
| EVAL-109부터 EVAL-130 | UNRELATED | FAQ | 근거는 없지만 통신 고객 질문 |
| EVAL-131부터 EVAL-160 | 답변 가능 | FAQ | FAQ 검색으로 처리할 통신 상담 |
| EVAL-161부터 EVAL-180 | UNRELATED | FAQ | 근거는 없지만 통신 고객 질문 |

`매장에서 처리할 수 있나요?`, `매장 방문 예약이 가능한가요?`처럼 일반적인 매장 이용 정책을 묻는 질문은 `FAQ`다. 특정 지역의 매장 위치나 영업시간을 찾아 달라는 질문만 `STORE`로 본다. FAQ 안내와 특정 매장 검색을 한 요청에서 모두 요구하면 `BOTH`다.

## 평가 범위의 한계

현재 검색 평가 180문항의 기대 intent는 FAQ 162개, UNKNOWN 18개다. 특정 매장 검색 문항과 FAQ 및 매장 복합 문항이 없어 `STORE`와 `BOTH` 정확도는 이 평가셋으로 확인할 수 없다. 두 intent는 라우팅 전용 평가 문항을 추가해 별도로 확인해야 한다.

이를 보완하기 위해 `scripts/data/eval_routing_cases_32.json`에 FAQ, STORE, BOTH, UNKNOWN을 각각 8개씩 두었다. 일반적인 매장 이용 정책은 FAQ, 특정 지역이나 지점 조회는 STORE, 정책 안내와 특정 매장 조회를 함께 요구하면 BOTH로 라벨링했다.

`RoutingEvaluationProbe`는 두 검색 평가 파일의 180문항을 읽고 기대 intent, 실제 intent, 일치 여부와 intent별 집계를 결과 JSON에 기록한다.

로컬에서 `exaone3.5:7.8b`를 Ollama로 실행한 상태에서 다음 명령으로 측정한다.

```powershell
$env:TELME_ROUTING_EVAL = "true"
.\gradlew.bat test --tests com.telme.probe.RoutingEvaluationProbe
```

결과는 기본적으로 `build/tmp/routing-eval-180.json`에 저장된다. `summary.confusion`에서 기대 intent가 실제로 어떤 intent로 분류됐는지 확인하고, `records`에서 실패 문항의 질문과 모델 원문 응답을 확인한다.

라우팅 전용 32문항은 다음과 같이 실행한다.

```powershell
$env:TELME_ROUTING_EVAL = "true"
$env:TELME_ROUTING_INPUT = "scripts/data/eval_routing_cases_32.json"
$env:TELME_ROUTING_OUT = "build/tmp/routing-eval-cases-32.json"
.\gradlew.bat test --tests com.telme.probe.RoutingEvaluationProbe --rerun-tasks
```

### 오분류 확인

명확한 라우팅 실패는 7건이다. 다음 외부 질문을 모두 높은 confidence의 FAQ로 분류했다.

- EVAL-086 다이어트 식단
- EVAL-087 파이썬 리스트 정렬
- EVAL-091 강아지 사료량
- EVAL-092 전세 대출 한도
- EVAL-093 노트북 추천
- EVAL-095 헬스장 등록
- EVAL-096 원두 보관

현재 프롬프트의 `FAQ`를 모델이 통신 FAQ가 아닌 일반적인 질문 답변으로 넓게 해석한 결과다. 통신 정책 및 서비스에 해당하지 않으면 `UNKNOWN`이라는 제외 기준과 부정 예시를 보강할 필요가 있다.

다음 2건은 일반적인 매장 영업시간을 FAQ로 답할지, 위치를 되물어 특정 매장을 찾을지 제품 기준을 먼저 확정해야 한다. 현재 라벨은 특정 지역이나 매장을 지정하지 않았고 FAQ에 일반 영업시간 근거가 있다는 이유로 FAQ로 두었지만 모델은 STORE로 분류했다.

- EVAL-027 평일 저녁 7시 이후에 매장 방문이 가능한가요?
- EVAL-067 퇴근이 늦어서 8시쯤 들르려는데 그 시간에 문을 열어 두나요

EVAL-135 `남은 데이터 50%만 넘어간다는 게 무슨 뜻이에요?`는 FAQ 대신 UNKNOWN으로 분류됐다. 이전 발화의 대상을 가리키는 후속 질문처럼 읽힐 수 있어, 단독 질문 라우팅 실패로 확정하기보다 이전 맥락을 포함한 라우팅 평가 문항으로 분리하는 것이 적절하다.

### 통신 범위 강조 프롬프트 실험

개발셋의 외부 질문 실패를 바탕으로 통신 상담 범위가 아니면 UNKNOWN으로 분류하라는 규칙과 일반 지식 부정 예시를 추가해 두 번 재측정했다.

| 구성 | 개발셋 130개 | 검증셋 50개 | 전체 180개 | UNKNOWN 일치 |
| --- | ---: | ---: | ---: | ---: |
| 기존 프롬프트 | 121 | 49 | 170 | 11/18 |
| 범위 강조 1차 | 124 | 48 | 172 | 13/18 |
| 범위 강조 2차 | 125 | 47 | 172 | 14/18 |

외부 질문 차단은 개선됐지만 검증셋의 정상 FAQ를 UNKNOWN으로 보내는 부작용이 반복됐다. `남은 데이터 50%`, `양수인 신용 심사`, `위임장만 있으면 한 사람만 방문`처럼 통신 대상이 문장에 직접 나오지 않는 질문이 영향을 받았다. 따라서 범위 강조 프롬프트는 반영하지 않았다.

이후 개선에서도 검색 평가 문항을 프롬프트 예시로 추가하지 않는다. 별도 도메인 판정과 외부 단어 목록 규칙은 아래에서 시험했지만 반영하지 않았다. 맥락 의존 질문은 이전 대화를 포함한 별도 평가셋으로 분리해야 한다. 개발셋으로 수정한 뒤 검증셋 수치가 유지되는 것을 완료 조건으로 삼는다.

### 라우팅 전용 32문항 결과

검색 평가셋에 없던 `FAQ`, `STORE`, `BOTH`, `UNKNOWN` 문항을 각각 8개씩 구성해 현재 프롬프트를 별도로 측정했다.

| 기대 intent | 일치 | 실제 분류 |
| --- | ---: | --- |
| FAQ | 7/8 | FAQ 7, STORE 1 |
| STORE | 8/8 | STORE 8 |
| BOTH | 8/8 | 복합 질문 안내 8 |
| UNKNOWN | 3/8 | UNKNOWN 3, FAQ 5 |
| 전체 | 26/32 | 81.3% |

특정 지역과 매장을 찾는 질문과 FAQ와 매장 검색이 섞인 복합 질문은 모두 의도대로 분류됐다. `매장은 보통 평일 몇 시까지 운영하나요?`는 일반 정책 FAQ로 라벨링했지만 STORE로 분류됐다. 앞선 180문항의 매장 영업시간 사례와 같은 제품 정책 결정 사항이다.

외부 질문은 요리, 코틀린, 주택 대출, 노트북, 반려동물 질문 5건을 높은 confidence의 FAQ로 잘못 분류했다. 현재 라우터가 `FAQ`를 통신 상담이 아니라 일반 질의응답으로 넓게 해석하는 문제를 재현했다. 별도의 EXAONE 도메인 판정도 시험했지만 명시적 통신 단어가 없는 정상 상담 질문을 외부 질문으로 차단해 전체 성능이 149/180까지 하락했다. 따라서 별도 LLM 판정과 검증셋 성능을 낮춘 프롬프트 변경은 반영하지 않는다.

이 시점의 결론은 라우팅의 기대 intent를 검색의 `UNRELATED` 라벨에서 분리해 관리하는 것이었다. 외부 질문은 라우팅이 아니라 검색 단계에서 막고, 라우팅에는 일반 매장 운영 질문 보정만 추가해 아래 평가셋으로 다시 측정했다.

외부 질문 차단을 근거 적합성 판정에 맡기지는 않는다. `eval_questions_130.json`의 `UNRELATED` 50건을 실제 FAQ 1,152건과 임베딩 1,152건으로 재실행한 결과, 외부 일반 질문 16건은 모델 적재가 끝난 실행에서 모두 검색 결과 0건으로 차단됐다. 나머지 통신 질문 중 3건은 FAQ가 검색됐지만 RAG 프롬프트가 모두 답변 불가 안내를 반환했다. 근거 적합성 판정을 켜도 최종 결과는 같았다.

첫 실행에서는 임베딩 모델 적재 중 첫 2건이 검색 오류로 끝났고, 모델 적재 후 반복 실행에서는 50건 모두 오류 없이 처리됐다. 운영 환경에서는 첫 요청 전에 임베딩 모델을 준비하는 방식을 별도로 검토해야 한다.

근거 적합성 판정은 외부 도메인 분류기가 아니라 검색된 FAQ가 질문의 세부 항목에 답하는지 확인하는 기능이다. EXAONE 판정 정확도가 20건 중 12건에 그쳐 기본값은 계속 비활성으로 유지한다. 현재 외부 질문은 검색 결과가 없으면 LLM 답변 생성을 건너뛰는 경로로 차단하며, 검색을 잘못 통과하는 새 사례가 발견되면 해당 사례를 별도 회귀셋에 추가해 검색과 최종 답변을 함께 재검증한다.

### 의도 오분류 보정

특정 지점을 찾는 표현이나 지역 조건이 없는 일반 매장 운영 질문을 STORE로 분류했을 때는 FAQ로 보정한다. 검색 질문에는 사용자의 원문을 남긴다. 특정 지점의 영업시간 요청과 이전 대화에서 지점을 가리키는 후속 질문은 STORE를 유지한다.

외부 주제 단어 목록으로 FAQ를 UNKNOWN으로 바꾸는 규칙은 두지 않는다. 평가셋의 외부 질문 주제(노트북, 강아지, 헬스장 등)로 단어 목록을 만들면, 같은 단어가 들어간 통신 질문도 막힌다. 실제 EXAONE에서 `노트북 테더링하면 요금 따로 나와요?`, `강아지 위치추적기 가입 되나요?`, `헬스장 제휴 할인 받을 수 있어요?` 등 통신 질문 6개를 모델은 모두 FAQ로 분류했지만, 단어 목록 규칙을 적용하면 6개 모두 UNKNOWN이 됐다. 규칙을 만들 때 쓰지 않은 새 질문 20문항의 결과는 규칙이 있을 때와 없을 때 모두 18/20으로 같았다. 규칙은 만들 때 쓴 질문에서만 효과가 있었다.

### 새 질문과 이전 맥락 평가

`eval_routing_holdout_20.json`은 기존 평가 질문과 중복되지 않는 20문항이다. FAQ 5/5, STORE 5/5, BOTH 5/5, UNKNOWN 3/5로 총 18/20이었다. HOLDOUT-017의 적금과 HOLDOUT-019의 영어 면접은 FAQ로 분류됐고, 채팅 API에서는 검색 결과가 없어 위 안내 문구로 끝났다.

`eval_routing_context_3.json`의 이전 상담 요약이 있는 질문 3개는 모두 일치했다. EVAL-135와 같은 데이터 선물 후속 질문은 FAQ, U+ 인터넷 상담 중 노트북 후속 질문은 FAQ, 강남역 매장 상담 중 영업시간 후속 질문은 STORE로 분류됐다. 이 수치는 단독 질문 180문항의 결과와 별도로 기록한다.

전용 평가셋과 새 질문에서 BOTH는 각각 8/8, 5/5다. 모델이 실제로 BOTH로 분류한 경우만 정답으로 셌고, 13건 모두 FAQ와 STORE 하위 질문을 각각 냈다. 복합 질문 안내는 하위 질문 intent가 섞인 경우에도 나오므로 안내 여부로 채점하지 않고, 결과 JSON의 `compound_guidance_by_expected_intent`에 따로 집계한다. 두 평가셋에서 복합 질문 안내는 기대값이 BOTH인 13건에서만 나왔다. 실제 채팅 파이프라인의 매장 결과 조회와 최종 답변 결합은 이 라우팅 평가 범위에 포함하지 않는다.

## 여러 FAQ를 묻는 질문

`eSIM 가격이랑 개통 방법 알려줘`처럼 FAQ 질문 여러 개를 한 번에 물으면, 라우터가 나눈 하위 질문마다 검색하고 답변을 만든 뒤 번호를 붙여 한 메시지로 합친다. FAQ와 매장 검색이 섞인 질문은 지금처럼 복합 질문 안내로 처리한다.

- 답변과 검색 모두 해당 하위 질문만 사용한다. 전체 원문으로 재검색하면 형제 질문의 FAQ를 잘못된 근거로 사용할 수 있어 재검색하지 않는다. 라우터는 `해외 로밍 데이터 차단 방법`처럼 공통 대상을 각 하위 질문에 포함해야 한다.
- 서로 독립된 FAQ 질문은 최대 3개까지 처리한다. 4개 이상이면 일부를 임의로 생략하지 않고 질문을 나누어 달라고 안내한다.
- 근거가 없는 하위 질문은 해당 번호에만 답변 불가 안내를 넣고, 나머지 답변은 유지한다.
- 같은 FAQ가 두 하위 질문의 근거가 되면 근거 목록에는 한 번만 남긴다.
- 여러 모델 호출의 중간 토큰은 저장된 최종 답변과 다를 수 있어, 합친 답변을 완료 후 한 번에 보낸다.

### 비교 질문 보정과 검색 확인 (2026-10-06)

#### 문제와 설계 근거

복합 요청은 하위 질문이 서로 독립적인지, 두 대상의 관계까지 답해야 하는 비교 요청인지 구분해야 한다. `eSIM 가격이랑 개통 방법 알려줘`는 각각 답을 받을 독립 요청 두 개지만, `5G와 LTE 요금제 차이를 비교해줘`는 두 대상을 놓고 차이를 설명해야 하는 비교 작업 한 개다. 현재 채팅 처리는 FAQ 하위 질문마다 답을 따로 만든 뒤 이어 붙인다. 비교 대상을 독립 설명 질문으로 나누면 답변 단계에서 차이라는 관계를 잃을 수 있다.

이 구분은 모델의 분할 결과만으로 맡기지 않기로 했다. 실제 EXAONE과 Qwen3 비교에서 두 모델 모두 비교 요청을 자주 여러 FAQ 질문으로 나눴고, 현재 파이프라인은 그 하위 질문을 비교·종합하지 않기 때문이다. 따라서 명확한 단독 비교 요청은 라우팅 단계에서 사용자 원문 한 건으로 유지하고, 서로 독립적인 여러 FAQ 질문은 기존처럼 각각 처리한다.

양쪽 검색이 성공한 첫 번째 문항은 원문 검색에서도 `5G랑 LTE랑 뭐가 달라요?`라는 비교 FAQ가 나왔다. 여덟 번째 문항의 원문 검색 결과는 가입 조건보다 데이터 사용량과 변경 절차에 가까워, 후보가 있다는 사실만으로 답변 가능한 근거라고 볼 수 없다. 이 10문항에서는 대상별 추가 검색이 비교 답변에 필요한 양쪽 근거를 새로 확보한 사례가 확인되지 않았다. 따라서 검색 호출을 일괄 추가하지 않고, 비교 질문의 정답 FAQ를 확인한 평가셋으로 검색 누락과 답변 품질을 먼저 측정한다. 필요하다면 검색 단계에서만 여러 질의를 사용하고, 최종 답변은 원래 비교 요청 하나에 대해 생성한다.

#### 검색 근거와 실제 생성 답변 재검증 (2026-10-06)

라우팅에서 멈추지 않고 Spring의 실제 `FaqSearchService`와 `RagAnswerGenerator`를 연결해 비교 질문 14개를 실행했다. FAQ와 임베딩 1,152건이 있는 로컬 PostgreSQL, `bge-m3` 임베딩, `exaone3.5:7.8b` 답변 모델을 사용했다. 검색은 이중 벡터, 답변 임계값 0.72, 질문 임계값 0.88, 각 검색 top-3이다. 왼쪽·오른쪽 검색어는 평가자가 각 비교 대상을 명시해 직접 작성했으며, 실제 라우터가 만든 하위 질문은 아니다. 같은 질문으로 세 입력을 비교했다.

1. 원문 비교 질문 검색 결과만 사용
2. 왼쪽·오른쪽 대상별 검색 결과만 합침
3. 원문 결과와 양쪽 대상별 결과를 모두 합침

두 대상 각각의 검색에서 FAQ 후보가 나온 문항은 **4/14**였다. 한쪽에만 후보가 나온 문항은 **3/14**, 양쪽 모두 결과가 없는 문항은 **7/14**였다. 원문 검색은 7/14에서 후보를 반환했고, 그 중 **5/14는 두 비교 대상의 핵심 사실을 직접 담은 FAQ 근거**였다. 따라서 단순 후보 존재 여부는 유효 근거 여부와 같지 않으며, 현재 FAQ 데이터에는 특정 비교를 한 FAQ가 있어 원문 검색이 대상별 검색보다 나은 경우도 있다.

나머지 CMP-002·003·004·006·007·009·010은 원문 검색과 양쪽 검색 모두 근거를 찾지 못해 답변 불가로 끝났다. CMP-005와 CMP-008에서 보듯 결과를 단순 병합하면 근거 공백을 모델이 일반 지식이나 다른 FAQ 내용으로 채울 수 있다. 반대로 CMP-013처럼 대상별 검색만 쓰면 원문 검색이 이미 찾은 비교 FAQ를 잃을 수 있다.

**판정:** 현재 원문 질문 보정은 비교 의도를 보존하며, 원문 검색은 직접 비교 FAQ가 있을 때 정확한 답을 낼 수 있었다. 하지만 전체 질문에 대해 양쪽 근거를 안정적으로 가져오거나 답변 정확도를 보장하지 못한다. 비교 대상별 검색 결과를 원문 검색 대신 쓰거나, 검색 결과를 표시 없이 한 덩어리로 합치는 변경은 현재 근거로 승인할 수 없다. 후속 구현 시에는 원문 검색 결과를 항상 보존하고, 하위 검색 결과를 어느 비교 대상의 근거인지 연결해 전달해야 한다. 양쪽 근거가 확인되지 않으면 빠진 쪽을 추측하지 않고 답변 불가 또는 부분 답변으로 처리해야 한다. 답변 검증은 대상별 핵심 조건 누락, 근거에 없는 비교·수치·추천 추가, 다른 대상 FAQ의 혼입을 따로 확인해야 한다.

이 실행에서 양쪽 대상 검색 모두에 관련 FAQ 후보가 나온 건 CMP-001·011·012·014의 **4/14**였다. 원문 검색이 이미 두 대상의 사실을 직접 담은 FAQ를 찾은 CMP-013까지 포함하면, 어느 검색 방식이든 양쪽 사실을 확인할 수 있는 근거가 나온 건 **5/14**였다. 나머지는 한쪽 근거만 있거나 없었다.

실제 `RagAnswerGenerator`와 `AnswerGuard`를 사용했으며, `rag.evidence-check`는 기본 설정대로 비활성화했다. 이는 검색 결과 적합성 사전 판정이 켜진 실서비스 전체 구성이 아니다. 또한 저장된 채팅 메시지·SSE까지 포함한 전체 API 통합 검증은 아니다. 답변 대조는 14개 소규모 문항의 FAQ 근거를 사람이 직접 읽어 수행했으며 전체 서비스 정확도나 환각률로 일반화하지 않는다. 재실행 프로브는 `src/test/java/com/telme/probe/ComparisonEvidenceProbe.java`이고, 측정 원시는 로컬 무시 경로 `build/tmp/comparison-evidence-final.json`에 생성됐다.

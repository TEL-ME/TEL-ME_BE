# TELME-190: 삭제 대상 비교 문장의 근거 판정

## 변경 이유

기존 recovery는 FAQ 177의 문구와 질문·답변 문법이 맞을 때 FAQ 원문으로 교체했다. 독립 리뷰에서는 의미가 같은 정상 질문과 답변도 복구되지 않았다. 이를 해결하기 위해 특정 FAQ 문법을 제거하고, 가드가 삭제하려는 비교 문장에만 근거 판정을 추가했다.

이번 구현은 접근 A다. 비교 대상만 일치시키는 접근 B는 기간, 부정, 적용 조건까지 확인하기 어렵기 때문에 단독 허용 규칙으로 사용하지 않는다.

## 처리 흐름

1. 기존 비교 가드가 그대로 허용하는 문장은 기존 경로를 유지한다.
2. 삭제 대상 비교 문장에서 근거 없는 금액·수량과 명시적 숫자 주 단위를 먼저 검사한다. 이 단계에서는 질문의 여행 기간과 상품 기간이 반드시 같다고 가정하지 않는다.
3. 남은 후보를 한 번의 판정 요청으로 묶는다. 고객 질문은 의도 파악용이고, 사실 근거는 FAQ 답변(A) 전체다. FAQ 질문(Q)을 검증 근거에 추가하지 않는다.
4. 판정 프롬프트는 비교 대상·속성·방향·최상급 범위·기간·금액·부정·국가·적용 조건을 함께 확인하도록 요구한다. `가장 유리`라는 표현만으로 `가장 저렴`을 허용하지 않는다.
5. 근거가 충분하다고 판정된 문장은 모델이 생성한 원래 표현을 유지한다. FAQ 원문으로 교체하지 않는다. 나머지는 기존대로 삭제한다.
6. 이후의 정책·채널·금액·기간 검증은 계속 실행한다. 판정이 기존 검사를 우회하지 않는다.

판정 응답은 후보 ID, boolean 판정, FAQ A의 연속된 원문 인용을 포함하는 JSON만 받는다. 누락·중복 ID, 잘못된 형식, 근거에 없는 인용, 예외, 시간 초과, 입력 제한 초과는 허용하지 않는다. **인용 존재 확인은 의미적 정답을 보장하지 않는다. 의미 판단의 정확도는 별도 평가가 필요하다.** 취소 요청은 상위로 전파한다.

## 호출과 설정

- 답변 생성 요청당 추가 판정 호출은 최대 한 번이다. 금액 오류로 생성이 재시도되면 동일 문장만 기존 승인을 재사용하고, 새 문장은 추가 호출 없이 거절한다.
- 기존 `evidenceJudgeLlmClient`를 사용한다. 판정 클라이언트는 재시도하지 않으며 기존 SDK 제한 시간은 8초다. 판정 클라이언트가 없으면 추가 허용 없이 기존 가드가 동작한다.
- `RAG_COMPARISON_CHECK_ENABLED` 기본값은 `true`다. `false`로 설정하면 추가 판정을 끌 수 있다.
- `rag.comparison-check`: 출력 최대 1,000토큰, 후보 최대 4문장, 질문·근거·후보 합계 최대 12,000자다. 가드 단계에도 개별 문장 1,000자, 질문 4,000자, 근거 12,000자 제한이 있다.
- 추가 판정이 발생하는 요청에는 지연과 모델 사용 비용이 생긴다. 실제 추가 호출 비율·지연·비용은 운영 반영 전 확인해야 한다.

## 코드 리뷰 순서

1. `AnswerGuard.java`, `ComparisonClaimPrecheck.java`: 판정 대상 선정과 기존 검사 유지.
2. `ComparisonEvidenceJudge.java`, `ComparisonEvidencePromptTemplates.java`: 호출 예산, 판정 계약, 실패 처리.
3. `RagAnswerGenerator.java`: 생성 완료 후 판정, 생성 재시도와 판정 세션 공유, 검증 후 토큰 전달.
4. `ComparisonCheckProperties.java`, `application.yml`: 설정과 비활성화.
5. `AnswerGuardRecoveryBehaviorTest.java`, `ComparisonEvidenceJudgeTest.java`, `RagComparisonReviewTest.java`: 정상 표현·오류·취소·재시도 계약.

기존 `ComparisonPriceRecovery.java`의 FAQ별 문법은 제거했다. DB 스키마 변경은 없다.

## 검증 결과

Java 21.0.12.1, Gradle offline, 로컬 PostgreSQL/pgvector/PostGIS에서 확인했다. `.env`를 읽거나 로드하지 않았고 실제 외부 API 호출 없이 mock/fake를 사용했다.

| 범위 | 결과 |
| --- | --- |
| 최신 develop `314bdb2fe28551086f511f73208ecfeac895ec0e`에 변경을 합친 전체 테스트 | 5,509건 중 5,379건 실행 성공, 조건부 skip 130건, 실패·오류 0 |
| 같은 통합 상태의 빌드 | `assemble` 통과 |
| 신규 핵심 계약 테스트 | 53건 통과: 가드 24, 판정기 22, 생성기 연결 7 |
| 공유 선택 회귀 (아래 명령) | 1,663건, 실패·오류·skip 0 |

전체 실행은 외부 호출 방지를 위해 Bedrock 및 추가 판정을 환경 설정으로 껐다. 판정 기능을 켠 Spring 빈 선택과 생성기 연결은 별도 mock 테스트로 확인했다. 따라서 전체 테스트 통과를 실제 판정 모델의 정확도 검증으로 해석하면 안 된다.

공유 선택 회귀의 의미 판정 결과는 명시적으로 주입한 mock이다. 정상 표현이 허용되는 연결 구조, 실패 시 차단, 기존 경로 보존 등을 확인하는 계약 테스트이며, 실제 모델의 복구율·오통과율 측정이 아니다. 과거 문법 기반 결과는 이 구현의 정확도 근거로 재사용하지 않는다.

핵심 테스트 실행:

```sh
./gradlew --offline test \
  --tests '*AnswerGuardRecoveryBehaviorTest' \
  --tests '*ComparisonEvidenceJudgeTest' \
  --tests '*RagComparisonReviewTest' assemble
```

공유 회귀 검증 실행 (새 클론에서도 실행 가능):

```sh
./gradlew --offline --max-workers=2 \
  -I scripts/answer-guard-regression/regression.init.gradle test assemble
```

경계 사례 161개, 과거 저장 답변과 기준 출력 각 651개, 이에 의존하는 테스트·실행 설정은 `scripts/answer-guard-regression/`에 공유한다. 원시 자료는 검토 가능한 JSON이며 개인 경로가 필요하지 않다. 위 init script를 명시할 때만 추가하므로 기본 테스트 범위는 바꾸지 않는다. 상세 출처·해석·결과 경로는 [공유 검증 안내](../scripts/answer-guard-regression/README.md)를 참고한다. 처음 실행하는 환경에서는 의존성 다운로드를 위해 `--offline`을 생략한다.

## 독립 리뷰어의 추가 확인 (전달받은 결과)

아래는 리뷰어가 실제 판정 모델로 확인해 전달한 결과다. 이 작업에서 직접 실행한 mock 검증과 구분한다. 블라인드 65문장과 결과 원본은 추후 전달 예정이므로 현재 공유 자료에는 포함되지 않는다.

- 블라인드 평가 3회: 정상 답변 변형 25개와 질문 변형 25개 모두 유지. 오답 15개 중 새로 통과한 사례는 0개이며, 통과한 4개는 develop에서도 통과하던 표현이라고 보고했다.
- 최신 develop 통합 품질셋 307턴: 판정 7턴, 유지한 6문장 모두 근거와 일치, 근거 없는 비교 1건 삭제. FAQ 2~3개가 섞인 근거에서도 맞는 문장을 인용했다고 보고했다. 판정 호출 p50은 0.83초다.
- 최신 develop 통합 전체 테스트 5,509건 통과 및 PR 승인으로 전달받았다. 실행·skip 상세와 원시 결과는 아직 받지 않아 위 자체 실행 수치와 합산하지 않는다.

## 자체 리뷰와 남은 확인

자체 리뷰에서 질문의 모든 기간을 상품 기간과 같다고 처리하는 오류, 상품 이름·부정 표현을 고정 문법으로 제한하는 오류, `중요한 주의사항`을 한 주로 오인하는 오류를 수정했다. 재리뷰에서 추가 필수 수정 사항은 확인하지 못했다.

직접 확인이 필요한 항목:

- 독립 리뷰어의 블라인드 문장·결과 원본을 전달받으면 위 보고와 연결해 보관한다. 공유 mock 테스트와 별도의 실제 모델 평가로 관리한다.
- 보고된 블라인드·품질셋 밖의 국가·예외·정정 조건과 운영 데이터 분포를 계속 확인한다. 실제 키를 쓰는 테스트는 사용자가 수동으로 진행한다.
- 품질셋의 호출 비율과 p50 외에 운영 호출 비율·지연 꼬리·토큰 비용을 확인한다.
- 기존 비교 가드가 이미 허용한 잘못된 비교는 이번 판정 대상으로 들어오지 않는다. 전체 사실 검증 문제를 해결한 변경으로 설명하지 않는다.

실제 판정 모델이 틀린 승인을 할 가능성은 남아 있다. 실패 시 차단 정책과 인용 검사는 그 위험을 줄이지만 제거하지 않는다. 기능 비활성화 또는 구현 커밋 되돌리기로 기존 비교 가드 경로를 사용할 수 있다.

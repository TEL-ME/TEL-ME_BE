# TELME-139 독립 질문의 문맥 확인 오탐 개선

## 동작과 설계

`요금 안 내면 언제 정지되나요?`처럼 현재 문장만으로 이해되는 질문을 이전 발언이 없다는 이유로 막지 않는다. 기본 `REGEX_GATED`의 정규식은 모델 호출 후보만 선택한다. `LLM_ALL`은 후보 검사 없이 모든 새 질문을 같은 판정 경로로 처리한다.

| 처리 단계 | 확인할 내용 | 처리 |
| --- | --- | --- |
| 현재 질문 판정 | 현재 원문에 업무나 상황이 있는가 | `EXPLICIT`이면 원문으로 진행하고 이전 주제를 전달하지 않음 |
| 대상 생략 | 현재에 대상이 없고 이전 대화가 필요한가 | `OMITTED`이며 이전 고객 발언이 있을 때만 연결 판정 호출 |
| 현재 대상 모호 | 현재 문장의 여러 대상 중 무엇인지 알 수 없는가 | `AMBIGUOUS`이면 확인 안내 |
| 이전 발언 분석 | 각 발언의 업무 개수와 후속 및 정정 관계 | 코드가 업무와 연결된 발언의 원문을 함께 선택 |

현재 질문 판정에 이전 주제를 넣지 않아 새 업무가 과거 업무에 끌리는 것을 줄인다. 같은 문장 안의 대상, 지시어, 비교 요청과 단순한 비용 및 기간 질문을 구분한다. 업무는 명확하지만 FAQ 정답이나 신청 조건이 부족한 경우는 이후 검색과 FAQ 되묻기가 처리한다.

### 출처와 정정 연결

- 모델은 고객 원문을 복사하거나 새 질문을 만들지 않는다. 이전 발언마다 `index`, `targetCount`, `parentIndex`를 반환한다.
- `index`는 제공한 고객 발언의 순서 번호다. DB의 큰 메시지 ID는 모델에 넘기지 않고 검증 후 실제 ID로 연결한다.
- `targetCount`는 새로 도입한 업무의 개수다. 발언 하나에 인터넷 가입과 번호이동이 있으면 두 대상이며 임의로 하나를 고르지 않는다.
- `parentIndex`는 이전 업무를 이어 묻거나 정정하는 발언의 연결이다. 부모는 앞선 업무에만 연결할 수 있고 순환 및 미래 참조를 거부한다.
- 모든 출처가 중복 없이 제공되어야 한다. 모델의 배열 순서는 원문 번호로 정렬하므로 `[1,3,2]`를 반환해도 올바른 원문에 연결한다.
- 일반 후속 질문의 `referenceScope=RECENT`에서는 코드가 최근 업무를 선택한다. `POSITION`은 모델이 지정한 이전 위치를 사용한다. 어느 경우든 선택한 업무의 정정과 후속 발언을 원문 순서로 함께 보존한다.
- 업무가 없거나 선택한 발언에 대상이 여러 개면 확인 안내를 제공한다. 코드가 확인하는 것은 구조, 출처 존재와 연결의 일관성이다. 모델의 업무 개수나 참조 의미가 정확하다는 보장은 아니다.

예를 들어 `유심 재발급을 대리인이 신청합니다` 다음에 `대리인이 아니라 제가 직접 신청합니다`가 있으면 두 원문을 함께 전달한다. 원래 업무만 남겨 최신 정정을 지우거나 정정만 남겨 업무를 잃지 않는다. 관련 없는 다른 업무와 이전 AI 답변은 전달하지 않는다.

### 설정과 기록

공개 API, DB 스키마와 `application.yml`은 변경하지 않는다. 정상 되묻기 응답의 기존 상담 연결은 유지한다.

두 판정은 `CONTEXT_RESOLUTION`으로 기록하고 프롬프트 버전은 `multiturn-resolution-v30-reference`, `multiturn-resolution-v30-sources`로 구분한다. 현재 판정 출력은 64토큰, 연결 출력은 `min(2048, 128 + 64 × 출처 수)`다. temperature는 0이고 Qwen3 및 EXAONE 4.0의 해당 요청에서는 사고 모드를 끈다.

Ollama JSON Schema는 출력 필드와 실제 출처 수에 맞는 배열 길이 및 번호 범위를 제한한다. 이후 코드가 중복, 누락, 숫자 타입, 부모 관계와 고객 원문을 검증한다. 잘못된 출력과 호출 실패는 출처 일부를 전달하지 않고 확인 안내로 처리한다.

실행 trace의 `questionResolution`에는 최종 관계와 실제 출처 ID를, `questionResolutionEvidence`에는 분석과 순서 번호 및 실제 ID의 대응을 남긴다. 내부 `EXPLICIT`, `OMITTED`, `AMBIGUOUS`는 실제 처리와 검증 결과에 따라 기존 `SELF_CONTAINED`, `HISTORY_DEPENDENT`, `CLARIFICATION_REQUIRED`로 기록한다.

## 검증 입력과 환경

[cases.json](../scripts/context-resolution-evaluation/cases.json)에 기대 관계와 필요한 이전 발언 번호를 고정한다. 질문의 최종 답변 정확도와 별개로 **관계와 출처가 모두 맞아야 일치**로 집계한다.

| 입력 키 | 구성 | 용도 |
| --- | --- | --- |
| `cases` | 기존 오탐 9, 새 독립 질문 15, 후속 10, 모호 10, 전환 및 정정 10, 같은 문장 참조 6. 총 60건과 공백 변형 20회 | 회귀 80회 |
| `confirmationCases` | 유형별 4건씩 20건 | 추가 회귀 |
| `evidenceValidationCases` | 독립, 후속, 모호, 정정, 같은 문장 참조 각각 4건 | 새로운 입력 20건 |
| `sourceSelectionCases` | 처음 및 두 번째 업무 참조, 다른 주제 뒤 정정, 과거의 복수 대상 | 위치 선택 회귀 4건 |

기존 입력의 `development` 및 `heldout`은 최초 분할 기록이다. 현재는 알려진 오판을 개선하는 데 사용한 회귀 입력으로 해석한다. 새로운 20건은 프롬프트 예시에 넣지 않았지만 반복 측정했으므로 독립 블라인드 평가로 주장하지 않는다. 기대값은 구현자가 실행 전에 작성했으며 별도의 사람 판정 결과가 아니다. 공백 변형과 반복을 독립 문항 수로 세지 않는다.

실행은 기준 커밋 `9693186`의 별도 워크트리, 실제 Spring 채팅 API(MockMvc), EXAONE 3.5 7.8B Q4_K_M, bge-m3, FAQ와 임베딩 1,152건을 복사한 독립 DB `telme_139_live`를 사용한다. Ollama 0.34.0, RTX 5070 Ti 16GB, 컨텍스트 8192 설정이다. 개발 DB는 수정하지 않는다.

80회 및 추가 입력은 이전 고객 발언을 완료된 메시지로 고정하고 현재 질문을 실제 API와 모델로 처리한다. 기존 멀티턴 회귀 17회에서는 앞선 질문도 실제 API로 전송한다. FAQ 되묻기는 기본 설정대로 켜며 정상 `WAITING_CONDITION`을 문맥 확인 오탐으로 세지 않는다.

기본 입력에서 새 독립 질문은 13/15에서 15/15, 모호한 대상은 7/10에서 10/10, 전환 및 정정은 6/10에서 10/10으로 개선됐다. **후속 질문은 9/10에서 8/10으로 낮아졌다. 개선 총합만으로 회귀가 없다고 판단하지 않는다.**

현재 기본 80회에서는 독립 질문의 오차단 1회, 후속 질문의 잘못된 독립 판정 2회와 필요한 출처 누락 2회가 있다. 마지막 두 항목은 같은 사례를 중복 집계한 것이다. 기본 80회에서 잘못된 모델 출력이나 실행 자체의 실패는 없었다.

전체 빌드는 테스트 2,304개 중 2,195개 통과, 109개 건너뜀, 실패 0이다. FAQ 실측 DB와 분리한 `telme_139_checks`에서 `clean build --build-cache`로 확인한다.

### 호출 수와 지연

앞선 구현의 문맥 호출은 80회였고 현재는 현재 판정 80회와 연결 판정 25회로 총 105회다. 기본 80회 중 55회는 한 번, 25회는 두 번 호출한다. 기본 모드의 후보 밖 질문에는 호출을 추가하지 않는다.

| 측정 | 앞선 구현 중앙값/P95 | 현재 중앙값/P95 |
| --- | ---: | ---: |
| 질문당 문맥 판정 호출 시간 합계 | 295/511ms | 222/747ms |
| 평가 사례 전체 처리 | 1,550/2,891ms | 1,575/2,622ms |

전체 처리에는 세션 생성, 실행 대기와 결과 조회가 포함된다. 서로 다른 시점의 로컬 실행이며 요청 경로와 실제 생성 여부도 달라지므로 지연 차이를 특정 코드 변경만의 효과로 단정하지 않는다.

## 남은 오판과 회귀

| 입력 ID | 문제 | 구분 |
| --- | --- | --- |
| `followup-08` | `그럼 비용은 얼마나 드나요?`를 독립으로 판정해 이전 업무 누락 | 앞선 구현에서 맞던 새 회귀 |
| `followup-09` | `이전에 문의한 건 취소할 수 있어요?`를 독립으로 판정해 이전 업무 누락 | 앞선 구현에서 맞던 새 회귀 |
| `same_sentence-03-compact` | 대상이 적힌 명의 변경 질문의 공백 제거 형태를 확인 안내로 처리 | 앞선 구현에서 맞던 새 회귀 |
| `fresh-followup-3` | 처리 기간 후속 질문을 독립으로 판정 | 추가 회귀 입력의 새 회귀 |
| `fresh-ambiguous-4` | 과거 두 업무 중 무엇인지 모호한 질문을 독립으로 통과 | 추가 회귀 입력의 새 회귀 |
| `evidence-followup-04` | `그때 요금은 얼마나 나와요?`에서 태국 로밍 맥락 누락 | 새로운 입력의 오판 |
| `earlier-ambiguous` | 첫 번째 과거 발언을 지칭했지만 모델이 `RECENT`로 판정해 다른 업무 선택 | 위치 판정 오판 |

우선 확인할 것은 모호한 대상의 통과와 잘못된 업무 선택이다. 단일 질문 판정이나 `referenceScope`가 틀리면 ID와 JSON 구조 검증만으로 의미 오류를 막을 수 없다. 현재 변경은 출처 검증과 정정 보존을 개선하지만 모델 의미 판정의 한계를 없애지는 않는다. **오판이 전부 해결된 상태나 모든 기존 성공을 유지한 상태는 아니다.**

공백에 따른 호출 경로는 같지만 모델 판정까지 같지는 않다. `followup-08-compact`는 원문보다 맞게 판정했고, `same_sentence-03-compact`는 원문보다 잘못 판정했다. 후보에 없는 생략 표현은 기본 모드에서 놓칠 수 있으며 `LLM_ALL`은 후보 검사만 생략하는 옵션이다.

이 수치는 문맥 관계와 출처 연결의 검사다. 검색 정답 포함률, 최종 답변 정확도나 환각률이 아니다. 원시 요청, 응답, 실행 상태, 검색 근거와 저장된 답변은 [comparison.tar.gz](../scripts/context-resolution-evaluation/runs/comparison.tar.gz)에, 집계와 실패 ID 및 해시는 [metrics.json](../scripts/context-resolution-evaluation/runs/metrics.json)에 보관한다.

## 재실행

실제 모델과 API 호출은 `ContextResolutionLiveEvaluationTest`가 수행한다. Python은 독립 DB 복사와 원시 결과 집계만 담당한다. 실측은 `RUN_TELME139_LIVE=true`에서만 실행하며 DB 이름이 `telme_139_`로 시작하는지 확인한다.

```powershell
$env:POSTGRES_PORT = '5440'
$env:POSTGRES_DB = 'telme_139_live'
$env:SPRING_FLYWAY_LOCATIONS = 'classpath:db/migration'
$env:RUN_TELME139_LIVE = 'true'
$env:TELME139_RUN = 'new-run'
$env:TELME139_FIXTURE_KEY = 'cases'
./gradlew.bat test --tests '*ContextResolutionLiveEvaluationTest' --rerun-tasks
```

DB가 없으면 먼저 빈 DB의 스키마를 준비하고 `prepare_database.py --source <FAQ가 있는 로컬 DB> --target <새 telme_139_ DB>`로 FAQ와 임베딩만 복사한다. 데이터가 있는 대상 DB에는 복사하지 않는다. `TELME139_FIXTURE_KEY`로 위 표의 입력 키를 선택하며 실행마다 새 `TELME139_RUN`을 사용한다.

`summarize.py --baseline <최초 결과> --previous <앞선 결과> --improved <현재 결과> --confirmation <추가 회귀> --heldout <새 입력> --source-selection <위치 선택>`으로 입력이 동일한지 검사해 집계한다. 실행 상태가 정상 완료되지 않거나 검증 실패로 확인 안내를 반환한 사례는 일치로 세지 않는다. 개발 원시 자료와 코드 스냅샷은 같은 압축 안에 최종 자료와 구분하여 보존한다.

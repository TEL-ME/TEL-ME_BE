# 문맥 판정과 이전 발언 연결

## 목적

현재 질문만으로 상담 대상을 알 수 있는지 먼저 판정하고, 대상이 생략된 경우에만 이전 고객 발언에서 대상을 찾아 연결한다. `요금 안 내면 언제 정지되나요?`처럼 혼자 이해되는 질문은 이전 대화가 없다는 이유로 막지 않고, `그럼 비용은 얼마나 드나요?`처럼 대상이 빠진 질문은 이전 업무와 그 정정을 함께 전달한다.

공개 API, DB 스키마와 `application.yml`은 변경하지 않는다. 정상 되묻기 응답의 기존 상담 연결은 유지한다.

## 처리 흐름

| 단계 | 판단 주체 | 처리 |
| --- | --- | --- |
| 호출 후보 선정 | 코드 | 기본 `REGEX_GATED`는 공백과 문장 부호를 무시한 정규식과 아래 일반어 규칙으로 후보를 고른다. 이전 고객 발언(인사 제외)이 있고 공백·문장 부호 제외 15자 이하인 질문과 `두 번째로 물어본` 같은 위치 지정 표현이 있는 질문도 후보로 본다. 흔들림 보완을 켜면, 이전 고객 발언이 있을 때 비용 항목(`수수료`, `위약금`, `할부금`, `방문비`, `출장비`, `부가세`, `설치비`, `가입비`)이 있는 질문은 길이와 관계없이 후보로 본다. 앞의 `[문의]` 같은 표시는 후보 선정과 모델 판정 입력에서 떼고, 결과 질문에는 원문을 쓴다. 후보가 아니면 원문 그대로 진행한다. `LLM_ALL`은 모든 새 질문을 후보로 본다 |
| 일반어 후속 질문 | 코드 | 문장 전체가 지시어·시점 표현·질문 항목·어미로만 이뤄지면 모델 없이 대상 생략으로 본다 |
| 현재 대상 판정 | 모델 | 위에 해당하지 않으면 현재 문장만 보고 `EXPLICIT`, `OMITTED`, `AMBIGUOUS` 중 하나를 고른다. 이전 주제는 넣지 않는다 |
| 이전 발언 분석 | 모델 | 대상이 생략됐고 이전 고객 발언이 있을 때만 호출한다. 발언마다 새 업무 개수와 정정 연결을 표시한다 |
| 출처 선택 | 코드 | 분석 결과로 참조할 업무를 고르고, 그 업무의 원래 발언부터 최신 정정까지 원문을 순서대로 전달한다 |

`EXPLICIT`이면 원문으로 진행하고 이전 주제를 전달하지 않는다. `AMBIGUOUS`이거나 대상을 하나로 정할 수 없으면 확인 안내를 제공한다. 업무는 명확하지만 FAQ 정답이나 신청 조건이 부족한 경우는 이후 검색과 FAQ 되묻기가 처리한다.

### 짧은 후속 질문

- `베트남도 돼요?`, `토요일에도 가능해요?`처럼 지시어 없이 조건만 말하는 후속 질문은 정규식과 일반어 규칙에 걸리지 않는다. 이전 고객 발언이 있을 때 15자 이하 질문을 후보로 두어 현재 대상 판정 모델이 판정하게 한다.
- 길이는 모델 호출 후보를 고르는 데만 쓴다. 짧아도 `청소년 요금제도 있나요?`처럼 상품이나 업무가 있으면 모델이 `EXPLICIT`으로 판정해 이전 주제를 붙이지 않는다.
- 현재 대상 판정 프롬프트는 나라, 요일, 수령 방법, 가족 관계, 기기 종류, 비용 항목(`수수료`, `방문비`, `할부금`)처럼 업무의 조건이나 세부 항목만 있는 문장을 `OMITTED`로 판정한다. 문의 창구, 상품, 서비스, 할인 제도 자체를 묻는 문장은 `도`가 붙어도 `EXPLICIT`이다.
- 장비 반납, 기사 방문, 데이터 소진처럼 어떤 업무에 딸린 절차나 상태만 묻고 업무 이름(해지, 이전 설치, 로밍 등)이 없으면 `OMITTED`다. `설치 기사`, `장비`처럼 업무를 연상시키는 낱말은 업무 이름으로 보지 않는다. 반대로 청구 시점이나 요금 줄이는 방법처럼 통신 요금 자체를 묻는 문장은 `EXPLICIT`이다.
- 이전 발언 분석 프롬프트는 `~하려고 합니다`, `~를 알아봅니다`처럼 업무를 말한 발언을 현재 질문과 관계없이 업무로 센다.
- 이전 대화가 있는 짧은 질문마다 현재 대상 판정 호출이 1회 늘어난다. 평가에서 이 호출의 중앙값은 약 400ms였다.

### 일반어 후속 질문 규칙

- 현재 문장을 이루는 낱말이 모두 정해진 목록에 있을 때만 적용한다. 목록은 지시어(`그건`, `그거`), 시점 표현(`그때`, `아까`, `이전에`), 위치 지정(`첫 번째로`), 질문 항목(`비용`, `요금`, `기간`, `방법`, `서류`), 행위(`신청`, `취소`), 어미와 조사로 구성한다. 흔들림 보완을 켜면 `그 상품`, `그 서비스`, `그 요금제`를 지시어로, `이용`을 질문 항목으로 더한다.
- 업무 이름이나 상황 낱말이 하나라도 있으면 일치하지 않으므로 모델 판정으로 넘어간다. `요금 너무 많이 나왔어요`, `이심 신청은요?`는 규칙에 걸리지 않는다.
- 규칙은 대상 생략 쪽으로만 판정한다. 이전 고객 발언이 없으면 모델을 부르지 않고 확인 안내로 끝난다.
- 공백 제거 후 30자를 넘는 문장에는 적용하지 않는다.
- `첫 번째로 물어본`, `두 번째로 문의한`, `처음 말한`처럼 대화 속 발언을 순서로 가리키면 다른 낱말이 있어도 모델 없이 대상 생략으로 본다. `처음 신청한`은 `처음 신청한 사람도 할인 받을 수 있나요?`처럼 일반 문장에도 쓰여 이 규칙에서 제외하고 모델이 판정한다.

### 출처와 정정 연결

- 모델은 고객 원문을 복사하거나 새 질문을 만들지 않는다. 이전 발언마다 `index`, `targetCount`, `parentIndex`를 반환한다.
- `index`는 제공한 고객 발언의 순서 번호다. DB 메시지 ID는 모델에 넘기지 않고 검증 후 실제 ID로 연결한다.
- `targetCount`는 그 발언에서 새로 도입한 업무 개수다. 발언 하나에 인터넷 가입과 번호이동이 있으면 2이며 임의로 하나를 고르지 않는다.
- `parentIndex`는 앞선 업무를 이어 묻거나 정정하는 발언의 연결이다. 앞선 업무 발언에만 연결할 수 있고 순환과 미래 참조는 거부한다.
- 모든 출처가 중복 없이 제공되어야 한다. 모델이 반환한 배열 순서와 관계없이 원문 번호로 정렬해 연결한다.
- 참조할 업무는 다음 순서로 정한다.
  1. 현재 문장에 `첫 번째로 물어본`, `두 번째로 문의한`, `처음 물어본` 같은 위치 지정이 있으면 코드가 정정을 제외한 업무 순서로 센다. 모델의 위치 판정은 쓰지 않는다. 해당 순서의 업무가 없으면 확인 안내다.
  2. 위치 지정이 없고 모델이 `referenceScope=RECENT`를 반환하면 가장 최근 업무를 고른다.
  3. 그 밖에는 모델이 지정한 위치를 쓰고, 위치가 없으면 업무가 하나뿐일 때만 그 업무를 쓴다.
- 고른 업무 발언에 대상이 여러 개면 확인 안내를 제공한다.
- 흔들림 보완을 켜면, 인사를 뺀 고객 발언이 하나뿐일 때 생략된 대상은 그 발언일 수밖에 없으므로 모델이 그 발언의 업무를 0개로 세도 한 업무로 보고 연결한다. 2개 이상으로 센 발언은 그대로 확인 안내다.

예를 들어 `유심 재발급을 대리인이 신청합니다` 다음에 `대리인이 아니라 제가 직접 신청합니다`가 있으면 두 원문을 함께 전달한다. 관련 없는 다른 업무와 이전 AI 답변은 전달하지 않는다.

## 검증과 실패 처리

- 판정기가 두 요청에 각각의 JSON Schema를 담아 보내 출력 필드, 배열 길이, 번호 범위를 제한한다. AI 요청 변환기는 요청에 담긴 형식을 그대로 전달하며 프롬프트 버전으로 형식을 정하지 않는다.
- 코드가 중복, 누락, 숫자 형식, 부모 관계, 고객 원문 여부를 다시 검증한다.
- 응답을 받았지만 형식이 틀리거나 검증에 실패하면 출처 일부만 전달하지 않고 확인 안내로 처리한다. 흔들림 보완을 켜면 이전 발언 분석 응답이 틀릴 때 한 번만 다시 묻고(trace `questionResolutionRetry`), 다시 틀리면 확인 안내다.
- AI 서버 연결 실패, 시간 초과, 모델 오류, 사용자 취소는 질문 문제가 아니므로 확인 안내로 바꾸지 않고 기존 채팅 실패 처리로 넘긴다. 사용자에게는 "답변 생성 서비스에 연결할 수 없습니다" 같은 오류 안내가 표시된다.
- 코드가 보장하는 것은 구조, 출처 존재, 연결의 일관성이다. 모델이 판정한 업무 개수나 참조 의미가 정확하다는 보장은 아니다.

## 설정과 기록

- 모드는 `chat.question-resolution.mode`(환경 변수 `CHAT_QUESTION_RESOLUTION_MODE`)로 선택하며 기본값은 `REGEX_GATED`다.
- 흔들림 보완은 `chat.question-resolution.stability-guards`(환경 변수 `CHAT_QUESTION_RESOLUTION_STABILITY_GUARDS`)로 켜며 기본값은 `false`다. 아래 TELME-165 2차의 코드 규칙 네 가지와 출력 한도 상향을 함께 켠다. EXAONE에서는 켜도 결과가 같아 지금은 끄고, 문맥 판정을 gpt-oss(Bedrock)로 바꿀 때 켠다. 끈 채로 gpt-oss를 쓰면 출력 한도가 작아 답이 비거나 잘린다.
- 두 모델 호출은 `CONTEXT_RESOLUTION` 작업으로 기록하고 프롬프트 버전은 `context-v32-reference`, `context-v32-sources`다. 기록 테이블의 30자 제한에 맞춰 각각 21자·19자로 관리한다.
- 현재 대상 판정 출력은 64토큰, 이전 발언 분석 출력은 `min(2048, 128 + 64 × 출처 수)`다. 흔들림 보완을 켜면 둘 다 최소 512토큰이다. gpt-oss(Bedrock)는 답 앞의 내부 추론도 출력 한도를 써서, 한도가 64였을 때 앱의 Bedrock 클라이언트로는 현재 대상 판정 응답의 16%가 비거나 잘렸다. temperature는 0이고, 두 요청이 사고 모드 끄기를 지정해 Qwen3와 EXAONE 4.0에서는 사고 모드를 끈다.
- 실행 trace의 `questionResolution`에 최종 관계와 실제 출처 ID를, `questionResolutionEvidence`에 분석 결과, 판정 주체(`referenceSource`: `RULE` 또는 `MODEL`), 순서 번호와 실제 ID의 대응을 남긴다.
- 내부 `EXPLICIT`, `OMITTED`, `AMBIGUOUS`는 처리 결과에 따라 `SELF_CONTAINED`, `HISTORY_DEPENDENT`, `CLARIFICATION_REQUIRED`로 기록한다.

## 한계

- 일반어 규칙에 걸리지 않는 문장의 대상 유무는 모델이 판정한다. 대상이 생략된 문장을 `EXPLICIT`로 판정하면 이전 업무 없이 진행한다.
- 기본 모드에서 15자를 넘고 지시어·시점 표현·질문 항목이 없는 생략형 후속 질문은 후보가 아니어서 독립 질문으로 처리한다. `LLM_ALL`은 후보 검사를 생략할 뿐 판정 방식은 같다.
- gpt-oss는 `설치 기사님 방문비`, `데이터 다 쓰면`(앞 질문 로밍)처럼 업무를 연상시키는 낱말이 있는 생략형 후속 질문을 `EXPLICIT`으로 판정한다. 비용 항목 질문을 후보로 넣어도 모델이 대상이 있다고 보면 연결하지 않는다. EXAONE은 `신청 언제까지 해요?`, `그건 위약금이 얼마나 나와요?`, `할부금 남은 건 어떻게 돼요?`처럼 질문 항목이나 행위를 대상으로 읽는다. 두 모델이 틀리는 문장이 다르다.
- 이전 고객 발언이 인사뿐이면 모델을 부르지 않고 독립 질문으로 둔다. `주말에도 되나요?`(앞: `감사합니다`)처럼 대상이 없는 질문도 확인 안내 없이 진행된다.
- 업무가 여럿이면 가장 최근 업무를 고른다. `폰 잃어버려서 분실신고 하려고요` 다음에 `로밍도 쓸 거예요`가 있으면 `찾으면 그건 어떻게 풀어요?`도 로밍에 연결된다.
- 위치 지정 질문에서 이전 발언 분석 모델이 업무 개수를 적게 세면 해당 순서의 업무가 없어 확인 안내가 된다. `해외 로밍을 신청하려고 합니다` 다음의 `두 번째로 물어본 건 수수료가…`가 그렇게 처리됐다.
- 가장 최근 업무를 고르는 규칙 때문에 이전 업무가 여러 개일 때 `그건 얼마예요?`는 확인 안내가 아니라 최근 업무로 연결된다.
- 같은 뜻의 문장이라도 띄어쓰기에 따라 모델 판정이 달라질 수 있다.

- 문맥 해석 평가와 `blindCases`는 관계(독립 질문, 이전 발언 연결, 확인 안내)와 연결한 이전 발언 번호가 모두 맞아야 일치로 센다. 질문의 최종 답변 정확도와는 별개다.
- gpt-oss는 같은 입력에도 결과가 흔들려 3회, EXAONE은 1회 쟀다.
- gpt-oss 호출 경로는 두 가지다. 측정용 중계기(`judge_router.py`)는 앱의 Ollama 요청을 받아 Bedrock으로 넘기며 출력 한도를 512 이상으로 올리고 JSON 출력 지시를 덧붙인다. 앱의 Bedrock 클라이언트는 실제 전환 때 쓰는 경로로, 요청에 적힌 출력 한도를 그대로 쓴다(운영 설정, 추론 강도 low, 시간 제한 8초).

### 요약 (TELME-165)

Bedrock gpt-oss-120b로 바꿀 때를 대비해 두 번 보완했다.

- 1차(항상 적용): 현재 대상 판정·이전 발언 분석 프롬프트에 업무에 딸린 절차·상태, 요금 자체, `~하려고 합니다` 발언 규칙과 예시를 넣었다(`context-v32-*`). 예시는 평가 문장과 겹치지 않게 새로 만들었다.
- 2차(흔들림 보완, `stability-guards` 플래그로 켬): 프롬프트는 그대로 두고 코드에 다섯 가지를 넣었다. 고객 발언이 하나뿐일 때의 연결, 이전 발언 분석의 한 번 재요청, 비용 항목 질문의 후보 선정, `그 상품`·`그 서비스`·`그 요금제` 일반어 규칙, 출력 한도 최소 512다.

| 구성 | 문맥 해석 213 EXAONE | 문맥 해석 213 gpt-oss | `blindCases` gpt-oss | `blindCases` EXAONE | 대화 흐름 |
| --- | --- | --- | --- | --- | --- |
| 보완 전 | 202 | 199 / 202 / 204 | - | - | 16 / 13 / 15 |
| 1차 | 201 | 205 / 202 / 205 | 22 / 23 / 25 | 20 | 16 / 15 / 15 |
| 1차 + 흔들림 보완 | 201 | 210 / 208 / 208 | 23 / 24 / 24 | 20 | 14 / 15 / 15 |

- gpt-oss 칸은 중계기 경로다. 보완 전은 이전 develop(`d86b0400`), 나머지는 최신 develop에서 쟀다. 1차를 이전 develop에서 잰 값은 gpt-oss 204 / 203 / 207, EXAONE 203이다.
- 흔들림 보완은 gpt-oss가 같은 입력에도 이전 발언의 업무를 0개로 세거나 형식을 깨는 실패를 막는다. 문맥 해석 213에서 gpt-oss 3회 실패 합계가 27건에서 13건으로 줄었다(예: `미국은요?`, `그때 신분증 꼭 필요해요?`, `그 상품의 이용 기간은요?`).
- `blindCases`에서는 1차와 차이가 없다. 이 문장들에는 위 실패 유형이 거의 없어 이득이 드러나지 않지만, 손해도 없다.
- EXAONE은 흔들림 보완을 켜도 두 평가 결과가 같다. 그래서 플래그 기본값을 꺼 두고 문맥 판정을 gpt-oss로 바꿀 때 켠다.
- 대화 흐름 차이는 흔들림 범위 안이다. 멀티턴 5개는 모두 3 / 3 / 3이고, 남은 실패는 되묻기 흐름과 검색 문제다([ROUTING_CALL_COMPARISON.md](ROUTING_CALL_COMPARISON.md) 마지막 확인).
- 호출 수는 거의 같다. 문맥 해석 213을 4회 돌린 합계로 현재 대상 판정은 616회에서 604회, 이전 발언 분석은 399회에서 406회(재요청 4회 포함)다.

### 앱의 Bedrock 클라이언트로 확인

위 gpt-oss 수치는 중계기 경로라, 실제 전환 경로인 앱의 Bedrock 클라이언트로 같은 문장을 다시 쟀다(`ContextResolutionClientProbe`, 흔들림 보완 켬).

| gpt-oss 3회 | 문맥 해석 213 | `blindCases` | 빈 응답·잘린 응답 |
| --- | --- | --- | --- |
| 앱 클라이언트, 출력 한도 64 | 187 / 185 / 185 | 20 / 21 / 20 | 852회 중 118회 |
| 중계기 | 209 / 206 / 207 | 24 / 23 / 24 | 0 |

- gpt-oss는 답 앞의 내부 추론에도 출력 한도를 쓴다. 한도가 64이면 현재 대상 판정 응답의 16%가 비거나 `{"reference":"EXPLICIT`처럼 잘려 확인 안내로 끝났다.
- 흔들림 보완을 켜면 한도가 512 이상이 되어 중계기와 같은 수준이다. 현재 대상 판정 응답 시간 중앙값은 390ms다.
- EXAONE은 한도 64와 512에서 모든 호출의 응답 문자열이 같았다.

### 시도했다가 버린 것

- 프롬프트에 판정 규칙(회선 업무 이름, 사람을 꾸미는 `처음`, 상품 없는 행위, `그럼`으로 이어 묻는 상태)을 더 넣었다. 문맥 해석 213에서는 gpt-oss 210 / 210 / 210이었지만 `blindCases`에서 1차보다 나아지지 않아(3회 합계 71에서 69) 버렸다.

## 평가 재실행

모델 판정만 빠르게 비교할 때는 `ContextResolutionClientProbe`를 쓴다. 앱과 DB 없이 `cases.json`의 문장마다 `ChatQuestionResolver`를 호출하고, 앱의 Bedrock 클라이언트(`bedrock`)와 Ollama 형식 요청(`router`, 중계기나 Ollama 주소)을 고를 수 있다. 결과 jsonl에는 호출마다 출력 한도, 응답, 시간이 남는다.

```bash
AWS_PROFILE=<Bedrock 권한 프로필> CONTEXT_PROBE=true CONTEXT_PROBE_OUT=build/context-probe.jsonl \
  CONTEXT_PROBE_CLIENTS=bedrock,router CONTEXT_PROBE_REPEATS=3 \
  ./gradlew test --tests '*ContextResolutionClientProbe' --rerun
# EXAONE: CONTEXT_PROBE_CLIENTS=router CONTEXT_PROBE_ROUTER_URL=http://127.0.0.1:11434 CONTEXT_PROBE_OLLAMA_MODEL=exaone3.5:7.8b
# 흔들림 보완 끄기: CONTEXT_PROBE_GUARDS=false
```

실제 모델과 API 호출은 `ContextResolutionLiveEvaluationTest`가 수행한다. 평가 입력은 [cases.json](../scripts/context-resolution-evaluation/cases.json)에 기대 관계와 필요한 이전 발언 번호로 고정한다. 관계와 출처가 모두 맞아야 일치로 센다. 질문의 최종 답변 정확도와는 별개다.

- `RUN_CONTEXT_EVAL_LIVE=true`일 때만 실행한다. 개발 DB를 쓰지 않도록 DB 이름이 `telme_context_eval_`로 시작하는지 확인한다.
- 빈 평가 DB에 스키마를 적용한 뒤 `prepare_database.py --source <FAQ가 있는 DB> --target <평가 DB>`로 FAQ와 임베딩만 복사한다. 데이터가 있는 대상 DB에는 복사하지 않는다.
- `CONTEXT_EVAL_FIXTURE_KEY`로 `cases.json`의 입력 묶음을 고르고, 실행마다 새 `CONTEXT_EVAL_RUN` 값을 쓴다.
- `summarize.py`가 원시 결과를 집계한다. 결과는 `scripts/context-resolution-evaluation/runs/`에 생성되며 저장소에 포함하지 않는다.
- `cases.json`의 일부 현재 질문은 프롬프트 예시와 같은 문장이다. 프롬프트에 없는 문장으로 측정한 결과와 구분해서 해석한다.
- `blindCases`는 프롬프트·평가셋을 보지 않은 다른 작성자가 쓴 문장이다. 다음 수정의 확인용으로 쓰고, 이 문장의 실패를 보고 프롬프트나 규칙을 고치지 않는다. 고친 뒤에는 새 확인용 문장을 따로 만든다. `holdoutCases`는 TELME-165 2차 작업 중에 만들어 수정에 쓰였다.

```powershell
$env:POSTGRES_DB = '<telme_context_eval_로 시작하는 평가 DB>'
$env:SPRING_FLYWAY_LOCATIONS = 'classpath:db/migration'
$env:RUN_CONTEXT_EVAL_LIVE = 'true'
$env:CONTEXT_EVAL_RUN = '<새 실행 이름>'
$env:CONTEXT_EVAL_FIXTURE_KEY = 'cases'
./gradlew.bat test --tests '*ContextResolutionLiveEvaluationTest' --rerun-tasks
```

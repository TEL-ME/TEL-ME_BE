# 요금제 변경 상담 되묻기

매장 외 상담 중 **가입월·당월 변경 횟수 기준 요금제 변경 상담 1개**의 조건 확인(되묻기), 되묻기 질문 설명, 후속 입력·정정·상담 전환, 백엔드 상태 복원 계약과 별도 화면 검증 절차를 다룬다.

## 구현 범위 구분

현재 코드 범위: 기본 되묻기·후속 입력 검증·고정 질문 설명이 연결돼 있다. 상태 조회 계약과 실제 화면 복원 검증은 구분한다.

- 기본 되묻기·후속 조건 처리와 고정 질문 설명은 서로 다른 구현 단계다.
- 기본 경로는 가입월·변경 이력 조건을 확인한다. 설명 처리기가 연결되지 않은 경로에서는 설명 본문 제공을 지원하지 않는다.
- 후속 입력 검증이 연결된 경로는 짧은 응답·타인·가정·모순·최신 정정을 추가 검증한다.
- 고정 설명은 PlanChangeQuestionExplanation이 턴 분석·저장 경로에 연결된 경우에만 제공한다. 클래스 존재만으로 활성화를 판단하지 않는다.
- 이력 조회·상담 대기 보존은 백엔드 계약이다. 실제 브라우저 새로고침·재접속 결과는 별도로 확인한다.

## 1. 기능 정의와 지원 범위

- 대상 상담: "제가 지금 요금제를 바꿀 수 있나요?" 류의 개인별 변경 가능 여부 질문 1종.
- 확인 조건: `joinedThisMonth`(이번 달 가입 여부, J), `changedThisMonth`(이번 달 이미 변경했는지, C). 값은 명시된 예/아니요만 허용하며 모델이 추정한 값은 저장하지 않는다.
- 일반 기준 질문(예: "요금제 변경 기준이 뭐예요?")에는 개인 조건을 묻지 않고 바로 안내한다. 개인별 가능 여부를 묻는 경우에만, 근거로 제한을 확정할 수 없는 조건을 하나씩 질문한다.
- 설명 처리기가 연결된 경로는 되묻기 질문의 뜻을 설명한다("가입한 달"·"변경 이력"이 무엇인지 고정 문구로 설명하고 원래 대기 질문으로 복귀).
- **포함하지 않는 것**: 전체 상담 유형 지원, 계정의 실제 변경 권한 확인, 로밍 국가·기간, 특정 요금제 연령 자격, 약정·위약금 상담, 복합 질문(동시에 여러 상담을 요구하는 발화)의 명시적 분기 선택.
- 두 조건이 모두 "아니요"이고 FAQ 제한 근거가 있어도 이는 **가입월·월 1회 기준에 한정한 안내**이며, 그 외 모든 가입 자격·변경 권한 충족을 확정한 것은 아니다.
- 변경 가능 여부·조건·횟수와 적용 시점·요금 계산은 구분한다. 적용·반영·일할 계산 질문은 기존 일반 FAQ 검색·생성 경로를 사용하며 가입월 질문이나 정책 보완 검색으로 대체하지 않는다.
- 명확한 규칙 값이 우선이다. 규칙이 놓친 응답은 현재 대기 키·예/아니요 형식·본인 동작·시점·극성을 확인한 LLM 값만 보완한다. 타인·가정·모순·미확인·보류·새 질문과 안내·신청 완료는 확정 값으로 저장하지 않는다.
- 가입 후 두 달 이상이 지났다는 명확한 사실은 이번 달 가입이 아님을 확인할 수 있지만 한 달·30일·4주는 달력상 가입월로 추정하지 않는다. 계정의 실제 권한을 확인하거나 변경 가능 시점을 계산하는 기능은 아니다.

| 399 / BILLING-0078 | 가입한 달엔 변경 불가, 다음 달부터 가능 | 가입월 제한 |
| 1387 / BILLING-0015 | 월 1회, 신청 다음 날 00:00 적용, 가입한 달엔 변경 불가 | 두 제한 |
| 1462 / BILLING-0106 | 월 1회, 이번 달 이미 변경했다면 다음 달부터, 가입한 달도 불가 | 변경 이력이 있는 경우 |
| 1451 / BILLING-0092 | 이번 달에 안 바꿨으면 가능, 한 달에 한 번 | 가입월 근거가 검색에서 빠질 수 있는 FAQ |
| 488 / PLAN-0114 | 시니어 요금제는 만 65세 이상만 가입 가능 | 이 상담 범위 밖 예시(연령 제한) |

표의 숫자 ID는 고정 검증 자료의 예시이며 다른 DB의 현재 ID를 보장하지 않는다. 정책 판단은 슬롯 번호가 아니라 요금제 변경 주제와 답변 본문의 제한 근거를 확인한다.

검색 후보가 있고 필요한 정책 근거가 빠진 경우에만 "요금제 변경 가입한 달 월 1회 기준"으로 1회 보완 검색한다. 검색 모델·임계값(Q_A 0.72 / QUESTION_ONLY 0.88)·Top-K·병합 방식은 이 기능에서 변경하지 않는다(검색 튜닝은 별도 담당 영역). 이미 제한을 확정할 수 있으면 추가 검색하지 않고, 근거가 계속 부족하면 되묻기 대신 기존 정보 없음(`NO_EVIDENCE`) 안내로 종료한다.

## 3. 처리 흐름

```
ChatSessionController.sendMessage
  → ChatSessionService → ChatProcessingDispatcher → ConsultChatProcessingService
  → FollowupContextService (대기 후보 조회: 세션 소유권·CLOSED 아님·완료된 사용자 QUESTION 확인)
  → QueryRoutingAnalysisProvider / QueryRoutingFollowupAnalysisProvider
      → QueryRoutingService.analyzeFollowUp ↔ RuleBasedRoutingFallback (모델 결과를 발화 근거와 대조)
      → PlanChangeConditions / FollowupConditionConverter (발화의 조건·허용 값 검증·변환)
      → FollowupSelectionValidator (현재 상담·질문·조건 선택 검증)
  → ConsultTurnPreparationService / ConsultService
  → FaqSearchAnswerProvider.prepare (검색 후 DialogueService.assessFaq)
  → RagSearchResultAnswerGenerator → RagAnswerGenerator
  → AnswerGuard → ConsultChatPersistenceService → SSE
```

- 상담은 기존 `consult_requests`, 조건은 기존 `consult_conditions`를 재사용한다. 새 테이블·새 조건 상태를 추가하지 않는다.
- 되묻기 질문은 생성 모델이 아닌 고정 문구이며 `CLARIFICATION` 메시지로 저장, SSE `complete`로 전달한다.
- 설명 처리기가 연결된 경로: 대기 중인 FAQ 요금제 질문이 있을 때 `PlanChangeQuestionExplanation`이 설명 요청인지 판별한다. 설명은 모델을 호출하지 않는 고정 안내문이며, 안내문 뒤에 기존 대기 질문을 그대로 덧붙인다. 새 `CLARIFICATION` 메시지를 만들지 않는다.
- 조건과 FAQ가 충족되면 policyCompletion·criteriaCompletion이 정책 문장을 구성한다. 이 문장이 있으면 RAG_ANSWER 생성 호출을 생략하며, 필요한 생성 전 근거 검사·취소 확인과 동일한 Answer Guard를 통과한 뒤 저장·전송한다. 정책이 없으면 기존 모델 생성 경로를 유지한다.
- 추적의 generationInputs·guardResults에 answerSource=POLICY_COMPOSED 또는 LLM_GENERATED로 출처를 구분한다. Guard 결과는 실제 후보 문장과 최종문을 비교한다. 호출하지 않은 생성 모델의 성공·사용량·시도 행을 만들지 않는다. 이를 모델 원문 품질 개선으로 표현하지 않는다.
- 최종 답변은 Guard → 저장 → token/complete 순서로 처리한다. 최종 token 앞에 DISPATCH_ATTEMPTED 기록용 DB 쓰기를 하지 않으며 전송 후 DISPATCH_RETURNED/DISPATCH_ERROR는 유지한다.

## 4. 입력별 판단 기준과 사용자 발화 예시

되묻기·가능/제한 안내 행은 필요한 FAQ 정책 근거가 확보된 경우를 뜻한다. 설명 요청·설명 저장 행은 고정 설명 처리기가 연결된 단계에만 적용한다.

표기: `J=joinedThisMonth`, `C=changedThisMonth`, FILLED=예/아니요 확정.

| 기존 조건·대기 | 사용자 후속 발화 | 기대 분류 | 갱신·유지 | 상태·다음 동작 |
| --- | --- | --- | --- | --- |
| 조건 없음(최초 질문) | 제가 지금 요금제를 바꿀 수 있나요? | 개인 상담 시작 | — | J부터 질문 |
| J 대기 | 네 / 네, 고마워요 | CONDITION_RESPONSE | J=예만 저장. C 추정 없음 | DONE, 확인된 가입월 제한 안내 |
| J=아니요, C 대기 | 아니요 | CONDITION_RESPONSE | C=아니요, J 유지 | DONE, 두 기준에 한정한 안내 |
| J=아니요, C 대기 | 이번 달엔 안 바꿨어요 / 아직 안 바꿨어요 / 변경 안 했어요 | CONDITION_RESPONSE | C=아니요, J 유지 | DONE, 유효 응답을 실패 횟수로 소비하지 않음 |
| J 대기 | 가입한 지 3개월 됐어요 | CONDITION_RESPONSE | J=아니요 | C만 질문; 경과 기간을 변경 가능 시점으로 바꾸지 않음 |
| J 대기 | 가입한 지 한 달 / 30일 / 4주 됐어요 | 해석 불가 | 가입월 추정 없음 | 현재 가입월 질문 유지, 기존 반복 기준 적용 |
| J 대기 | 지난달이요 | CONDITION_RESPONSE | J=아니요 | WAITING_CONDITION, C만 질문 |
| 대기 없음·완료 상담 | 네 / 아니요 | 초기 라우팅 | 옛 상담 조건 변경 없음 | 옛 DONE 유지 |
| J 대기 | 네, 유심 비용도 알려주세요 | NEW_QUESTION | 앞의 "네"를 J에 저장하지 않음 | 옛 상담 CANCELLED, 새 FAQ 안내 |
| J 대기 | 지난달에 가입했고, 이번 달엔 아직 안 바꿨어요 | CONDITION_RESPONSE | J·C 모두 아니요(동시 저장) | DONE, 추가 질문 없음 |
| J=아니요, C 대기 | 아니, 이번 달에 가입했어요 | CONDITION_RESPONSE·정정 | J=예로 갱신, C 값 없음 유지 | DONE, 다른 조건 질문 없이 제한 안내 |
| J 대기 | 이번 달에 가입했어요. 아니, 지난달이에요 | CONDITION_RESPONSE·정정 | 최신 값 J=아니요(원문 값으로 덮지 않음) | C만 질문 |
| J 대기 | 이번 달에 가입했어요. 지난달에 가입했어요(순서 불명확) | 해석 불가 DEFERRED | 값 저장 없음 | 기존 질문 유지, 반복 실패 기준 적용 |
| J/C 대기 | 가입한 것 같아요 / 바꾼 것 같기도 하고 아닌 것 같기도 해요 | 해석 불가 DEFERRED | 값 추정 없음 | 질문 추가 없이 대기 |
| J 대기 | 이번 달인지 지난달인지 모르겠어요 | CONDITION_RESPONSE·미확인 | J=DECLINED, 값 없음 | DONE, 조건별 기준 안내 |
| J 대기 | 이번 달에 가입했다면 / 친구는 이번 달에 가입했어요(가정·타인) | 해석 불가 DEFERRED | 본인 J 저장 없음 | 기존 질문 유지, 반복 실패 기준 적용 |
| J 대기 | 저는 지난달, 친구는 이번 달이에요 | CONDITION_RESPONSE | 본인 J=아니요만 저장 | C만 질문 |
| J/C 대기 | 잘 모르겠어요 / 알려주고 싶지 않아요 | CONDITION_RESPONSE(거절) | 현재 키 DECLINED, 값 없음 | 가능한 기준 안내로 DONE, 반복 질문 없음 |
| J/C 대기 | 나중에요 | DEFERRED(명시적 보류) | 조건·질문 유지, 추정 없음 | WAITING_CONDITION, 출력 없음 |
| J=아니요, C 대기 | 가입한 달은 모르겠어요. 이번 달엔 아직 안 바꿨어요(미확인+정정) | CONDITION_RESPONSE·미확인 정정 | 옛 J 값 제거·DECLINED, C=아니요 | DONE, 미확인 개인 판단 없음 |
| J 대기 | 가입한 달이 무슨 뜻이에요? | 설명 요청(DEFERRED 아님, 별도 처리) | 조건·질문 변경 없음 | 고정 설명문 + 원래 질문 재안내, 반복 실패 횟수 소비 안 함 |
| 서로 다른 세션·소유자 | 임의 후속 값 | 접근 거절 | 해당 세션·소유 상담만 접근 | 다른 세션 상담·조건 변경 없음 |
| 완료·취소 상담 | 임의 후속 값 | 후보 제외 | 닫힌 상담 갱신 없음 | 새 질문 경로 또는 기존 오류 |
| 같은 세션 복수 대기 후보 | 임의 후속 값 | STATE_CONFLICT | 어느 후보에도 저장하지 않음 | 실행 FAILED, 두 상담은 WAITING 유지(명시적 선택 UI는 미지원) |

판단 원칙:
- 모름과 거절은 의미가 다르지만 저장은 기존 `DECLINED`/값 없음으로 통일한다(새 상태 도입 안 함).
- 명확한 정정은 최신 값으로 교체, 명확한 미확인 정정은 옛 값도 제거한다. 단순 불확실 충돌만으로는 기존 확정 값을 바꾸지 않는다.
- 확정값 추출과 미확인 키 추출 모두 절 순서·주체(본인/타인)를 함께 검증한다. 타인·가정의 발화로 본인 조건을 채우거나 DECLINED로 덮지 않는다.
- 같은 대기 조건의 해석 불가 응답이 **2회**가 되면 값을 만들지 않고 일반 기준 안내로 종료한다. 명시적 보류·명확한 정정·새 상담 전환·설명 요청은 이 실패 횟수에 포함하지 않는다.
- 새 질문으로 전환되면 이전 대기 상담은 CANCELLED로 닫고, 새 상담에 이전 조건을 복사하지 않는다.

### 되묻기 질문 설명 문구

- 가입한 달은 가입 날짜가 속한 달력상의 달이다(가입 후 한 달 경과 여부가 아님, 이번 달 가입 여부를 확인).
- 변경 이력은 이번 달에 이미 요금제를 바꾼 적이 있는지를 뜻한다.
- 설명에는 개인별 가능·불가, 구체적 기간·비용·제한을 넣지 않는다. 설명 자체에는 FAQ grounded 판정을 부여하지 않는다.

### 대화 예시

1. 사용자: 제가 지금 요금제를 바꿀 수 있나요? → 되묻기: 이번 달에 가입하셨나요?
2. 사용자: 가입한 달이 무슨 뜻이에요? → 설명(달력상 가입월) + 같은 질문 재안내.
3. 사용자: 지난달이요. → J=아니요 저장 → 되묻기: 이번 달에 이미 요금제를 변경하셨나요?
4. 사용자: 그 질문 뜻이 뭐예요? → 설명(변경 이력) + 같은 질문 재안내. J=아니요 유지.
5. 사용자: 아니요. → C=아니요 저장 → 두 조건·FAQ 근거로 생성·Guard 재개 → "가입한 달이 아니며 이번 달에 아직 변경하지 않으셨으므로, 가입월과 월 1회 기준에 한정하면 요금제 변경이 가능합니다." 저장 후 동일 문자열 전송·조회.

## 5. 저장·조회·전송 계약

| 항목 | 설명 후 상태 |
| --- | --- |
| 이번 chat_execution | COMPLETED, 설명 output_message_id 연결 |
| 설명 chat_message | ANSWER/COMPLETED, reply_to는 설명 요청 입력 |
| 상담 consult_request | 기존 ID·WAITING_CONDITION·version 유지 |
| 대기 조건 | 기존 key·PENDING·값 없음·asked_message_id 유지 |
| 이미 확인한 조건 | 기존 값·상태·응답 연결 유지 |
| 세션 | NEED_CLARIFICATION 유지 |
| 다음 후속 응답 | 같은 상담·원래 질문의 조건으로 반영 |

- 설명 메시지는 일반 직접 안내와 동일한 `complete` 이벤트/메타데이터 계약을 쓴다(별도 start/token 없음).
- 일반 `completeAnswer`는 세션을 OPEN으로 재개하므로 설명에는 쓰지 않는다. 대신 `completeAnswerWhileWaiting`으로 메시지·실행을 완료하면서 세션의 `NEED_CLARIFICATION`은 유지한다. 오래된 질문·다른 세션 질문에 저장을 시도하면 같은 트랜잭션에서 롤백한다.
- 세션 ID만으로는 접근할 수 없고 기존 소유권 검증을 거친다. 독립된 이력 조회(GET)를 반복해도 상담 조건·대기 상태는 바뀌지 않으며 새 실행을 만들지 않는다(새로고침·재접속 복원의 기반).
- 완료 답변과 근거는 기존 이력 API 및 `/api/v1/chat/messages/{messageId}/sources`로 확인한다. 오류·취소·타임아웃 상태는 정상 완료와 구분해 기록한다.

## 6. 오류·취소·타임아웃 처리

- 검색 오류, 모델 오류·타임아웃·취소는 기존 실패 상태·안내로 처리하며 되묻기로 전환하지 않는다.
- 판단에 필요한 정책 근거가 전혀 없으면(`NO_EVIDENCE`) 되묻기 없이 정보 없음으로 종료한다.
- 같은 세션에 복수의 대기 후보가 존재하면 `STATE_CONFLICT`로 안전하게 거절하고 실행을 FAILED로 기록한다. 두 상담 모두 WAITING 상태를 유지하며 임의로 하나를 선택하지 않는다. 복수 후보 중 명시적 선택(UI)을 지원할지는 별도 확인이 필요하다.
- 완료·취소된 상담은 후속 입력 대상 후보에서 제외한다.

## 7. 설정·실행 준비·검증 방법

### 로컬 검증 환경(참고)

아래 표의 프롬프트 버전은 고정 자료의 과거 재현 조건이다. 현재 통합 전문은 v4.2 일반 규칙과 요금제 조건 블록을 보존한 `rag-answer-v4.2-plan-v2`이며 과거 결과·해시는 소급 변경하지 않는다.

| 항목 | 값 |
| --- | --- |
| DB | 전용 로컬 PostgreSQL + PostGIS + pgvector (운영/개발 DB와 분리) |
| 생성·분류 모델 | 로컬 `exaone3.5:7.8b` |
| 생성 옵션 | temperature 0, num_ctx 8192, num_predict 1024(후속 분류는 num_predict 300) |
| 검색 | bge-m3, Q_A 0.72 / QUESTION_ONLY 0.88, Top-3 |
| 프롬프트 | `rag-answer-v3-plan-v2`(기존 v3 시스템 지시 유지 + 상담 전용 조건 블록 추가) |

### 재현 명령

```sh
TELME_DB_TESTS=true POSTGRES_HOST=127.0.0.1 POSTGRES_PORT="<전용 테스트 DB 포트>" \
POSTGRES_DB=telme POSTGRES_USER=telme POSTGRES_PASSWORD="<전용 테스트 DB 비밀번호>" \
JAVA_HOME="<JDK 21 경로>" ./gradlew build
```

직접 JDBC를 쓰는 일부 DB 테스트는 DB명을 telme로 고정하고 POSTGRES_PORT·USER·PASSWORD를 사용한다. POSTGRES_DB만 바꿔서는 이 테스트가 격리되지 않는다. DB 옵트인을 켤 때는 별도 테스트 컨테이너·포트의 telme DB를 준비한다. Spring datasource도 같은 독립 환경으로 맞추며 개발·운영 DB를 대상으로 하지 않는다.

공유해야 할 평가 입력(기대 사례, 발화-FAQ-점수 기록, 합성 대화 원문 발췌, 재현 시나리오)은 `scripts/data/`의 평가 자료 경로로 정리한다(기존 `docs/evidence/*.json`에서 이동). 전체 원시 대화·SSE·DB 덤프 등 로컬 전용 자료는 팀 문서·scripts/data에 포함하지 않는다.

### 화면 검증 체크리스트(백엔드 검증과 구분해서 별도 확인 필요)

1. 되묻기가 한 번만 표시되고, 새로고침 후에도 같은 질문·이력이 유지되는지.
2. Guard 통과 전 토큰이 화면에 노출되지 않고 최종 답변이 한 번만 표시되는지.
3. 설명 요청 후 원래 질문으로 정상 복귀하는지, 설명 자체가 대기 질문으로 오인되지 않는지.
4. 모름·거절 후 기준 안내가 표시·저장되고 새로고침 후 동일한지.
5. 보류·첫 애매한 응답에서 `complete`(출력 없음)로 로딩이 끝나고 기존 질문이 유지되는지.
6. 정정·새 주제 전환에서 과거 조건이 새 상담에 유출되지 않는지.
7. 오류·타임아웃·취소 화면에서 부분 생성문이나 잘못된 정상 완료가 보이지 않는지.
8. 로그인 전환·쿠키 상실·서버 재시작 이후 게스트 접근이 기존 권한 체계대로 거절되는지.

## 8. 평가 지표와 해석 한계

- 자동 테스트 통과, 실제 로컬 모델 검증, 실제 브라우저 화면 검증은 서로 다른 단계이며 하나가 다른 하나의 완료를 의미하지 않는다. 이 문서의 각 절은 어느 단계까지 확인됐는지를 섹션 제목으로 구분한다(처리 흐름/계약=코드 기준, 화면 체크리스트=미검증 영역).
- 생성된 답변 문자열의 사례별 비교는 소규모 선택 샘플 검증이며, 자동 테스트 통과만으로 환각률 개선이나 전체 답변 품질 개선을 주장하지 않는다.
- 설명 기능은 고정 문구만 제공하며 모델을 호출하지 않는다. 복합 질문의 동시 처리는 지원하지 않으며 조건 응답과 새 요청이 섞이면 기존 NEW_QUESTION 전환 정책을 따른다. 복수 대기 후보의 명시적 선택은 지원하지 않고 STATE_CONFLICT로 거절한다. 두 상황을 같은 오류로 설명하지 않는다.
- 물리적 오프라인 복구, 화면 조회 타임아웃, 로그인 전환/쿠키 상실/서버 재시작 후 게스트 접근은 별도 환경에서 검증이 필요하다. 상담 조건이 서버 DB에 남아 있어도 게스트 세션이 사라지면 기존 권한 체계상 접근할 수 없다.
- 실제 화면의 새로고침·재접속·브라우저 SSE 연결은 백엔드 통합 테스트로 대체 검증되지 않는다. 담당자와 별도로 확인한다.

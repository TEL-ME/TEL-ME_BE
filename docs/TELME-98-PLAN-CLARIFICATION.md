# TELME-98 — 요금제 변경 상담의 조건 확인과 후속 답변 연결

## 완료 범위와 기준

매장 외 상담 중 **가입월·당월 변경 횟수에 따른 요금제 변경 상담 1개**를 추가한다. 전체 상담 지원, 전체 답변 품질 개선, 계정의 실제 변경 권한 확인을 뜻하지 않는다. 로밍 국가·기간, 특정 요금제의 연령 자격, 약정·위약금 상담은 추가하지 않았다.

작업 브랜치: `feat/TELME-98-plan-change-clarification`.
최초 구현은 PR #85의 `b19fc03`와 develop `e553066`을 기준으로 했다. 오류 보완 준비본은 최신 PR #85 `47cbbe5`(develop `c4f4458` 포함)에 되묻기 변경만 적용했다. #74 Guard와 #83 저장·조회 보완을 포함하고, 기존 작업본은 별도로 보존했다. 현재 결과는 [오류 보완 검증](TELME-98-CLARIFICATION-FIXES.md)에 기록한다.

## 실제 처리 경로와 재사용

`ChatProcessingDispatcher → ConsultChatProcessingService → ConsultTurnAnalysisAdapter → QueryRoutingAnalysisProvider / QueryRoutingFollowupAnalysisProvider → ConsultTurnPreparationService / ConsultService → DialogueService → FaqSearchAnswerProvider → RagSearchResultAnswerGenerator → RagAnswerGenerator / AnswerGuard → ConsultChatPersistenceService → SSE`

- 활성 `ChatProcessingPort`는 `ConsultChatProcessingService` 하나다.
- 원문은 사용자 메시지 및 `originalUserQuery`, 재작성은 기존 라우팅의 `queryText`/`searchQuery`를 사용한다. 개인 조건을 원문에 덧붙여 원문을 바꾸지 않는다.
- 상담은 `consult_requests`, 조건은 `consult_conditions`를 재사용한다. 기존 `consultRequestId`, `condition_key`, `asked_message_id`, `answered_message_id`, optimistic version을 사용한다. 새 테이블이나 새 조건 상태를 추가하지 않는다.
- 기존 대기 질문 후보 조회·대화 소유권 검증·후속 답변 선택·정정 저장을 재사용한다.
- 기존 메시지 유형 `CLARIFICATION`을 저장하고 SSE `complete`로 전달한다. 생성 모델로 새 질문을 작성하지 않고 고정 질문을 사용한다.
- 최종 답변은 기존 근거 검사·생성·Guard를 거쳐 저장 후 한 번 전송한다. 화면 전송 문자열과 DB·조회 문자열을 동일하게 유지한다.

기존 코드에서 `GENERAL_FAQ`는 바로 `PROCEED`였으며 `PROCEED`는 검색 진행 허용을 뜻했다. 이를 유지하고, FAQ 개인 상담은 **실제 검색 후 생성 전**에 `DialogueService.assessFaq`를 호출한다. 대기 중인 요금제 질문에 대한 보류·다른 조건 정정에는 기존 질문을 유지한다.

## 근거와 최소 조건

2026-10-01 로컬 DB의 활성 FAQ 1,152건을 기준으로 확인했다. 배포 DB가 같은 상태라고 가정하지 않는다.

| FAQ ID / slot_id | 확인한 답변 원문 | 역할 |
| --- | --- | --- |
| 357 / BILLING-0001 | 요금제 변경은 한 달에 1회만 가능합니다. 변경을 신청하시면 다음 날 00:00부터 새 요금제가 적용되고, 그 달 요금은 일할 계산됩니다. 가입한 달에는 변경할 수 없고 다음 달부터 가능합니다. | 두 제한과 적용 시점 |
| 399 / BILLING-0078 | 가입한 달에는 변경할 수 없습니다. 다음 달부터 변경하실 수 있습니다. | 가입월 제한 |
| 1387 / BILLING-0015 | 월 1회 변경할 수 있고, 신청일 다음 날 00:00부터 적용됩니다. 가입한 달에는 변경할 수 없습니다. | 두 제한 |
| 1462 / BILLING-0106 | 요금제 변경은 월 1회이며, 이번 달에 이미 변경했다면 다음 달에 가능합니다. 가입한 달에도 변경할 수 없습니다. | 변경 이력이 있는 경우 |
| 1451 / BILLING-0092 | 이번 달에 아직 안 바꾸셨으면 됩니다. 한 달에 한 번입니다. | 가입월 근거가 빠질 수 있는 검색 결과 |
| 488 / PLAN-0114 | 시니어 요금제는 만 65세 이상만 가입할 수 있어 나이가 안 되시면 변경이 어렵습니다. 신분증으로 확인이 필요합니다. | 이번 범위 밖의 별도 제한 예시 |

필수 조건은 `joinedThisMonth`(이번 달 가입 여부), `changedThisMonth`(이번 달 이미 변경했는지)다. 값은 명시된 `예`/`아니요`만 허용한다. 가입한 달이거나 이번 달 이미 변경했다는 조건과 해당 제한 근거가 있으면 다른 조건을 추가로 물을 필요가 없다. 변경 가능 방향의 안내에는 두 제한 근거와 두 조건을 모두 확인한다.

두 조건만으로 특정 요금제의 연령 자격·약정 등의 모든 제한까지 충족했다고 확정하지 않는다. 이 상담은 가입월·월별 변경 횟수 기준에 한정한다. 시니어·청소년·약정·위약금 등을 명시한 질문은 이번 개인 조건 확인 대상에서 제외하고 기존 FAQ 답변 경로로 보낸다.

### 실제 검색 확인

무료 로컬 `bge-m3`와 PostgreSQL의 벡터를 읽기 전용으로 조회했다. 생산 검색 코드의 ACTIVE/SYNCED·버전 일치·모델 일치 필터, Q_A 0.72, QUESTION_ONLY 0.88, 각 Top-3와 질문 벡터 우선 병합을 재현했다. 실제 Chat API 호출이나 배포 환경 검색 검증은 아니다.

| 검색 문구 | 실제 반환 slot_id와 점수 |
| --- | --- |
| 요금제 변경 기준이 뭐예요? | slot_id 없는 샘플 FAQ 0.8926, BILLING-0050 0.7282 |
| 제가 지금 요금제를 바꿀 수 있나요? | BILLING-0092 0.8951, BILLING-0057 0.8945 |
| 이번 달에 가입했는데 변경할 수 있나요? | BILLING-0106 0.7442, BILLING-0078 0.7371 |
| 요금제 변경 가입한 달 월 1회 기준 | BILLING-0001 0.7974, BILLING-0015 0.7970, BILLING-0106 0.7791 |

원문 개인 질문의 검색 결과에는 가입월 제한이 빠졌다. 해당 상담에서 판단에 필요한 정책 근거가 빠진 경우에만 `요금제 변경 가입한 달 월 1회 기준`으로 한 번 보완 검색한다. 모델·임계값·Top-K·병합 방식은 바꾸지 않는다. 이미 제한을 확정할 수 있으면 관련 없는 제한 때문에 추가 검색하지 않는다. 근거가 계속 부족하면 되묻기 대신 기존 정보 없음 안내로 종료한다.

선택한 근거는 같은 턴의 최종 생성에 재사용하며 되묻기 평가와 생성 사이에 재검색하지 않는다. 재개 턴에서는 정책 변경을 놓치지 않도록 검색을 다시 수행한다. 검색 비용은 필요한 턴에서 기존 검색에 최대 1회 보완 조회가 추가된다. 되묻기 질문 작성용 모델 호출은 추가하지 않는다.

원문·FAQ 답변·점수·모델 digest·검색 조건은 [검색 기록](evidence/telme98-local-search-20261001.json)에 보존했다. 이는 평가셋이나 Judge 기준이 아니다.

검색 전에는 기존 의도 분류·불확실 질문 안내를 재사용한다. 이번에 임의의 일반 FAQ 분류기나 모든 상담용 필수 조건 목록을 만들지 않았다. 검색 후 조건 확인은 위 개인 요금제 상담만 대상으로 한다. 일반 요금제 변경 기준 질문도 같은 정책 근거를 확인하되 개인 조건을 요구하지 않고 기준을 안내한다. 점수 하나, Guard 차단 여부, FAQ 질문에만 있는 정책을 되묻기 근거로 삼지 않는다.

## 후속 입력과 상태

- `지난달에 가입했어요`, `이번 달에는 아직 안 바꿨어요` 등 명시적 표현을 추출한다. 단독 `네`/`아니요`는 지금 묻는 조건 하나에만 반영한다.
- 기존 후속 입력 LLM 프롬프트에 두 키를 추가했다. 허용 키·값·사용자 발화 대조·규칙 fallback·상담 조건 변환을 함께 연결했다. 초기 STORE 조건 추출에는 새 키를 허용하지 않는다.
- 모델이 사용자에게 없는 가입 여부나 다른 지역을 생성하면 저장하지 않는다. 조건 값이 정규화되었더라도 실제 발화에서 확인되지 않으면 채우지 않는다.
- 정정은 해당 상담의 조건만 갱신한다. 원문의 옛 조건으로 최신 정정을 덮지 않는다.
- 거절·모름은 기존 `DECLINED` 상태로 미확인을 표현한다. `아니요`로 간주하지 않고, 조건별 기준 안내를 생성한다. 보류는 기존 질문을 유지하고 새 질문 메시지를 만들지 않는다.
- 새 질문으로 전환하면 이전 요금제 대기 상담을 `CANCELLED`로 닫는다. 이전 조건은 새 상담에 복사하지 않는다. 다른 세션의 조건을 공유하지 않는다.
- 가입월 정정만으로 변경 불가가 결정되면 남은 질문을 더 묻지 않고 완료한다. 미답변 조건 값은 임의로 채우거나 거절로 바꾸지 않는다. 그 기록은 미답변으로 보존하고 상담을 `DONE`으로 닫아 후속 입력 후보에서 제외한다. 위치 등 다른 대기 조건의 완료 금지 규칙은 유지한다.
- 날짜가 간접적으로 표현되거나 문구가 불명확하면 임의로 월을 계산해 추출하지 않는다. 실제 모델의 다양한 표현 처리 성능은 별도 확인해야 한다.

### 대화 예시

통합 테스트에서 확인한 흐름이며 실제 로컬 생성 모델의 품질 측정 결과가 아니다.

1. 사용자: 제가 지금 요금제를 바꿀 수 있나요?
2. 되묻기: 이번 달에 가입하셨나요?
3. 사용자: 지난달에 가입했어요.
4. 되묻기: 이번 달에 이미 요금제를 변경하셨나요?
5. 사용자: 이번 달에는 아직 안 바꿨어요.
6. 원문 질문·두 확정 조건·현재 FAQ 근거로 생성과 Guard를 재개한다. 가입월·월별 변경 횟수에 한정한 답변을 저장한 뒤 같은 문자열을 전송하고 조회한다.

중간에 “가입은 이번 달이에요”라고 정정하면 두 번째 조건을 더 묻지 않고 가입월 제한 안내로 끝난다. “나중에요”이면 질문을 중복 전송하지 않고 대기한다. “유심 재발급 비용 알려주세요”이면 새 상담으로 분리한다.

## 최초 구현 검증과 한계

최초 구현 당시 전체 빌드: **1,349건 통과, 실패·오류 0건, 2건 스킵**(총 1,351건). 스킵은 명시적 실행이 필요한 평가 프로브 2개이며 이번 상담 테스트가 아니다. DB 선택 실행 테스트도 활성화했다. 신규 57건은 정책·조건 추출 34건, 실제 활성 Chat 통합 18건, 후속 입력 검증 추가 5건이다. 실제 PostgreSQL 테스트 DB를 사용했으며 사용자 FAQ DB를 테스트 저장소로 쓰지 않았다.

| QueryRoutingServiceFollowUpTest (기존 포함) | 17 |
| DialogueServiceTest | 19 |

위 표는 전체 집계의 일부이며 별도 합산하지 않는다. 재실행은 PostGIS/pgvector가 설치된 전용 테스트 DB에 `TELME_DB_TESTS=true POSTGRES_PORT=<전용 포트> ./gradlew build`를 사용한다. 개발·운영 DB를 테스트 대상으로 지정하지 않는다.

- 실제 라우팅·후속 분석·상담 준비·저장·Guard·SSE·조회 API를 연결한 통합 테스트에서 외부 검색과 모델만 재생했다. HTTP 메시지 전송 진입점의 기존 통합 테스트도 회귀로 실행했다.
- 정상, 정보 있음/없음, 제한 근거 보완, 정정, 거절·모름·보류, 새 질문, 매장 지역 확인, 모델 오류·타임아웃·취소를 확인했다.
- 로컬 bge-m3 + FAQ DB 검색은 실제로 실행했다. 최초 구현 검증에서는 로컬 생성 모델을 연결한 전체 대화가 미검증이었다. 이후 실제 모델 실험 및 오류 보완 결과는 별도 검증 문서에 기록한다. 배포 DB는 미검증이다.
- 실제 화면의 되묻기 표시·새로고침·후속 입력은 미검증이다. API·SSE 테스트 통과를 화면 검증 완료로 표현하지 않는다.
- 일반 의미 이해나 모든 정책 텍스트를 지원하지 않는다. 정책 답변 표현이 바뀌거나 제한이 추가되면 이 상담 정책과 근거 사례를 다시 검토해야 한다.

### 남은 화면 확인 절차

위 3턴 대화를 화면에서 실행하고, 각 되묻기가 한 번만 표시되는지 확인한다. 매 턴 새로고침했을 때 저장된 질문과 조건을 이어가는지, 최종 답변 새로고침 후 내용이 동일한지 확인한다. 모름·거절은 조건별 안내, 보류는 같은 질문 유지, 새 주제는 새 상담으로 처리되어야 한다. 오류·취소 화면에서 부분 생성문이 보이면 안 된다.

## 협업·선행 PR·게시 전 확인

- [PR #82](https://github.com/TEL-ME/TEL-ME_BE/pull/82), [#83](https://github.com/TEL-ME/TEL-ME_BE/pull/83), [#84](https://github.com/TEL-ME/TEL-ME_BE/pull/84), [#85](https://github.com/TEL-ME/TEL-ME_BE/pull/85)의 저장 후 전송·이력·실패·추적 작업을 포함한 기반이다. 별도 기능이 이미 develop에 모두 병합됐다고 표현하지 않는다.
- 최초 구현 당시 매장 V15/V16과 추적 V15가 충돌해 추적 파일을 V17로 옮겼다. 현재 PR #85 `47cbbe5`에도 V17 조정이 반영되어 준비본에서는 동일 파일을 그대로 사용한다. 기존 매장 V15/V16과 SQL 내용은 수정하지 않았다. 이미 구 V15 추적을 적용한 별도 환경은 단순 파일 교체 대상이 아니므로 Flyway 이력을 따로 확인해야 한다.
- [용재님 PR #75](https://github.com/TEL-ME/TEL-ME_BE/pull/75)는 `ConsultChatProcessingService`, `ConsultTurnAnalysisAdapter`, `QueryRoutingService` 등을 함께 수정한다. 미병합 코드를 임의로 적용하거나 덮어쓰지 않았다. 병합 시 복합 상담의 각 하위 상담에서도 검색 후 되묻기 평가가 수행되고 올바른 대기 상담을 선택하는지 함께 확인해야 한다.
- [PR #86](https://github.com/TEL-ME/TEL-ME_BE/pull/86)의 답변 시스템 프롬프트 변경은 이 브랜치에 포함하지 않았다. 기존 v3 시스템 지시는 유지하며, 현재 오류 보완에서는 두 조건의 표시 이름과 별도 상담 적용 기준 블록을 사용한다(`rag-answer-v3-plan-v2`). 두 작업을 합칠 때 최종 프롬프트와 조건 전달을 함께 검증해야 한다.
- 용재님과 확인: 새 두 조건 키의 canonical 값, 후속 발화의 정정·새 질문 분류, 로컬 모델을 통한 전체 대화. 초기 의도 분류 JSON 계약과 의도 enum은 변경하지 않는다.
- 프론트와 확인: 기존 `CLARIFICATION`/`complete` 표시와 이력 복원, 보류 턴의 새 출력 없음 처리. 새 SSE 이름이나 별도 조건 제출 API가 필요하지 않다.
- 중요 정책 결정은 이 문서에 남겼다. 프로젝트 공통 `decisions.md`에는 “검색 근거에 기반한 상담별 최소 조건 확인, 제한에 이미 해당하면 추가 질문 생략, 거절과 보류 구분, 새 질문에서 상태 분리”를 반영할 필요가 있다. 기존 로컬 미커밋 문서는 수정하지 않았다.

게시 시 PR 대상은 `develop`으로 설정해야 기존 CI가 실제 실행된다. 현재는 로컬 검증·PR 초안까지 준비하며, 사용자 코드 확인 후 커밋·푸시·PR 게시와 최신 커밋의 CI 확인을 진행한다. PR 병합은 하지 않는다.

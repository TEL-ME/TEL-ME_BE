# 회색 구간 판정 위로 넓히기 측정 — 2026-10-13 (TELME-156), 10-14 구현 전 확인 추가 (TELME-160)

TELME-122(#139) 회색 구간 판정에 이어서 잰 결과다. develop 기준.
수치는 모두 **검색 근거 단계**(정답 FAQ가 근거로 들어갔는가)이며, 최종 답변 품질은 아니다.

## 범위와 결론

**판정기(Bedrock gpt-oss-120b, B3) + 회색 구간(Q_A 0.69 / 질문 0.80) + 위로 넓히기(Q_A 0.72~0.80도 판정)**를 적용하면

- 정답 근거 **59 → 73 (54% → 66%)**
- 엉뚱한 근거 **8 → 4 (절반)**. 세트별로 지금 이하라 TELME-84 선택 규칙을 지킨다
- 위로 넓히기는 정답을 하나도 잃지 않고 엉뚱한 근거만 줄였다
- 대가: 판정 붙는 질문이 TELME-122 추천안 41% → 채택안(0.69 ~ 0.80) 60% (지금은 판정 없음), 해당 질문에 판정 시간 추가
- 구현 전 확인(4절): Q_A 상한은 0.76 / 0.78 / 0.80 / 0.82 중 **0.80**, 판정 실패 시 **아래쪽 버림 / 위쪽 통과**, 질문당 추가 시간 p50 2.0초 / p95 3.8초(로컬)

1회 실행(3회 다수결) 결과다. 같은 조건으로 판정 안정성을 재확인하고, 답할 수 있는 질문이 들어 있는 별도 세트에서 정답 증가를 확인한 뒤 채택한다.

- 0.72~0.80에 있던 정답 FAQ는 판정기가 모두 통과시켰다
- 막은 엉뚱한 근거는 FAQ에 없는 세부 사항을 묻는 질문이다. 예: "eSIM 비용 2,750원은 부가세 포함인가요?", "유심 재발급 비용은 현금영수증 되나요?", "로밍 하루 9,900원은 한국 시간 기준인가요?"

## 4. 구현 전 확인 (2026-10-14, TELME-160)

채택안을 구현하기 전에 상한, 판정 실패 처리, 지연을 확인했다. 아래 선은 Q_A 0.69 / 질문 0.80으로 고정했다.

### 4.1 Q_A 상한 (0.76 / 0.78 / 0.80 / 0.82)

| Q_A 상한 | 정답 공식 / 다중 | 엉뚱한 근거 기존 / 보강 | holdout | 판정 붙는 질문 | 위쪽 의존 정답 24건 중 잃음 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.76 | 73 / 82 | 3 / 4 (7) | 13 | 57% | 0 |
| 0.78 | 73 / 82 | 3 / 4 (7) | 12 | 59% | 0 |
| **0.80** | **73 / 82** | **2 / 2 (4)** | **11** | **60%** | **0** |
| 0.82 | 73 / 82 | 2 / 2 (4) | 11 | 61% | 0 |

- 엉뚱한 근거는 판정까지 거친 뒤에도 남은 수다. 상한을 올리면 판정하는 범위가 넓어져 더 걸러진다
- 0.78 → 0.80에서 0.78 ~ 0.80 구간의 엉뚱한 FAQ 3개가 걸러졌다(7 → 4). 0.80 → 0.82는 걸러지는 것이 없고 판정만 1%p 늘었다
- 0.80에서도 남는 4건(3.7절)은 질문 벡터 0.88 이상으로 판정 없이 통과하거나(EVAL-122), 판정기가 통과시킨 것이다. Q_A 상한을 더 올려도 줄지 않는다
- 고르는 규칙: 선택 규칙(엉뚱한 근거가 세트별로 지금 이하) 안에서 정답 최대 → **엉뚱한 근거가 적은 쪽** → 판정 붙는 질문이 적은 쪽. 정답이 같을 때 판정 수를 먼저 보면 0.76이 뽑히는데, 위로 넓히는 목적이 엉뚱한 근거를 줄이는 것이라 엉뚱한 근거를 먼저 본다
- 결과: **0.80**

### 4.2 위쪽 구간에만 기대는 정답 24건

현행(0.72 / 0.88)에서 정답을 받는 59건 중 24건(41%)은 Q_A 0.72 ~ 0.80 후보로만 정답을 받는다(질문 벡터 0.88 이상이나 Q_A 0.80 이상 결과에는 정답이 없다).

- 대상: EVAL-008, 009, 028, 032, 033, 039, 048, 050, 060, 131, 134, 137, 139, 142, 144, 146, 148, 149, 150, 152, 154, 158, 159, 160
- 3회 다수결에서는 상한 0.76 ~ 0.82 어디서도 24건 모두 통과했다
- 운영은 1회 판정이라 판정 시험의 잘못 막음 비율(1 / 17, 약 6%)로 보면 1 ~ 2건을 잃을 수 있다. 구현 후 1회 판정으로 남는 수를 센다(잃은 건 2 이하면 그대로)

### 4.3 판정 실패 시 처리

Bedrock이 전부 실패(타임아웃·오류)했을 때를 판정 결과 없이 계산했다. 아래쪽(Q_A 0.69 ~ 0.72, 질문 0.80 ~ 0.88)은 둘 다 버린다.

| 위쪽(Q_A 0.72 ~ 0.80) 처리 | 정답 공식 / 다중 | 엉뚱한 근거 기존 / 보강 | holdout |
| --- | ---: | ---: | ---: |
| **통과** | 59 / 64 | 3 / 5 | 20 |
| 버림 | 35 / 38 | 1 / 0 | 6 |

- 위쪽을 통과시키면 장애 때 지금(판정 없음)과 똑같다
- 버리면 4.2절의 24건이 한꺼번에 빠져 정답이 59 → 35로 떨어진다
- 결과: **아래쪽은 버림(원래 버리던 후보), 위쪽은 통과(원래 통과하던 후보)**

### 4.4 판정 지연

판정 붙는 질문 108개 중 30개를 골라, 운영처럼 질문마다 판정 후보를 1회씩 동시에 보냈다(`--latency-sample 30`).

| | p50 | p95 | 최대 |
| --- | ---: | ---: | ---: |
| 판정 호출 1회 (68회) | 1.9초 | 3.1초 | |
| 질문당 추가 시간 (30개 질문, 후보 평균 2.3개) | 2.0초 | 3.8초 | 6.1초 |

- 후보를 동시에 보내 질문당 추가 시간이 호출 1회와 거의 같다
- 로컬(한국 → us-east-1)에서 30개만 잰 값이다. 서버 위치와 부하에 따라 달라지므로 구현 후 다시 잰다
- 판정 타임아웃은 p95 기준 약 4 ~ 5초로 잡고, 넘으면 4.3절 실패 처리로 넘긴다

| 기존 후보 판정기(`LlmFaqCandidateEvidenceResolver`) 그대로 | 0건. 핵심 단어 검사가 사용자 말투 질문을 전부 막고, 복합 질문에서만 켜져 있음 (TELME-122와 같은 결과) |
| 로컬 EXAONE 3.5 7.8B 판정기 | 엉뚱한 근거를 못 막음 |
| 로컬 Qwen3 14B 판정기 (참고) | Bedrock과 경향은 비슷하지만 더 엄격해 정답을 3개 잃음(0.71 ~ 0.80에서 62 vs 67). 1회 측정 |

TELME-122의 예상 질문 생성, 쌍둥이 FAQ 정리도 효과가 없었다. 검색 문장이나 FAQ 데이터를 손보는 방향은 양쪽 모두 막혔다.

## 6. 한계

- 검색 근거 단계까지만 봤다. 최종 답변 정확도와 환각률은 구현 후 실제 채팅으로 다시 재야 한다
- 라우터를 뺀 측정이라 라우터에서 UNKNOWN으로 빠지는 질문만큼 실제 효과는 작을 수 있다
- 110개라 1개 ≈ 1%p. 실행마다 1~2개씩 흔들린다
- 정답 증가는 개선용 180에서만 확인했다. holdout은 엉뚱한 근거만 확인할 수 있는 세트다
- 위로 넓히기와 0.69 / 0.70은 1회 실행(3회 다수결) 결과다
- 지연은 로컬에서 30개 질문만 잰 값이다(4.4절)
- 설정을 180문항으로 골랐고 holdout 90은 모두 무관 질문이라, 정답 증가(59 → 73)는 독립 검증되지 않았다. 같은 180문항을 다시 돌리면 판정 흔들림은 확인할 수 있지만 평가셋에 맞춘 효과는 확인할 수 없다

## 9. 재현

`scripts/gray_zone_upper_band_bedrock.py`. 로컬 DB(`telme-postgres`)와 Ollama `bge-m3`가 떠 있어야 한다.

```bash
# 예상 비용만 출력 (판정 캐시에 없는 쌍만 셈, 호출 안 함)
python3 scripts/gray_zone_upper_band_bedrock.py

# 판정 실행 후 결과 표. BEDROCK_API_KEY, AWS_REGION 필요
set -a; source .env; set +a
python3 scripts/gray_zone_upper_band_bedrock.py --run

# 4.1절 상한 비교 + 4.4절 지연 (지연 결과는 캐시에 저장하지 않음)
python3 scripts/gray_zone_upper_band_bedrock.py --qa-floors 0.69 --qa-tops 0.76 0.78 0.80 0.82 --run --latency-sample 30
```

- 판정 결과는 `.measure/gray-upper-judgments-b3.json`에 쌓인다. 쌍마다 실제로 보낸 입력(모델, 시스템 프롬프트, FAQ 질문·답변, 고객 질문)의 해시를 같이 저장하고, 해시가 같은 쌍만 다시 호출하지 않는다. 평가 질문이나 FAQ 문장이 바뀐 쌍은 다시 판정한다
- 호출 오류(재시도 후 실패)가 섞인 쌍은 저장하지 않고 실행을 실패로 끝낸다. `--run`을 다시 하면 그 쌍만 다시 판정한다. 응답은 왔는데 JSON이 깨진 경우는 #139와 같이 '답 됨'으로 본다(fail-open)
- 판정 프롬프트(B3)는 #139 `evidence_check_bedrock.py`와 같은 문자열이다. 저쪽을 고치면 함께 고친다
- 이 문서 수치는 위 캐시(409쌍)로 다시 계산해 그대로 나오는 것을 확인했다. 4.3절은 판정 결과 없이 점수만으로 계산한다

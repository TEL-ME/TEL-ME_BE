# 회색 구간 판정 위로 넓히기 측정 — 2026-10-13 (TELME-156), 10-14 구현 전·후 확인 추가 (TELME-160)

TELME-122(#139) 회색 구간 판정에 이어서 잰 결과다. develop 기준.
수치는 모두 **검색 근거 단계**(정답 FAQ가 근거로 들어갔는가)이며, 최종 답변 품질은 아니다.

## 범위와 결론

**판정기(Bedrock gpt-oss-120b, B3) + 회색 구간(Q_A 0.69 / 질문 0.80) + 위로 넓히기(Q_A 0.72~0.80도 판정)**를 적용하면

- 정답 근거 **59 → 73 (54% → 66%)**
- 엉뚱한 근거 **8 → 4 (절반)**. 세트별로 지금 이하라 TELME-84 선택 규칙을 지킨다
- 위로 넓히기는 정답을 하나도 잃지 않고 엉뚱한 근거만 줄였다
- 대가: 판정 붙는 질문이 TELME-122 추천안 41% → 채택안(0.69 ~ 0.80) 60% (지금은 판정 없음), 해당 질문에 판정 시간 추가
- 구현 전 확인(4절): Q_A 상한은 0.76 / 0.78 / 0.80 / 0.82 중 **0.80**, 판정 실패 시 **아래쪽 버림 / 위쪽 통과**, 질문당 추가 시간 p50 2.0초 / p95 3.8초(로컬)
- 질문 벡터 위 선(4.5절): 0.88 / 0.90 / 0.92 중 **0.90**. 엉뚱한 근거 4 → 3, holdout 11 → 9, 정답 그대로, 판정이 새로 붙는 질문 0
- 구현 후 확인(5절): 운영 코드로 실제 채팅 API 180문항을 돌려 정답 근거 공식 **61 → 73**, 엉뚱한 근거 **10 → 5**, holdout 원문 검색 기준 **11**로 측정과 같은 효과를 확인했다. 재검색 결과가 판정을 건너뛰는 경로를 찾아 막았다

1회 실행(3회 다수결) 결과다. 같은 조건으로 판정 안정성을 재확인하고, 답할 수 있는 질문이 들어 있는 별도 세트에서 정답 증가를 확인한 뒤 채택한다.

## 4. 구현 전 확인 (2026-10-14, TELME-160)

채택안을 구현하기 전에 상한, 판정 실패 처리, 지연을 확인했다. 아래 선은 Q_A 0.69 / 질문 0.80으로 고정했다.

### 4.1 Q_A 상한 (0.76 / 0.78 / 0.80 / 0.82)

| Q_A 상한 | 정답 공식 / 다중 | 엉뚱한 근거 기존 / 보강 | holdout | 판정 붙는 질문 | 위쪽 의존 정답 24건 중 잃음 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.76 | 73 / 82 | 3 / 4 (7) | 13 | 57% | 0 |
| 0.78 | 73 / 82 | 3 / 4 (7) | 12 | 59% | 0 |
| **0.80** | **73 / 82** | **2 / 2 (4)** | **11** | **60%** | **0** |
| 0.82 | 73 / 82 | 2 / 2 (4) | 11 | 61% | 0 |

- 엉뚱한 근거는 판정까지 거친 뒤에도 남은 수다. 상한을 올리면 판정하는 범위가 넓어져 더 걸러진다
- 0.78 → 0.80에서 0.78 ~ 0.80 구간의 엉뚱한 FAQ 3개가 걸러졌다(7 → 4). 0.80 → 0.82는 걸러지는 것이 없고 판정만 1%p 늘었다
- 0.80에서도 남는 4건(3.7절)은 질문 벡터 0.88 이상으로 판정 없이 통과하거나(EVAL-122), 판정기가 통과시킨 것이다. Q_A 상한을 더 올려도 줄지 않는다
- 고르는 규칙: 선택 규칙(엉뚱한 근거가 세트별로 지금 이하) 안에서 정답 최대 → **엉뚱한 근거가 적은 쪽** → 판정 붙는 질문이 적은 쪽. 정답이 같을 때 판정 수를 먼저 보면 0.76이 뽑히는데, 위로 넓히는 목적이 엉뚱한 근거를 줄이는 것이라 엉뚱한 근거를 먼저 본다
- 결과: **0.80**

### 4.2 위쪽 구간에만 기대는 정답 24건

현행(0.72 / 0.88)에서 정답을 받는 59건 중 24건(41%)은 Q_A 0.72 ~ 0.80 후보로만 정답을 받는다(질문 벡터 0.88 이상이나 Q_A 0.80 이상 결과에는 정답이 없다).

- 대상: EVAL-008, 009, 028, 032, 033, 039, 048, 050, 060, 131, 134, 137, 139, 142, 144, 146, 148, 149, 150, 152, 154, 158, 159, 160
- 3회 다수결에서는 상한 0.76 ~ 0.82 어디서도 24건 모두 통과했다
- 운영은 1회 판정이라 판정 시험의 잘못 막음 비율(1 / 17, 약 6%)로 보면 1 ~ 2건을 잃을 수 있다. 구현 후 1회 판정으로 남는 수를 센다(잃은 건 2 이하면 그대로)

### 4.3 판정 실패 시 처리

Bedrock이 전부 실패(타임아웃·오류)했을 때를 판정 결과 없이 계산했다. 아래쪽(Q_A 0.69 ~ 0.72, 질문 0.80 ~ 0.88)은 둘 다 버린다.

| 위쪽(Q_A 0.72 ~ 0.80) 처리 | 정답 공식 / 다중 | 엉뚱한 근거 기존 / 보강 | holdout |
| --- | ---: | ---: | ---: |
| **통과** | 59 / 64 | 3 / 5 | 20 |
| 버림 | 35 / 38 | 1 / 0 | 6 |

- 위쪽을 통과시키면 장애 때 지금(판정 없음)과 똑같다
- 버리면 4.2절의 24건이 한꺼번에 빠져 정답이 59 → 35로 떨어진다
- 결과: **아래쪽은 버림(원래 버리던 후보), 위쪽은 통과(원래 통과하던 후보)**

### 4.4 판정 지연

판정 붙는 질문 108개 중 30개를 골라, 운영처럼 질문마다 판정 후보를 1회씩 동시에 보냈다(`--latency-sample 30`).

| | p50 | p95 | 최대 |
| --- | ---: | ---: | ---: |
| 판정 호출 1회 (68회) | 1.9초 | 3.1초 | |

- 후보를 동시에 보내 질문당 추가 시간이 호출 1회와 거의 같다
- 로컬(한국 → us-east-1)에서 30개만 잰 값이다. 서버 위치와 부하에 따라 달라지므로 구현 후 다시 잰다
- 판정 타임아웃은 처음에 p95 기준 5초로 잡았고, 구현 후 느린 호출을 끝까지 재 보고 8초로 바꿨다(5.5절)

### 4.5 질문 벡터 위 선 (0.88 / 0.90 / 0.92)

Q_A는 0.69 ~ 0.80 판정으로 두고, 질문 벡터의 통과 선만 기존 임계값 0.88에서 올려 0.88 이상 일부도 판정하게 했다(질문 벡터 위로 넓히기). 새로 판정한 쌍은 3개(9호출)이고 나머지는 같은 FAQ의 기존 판정을 썼다.

| 질문 벡터 위 선 | 정답 공식 / 다중 | 엉뚱한 근거 기존 / 보강 | holdout | 판정 붙는 질문 |
| --- | ---: | ---: | ---: | ---: |
| 0.88 (위로 넓히지 않음) | 73 / 82 | 2 / 2 (4) | 11 | 60% |
| **0.90** | **73 / 82** | **1 / 2 (3)** | **9** | **60%** |
| 0.92 | 73 / 82 | 1 / 2 (3) | 9 | 60% |

- 질문 벡터는 FAQ 질문 문장끼리 비교해 점수가 높게 나온다. 문장 모양이 같고 묻는 내용이 다른 경우가 0.88 ~ 0.90에 있었다
  - EVAL-122 "유심 재발급 비용은 카드로 결제할 수 있나요?" ↔ "유심 재발급 비용이 얼마예요?" 0.885 → 안 됨, 빠짐
  - H-116 위약금 납부 기한 0.890, H-126 로밍 해지 적용 시점 0.897 → 안 됨, 빠짐. H-087은 하나만 빠짐
  - EVAL-017(답변 가능)은 0.895의 명의변경 FAQ가 빠지고 번호이동 FAQ로 바뀌었다. 정답은 그대로다
- 0.90 → 0.92는 걸러지는 것이 없다. 4.1절과 같은 규칙(정답 최대 → 엉뚱한 근거 적은 쪽 → 판정 적은 쪽)으로 **0.90**
- 판정이 새로 붙는 질문은 개선용 180, holdout 90 모두 0개다. 0.88 ~ 0.90 후보가 있는 질문은 이미 다른 후보를 판정하고 있었고, 한 질문의 판정은 동시에 보내 지연이 늘지 않는다. 판정 쌍은 개선용에서 275 → 278
- 0.88 ~ 0.90은 판정 전에도 바로 통과하던 구간이라, 판정이 실패하면 통과한다(4.3절 위쪽 규칙)

## 5. 구현 후 확인 (2026-10-14, TELME-160)

운영 코드(Java)로 구현한 뒤, 실제 채팅 API로 같은 평가셋을 돌려 측정 결과가 재현되는지 확인했다.

### 5.1 구현 요약

| 항목 | 내용 |
| --- | --- |
| 설정 | `search.gray-zone`(기본 꺼짐, Q_A 통과 0.80 / 아래 0.69, 질문 통과 0.90 / 아래 0.80), `llm.bedrock`(기본 꺼짐, us-east-1, `openai.gpt-oss-120b-1:0`, 호출 제한 8초, 동시 연결 50, 연결 대기 1초). 회색 구간을 켰는데 `llm.bedrock`이 꺼져 있으면 앱이 뜨지 않는다 |
| 검색 | 벡터별 상위 3개를 점수로 나눈다(통과 / 판정 필요 / 버림). 기존 `search()`와 후보 검색(`searchCandidates`)은 바꾸지 않았다 |
| 판정 | 판정 필요 후보를 FAQ 하나씩 B3(`evidence-check-v3`)로 1회 판정한다. 한 질문의 후보는 동시에 보내고, 두 벡터에 같은 FAQ가 나오면 한 번만 판정한다. 판정 질문은 검색 문장이 아니라 고객 질문(문맥 복원 질문 포함)이다 |
| 합치기 | 남은 후보를 질문 벡터 우선, 중복 제거, 상위 3개로 합친다. 측정 기준 함수 `served()`와 같은 순서다 |
| 재검색 | 재검색(#131) 결과는 점수와 관계없이 모두 판정한다(5.6절). 같은 실행에서 이미 받은 판정은 다시 쓴다 |
| 실패 | 시간 초과·호출 오류·응답 해석 실패는 판정을 붙이기 전 임계값(Q_A 0.72 / 질문 0.88) 이상이면 통과, 미만이면 버린다. 장애 때 판정이 없던 때와 같다 |
| slot 없는 후보 | 판정 구간이면 판정하지 않고 거부한다 |
| 기록 | 판정 호출은 `llm_generations`에 `EVIDENCE_CHECK`로, 후보별 판정(점수, 위쪽 구간 여부, 결과, 남김 여부, 재사용, 지연)은 실행 기록 `grayZoneJudgments`에 남긴다. 모델이 쓴 문장은 남기지 않는다 |
| 인증 | AWS SDK가 환경에서 찾는다. `AWS_BEARER_TOKEN_BEDROCK`(Bedrock API 키) 또는 AWS 기본 자격 증명(EC2 역할 포함) |

### 5.2 실제 채팅 API, 개선용 180 (끔 vs 켬)

`scripts/single-faq-search-evaluation/run_chat_eval.py`로 문항마다 새 채팅을 보내고 앱이 남긴 검색 기록을 셌다. 개발 DB 복사본, 답변 생성 EXAONE 3.5 7.8B(Ollama), 판정 Bedrock 1회, 라우터 포함. 측정 때 코드는 재검색 수정(5.6절) 전이다.

| 항목 | 끔 | 켬 | 측정(검색 단계) |
| --- | ---: | ---: | ---: |
| 정답 근거 공식 / 다중 (/110) | 61 / 65 | **73 / 80** | 59 → 73 / 64 → 82 |
| 근거 있는 답변 GROUNDED (/110) | 38 | **48** | - |
| 엉뚱한 근거 (/70) | 10 | **5** | 8 → 4 |
| 엉뚱한 근거로 나간 답변 GROUNDED (/70) | 5 | 4 | - |
| 처리 시간 중앙값 / p95 | 3.7초 / 7.0초 | 5.4초 / 10.7초 | - |

- 끔 쪽은 #131 측정(정답 근거 66, GROUNDED 34, 엉뚱한 근거 12, 엉뚱한 답변 5)과 거의 같다
- 엉뚱한 근거는 후보 검색(답을 못 할 때 FAQ 후보 찾기)이 세어진 2건(EVAL-099, 109, 끔·켬 모두)을 뺐다
- 켬에서 정답 근거를 잃은 문항은 0건, 새로 찾은 문항은 15건이다
- 4.2절의 위쪽 구간에만 기대는 정답 24건은 24건 모두 유지됐다(기준: 잃은 건 2 이하)
- 엉뚱한 답변은 5 → 4지만 질문이 바뀌었다. 원래 새던 EVAL-123, 163, 164, 167은 막혔고, 3.7절의 EVAL-125, 173, 175가 새로 나갔다(0.69 ~ 0.72에서 들어온 후보를 판정기가 통과시킴)
- 근거가 늘면서 GROUNDED였던 4문항(EVAL-002, 010, 137, 146)은 조건을 먼저 묻는 되묻기로 바뀌었다. 2문항(EVAL-140, 157)은 정답이 아닌 FAQ로 답하던 근거가 판정에서 빠져 근거 없음이 됐다
- 라우터가 UNKNOWN으로 보낸 답변 가능 문항 4개(EVAL-049, 056, 070, 147)는 끔·켬 모두 검색 전에 끝났다

### 5.4 판정 시험 25건 (운영 방식)

근거는 판정 시험과 같이 현행 임계값을 통과한 상위 3개이고, FAQ 하나씩 1회 판정해 하나라도 답 됨이면 답할 수 있음으로 봤다.

| | 잘못 막음 | 막음 | 합격 |
| --- | ---: | ---: | --- |
| TELME-122 (근거 묶음, 3회 다수결) | 1 | 7 | 합격 |
| 운영 방식 (FAQ 하나씩, 1회) | **0** | **5** | 합격 |

- 막지 못한 2건(HALLU-018, 020)은 근거 3개 중 하나를 답 됨으로 봤다. FAQ를 하나씩 보면 하나라도 통과할 때 답이 나간다
- EVAL-122는 판정기가 근거 3개를 모두 막았다. 5.2절 측정 때는 질문 벡터 0.885라 판정 구간 밖이어서 그대로 통과했고, 질문 통과 선을 0.90으로 올려 판정 구간에 넣었다(4.5절)

### 5.5 지연과 판정 실패

| 항목 | 결과 |
| --- | --- |
| 판정 호출 1회 | p50 1.5초 / p95 3.8초 (180셋 켬, 289회) |
| 검색 1번당 판정 시간 | p50 1.8초 / p95 4.8초 / 최대 5.0초 |
| 판정 재사용 | 19회 (재검색 때 같은 FAQ) |
| 시간 초과 (호출 제한 5초 때) | 180셋·holdout에서 12회(약 3%) |

- 시간 초과로 정답 근거 1건(EVAL-072, 아래쪽 0.71)을 놓쳤고, 엉뚱한 근거 1건(H-116, 위쪽 0.767)이 규칙대로 통과했다
- 앱은 5초에서 끊어 그 뒤를 볼 수 없어, 측정 스크립트로 끊지 않고 끝까지 기다린 호출 119회(판정 시험 65회, 상한·질문 벡터 비교 54회)를 봤다

| 걸린 시간 | 횟수 |
| --- | ---: |
| 5초 초과 | 7회 (5.9%) |
| 6초 초과 | 3회 (2.5%) |
| 8초 초과 | 1회 (0.8%) |
| 10초 초과 | 0회 |
| 가장 오래 걸린 호출 | 8.6초 |

- 5초를 넘긴 호출도 모두 9초 안에 끝났다. 멈춘 호출이 아니라 조금 느린 호출이라, 호출 제한을 **8초**로 늘렸다
- 판정이 실패하면 아래쪽 정답을 놓치거나 위쪽 엉뚱한 근거가 통과해 판정의 목적이 줄어든다. 대신 느린 판정이 붙은 질문(판정 붙는 질문의 수 %)은 최대 3초 더 기다린다. 판정 1회 중앙값(약 1.5초)은 그대로다
- 119회는 표본이 작고 스크립트는 동시에 여러 개를 보내 조건이 다르다. 켠 뒤 `llm_generations`의 실패 비율과 걸린 시간을 보고 다시 맞춘다
- 판정 붙는 질문의 처리 시간이 약 2초 늘었다. 원문 검색 뒤 재검색까지 가면 판정도 두 번 붙는다

### 5.6 재검색이 판정을 건너뛰는 경로

재검색은 원문 검색 결과가 0건일 때 라우터가 다듬은 문장으로 다시 찾는다. 다듬은 문장은 FAQ 말투라 점수가 높게 나와, 원문 검색에서 판정기가 막은 FAQ가 통과 선을 넘어 판정 없이 들어왔다.

| | 원문 검색 | 재검색 (수정 전) |
| --- | --- | --- |
| EVAL-177 로밍 하루 9,900원은 한국 시간 기준인가요? | ROAMING-0036 Q_A 0.796 판정 → 안 됨 | 같은 FAQ가 0.853 → 바로 통과 → 근거로 답변 |
| H-127 로밍 신청 상태를 문자로도 알려주나요? | ROAMING-0005 Q_A 0.837 판정 → 안 됨 | 같은 FAQ가 질문 0.895 → 바로 통과 |

- 수정: 재검색 결과는 점수와 관계없이 모두 판정한다. 원문에서 받은 판정은 다시 쓴다
- 확인(실제 채팅, 수정 후): EVAL-177, H-127은 근거 없음으로 끝났다. 재검색으로 정답을 찾던 EVAL-041은 그대로 정답 근거로 답했다. EVAL-154는 이번에 원문 검색에서 DEVICE-0076(0.737)이 답 됨으로 판정돼 재검색까지 가지 않았다. 1회 판정의 흔들림이다
- 영향 범위: 180셋·holdout에서 재검색으로 근거가 나온 문항은 6개였고, 그중 이 경로는 2개다

## 7. 한계

- 검색 근거 단계까지만 봤다. 최종 답변 정확도와 환각률은 구현 후 실제 채팅으로 다시 재야 한다
- 라우터를 뺀 측정이라 라우터에서 UNKNOWN으로 빠지는 질문만큼 실제 효과는 작을 수 있다
- 110개라 1개 ≈ 1%p. 실행마다 1~2개씩 흔들린다
- 정답 증가는 개선용 180에서만 확인했다. holdout은 엉뚱한 근거만 확인할 수 있는 세트다
- 위로 넓히기와 0.69 / 0.70은 1회 실행(3회 다수결) 결과다
- 지연은 로컬에서 30개 질문만 잰 값이다(4.4절). 5.5절은 개발 PC의 앱에서 잰 값이라 서버 위치와 부하에 따라 달라진다
- 운영은 1회 판정이라 같은 후보도 실행마다 결과가 바뀔 수 있다(5.6절 EVAL-154). 180셋 수치가 1~2건 흔들리는 이유다
- 5.2절 180셋은 재검색 수정 전 코드로 쟀다. 수정은 재검색으로 근거가 나온 문항에만 영향이 있다
- 설정을 180문항으로 골랐고 holdout 90은 모두 무관 질문이라, 정답 증가(59 → 73)는 독립 검증되지 않았다. 같은 180문항을 다시 돌리면 판정 흔들림은 확인할 수 있지만 평가셋에 맞춘 효과는 확인할 수 없다

### 8.1 플래그를 켜기 전에 할 것

- 환각률: develop 기준선과 켠 뒤 비교
- 판정 호출 제한: **8초**(5.5절). 켠 뒤 `llm_generations`의 실패 비율과 걸린 시간을 보고 다시 맞춘다
- 동시 연결 수(`llm.bedrock.max-connections`, 기본 50): 앱 전체에서 동시에 진행되는 Bedrock 호출 수 상한이다. 연결을 1초 안에 못 얻으면 판정 실패로 처리한다
- 분당 호출 수 한도: 연결 수는 분당 한도가 아니다. 끝난 연결은 바로 다시 쓰여, 응답이 빠르거나 오류가 바로 돌아오면 분당 호출이 늘어난다(평균 1.5초면 분당 약 연결 수 × 40회). 계정의 Bedrock 분당 한도를 확인하고, 반드시 지켜야 하면 부하 측정 뒤 분당 호출 제한(rate limiter)을 따로 둘지 정한다

## 10. 재현

`scripts/gray_zone_upper_band_bedrock.py`. 로컬 DB(`telme-postgres`)와 Ollama `bge-m3`가 떠 있어야 한다.

```bash

python3 scripts/gray_zone_upper_band_bedrock.py --qa-floors 0.69 --qa-tops 0.80 --qo-tops 0.88 0.90 0.92 --run
```

- 판정 결과는 `.measure/gray-upper-judgments-b3.json`에 쌓인다. 쌍마다 실제로 보낸 입력(모델, 시스템 프롬프트, FAQ 질문·답변, 고객 질문)의 해시를 같이 저장하고, 해시가 같은 쌍만 다시 호출하지 않는다. 평가 질문이나 FAQ 문장이 바뀐 쌍은 다시 판정한다
- 호출 오류(재시도 후 실패)가 섞인 쌍은 저장하지 않고 실행을 실패로 끝낸다. `--run`을 다시 하면 그 쌍만 다시 판정한다. 응답은 왔는데 JSON이 깨진 경우는 #139와 같이 '답 됨'으로 본다(fail-open)

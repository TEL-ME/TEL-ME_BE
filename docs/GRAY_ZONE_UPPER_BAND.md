# 회색 구간 판정 위로 넓히기 측정 — 2026-10-13 (TELME-156)

TELME-122(#139) 회색 구간 판정에 이어서 잰 결과다. develop 기준.
수치는 모두 **검색 근거 단계**(정답 FAQ가 근거로 들어갔는가)이며, 최종 답변 품질은 아니다.

## 범위와 결론

**판정기(Bedrock gpt-oss-120b, B3) + 회색 구간(Q_A 0.69 / 질문 0.80) + 위로 넓히기(Q_A 0.72~0.80도 판정)**를 적용하면

- 정답 근거 **59 → 73 (54% → 66%)**
- 엉뚱한 근거 **8 → 4 (절반)**. 세트별로 지금 이하라 TELME-84 선택 규칙을 지킨다
- 위로 넓히기는 정답을 하나도 잃지 않고 엉뚱한 근거만 줄였다
- 대가: 판정 붙는 질문 41% → 60% (0.69 기준), 해당 질문에 판정 시간 추가

1회 실행(3회 다수결) 결과라 #139 쪽에서 같은 조건으로 한 번 더 확인하고 채택하는 것을 권장한다.

## 1. 평가 기준

| 항목 | 내용 |
| --- | --- |
| 평가 세트 | 180문항 = 답할 수 있는 질문 110 + 답이 없는 질문 70 (`eval_questions_180_multigold.json`) |
| 정답 | 110개 중 검색 상위 3개에 정답 FAQ가 들어온 수 (공식 라벨 `eval_questions_130.json` + `eval_questions_supplement_50.json` / 다중 정답 라벨) |
| 엉뚱한 근거 | 70개(기존 EVAL-081~130 50개 / 보강 EVAL-161~180 20개) 중 FAQ가 붙은 수. FAQ에 답이 없는데 근거가 붙어 틀린 답이 나갈 위험 |
| holdout | 경계 무관 질문 90개(`eval_questions_holdout_90.json`) 중 FAQ가 붙은 수. 선택에 쓰지 않고 확인만 한다 |
| 판정기 | Bedrock `openai.gpt-oss-120b-1:0`, 프롬프트 B3, `reasoning_effort=low`, temperature 0, 3회 다수결 (TELME-122와 같은 조건) |
| 선택 규칙 (TELME-84) | 엉뚱한 근거가 세트별로 지금 이하(기존 3 / 보강 5) → 그 안에서 정답 최대 |

- 검색은 앱과 같은 쿼리(`FaqEmbeddingRepository`의 필터, 벡터별 상위 3개, 질문 벡터 먼저 합쳐 3개 컷)로 로컬 DB에서 읽었다
- 재현 확인: 판정 없는 현행 59 / 64, 엉뚱한 근거 3 / 5, holdout 20이 TELME-122 결과와 같다

## 2. 구간

| 용어 | 뜻 |
| --- | --- |
| 회색 구간 | 지금 임계값 바로 아래. 판정기가 "이 FAQ로 답이 되나"를 확인해야 근거로 쓴다 |
| 추천안 | Q_A 0.71 / 질문 0.80 + 판정기 (TELME-122 추천) |
| 완화안 | Q_A 0.69 / 질문 0.80 + 판정기 |
| **위로 넓히기** | 지금은 판정 없이 바로 통과하는 **Q_A 0.72~0.80**도 판정기가 확인하게 하는 것 |


질문 벡터는 위로 넓히지 않았다(0.88 이상은 그대로 바로 통과).

## 3. 결과

### 3.1 안별 비교 (같은 실행 안에서 비교)

| 안 | 정답 공식 / 다중 (110) | 엉뚱한 근거 기존 / 보강 (70) | holdout (90) | 180 중 제대로 처리 |
| --- | ---: | ---: | ---: | ---: |
| 지금 (0.72 / 0.88, 판정 없음) | 59 / 64 | 3 / 5 (8) | 20 | 121 (67%) |
| 추천안 (Q_A 0.71) | 67 / 72 | 3 / 7 (10) | 20 | 127 (71%) |
| 추천안 + 위로 넓히기 | 67 / 72 | 1 / 2 (3) | 10 | 134 (74%) |
| 0.70 + 위로 넓히기 | 69 / 74 | 2 / 2 (4) | 10 | 135 (75%) |
| **완화안 + 위로 넓히기** | **73 / 82** | **2 / 2 (4)** | **11** | **139 (77%)** |

- 제대로 처리 = 답할 수 있는 질문은 정답(공식)을 찾고, 답이 없는 질문은 아무것도 안 붙은 수
- 추천안 줄은 TELME-122 결과(66 / 70, 8)와 1~2건 다르다. 같은 모델·프롬프트라도 실행마다 판정이 흔들린다(394쌍 중 14쌍이 3회 안에서 갈림)

### 3.3 위로 넓히기의 효과

| | 정답 | 엉뚱한 근거 (70) | holdout (90) | 판정 붙는 질문 |
| --- | ---: | ---: | ---: | ---: |
| 추천안 | 67 | 10 | 20 | 41% |
| 추천안 + 위로 넓히기 | **67 (그대로)** | **3** | **10** | 52% |

- 0.72~0.80에 있던 정답 FAQ는 판정기가 모두 통과시켰다
- 막은 엉뚱한 근거는 FAQ에 없는 세부 사항을 묻는 질문이다. 예: "eSIM 비용 2,750원은 부가세 포함인가요?", "유심 재발급 비용은 현금영수증 되나요?", "로밍 하루 9,900원은 한국 시간 기준인가요?"
- 위로 넓히기는 정답을 새로 찾지 않는다. 이미 통과하던 것 중 엉뚱한 것만 빼는 장치라 정답 수는 같거나 줄어든다

### 3.4 0.71 / 0.70 / 0.69 선택

| Q_A 아래 선 (위로 넓히기 포함) | 정답 | 엉뚱한 근거 | holdout |
| --- | ---: | ---: | ---: |
| 0.71 | 67 | 3 | 10 |
| 0.70 | 69 | 4 | 10 |
| 0.69 | 73 | 4 | 11 |

- 0.69는 0.71보다 경계 질문이 1개 더 샌다. TELME-122에서는 EVAL-173, 이번 실행에서는 EVAL-125였다. 어떤 질문이 새는지는 실행마다 바뀌지만 "+1"은 같다
- TELME-122에서 0.71이 추천안이었던 이유가 이 +1이다. **위로 넓히기를 더하면 전체가 8 → 4로 줄어 0.69도 선택 규칙을 지킨다** → 같은 규칙으로 고르면 0.69 + 위로 넓히기가 된다
- 0.70은 엉뚱한 근거가 0.69와 같은데 정답이 4개 적어 고를 이유가 없다

### 3.5 질문 벡터와 Q_A가 살린 질문은 다르다

| 바꾼 것 | 살아난 질문 (공식) |
| --- | ---: |
| 질문 벡터 0.88 → 0.80 | +6 |
| Q_A 0.72 → 0.71 | +2 |
| Q_A 0.72 → 0.69 | +8 |
| 둘 다 (질문 0.80 + Q_A 0.69) | +14 = 6 + 8, 겹침 0 |

- 질문 벡터 0.80이 살린 6개: EVAL-005, 018, 023, 031, 035, 046 (대부분 SIMILAR)
- Q_A 0.69가 살린 8개: EVAL-038, 043, 062, 063, 072, 078, 132, 136 (대부분 VARIANT, ANSWER)
- 정답은 더해도 되지만, 엉뚱한 근거는 양쪽에서 같은 질문이 겹쳐 단순 합이 아니다

### 3.6 유형별 (공식 라벨)

| 유형 | 지금 | 완화안 + 위로 넓히기 |
| --- | ---: | ---: |
| SIMILAR (40) | 33 (82%) | 39 (98%) |
| ANSWER (30) | 22 (73%) | 24 (80%) |
| VARIANT (40) | 4 (10%) | 10 (25%) |

- 실패는 대부분 VARIANT(말을 많이 바꾼 질문)에 몰려 있다. 일부는 "지난달에 한 번 바꿨는데 이달에 또 바꿔도 되나요"처럼 대상이 빠진 질문이라 검색보다 되묻기가 맞을 수 있다
- 평가 세트가 유형을 고르게(40 / 30 / 40) 넣어 일부러 어렵게 만든 것이라, 전체 정답률을 실제 사용자 체감으로 읽으면 과장된다

## 4. 해 봤지만 효과 없던 것

| 시도 | 결과 |
| --- | --- |
| 고객 질문을 FAQ 문체로 다듬어 재검색 | 정답 +1~2, 엉뚱한 근거 +1. 원문이 0건인 105개를 전부 다듬어도 결과가 나온 건 5개. 문장을 바꿔도 점수가 임계값까지 안 오른다 |
| 판정 프롬프트 구조화 (대상·조건·알고 싶은 정보를 칸으로 나누고 코드가 계산) | B3보다 엉뚱한 근거가 더 샘. 칸을 나눠도 FAQ의 조건을 고객 조건으로 섞어 적는 등 칸이 제대로 채워지지 않음 |
| 기존 후보 판정기(`LlmFaqCandidateEvidenceResolver`) 그대로 | 0건. 핵심 단어 검사가 사용자 말투 질문을 전부 막고, 복합 질문에서만 켜져 있음 (TELME-122와 같은 결과) |
| 로컬 EXAONE 3.5 7.8B 판정기 | 엉뚱한 근거를 못 막음 |
| 로컬 Qwen3 14B 판정기 (참고) | Bedrock과 경향은 비슷하지만 더 엄격해 정답을 3개 잃음(0.71 ~ 0.80에서 62 vs 67). 1회 측정 |

TELME-122의 예상 질문 생성, 쌍둥이 FAQ 정리도 효과가 없었다. 검색 문장이나 FAQ 데이터를 손보는 방향은 양쪽 모두 막혔다.

## 5. 한계

- 검색 근거 단계까지만 봤다. 최종 답변 정확도와 환각률은 구현 후 실제 채팅으로 다시 재야 한다
- 라우터를 뺀 측정이라 라우터에서 UNKNOWN으로 빠지는 질문만큼 실제 효과는 작을 수 있다
- 110개라 1개 ≈ 1%p. 실행마다 1~2개씩 흔들린다
- 정답 증가는 개선용 180에서만 확인했다. holdout은 엉뚱한 근거만 확인할 수 있는 세트다
- 위로 넓히기와 0.69 / 0.70은 1회 실행(3회 다수결) 결과다

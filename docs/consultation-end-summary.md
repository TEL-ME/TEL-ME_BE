# 사용자용 상담 종료 요약

구현 기준: 2026-10-16, `feat/TELME-170-consultation-summary`의 `f4d9aec9` 이후 로컬 되묻기 해결 판정 보완을 포함한다.
브랜치 분기 기준은 `ef23b28a`다. 해당 작업 브랜치의 명세이며 최신 `develop` 통합·병합·배포 완료를 뜻하지 않는다.

## 기능과 처리 흐름

- 기존 상담 종료 API에서 최초 종료 전환과 요약 요청을 함께 저장한다. 요약은 종료 응답 뒤 비동기로 생성한다.
- 진행 중인 답변이 끝난 뒤 입력 범위를 확정한다. 사용자용 결과는 내부 문맥 기억인 `chat_sessions.summary`와 분리한다.
- **AI가 안내 번호를 선택하고, 서버가 실제 답변 원문을 같은 문의끼리 묶는다.** 안내를 자유롭게 재작성하는 추가 모델 호출은 없다.
- 서버가 실제 질문에 맞는 제목을 만들고, 저장된 상담 상태로 남은 사항을 구분한다. 안내를 받았다는 사실과 실제 신청·변경 완료는 구분한다.

종료 요청 → 요청 저장 → 답변 처리 종료 확인 → 입력·원문 후보 준비 → AI 선택·검증 → 문의별 원문 구성·남은 상태 판별 → 저장 → 조회

## 입력과 생성

- 같은 세션의 메시지 순서·질문과 답변 연결·하위 상담의 원래 문의와 상태를 사용한다. `ERROR`, `BLOCKED`, 미완성 답변 원문은 안내 후보에서 제외한다.
- 순수 인사와 고정 응답만 있는 상담은 빈 상담으로 처리한다. 조건 응답·혼합 문의를 단어만 보고 제외하지 않는다.
- 지원 민감번호는 모델 전달 전 문장 필드에서 마스킹한다. 최종 제목·본문·남은 사항에도 입력 검사와 출력 보호를 적용한다.
- 기존 모델 클라이언트와 `SUMMARY` 작업 유형을 사용한다. 저장되는 프롬프트 버전은 `consultation-end-summary-v13`이다.
- 요약은 기본 `LlmClient`를 사용한다. 현재 Ollama 설정에서는 엑사원을 호출하며, 판정기 전용 Bedrock 설정을 켜도 요약 모델은 바뀌지 않는다. 모델 교체 시에는 요약 전용 연결과 번호·JSON 스키마 계약을 따로 검증해야 한다.
- 채팅 목록 제목은 `ChatSessionTitleService`가 첫 질문을 보고 별도로 생성한다. 되묻기나 종료 요약 제목과 다른 기능이며 현재는 같은 기본 모델 연결을 사용한다. 종료 요약만의 모델을 선택하는 설정은 아직 없다.
- 이후 종료 요약 모델을 별도로 교체할 때도 원문 출처·문의 연결·남은 사항 판정·개인정보 보호와 고객용 응답 필드는 유지한다. 모델 연결을 분리한 뒤 기존 상담과 긴 상담의 완료율·사실 보존·출력 형식·지연을 다시 검증한다.
- 모델 출력은 문의 번호를 키로 한 `topics`, 안내 번호 배열 `selectedSentenceIds`, 빈 배열 `pendingItems`다. 모델이 남은 상태 문구를 만들지 않도록 `pendingItems`의 스키마 상한은 0개다.
- 안내 후보에 상담 전체에서 고정한 번호를 부여한다. 서버가 선택된 번호의 원문과 출처를 조립하며, 잘못된 번호는 작업 기한 안에서 한 번 재요청한다. 계속 잘못되면 실패로 저장하고 첫 안내로 대체하지 않는다.
- 답변 검사에서 잘못된 안내 창구가 섞인 방문 절차는 대상·업무·명시한 방문자 조건이 맞는 단일 근거로만 복원한다. 양쪽 모두 대상이 없는 공통 방문 문구는 서로 충돌하는 업무가 없을 때만 복원하며, 준비물·부정 조건을 원문 그대로 남긴다.
- 안내는 조건과 예외를 함께 보존하도록 문단 단위로 준비한다. 제목만 있는 항목·되묻기 질문·근거 없음·범위 밖 대체 문구는 안내에서 제외한다.
- 조건 응답과 각 문의의 마지막 근거 있는 답변 원문은 모델이 일부 번호만 골라도 보존한다. 원래 문의·역할·출처·JSON 타입·길이를 검사한다.
- 전체 원문의 검사·문단 분리·후보 번호 계산은 생성 작업 안에서 한 번 수행한다. 분할·병합에서는 해당 구간의 출처만 사용하며 다른 상담이나 생성 요청과 공유하지 않는다.
- `ChatEndSummaryGroundedGenerator`가 발췌 결과를 문의별로 구성한다. 내부 버전 `consultation-end-inquiry-grounded-v1`은 별도 처리 단계의 번호이며 저장 프롬프트 v13과 같은 버전 계열이 아니다.

## 문의별 구성과 남은 사항

- 저장된 요청 의도와 답변에 연결된 FAQ 카테고리 10종을 문의 키·제목에 우선 사용한다. 근거와 현재 FAQ의 버전이 다르면 현재 분류를 과거 상담에 적용하지 않는다.
- 분류 정보가 없는 과거 기록도 동일한 단일 요청의 여러 안내는 묶는다. 서로 다른 원래 질문·사람·회선은 분류가 같다는 이유로 합치지 않으며, 복수 요청이나 카테고리가 모호하면 분리한다.
- 같은 문의의 이어묻기는 대상·회선·상품과 질문 연결을 확인해 한 묶음으로 만든다. 다른 사람·회선·문의는 구분하며, 모호한 연결은 억지로 합치지 않는다.
- 같은 문장의 중복 제거는 같은 문의 안에서만 한다. 다른 대상에게 같은 비용을 안내했다면 각 대상 문단에 보존한다. 문맥에 필요한 지시어·조건 문장은 유지한다.
- 제목은 실제 문의에서 만들고, 안내 앞의 중간 처리 표식은 최종 본문에서 제거한다. 일부 방문 요청 표현은 기록형으로 바꾸지만 안내 전체를 AI로 다시 쓰지는 않는다.
- 가입 기간은 비용·무료 조건의 이유로 임의 연결하지 않는다. 가족·회선의 주체나 정정 관계가 명확하지 않으면 해당 기간 발화를 인용한다.
- 이전 안내를 대체하는 처리는 요금제·요금/청구 분류에서 명시적인 이전 안내 철회가 확인되는 경로에 적용한다. 모든 주제의 정정을 자동 해결한다고 보장하지 않는다.
- 최종 원문 복원은 대화와 원문 문단 순서를 따른다. 모델의 선택 순서 때문에 최신 정정이 과거 안내보다 먼저 처리되지 않도록 한다. 따로 나뉜 조건 응답은 저장된 조건 연결이 있을 때만 원래 문의로 복원한다.
- 남은 사항은 `ChatEndSummaryPendingResolver`가 미확인 조건·답변 근거·실행 상태에서 만든다. 지역 미확인과 본인·대리인 미확인은 별도로 보존한다. 필수 확인 항목을 화면에서 8개로 자르지 않는다.
- `ChatEndSummaryResolution`이 같은 하위 요청의 되묻기·사용자 응답·최종 답변을 저장된 조건 연결로 확인한다. 입력 준비와 최종 남은 사항 구성에서 동일한 판정을 사용한다.
- 요청이 `DONE`이고 미확인·거절 조건이 없으며 연결된 사용자 응답에 최종 `GROUNDED` 답변이 있으면 해결된 되묻기를 제외한다. 원래 질문에 직접 달린 답변뿐 아니라 조건 응답 뒤의 답변도 사용한다. 답변 뒤에 추가 되묻기나 근거 없음 안내가 있으면 완료 표시만으로 제외하지 않는다.
- 같은 조건의 재질문은 현재 저장된 질문·응답 연결을 사용한다. 하위 문의 번호가 없는 과거 복합 기록이나 연결이 누락·모호한 기록은 다른 문의의 답변으로 해결 처리하지 않는다. 유실된 과거 연결 전체를 복원하는 기능은 아니다.
- 복합 문의는 미해결 하위 요청과 조건을 유지한다. 조건 응답에 새 문의가 함께 있으면 그 요청도 별도로 판단한다. 단답형 응답을 단어만 보고 숨기지 않는다.
- 같은 사용자 응답을 여러 하위 요청이 공유하면 통합 `GROUNDED` 상태만으로 모두 해결됐다고 판단하지 않는다. 개별 답변 연결이 불명확하면 답변 상태 확인 대상으로 남길 수 있다.
- 연결된 조건 응답 뒤 검색 실패·범위 밖 안내가 나오면 원래 문의의 미답변·범위 밖 사유로 남긴다. 원래 문의가 확인된 단답형 응답을 별도 미해결 문의로 중복 표시하지 않는다.
- 답변 실패·취소와 미확인 조건이 함께 있으면 중단 사유와 조건을 함께 남길 수 있다. 다른 문의·사람·회선·세션의 답변으로 미해결 항목을 제거하지 않는다.
- `DONE`, `COMPLETED`, 상담 종료는 신청 접수·업무 처리 완료의 근거가 아니다. `WAITING_RESPONSE`도 신청 처리 대기를 뜻하지 않는다.

| `remaining.kind` | 의미 |
| --- | --- |
| `NEEDS_CONFIRMATION` | 지역·방문자 등 추가 확인이 남음 |
| `UNANSWERED` | 근거 있는 답변을 확인하지 못함 |
| `OUT_OF_SCOPE` | 상담 범위에 해당하는 안내를 받지 못함 |
| `INTERRUPTED` | 답변 실행이 실패·취소되어 마치지 못함 |
| `WAITING_RESPONSE` | 답변 완료 여부를 확인하지 못함 |

## 긴 대화와 작업 한도

- 짧은 상담은 한 번에 처리하고, 긴 상담은 질문·답변 묶음을 나눠 선택 결과와 원본 연결을 단계적으로 병합한다.
- 모델에 전달하는 안내 구간은 최대 480자, 한 호출에서 제공·선택하는 번호는 최대 8개다. 문단이 길면 문장·공백 경계를 우선해 나누고, 더 긴 단일 문장도 문자 경계를 보존해 나눈다. 원문을 잘라 버리거나 새로 쓰지 않는다.
- 한 질문·답변의 안내만으로 입력·개수 한도를 넘으면 같은 문의와 출처를 유지한 채 여러 호출로 나눈다. 각 호출의 3072 추정 입력 토큰·출력 768 예산은 유지한다.
- 최종 단계에서는 검증된 선택과 마지막 답변 출처를 사용해 원래 문단 전체를 복원한다. 최종 고객용 문단을 480자로 자르지 않는다. 같은 문의는 후속 단계에서 한 문단으로 묶는다.
- 전체 보존 대상은 고유 원문 문단 64개·원문 합산 32,768자까지다. 상한 초과는 모델 호출 전에 `WORK_LIMIT`으로 종료하며 일부 안내를 전체 상담 요약으로 제공하지 않는다. 같은 원문이 여러 대상에 연결돼 최종 문의 문단 수가 늘어나는 경우와 구분한다.
- 부분 결과의 고유 안내가 호출별 8개를 넘거나 병합 라운드가 진행되지 않으면 검증된 원문·출처를 서버에서 합친다. 전체 상태·출처·개인정보를 다시 검사하며 추가 모델 재작성은 하지 않는다. 호출별 선택 8개와 최종 원문 한도를 분리한다.
- 단일 묶음·구간 수·입력·작업 기한을 넘으면 일부를 전체 상담 요약처럼 제공하지 않는다. 원래 답변 실행을 요약 작업이 강제로 종료하지 않는다.
- 모델 호출 중 DB 잠금과 트랜잭션을 유지하지 않는다. 세션당 요청 행은 하나이며 소유권이 바뀐 작업의 늦은 결과는 저장하지 않는다.
- 이벤트 유실·큐 포화·작업 중단은 DB 주기 점검으로 회복한다. 실행기는 1개 스레드와 대기 20개를 사용하고 같은 세션의 중복 제출을 방지한다. 외부 모델 호출까지 정확히 한 번을 보장하지는 않는다.

## API

### 종료

`PATCH /api/v1/chat/sessions/{sessionId}/close`

- 기존 인증·게스트 쿠키·소유권 검사, 200 응답과 `CLOSED` 상태를 유지한다. 종료 성공은 요약 생성 완료를 뜻하지 않는다.
- 반복 종료는 새 작업을 만들거나 완료 결과를 초기화하지 않는다. 요청 기록이 없는 과거 상담을 소급 생성하지 않는다.

### 조회

`GET /api/v1/chat/sessions/{sessionId}/summary`

- 본인 상담만 조회한다. 로그인 승계는 현재 세션 소유권으로 판단한다.
- 정상 조회는 200, `CustomResponse.result`, `Cache-Control: no-store`를 사용한다. 다른 사용자·없는 상담은 기존 상담 조회 오류 계약을 따른다.
- 조회는 새 모델 호출·재시도·상담 변경을 하지 않는다. 새로고침·재접속에서도 저장 결과를 읽는다.

| 응답 필드 | 의미 |
| --- | --- |
| `sessionId` | 대상 상담 |
| `sessionStatus` | 현재 상담 상태 |
| `summaryStatus` | 아래 생성 상태 |
| `summary` | 완료 시 아래 5개 필드를 가진 객체. 미완료는 null |
| `generatedAt` | 검증된 결과 저장 시각. 미완료는 null |
| `message` | 상태 안내 |

| `summary` 필드 | 구조와 의미 |
| --- | --- |
| `topics` | 기존 주요 문의 문자열 배열 |
| `guidance` | 기존 안내 문자열 배열 |
| `pendingItems` | 기존 남은 사항 문자열 배열 |
| `inquiries` | 문의별 `{title, text}` 배열. 같은 문의로 묶은 답변 본문 |
| `remaining` | 남은 사항별 `{title, text, kind}` 배열 |

`CustomResponse.result.summary` 형식 예시다. 설명용 합성 문구이며 실제 실행 결과나 요금 정책을 나타내지 않는다.

```json
{
  "topics": ["유심 재발급", "방문 매장 위치"],
  "guidance": ["신분증을 지참해 매장을 방문하는 절차를 안내받았습니다."],
  "pendingItems": ["매장 안내를 위한 방문 지역은 아직 확인되지 않았습니다."],
  "inquiries": [
    {"title": "유심 재발급", "text": "신분증을 지참해 매장을 방문하는 절차를 안내받았습니다."}
  ],
  "remaining": [
    {"title": "방문 매장 위치", "text": "매장 안내를 위한 방문 지역은 아직 확인되지 않았습니다.", "kind": "NEEDS_CONFIRMATION"}
  ]
}
```

| 생성 상태 | 의미 |
| --- | --- |
| `NOT_REQUESTED` | 요청 기록 없음 또는 기능 비활성 |
| `PENDING` | 답변 처리 종료 또는 작업 순서 대기 |
| `GENERATING` | 요약 생성 중 |
| `COMPLETED` | 검증된 결과 저장 |
| `EMPTY` | 요약할 상담 내용 없음 |
| `FAILED` | 생성·검증·작업 한도 실패 |

### 프론트 담당자와 맞출 표시 계약

- 제안 화면은 상담 요약 카드 하나 안에 ‘문의 내용 및 답변’과 ‘남은 사항’을 둔다. `inquiries` 항목별로 제목·본문을 표시하고, `remaining`이 없으면 해당 영역을 숨긴다. 이번 문서 정리는 프론트 구현 변경이 아니다.
- 이전 저장 결과는 재생성하지 않는다. 제목·상태 메타데이터가 없는 과거 결과는 기존 문자열 배열에 내용이 있어도 `inquiries`·`remaining`이 비어 있을 수 있다. 기존 배열을 표시하는 대체 처리가 필요하며, 새 배열이 비었다고 내용 없음으로 판단하지 않는다.
- 남은 사항이 없다는 이유로 `모두 해결됨`이나 `신청 완료`를 추가하지 않는다. 조회 실패·화면 대기 종료도 빈 상담이나 서버 생성 실패로 단정하지 않는다.
- 준비 중에만 정기 조회하고 완료·빈 상담·실패에서 멈추는 표시를 협의한다. 과거 로컬 검증 화면의 조회 주기를 운영 프론트 계약으로 고정하지 않는다.

## 저장과 설정

- 기존 `chat_session_end_summaries`에 원본 연결·작업 소유권·실패 상태·시각과 결과를 저장한다. 부모 세션으로 소유권을 확인하며 사용자·게스트 ID를 중복 저장하지 않는다.
- 저장 JSON의 최상위는 기존 `topics`, `guidance`, `pendingItems`를 유지한다. 문의별 안내에 `title`, 남은 사항에 `title`·`kind`를 함께 저장해 조회 DTO를 구성한다. 내부 출처 번호는 고객용 본문으로 노출하지 않는다.
- 기존 `V31__add_chat_session_end_summary.sql`로 마련된 저장 구조를 사용한다. 되묻기 해결 판정은 기존 `consult_conditions`의 `asked_message_id`·`answered_message_id`를 조회한다. 새 테이블·Flyway 마이그레이션과 고객용 응답 필드 변경은 없다.
- 내부 문맥 요약·기존 채팅 메시지·질문 통계에 새 요약 메시지를 추가하지 않는다. 기존 마이그레이션 적용 후 기능 설정을 활성화한다.

| 설정 | 기본값 |
| --- | --- |
| `chat.end-summary.enabled` | false |
| `chat.end-summary.dispatch-enabled` | true |
| `chat.end-summary.scheduler-enabled` | true |
| `chat.end-summary.max-input-tokens` | 3072 추정 토큰 |
| `chat.end-summary.max-output-tokens` | 768 |
| `chat.end-summary.max-messages` | 400 |
| `chat.end-summary.max-chunks` | 8 |
| `chat.end-summary.max-attempts` | 2 |
| `chat.end-summary.lease-duration` | 5분 |
| `chat.end-summary.max-age` | 15분 |
| `chat.end-summary.poll-delay` | 5초 |

토큰 계산은 시스템·사용자 프롬프트의 추정치이며 모델의 실제 토큰 수나 최대 문맥 길이와 다르다.
3072는 서비스가 정한 호출별 입력 예산이다. 모델 변경만으로 이 제한이 해제되지는 않는다.
실제 실행 문맥에서 출력 예산·추가 오버헤드와 여유를 확보하고, 메모리·지연을 측정한 뒤 조정한다.
모델 호출 재시도·선택 번호 재요청·작업 회복 횟수는 서로 별개다.

## 생성 실패와 검증 범위

- 분류되지 않은 런타임 오류는 `FAILED`·`GENERATION_FAILED`로 저장하고 세션 ID·예외 종류만 경고 로그에 남긴다. 예외 본문·원인·스택·프롬프트·응답·고객 원문을 기록하지 않는다.
- `INPUT_LIMIT`, `WORK_LIMIT`, 잘못된 출력, 출력 정책 차단 등 기존 실패 분류를 유지한다. 진단 정보를 고객용 오류 상세나 새 자동 재시도로 확대하지 않는다.
- 인사·감사 또는 무응답에 따른 자동 종료, 과거 상담 소급 생성, 수동 재생성, 요약 SSE는 지원하지 않는다.
- 원문 선택은 안내의 의미 변경을 줄이지만 원답변 자체의 오류·누락, 중요한 후보의 미선택, 규칙 기반 문의 연결의 한계는 남는다. 형식·출처 검사가 의미 정확도를 보장하지는 않는다.
- 최신 `origin/develop`의 `0f7d7612`까지 합친 로컬 전체 `clean build`는 총 4,411개 중 4,290개 통과, 실패·오류 0개, 조건부 스킵 121개다. 모델·판정기 대역과 전용 로컬 DB를 사용했다. 되묻기 해결 판정 단위 테스트 19개·DB/API 통합 테스트 8개가 포함된다.
- 실제 로컬 엑사원으로 합성 상담 기록 15종을 검증했다. 기존 6개 결과와 핵심 사실 25개가 유지됐으며, 추가 9개에서 해결·다른 문의·미확인 조건·검색 실패·재질문·개인정보·후속 되묻기를 검사했다. 채팅 라우팅부터 브라우저까지의 전체 검증은 아니다.
- 개인정보는 최종 평가에 사용한 모델 입력·원응답·최종 응답 45개 단계에서 지원 합성 번호와 끝자리 노출 0건을 확인했다. 누락·사실 왜곡 검사는 별도로 수행했으며 정의한 사실 누락·새 수치·잘못된 원문 출처·내부 번호 표시를 발견하지 못했다. 모든 상담의 무누락·무환각을 보장하지 않는다.
- 최신화 과정에서 기존 6개와 합성 18메시지를 실제 엑사원으로 다시 생성했다. 실제 호출 8회로 7개 모두 완료했고, 정의한 핵심 사실 25개를 보존했다. 입력·원응답·최종 응답 23개 단계에서 지원 합성 번호와 끝자리 노출을 발견하지 못했다. 위 15종 결과와 별도 실행이다. Bedrock 새 호출은 없었으며 저장 응답 재검증을 새 모델 실측으로 집계하지 않았다.
- 이번 검증에 브라우저 화면과 새 원격 CI는 포함하지 않았다. 프론트와 고객용 응답 필드는 변경하지 않았고, 이전 검증 결과와 보완 전 원본은 로컬 산출물에 별도로 보존한다.
- 비교 보고서·스크린샷·평가 원자료는 로컬 산출물로 분리한다. 서로 다른 시점의 검증 수치는 합산하지 않는다.

# 사용자용 상담 종료 요약

## 기능과 처리 흐름

- 사용자가 기존 상담 종료 API를 호출하면 최초 종료 전환과 요약 요청을 함께 저장한다.
- 요약 생성은 종료 응답 뒤 비동기로 처리한다. 진행 중인 답변이 있으면 그 처리가 끝난 뒤 대화 범위를 확정한다.
- 사용자용 결과는 내부 문맥 기억인 `chat_sessions.summary`와 분리한다.
- 요약은 주요 문의, 안내 내용, 남은 사항으로 구성한다. 안내 내용은 실제 답변의 원문 문장을 발췌하고 `안내받은 내용:`으로 표시한다.
- 원문에 없는 정책·금액·처리 결과를 추가하지 않는다. 안내를 받았다는 것과 실제 신청·변경 완료는 구분한다.
- 문의별 목록(`inquiries`)에는 모델이 고른 안내마다 쓴 짧은 요약(`guidanceSummaries`, 한 문장)을 보인다. 서버는 요약과 원문의 숫자(금액·기간·횟수, 쉼표 제외)가 같은지(지어내지도 빼지도 않음), 기간 낱말(하루·열흘·일주일 등)과 대리 표현(대신·대리·위임·본인), 부정(없·않·못·불가·안 되)이 양쪽에 함께 있는지, 물음이 아닌지, 120자 이하인지 확인하고, 하나라도 어기면 원문 발췌를 대신 보인다. `guidance` 목록과 출처는 계속 원문 발췌다.
- 같은 문의를 다시 물어 문장만 조금 다른 안내(같은 제목, 글자 두 개씩 겹침 0.6 이상)는 마지막 것 하나만 문의별 목록에 남긴다. 같은 내용인지는 요약이 아니라 원문으로 판단한다.

종료 요청 → 요청 저장 → 답변 처리 종료 확인 → 입력 준비 → 생성·검증 → 별도 결과 저장 → 조회

## 입력과 생성

- 같은 세션의 메시지 순서·질문과 답변 연결·하위 상담의 원래 문의와 상태를 사용한다.
- 완료된 정상 대화만 준비하며 `ERROR`, `BLOCKED`, 미완성 답변 원문은 제외한다.
- 순수 인사와 고정 응답만 있는 상담은 빈 상담으로 처리하고 모델을 호출하지 않는다. 조건 응답·혼합 문의를 단어만 보고 제외하지 않는다.
- 지원 민감정보는 모델 전달 전 문장 필드에서 마스킹한다. 출력에도 같은 보호를 적용한다.
- 기존 모델 클라이언트와 `SUMMARY` 작업 유형을 사용하며 프롬프트 버전은 `consultation-end-summary-v15`이다. 이전 저장 결과는 재생성 없이 조회할 수 있다.

## 모델

- 기본은 gpt-oss(Bedrock)이고 실패하면 엑사원으로 대체한다(`CHAT_END_SUMMARY_BEDROCK`, 기본 true. `ChatEndSummaryConfiguration`). false면 엑사원만 쓴다.
- 엑사원으로 넘어가는 것은 **Bedrock 호출 자체가 예외로 실패할 때**(연결 실패, 시간 초과, 오류 응답)뿐이다. gpt-oss가 응답했지만 형식이 틀린 JSON을 주면 대체 없이 `INVALID_OUTPUT`으로 끝나고, 작업 재시도(`maxAttempts`)도 같은 Bedrock으로 간다. 블라인드 평가 7~10차에서 gpt-oss 요약 220건 중 이 경우는 0건이었다.
- Bedrock 요청 변환기는 JSON 스키마를 보내지 않으므로 스키마를 사용자 프롬프트 끝에 지시문으로 붙인다(`SchemaInstructionLlmClient`). 엑사원 대체에는 원래 요청(스키마 강제)을 그대로 보낸다. 응답 검증은 두 모델에 똑같이 적용한다.

## 정정과 이어 묻기

- 고객 발화 문구로 바로 앞 문의를 이어받는지 판단한다(`ChatEndSummaryFollowUps`, 기록된 상담만). "아니 그러니까", "제 말은"으로 시작하거나, "그니까"로 시작해 "~냐구요", "~거에요"처럼 같은 말을 되풀이하는 어미로 끝나면 다시 묻기다("그니까 아예 차단하는 방법은요?"는 새 질문). "A 말고 B", "A 아니고 B", "아니 그냥 …", "아 아니다 …"이면 정정이다. 새로 묻는 말("유심 말고 eSIM은 얼마예요", 물음표·의문 어미)과 "아니 근데 …", 조건에 답한 발화는 제외한다.
- 두 발화 모두 모델 주제가 있으면 앞 문의의 주제를 뒤 발화 주제(정정 뒤 값)로 바꿔 한 문의로 묶는다. 뒤 발화에도 남은 사항이 있으면(되묻기에 답하지 않음 등) 앞 문의는 따로 남기지 않는다.
- 정정이고 뒤 발화의 답이 안내로 남아 있으면 앞 발화의 답은 문의별 목록(`inquiries`)에서 뺀다. `guidance` 목록과 출처는 그대로다. 앞 발화가 복합 질문이면 어느 하위 질문을 고친 것인지 알 수 없어 빼지 않는다.
- 앞 발화가 복합 질문이면 어느 하위 질문을 이어받았는지 알 수 없어 묶지 않는다(답 못 받은 하위 질문이 사라지지 않게).
- "그건 됐고 …", "매장은 됐고 …"처럼 바로 앞 문의를 거두면 앞 문의는 남은 사항에 넣지 않는다.
- 마무리 인사(`ChatEndSummaryClosingRemarks`)에는 "고생하세요", "애쓰셨어요", "들어가세요"도 포함한다.
- 정정 말투에는 "잘못 말했어요 …", "정정할게요 …", "A가 아니라 B"도 포함한다. 다시 묻기에는 "다시 여쭤볼게요"도 포함한다.
- 범위 밖 안내(`OUT_OF_SCOPE`)만 받은 발화는 남은 사항 후보로 넣지 않는다. 실시간 경로가 통신 후속 질문("데이터 다 쓰면 어떻게 돼요")을 범위 밖으로 답하는 경우가 있지만, 후보로 넣으면 모델이 잡담(날씨·로또·점심)에도 주제를 붙여 13차 블라인드 평가에서 잡담 4건이 세 모델 모두 문의로 남았다. 이 문제는 실시간 경로의 범위 판정에서 고친다.
- 답변 머리말만 있는 문단("요금제 안내예요.")은 안내 후보로 쓰지 않는다. 마무리 인사의 "다", "너무" 같은 짧은 말은 글자 그대로만 본다("넵 덕분에 다 해결했어요 감사합니다").

- 실시간 경로는 "아 3월 말고 4월이요", "아 아니다 일주일 가요" 같은 정정을 별개 질문으로 처리하거나 주제 확인 안내로 답하며 정정이라고 기록하지 않는다. 요약에서 모델이 대화를 보고 묶는다.
- 프롬프트(v12): 정정·이어 묻기 발화에는 앞 문의와 글자까지 같은 주제를 쓰고 주제에는 정정 뒤 값을 쓴다. 한 발화의 하위 질문은 한 주제에 모두 쓴다. 조건에 답한 발화는 주제로 만들지 않는다.
- 상담 요청 없이 남은 문의(정정 발화에 주제 확인 안내만 받은 경우 등)도 주제를 달 수 있다(필수는 원래 문의뿐).
- 서버는 같은 주제 문구를 하나로 합치고, 같은 주제로 묶인 답하지 못한 문의(하위 질문이 하나인 문의)를 `답변을 받지 못한 문의: {주제}` 한 줄로 적는다. 정정 전 값을 따로 남기지 않는다. 복합 질문의 하위 질문 문구와 미확인 조건은 묶지 않는다.
- 되묻다 취소된 문의가 같은 주제의 뒤 문의에서 답을 받았으면 남은 사항에서 뺀다(“eSIM으로 바꿀 수 있나요?” 되묻기 중 “그거 아이폰도 돼요?”로 이어 물어 답을 받은 경우).
- 모델이 주제를 다르게 붙이면 묶지 않고 문의마다 적는다.
- 하위 질문이 하나인 문의의 서버 문구(`답변을 받지 못한 문의`, `미확인 조건`)는 고객 원문 대신 모델 주제를 쓴다. 주제에 정정 뒤 값을 쓰라고 지시하므로 원문의 정정 전 값(“70대 어머니” → 65세)이 남지 않는다. 주제가 없으면 원문 그대로다. 복합 질문의 하위 질문 문구는 소제목 그대로다.
- 매장 찾기를 되묻는 중에 바로 다음 발화가 다시 매장 찾기면 지역·업무를 고쳐 말한 것으로 보고, 취소된 앞 매장 찾기를 남은 사항에 따로 두지 않는다(“서면 말고 해운대요”).
- 기록된 결과가 있는 상담에서 범위 밖 안내를 받은 발화는 입력에 남겨 정정 맥락(“아 5일 아니고 10일이요”가 범위 밖으로 처리된 경우)을 모델이 보게 한다. 남은 사항·주제·안내로는 쓰지 않는다. 상담 요청이 하나도 없는 상담에서는 빼서 인사·잡담만 한 대화를 빈 상담으로 둔다.
- 기록된 결과가 있는 상담은 남은 사항을 서버가 모두 적고 모델이 쓴 남은 사항은 쓰지 않는다. 모델이 지어낸 조건·서류(“신분증, 가족관계증명서”)가 남은 사항에 들어가지 않는다.
- 같은 주제로 묶인 문의 중 뒤 문의가 답을 받았으면 앞 문의(근거 없음, 되묻다 취소됨)는 해결된 것으로 보고 남은 사항에 두지 않는다(“지난달 말고 3개월 전꺼요”로 정정해 답을 받은 경우).
- 되묻는 중에 고객이 조건 대신 새 질문을 하면 실시간 경로가 조건 답으로 받아 같은 질문을 다시 묻는다(“유심 비번 까먹었어요”에 “답변을 잘 이해하지 못했어요”). 새로 묻는 되묻기는 하위 질문 결과(ASKED)로 기록되고 다시 묻기는 기록되지 않으므로, 상담 요청 없는 발화에 기록되지 않은 되묻기만 돌아왔으면 남은 문의 후보로 둔다. 조건 답을 못 알아들은 경우와 섞이므로 아래 직접 답변과 같이 모델이 주제를 붙였을 때만 적는다.
- 감사·작별 인사로 보이는 발화라도 실시간 경로가 그 발화로 접수한 요청에 실제 안내를 했으면(“ㅇㅋ 땡큐”에 앞 질문의 안내가 나간 경우) 빼지 않는다.
- 상담 요청 없이 주제 확인 등 직접 답변만 받은 발화는 모델이 주요 문의 주제를 붙였을 때만 남은 문의로 적는다. 프롬프트는 인사와 통신과 무관한 잡담에 주제를 쓰지 않게 한다(“점심 뭐먹을지 추천좀”에 주제 확인 안내가 나간 경우).

## vLLM 호환

- 배포에서 엑사원은 vLLM(guided decoding)으로 출력 스키마를 강제한다. vLLM의 스키마 엔진은 `uniqueItems`를 지원하지 않아 요청 전체를 400으로 거절하므로 종료 요약 스키마에 쓰지 않는다. 같은 안내 번호를 두 번 고르면 서버가 한 번으로 본다.
- 엑사원 결과는 배포와 같은 조건(vLLM, `LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct-AWQ`, `--dtype half`, `--max-model-len 8192`)으로 측정한다. 로컬 Ollama(Q4_K_M GGUF)와는 양자화와 스키마 강제 방식이 달라 결과를 그대로 옮기지 않는다.

## 하위 질문 결과 기록 (V41)

실시간 경로가 하위 질문(`consult_requests` 한 줄)마다 고객에게 실제로 보인 결과를 기록하고, 요약은 답변 글자를 거꾸로 해석하지 않고 이 값을 읽는다. 기록은 답변을 만든 뒤에 하며 답변 내용·라우팅·상태 전이를 바꾸지 않는다.

| 컬럼 | 값 |
| --- | --- |
| `answer_outcome` | `ANSWERED`(근거 있는 FAQ 답), `STORES`(매장 목록), `NO_EVIDENCE`(근거 없음, 지역 없는 매장 찾기 안내), `ASKED`(조건을 되물음), `SPLIT_REFUSED`(지역이 필요한 매장 찾기가 여럿이라 나눠 보내 달라고 안내) |
| `answer_text` | 이 하위 질문에 대해 보인 문구. 복합 답변이면 그 하위 질문 문단의 본문, `ASKED`면 물어본 질문. `NO_EVIDENCE`는 비운다 |
| `answer_message_id` | 그 문구가 담긴 메시지 |
| `display_question` | 복합 답변 소제목으로 보인 하위 질문. 단일 질문은 비운다(원문 메시지가 곧 질문). 복합 되묻기에서 기록한 소제목은 조건을 받은 뒤 단일 경로로 답할 때도 유지한다 |

- 기록 지점은 `ConsultChatPersistenceService`의 최종 답변(`persistFinalAnswer(s)`), 되묻기(`persistClarification`), 복합 되묻기(`persistCompoundClarification`), 나눠 보내기 안내(`persistSplitGuidance`)다. 메시지·상태를 저장하는 같은 트랜잭션에서 `JdbcConsultStateStore.recordOutcome`이 기본 키로 한 줄을 갱신하며 버전은 올리지 않는다.
- 상담 요청을 만들지 않는 직접 답변(기본 대화, 범위 밖, 주제 확인, 질문 나누기·개수 초과 안내)은 기록 대상이 아니다. 요약은 이 답들을 메시지에 이미 있는 값(근거 표시 없음, 상담 요청 없음)으로 구분한다.
- 한 상담에 기록된 결과가 하나라도 있으면 요약은 아래 규칙을 쓴다. 기록 전 상담은 기존 규칙 그대로다.
  - 안내 후보는 `ANSWERED`·`STORES` 하위 질문의 `answer_text`에서만 만든다. 복합 답변 소제목, 근거 없음 문구, 되묻기, 직접 답변은 후보가 되지 않는다.
  - 남은 사항은 하위 질문마다 서버 문구로 적는다. `NO_EVIDENCE`·`SPLIT_REFUSED`와 되묻다가 취소된 하위 질문은 `답변을 받지 못한 문의: {소제목 또는 고객 원문}`, 확인 대기 중인 하위 질문은 `미확인 조건: {소제목 또는 고객 원문} — {물어본 질문}`이다. 계획에만 있고 묻지 않은 조건은 적지 않는다. 같은 원문의 답을 받은 하위 질문과 섞이지 않는다.
  - 상담 요청 없이 범위 밖 안내만 받은 발화(잡담·인사)는 요약하지 않는다. 실시간 경로가 통신 질문을 범위 밖으로 잘못 처리한 경우도 빠지므로 그런 오분류는 실시간 쪽에서 고친다.
  - 상담 요청 없이 주제 확인 등 직접 답변만 받은 질문은 남은 문의다. 모델이 빠뜨리면 `답변을 받지 못한 문의: {고객 원문}`으로 채운다.
- 답이 전부 기본 대화 고정 응답(인사·감사·정체 질문 등, 페르소나 문구 포함)인 발화는 기록 여부와 관계없이 요약하지 않는다.
- 서버가 적는 남은 사항 문구가 240자를 넘으면 요약을 실패시키지 않고 자른다.
- 결과가 기록된 상담에서 답을 받은 하위 질문의 안내를 모델이 하나도 고르지 않으면 그 답의 첫 문단을 원문 그대로 더한다(안내 최대 8개 안). 문의별 화면은 안내가 없는 문의를 보여 주지 않기 때문이다.
- 감사·작별 인사로만 이뤄진 고객 발화(`네 감사합니다 수고하세요~`, `ㄳㄳ 좋은하루요`, `알겠어 땡큐`)는 실시간 경로가 후속 질문으로 접수해 근거 없음·주제 확인으로 답했어도 그 답과 함께 요약하지 않는다(`ChatEndSummaryClosingRemarks`). 하위 질문 기록만으로는 인사와 구분할 수 없어 고객 발화의 낱말만 본다. 물음표가 있거나 인사 낱말이 아닌 낱말이 하나라도 있으면 빼지 않는다. 그 뒤 답이 다른 하위 질문의 결과로 기록됐으면(조건 답으로 받아 앞 문의를 답한 경우) 그 답은 남긴다.
- 정정(“3일 아니고 5일”)은 실시간 경로가 판단해 기록해 두지 않아 요약이 정정 전 값을 남길 수 있다. 정정 정보를 결과와 함께 기록하는 것은 후속 작업이다.
- 모델에는 종료 요약 전용 JSON 스키마를 전달한다. 안내 후보에는 상담 전체에서 고정한 정수 번호를 부여하고, 모델은 번호만 선택한다. 서버가 해당 원문과 출처를 조립한다.
- 모델의 주요 문의는 원래 문의 번호를 키로 하는 필수 객체다. 고객 조회 응답에서는 기존 문자열 배열을 유지한다. 분할·병합에서 문의 번호를 다시 부여하지 않는다.
- 조건과 예외가 분리되지 않도록 안내는 문단 단위로 준비한다. 조건 응답에 실제로 연결된 최신 근거 안내는 모델이 누락해도 보존하고, 선택된 이전 안내와 조건 확인 후 안내를 구분한다. 안내 후보는 최대 480자이며, 단일 안내가 한도를 넘으면 일부만 성공 결과로 잘라 표시하지 않는다.
- 모델 선택과 최종 안내는 최대 8개다. 최신 조건에 답한 필수 안내의 자리를 먼저 확보하고, 남는 자리에 모델이 고른 일반 안내를 선택 순서대로 넣는다. 모델이 일반 안내 8개를 선택하고 최신 안내를 빠뜨려도 보정 때문에 9개가 되어 실패하지 않는다. 필수 최신 안내 자체가 8개를 넘으면 누락된 부분 요약을 성공으로 제공하지 않고 `INPUT_LIMIT`으로 실패한다.
- 전체 안내 원문의 마스킹·문단 분리와 고정 후보 번호 계산은 한 번의 요약 생성에서 한 번만 수행한다. 분할·병합·검증에서는 해당 구간에 속한 출처만 사용하며, 결과를 다른 상담이나 다음 생성 요청과 공유하지 않는다.
- 종료 시점의 조건값·상태·출처·응답 메시지와 최신 고객 발화를 각 부분 생성과 병합에 전달한다. 다른 문의·가족·상품의 조건을 마지막 값 하나로 덮어쓰지 않는다.
- 잘못된 선택 번호는 작업 기한 안에서 한 번만 다시 요청한다. 계속 잘못되면 안전한 실패 상태를 저장하며 첫 안내로 임의 대체하지 않는다.
- 주요 문의는 최소 한 항목, 실제 근거 안내가 있으면 안내도 최소 한 항목으로 요청한다. 출처 번호는 입력에 존재하는 해당 역할의 메시지로 제한한다. 하위 상담의 원래 문의가 있으면 주요 문의는 그 질문을 연결하며 단순 조건 응답만 출처로 쓰지 않는다.
- JSON 타입·필수 항목·길이·같은 상담의 원본 ID를 검사하고 최종 저장 문자열에 출력 검사를 적용한다.
- 주요 문의·남은 사항은 종료 기록의 문구로 정리하며 새 상담의 안내 약속으로 표현하지 않는다.
- 형식·원본 연결 검사는 의미 정확도나 누락 없음의 보장이 아니다. 주요 문의·남은 사항의 정정과 조건 보존은 실제 모델 검증이 필요하다.
- 저장된 원래 문의는 모두 주요 문의에 연결됐는지 검사한다. 여러 주제를 다룬 상담에서 마지막 문의만 남긴 결과는 저장하지 않는다.
- 되묻기 질문을 안내 문장으로 발췌하지 않는다. 아직 응답하지 않은 조건의 실제 질문은 별도 입력으로 전달해 남은 사항을 구체화한다.
- 근거 없음·범위 밖 대체 문구는 안내 후보에서 제외하며 답하지 못한 문의는 남은 사항으로 보존한다.
- 원래 문의는 항목별로 구분하고, 같은 안내 문장의 반복은 실제 출처 번호를 보존해 합친다.
- 저장 상태에서 확인되는 미응답 조건은 하위 상담 번호별로 읽어 해당 문의와 함께 표시한다. 모델이 일부만 선택해도 조건이 요약에서 사라지지 않는다. 같은 방문자 선택의 본인·대리인 조건은 관계가 확인되는 경우 하나의 확인 사항으로 표시한다.
- 남은 사항의 기본 상한은 8개다. 저장된 필수 확인 항목 수와 아직 구체 문구가 없는 남은 문의 수의 합이 더 크면 그 개수만큼 상한을 늘린다. 모델의 응답 스키마, 원본 연결 검증, 서버 보정 후 검증에 같은 상한을 적용한다. 예를 들어 필수 확인 항목이 9개이면 모델이 하나만 적어도 9개를 모두 복원해 저장·조회한다. 저장된 근거 없이 모델이 항목을 임의로 늘리는 것은 허용하지 않는다.
- 상한 확장은 개수에만 적용한다. 원본 문의·역할·출처 검사, 항목당 240자, 안내 후보당 480자, 입력 토큰·메시지·구간 수·작업 기한 제한은 유지한다. 조회 응답의 필드와 문자열 배열 구조는 같으며, 화면에서 남은 사항을 8개까지만 표시한다고 가정하지 않아야 한다.
- 저장 상태에 남은 문의가 없는 경우 모델이 새 미답변 항목을 추가하지 못한다. 이는 종료 기록이며 새 질문 전송이나 상담 재개가 아니다.
- 실패·취소된 실행의 문의는 모델의 재입력 요청 대신 `답변을 마치지 못한 문의`로 표시한다. 기존 미확인 조건이 있으면 그 조건을 우선 보존한다. 원래 문의가 있는 상담에서 주제는 원래 문의에만 달 수 있으므로, 상담 요청 없이 실패한 질문(되묻기 뒤 후속 질문 등)은 주제 대신 고객 원문으로 적는다.

## 긴 대화와 작업 한도

- 짧은 상담은 한 번에 요약한다. 긴 상담은 질문·답변 묶음을 나누어 요약하고 원본 연결을 유지하며 단계적으로 병합한다.
- 단일 묶음·구간 수·최종 결과가 한도를 초과하면 일부를 전체 상담 요약으로 표시하지 않고 실패 처리한다.
- 대기·생성의 기한과 작업 회복 횟수를 제한한다. 원래 답변 실행을 요약 작업에서 강제로 종료하지 않는다.
- 모델 호출 동안 DB 잠금과 트랜잭션을 유지하지 않는다.
- 세션당 요청 행은 하나다. 작업 소유권이 바뀌면 이전 작업의 늦은 결과를 저장하지 않는다.
- 이벤트 유실·큐 포화·작업 중단은 DB 상태의 주기 점검으로 회복한다. 실행기에 이미 대기·실행 중인 같은 세션은 중복 제출하지 않는다. 거절·완료·실패 시 제출 표식을 해제한다.
- 실행기는 1개 스레드와 대기 20개를 사용한다. DB 작업 소유권 검사는 여러 프로세스 사이의 저장 경합을 방어하며, 외부 모델 호출까지 정확히 한 번을 보장하지는 않는다.

## 생성 실패 진단

- 분류되지 않은 런타임 오류는 기존처럼 `FAILED`와 `GENERATION_FAILED`로 저장한다. 이 경로에서만 경고 로그에 `sessionId`와 `exceptionType`을 남긴다.
- 로그에 예외 본문, 원인 예외, 스택, 모델 프롬프트·응답, 후보·고객 원문을 넣지 않는다. 예외 객체를 로깅 인수로 전달하지 않는다. `GeneralException`이라는 종류만으로 구체적인 모델 장애 원인까지 판별할 수 있는 것은 아니다.
- `INPUT_LIMIT`, `WORK_LIMIT`, 잘못된 출력, 출력 정책 차단 등 기존 실패 분류와 조회 응답은 유지한다. 진단 로그 추가를 자동 재시도나 고객용 오류 상세 노출로 확대하지 않는다.

## API

### 종료

`PATCH /api/v1/chat/sessions/{sessionId}/close`

- 기존 인증·게스트 쿠키·소유권 검사를 사용한다.
- 기존 200 응답과 `CLOSED` 상태를 유지한다. 응답 성공은 요약 생성 완료를 뜻하지 않는다.
- 반복 종료는 새 작업을 만들거나 완료 결과를 초기화하지 않는다.
- 이미 종료된 과거 상담의 요청 기록이 없으면 반복 종료로 소급 생성하지 않는다.

### 조회

`GET /api/v1/chat/sessions/{sessionId}/summary`

- 본인 상담만 조회하며 로그인 승계는 현재 세션 소유권으로 판단한다.
- 정상 조회는 200, `CustomResponse.result`, `Cache-Control: no-store`를 사용한다.
- 다른 사용자·없는 상담은 기존 상담 조회 오류 계약을 따른다.
- 조회는 요약 요청·모델 호출·재시도·상담 변경을 하지 않는다. 답변 실행 ID나 SSE 접수가 아니다.

| 응답 필드 | 의미 |
| --- | --- |
| `sessionId` | 대상 상담 |
| `sessionStatus` | 현재 상담 상태 |
| `summaryStatus` | 아래 생성 상태 |
| `summary` | 완료된 `topics`, `guidance`, `pendingItems` 문자열 배열. 미완료는 null |
| `summary.inquiries` | 안내를 문의별로 묶은 `{title, text}` 목록. `title`은 복합 질문이면 고객에게 보인 하위 질문, 아니면 주요 문의 주제다. 화면은 같은 제목을 한 문단으로 묶어 "문의 내용 및 답변"으로 보여 준다. `text`는 확인을 통과한 짧은 요약, 없으면 원문 발췌다. 이 필드가 생기기 전 저장된 요약은 빈 목록 |
| `summary.remaining` | 남은 사항 `{title, text, kind}` 목록. `kind`는 `NEEDS_CONFIRMATION`(물어본 조건에 답하지 않음) 또는 `UNANSWERED`(답을 받지 못함). `text`는 접두어(`미확인 조건:` 등)를 뗀 문구다 |
| `generatedAt` | 검증된 결과 저장 시각. 미완료는 null |
| `message` | 상태 안내 |

| 생성 상태 | 의미 |
| --- | --- |
| `NOT_REQUESTED` | 요청 기록 없음 또는 기능 비활성 |
| `PENDING` | 답변 처리 종료 또는 작업 순서 대기 |
| `GENERATING` | 요약 생성 중 |
| `COMPLETED` | 검증된 결과 저장 |
| `EMPTY` | 요약할 상담 내용 없음 |
| `FAILED` | 생성·검증·작업 한도 실패 |

- 없는 남은 사항을 화면에서 임의로 `모두 해결됨`으로 표시하지 않는다.
- 조회 실패를 빈 상담이나 생성 실패로 단정하지 않는다. 기존 대화 기록은 별도로 조회할 수 있다.
- 새로고침·재접속에서는 같은 조회 API로 저장 상태를 읽는다. 자동 종료나 모델 재생성을 하지 않는다. 비회원은 기존 식별이 유지되어야 하며, 식별 복원 문제를 요약 기능에서 인증 우회로 처리하지 않는다.
- 화면은 준비 중에만 정기 조회하고 완료·빈 상담·실패에서 멈춘다. 검증용 화면은 처음 10초 동안 2초, 이후 5초 간격이며 2분 뒤 자동 조회를 멈춘다. 수동 조회는 GET만 다시 호출한다.
- 화면 대기 종료는 서버 작업 실패가 아니다. 서버는 기존 작업 기한과 복구 한도를 유지한다.

## 저장과 설정

- `chat_session_end_summaries`에 세션별 결과·원본 연결·작업 소유권·실패 상태·시각을 저장한다.

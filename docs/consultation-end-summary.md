# 사용자용 상담 종료 요약

구현 기준: 2026-10-19, `develop`의 `99e81377`을 반영한 상담 종료 요약이다. 문의·대상 구분과 서버 병합, 전용 엑사원 기본 선택, 선택형 베드락 연결·정상 종료 검사·일시 장애 시 엑사원 대체, 준비물 단정 검사를 포함한다. 실제 배포 반영 여부는 배포 기록에서 별도로 확인한다.

## 이번 보완과 후속 작업의 경계

- 이번 보완은 문장·줄바꿈으로 나뉜 최신 기간 정정과 유심 외 같은 문의의 이어묻기 연결이다. 원문 선택과 문의별 구성, 기존 출처·형식·개인정보 검사는 유지한다.
- 종료 요약 기본 모델은 엑사원이다. 베드락 주 모델 전환은 공통 오류 보완 후 실제 앱의 품질·속도·비용·장애 복구 검증으로 결정한다.
- 저장 전 유사도·추가 핵심 조건 검사와 임계값 확대 검증, 해당 임베딩 호출의 일시 장애 재시도는 후속 이슈·PR로 분리한다. 현재 완료 저장 경로에는 이 검사를 연결하지 않는다. 기존 로컬 구현·테스트·비교 결과는 별도로 보존한다.

## 기능과 처리 흐름

- 기존 상담 종료 API에서 최초 종료 전환과 요약 요청을 함께 저장한다. 요약은 종료 응답 뒤 비동기로 생성한다.
- 진행 중인 답변이 끝난 뒤 입력 범위를 확정한다. 사용자용 결과는 내부 문맥 기억인 `chat_sessions.summary`와 분리한다.
- **AI가 안내 번호를 선택하고, 서버가 실제 답변 원문을 같은 문의끼리 묶는다.** 안내를 자유롭게 재작성하는 추가 모델 호출은 없다.
- 서버가 실제 질문에 맞는 제목을 만들고, 저장된 상담 상태로 남은 사항을 구분한다. 안내를 받았다는 사실과 실제 신청·변경 완료는 구분한다.

종료 요청 → 요청 저장 → 답변 처리 종료 확인 → 입력·원문 후보 준비 → AI 선택·검증 → 문의별 원문 구성·남은 상태 판별 → 저장 → 조회

## 입력과 생성

- 같은 세션의 메시지 순서·질문과 답변 연결·하위 상담의 원래 문의와 상태를 사용한다. `ERROR`, `BLOCKED`, 미완성 답변 원문은 안내 후보에서 제외한다.
- 순수 인사와 고정 응답만 있는 상담은 빈 상담으로 처리한다. 조건 응답·혼합 문의를 단어만 보고 제외하지 않는다.
- 지원 민감번호는 모델 전달 전 문장 필드에서 마스킹한다. 최종 제목·본문·남은 사항에도 입력 검사와 출력 보호를 적용한다.
- 요약 전용 `ChatEndSummaryModel`과 `SUMMARY` 작업 유형을 사용한다. 공통 프롬프트 버전은 `consultation-end-summary-v14`이다.
- 모델 입력의 `requiredTopicMessageIds`와 출력 스키마에 같은 원래 문의 번호를 명시한다. 모델은 이 번호를 새 순번으로 바꾸거나 누락·추가할 수 없다. 조건 응답만 분할된 구간은 실제 사용자 메시지 번호를 사용한다.
- 모델은 지정된 세 필드의 JSON 객체 하나만 반환한다. 안내는 유효한 후보 번호로 선택하고, 남은 사항은 빈 배열로 받아 서버가 저장 상태로 복원한다. 번호·원문·길이·개수·개인정보 검사를 통과해야 저장한다.
- 종료 요약의 시스템 프롬프트는 하나이며 모델별 문장 규칙을 따로 두지 않는다. 모델을 비교할 때는 같은 마스킹 입력과 규칙을 사용하고, 클라이언트의 출력 스키마 전달 유무를 별도 조건으로 기록한다.
- 종료 요약은 기본적으로 전용 엑사원 `exaone3.5:7.8b`를 사용한다. 답변용 기본 모델이나 판정기 모델이 바뀌어도 요약 모델이 함께 바뀌지 않도록 연결을 분리한다. 베드락은 명시적으로 선택한 경우에만 사용한다.
- 채팅 목록 제목·내부 문맥 요약·답변 생성은 기존 기본 모델 연결을 사용한다. 이 변경으로 해당 기능의 모델이나 프론트 응답 필드를 바꾸지 않는다.
- 베드락은 공통 프롬프트로 출력 형식을 지정하고 출력 스키마를 전송하지 않는다. 확인된 일시 장애 시 엑사원에 같은 마스킹 입력과 원래 스키마를 전달한다. 양쪽 응답에 동일한 문의 번호·원문 출처·남은 사항·개인정보 검사를 적용한다.
- 모델 출력은 문의 번호를 키로 한 `topics`, 안내 번호 배열 `selectedSentenceIds`, 빈 배열 `pendingItems`다. 모델이 남은 상태 문구를 만들지 않도록 `pendingItems`의 스키마 상한은 0개다.
- 안내 후보에 상담 전체에서 고정한 번호를 부여한다. 서버가 선택된 번호의 원문과 출처를 조립하며, 잘못된 번호는 작업 기한 안에서 한 번 재요청한다. 계속 잘못되면 실패로 저장하고 첫 안내로 대체하지 않는다.
- 답변 검사에서 잘못된 안내 창구가 섞인 방문 절차는 대상·업무·명시한 방문자 조건이 맞는 단일 근거로만 복원한다. 양쪽 모두 대상이 없는 공통 방문 문구는 서로 충돌하는 업무가 없을 때만 복원하며, 준비물·부정 조건을 원문 그대로 남긴다.
- 조건과 특정 업무가 없는 단일 공통 신청 안내는, 생성 문장의 신청 행위·창구 전체·전화나 방문 방식이 모두 일치할 때만 자연스러운 선택 표현을 보존한다. 창구를 추가하거나 일부를 빼고, 전화·방문을 바꾸거나 즉시 처리·무료·방문자 조건을 덧붙이면 이 예외로 허용하지 않는다.
- 전화한 뒤 홈페이지로 신청하는 등의 순차 절차는 창구 선택지로 바꾸지 않는다. 중간 동작의 연결 표현 뒤에 쉼표가 있어도 선행 단계를 생략하지 않으며, 순차 절차를 원문 그대로 안내한 경우는 보존한다.
- 고객에게 방법을 고르라는 중립적인 안내는 특정 방법이 더 편리하다는 비교 주장이 아니다. 동시에 그런 선택 안내 자체를 특정 방법의 편의성 우위를 입증하는 근거로 사용하지 않는다. 여러 근거나 추가 조건이 있는 경우에는 공통 선택 예외를 쓰지 않고 기존 대상·업무 일치 및 원문 조건 보존 검사를 유지한다.
- 안내는 조건과 예외를 함께 보존하도록 문단 단위로 준비한다. 제목만 있는 항목·되묻기 질문·근거 없음·범위 밖 대체 문구는 안내에서 제외한다.
- 조건 응답과 각 문의의 마지막 근거 있는 답변 원문은 모델이 일부 번호만 골라도 보존한다. 원래 문의·역할·출처·JSON 타입·길이를 검사한다.
- 전체 원문의 검사·문단 분리·후보 번호 계산은 생성 작업 안에서 한 번 수행한다. 분할·병합에서는 해당 구간의 출처만 사용하며 다른 상담이나 생성 요청과 공유하지 않는다.
- `ChatEndSummaryGroundedGenerator`가 발췌 결과를 문의별로 구성한다. 내부 버전 `consultation-end-inquiry-grounded-v1`은 별도 처리 단계의 번호이며 저장 프롬프트 v14와 같은 버전 계열이 아니다.

## 답변 검사와 종료 요약의 경계

- 원답변의 ‘신분증만’, ‘신분증이면 충분’, ‘다른 서류 불필요’, ‘위임장 없이’ 같은 준비물 단정은 답변 검사에서 먼저 확인한다. 고객 질문은 문의 범위 확인에만 사용하며 정책 근거로 사용하지 않는다.
- 생성기는 검색 결과별 FAQ 답변 본문을 별도로 전달한다. 같은 FAQ의 줄바꿈 뒤에 있는 준비물·방문자·미접수 조건도 같은 근거로 유지하며, 서로 다른 FAQ를 줄바꿈만 보고 합치지 않는다. 모델이 앞 문장을 그대로 가져왔더라도 준비물 문의의 필수 조건은 해당 FAQ 본문과 함께 대조한다.
- 준비물 근거가 문의 범위와 일치하면 조건을 포함한 본문으로 복원해 조건 누락과 새 서류·확인 절차의 추가를 함께 줄인다. FAQ 경계가 없는 기존 문자열 입력이 여러 줄이면 일부 준비물만 임의로 복원하지 않고 확인할 수 없는 생성 문장을 제거한다.
- 준비물 복원 전 수치 검사는 단일·복수 FAQ 경로에 동일하게 적용한다. 앞선 창구·신청 안내 검사 뒤에 남은 생성 답변의 금액·기간 등이 근거에 없으면 기존 안전 안내로 처리하며, 정상 원문으로 덮어 수치 오류를 숨기지 않는다. 고객이 확인한 조건 값은 기존 수치 근거 범위를 유지한다.
- 같은 상품·업무·사람·회선·방문자에 대응하는 준비물 근거가 하나일 때만 복원한다. 고객 질문과 생성 문장을 모두 대조하므로 모델이 사람을 바꾼 문장을 원래 질문의 대신으로 쓰지 않는다. `민수의 유심`·`민수의 실물 유심`처럼 지원하는 이름 소유격도 다른 사람과 구분한다.
- 소유격에 이름을 추가해도 기존 가족 호칭 기준을 유지한다. `엄마의 유심`과 `어머니의 유심`, `아빠의 유심`과 `아버지의 유심`은 같은 대상으로 읽으며 서로 다른 부모의 안내는 합치지 않는다.
- 여러 FAQ 중 상품·업무가 생략된 준비물 근거는 다른 FAQ의 상품·업무를 빌려 맞추지 않는다. 방문자를 특정하지 않은 공통 서류 소유 안내의 전체 원문은 대상이 맞으면 유지하지만, 생성한 본인 방문 허용·준비물 충분성 주장까지 같은 예외로 허용하지 않는다.
- 신분증 소유자를 실제 방문자로 읽지 않는다. `명의자 본인의 신분증`뿐 아니라 `명의자 본인 명의의 신분증`·`원본 신분증` 등 지원하는 서류 수식어도 소유 표현으로 구분한다. 근거가 없거나 다른 업무·방문자이거나 여러 후보로 모호하면 해당 생성 문장을 제거한다.
- 원문 복원은 신분증 지참·매장 방문·명의자·대리인·위임장 조건과 미접수 상태를 유지하며, 답변 저장과 고객 전송 전에 수행한다. 이후 기존 금액·개인정보 검사를 그대로 적용한다.
- 상담 종료 요약은 검사 후 저장된 답변을 사용한다. 과거 저장 답변과 종료 요약은 소급 변경하지 않는다. 이 검사는 지정된 준비물 표현과 범위 대조에 대한 보완이며 모든 표현·사실 오류를 판정하는 기능은 아니다.
- 이 보완은 백엔드 내부 근거 전달과 답변 검사에만 적용한다. 고객 응답 필드·프론트 계약·저장 스키마는 변경하지 않으며 모델 호출을 추가하지 않는다.

## 요약 모델 선택과 실패 처리

- 기본값 `chat.end-summary.model.provider=ollama`는 `ollama.url`의 전용 엑사원을 호출한다. AWS 인증이나 베드락 런타임을 만들지 않으며, `llm.provider`·`llm.model`을 변경해도 요약 모델은 유지된다. 엑사원 모델·연결·읽기·문맥 설정은 기존 `fallback-*` 설정을 함께 사용한다.
- 요약이 활성화되고 `chat.end-summary.model.provider=bedrock`이면 `openai.gpt-oss-120b-1:0`을 사용한다. 기본 지역은 미국 동부, 추론 수준은 `low`, 호출 전체 제한은 8초다.
- 베드락 선택 시 요약 전용 런타임은 연결 수 2개와 연결 대기 1초를 사용한다. SDK 자동 재시도는 끄며, 요약이 꺼져 있거나 `ollama`·`primary`를 선택하면 전용 베드락 런타임 생성을 생략한다.
- 베드락의 정상 종료 사유 `end_turn`과 비어 있지 않은 본문을 확인한 후 JSON을 검사한다. 출력 한도 도달·보안 차단·알 수 없는 사유·빈 응답은 성공으로 저장하지 않는다. 이 엄격한 종료 검사는 요약 전용 연결에만 적용한다.
- 베드락 호출의 SDK 시간 초과·모델 처리 시간 초과 응답 `408`, 모델 HTTP 전송 중 확인된 접속 거부·이름 조회 실패·연결 끊김, 응답 상태 `429`, `500`, `502`, `503`, `504`일 때 엑사원 `exaone3.5:7.8b`를 한 번 호출한다. 부분 요약의 모델 호출마다 적용하며 대체 모델 실패 후 같은 호출을 재반복하지 않는다.
- 모델 HTTP 전송 단계와 정상 응답 본문을 읽는 단계에만 통신 장애 표식을 붙인다. 인증 정보 조회 중 통신 실패가 발생해도 이 표식은 붙이지 않는다. 인증·권한 오류 응답의 본문이 끊겨도 대체하지 않는다. SDK의 일반 연결 실패 코드만으로는 대체하지 않으며, 인증서·알 수 없는 입출력 오류도 일시 장애로 추측하지 않는다.
- 인증·권한·입력 오류, 일시 오류로 분류하지 않은 서버 응답, 출력 잘림, 보안 차단, 잘못된 JSON·문의 번호·출처, 개인정보 검사 실패는 대체 호출로 우회하지 않는다. `429` 요청 제한과 일반 `400` 입력 오류를 구분하며 후자는 대체하지 않는다. 엑사원도 실패하면 다시 베드락으로 돌아가거나 반복하지 않는다.
- 기존 공개 오류 코드와 기본 모델·판정기의 연결 및 대체 정책은 유지한다. 배포 환경에서도 `ollama.url`의 엑사원 모델이 실행 중이어야 하며 베드락·엑사원이 모두 불가하면 요약 실패를 저장한다.
- 주 호출 전에는 베드락 호출 예산, 대체 전에는 엑사원의 연결 5초·읽기 60초 예산이 작업 기한 안에 남아 있는지 확인한다. 중단된 작업은 새 호출을 시작하지 않으며 기존 기한·작업 소유권·저장 전 검사를 유지한다.
- 엑사원의 출력 스키마와 공통 프롬프트는 그대로 유지한다. 모델 선택 단계의 잘못된 후보 재요청과 시간 초과 대체는 별도 경로이며 전체 구간 수·입력·출력·작업 기한 한도를 넘기지 않는다.
- 실제 호출 모델·공급자·성공 또는 시간 초과를 기존 `llm_generations`에 기록한다. 대체 호출은 두 번째 시도로 기록한다. 자격 증명이나 상담 원문을 새 진단 로그에 남기지 않는다.
- `chat.end-summary.model.provider=primary`는 종료 요약을 기존 기본 모델 연결로 되돌리는 설정이다. 기존 저장 요약을 다시 만들거나 다른 기능의 모델을 바꾸지 않는다.

## 문의별 구성과 남은 사항

- 저장된 요청 의도와 답변에 연결된 FAQ 카테고리 10종을 문의 키·제목에 우선 사용한다. 근거와 현재 FAQ의 버전이 다르면 현재 분류를 과거 상담에 적용하지 않는다.
- 분류 정보가 없는 과거 기록도 동일한 단일 요청의 여러 안내는 묶는다. 서로 다른 원래 질문·사람·회선은 분류가 같다는 이유로 합치지 않으며, 복수 요청이나 카테고리가 모호하면 분리한다.
- 같은 문의의 이어묻기는 대상·회선·상품과 질문 연결을 확인해 한 묶음으로 만든다. 다른 사람·회선·문의는 구분하며, 모호한 연결은 억지로 합치지 않는다.
- 유심 외 분야도 `같은 문의`·`그 안내`·`앞서` 등 명시적인 참조와 같은 분야·사람·회선·업무가 확인되면 연결한다. 후보가 여럿이면 최근 문의에 임의로 붙이지 않는다. 단순히 분야가 같거나 비용·조건이라는 단어가 있다는 이유만으로 합치지 않으며, 요금제 추천과 변경·납부와 환불 등 지원하는 서로 다른 업무를 구분한다.
- `가입 기간을 정정할게요. 18개월이 아니라 24개월입니다`처럼 대상과 값이 문장·줄바꿈으로 나뉘어도 두 원문을 함께 보존한다. 같은 대상·회선·기간 종류의 확정된 정정은 이전 기간 인용을 대체하며, 이미 흡수한 과거 기간을 요약 제목 목록에 다시 추가하지 않는다. 정정 질문은 확정 사실로 바꾸지 않고 다른 사람·회선·약정 기간을 함께 지우지 않는다.
- 기간 인용에서 생략한 대상·회선은 원래 사용자 발언에서 확인한다. 기간 문장에 직접 명시한 대상은 다른 문장에 나오는 양도 상대방보다 우선한다. 가입 기간과 약정 기간이 같은 발언에 있어도 정정한 종류만 대체하며, 여러 대상 중 누구인지 불명확하면 임의로 축소하지 않는다.
- 가족·형·동료를 나타내는 대상 표현도 본인 문의와 구분한다. 문의 문단과 유심 제목에 같은 대상 판정을 사용하며, 여러 대상 뒤의 모호한 지시어를 최근 문의에 임의 연결하지 않는다. `그럼 형`처럼 연결어 뒤의 호칭은 원문 단어 경계로 확인한다. `유형`·`선택형`·`신형`·`가족 결합`·`가족 할인` 같은 상품 표현은 사람 호칭으로 오인하지 않는다. 모든 호칭이나 개별 인물을 식별하는 기능은 아니다.
- `다른 가족`·`다른 형`·`다른 동료`처럼 명시적인 대상 전환은 같은 호칭이라도 분리한다. `큰형`·`작은형`·`친형`·`사촌형`은 관계 표현을 문단과 제목에 보존한다. 이후 여러 사람 중 누구인지 모호한 지시어는 임의로 연결하지 않는다.
- 명시적 소유 표현과 방문·준비물 조건은 공통 대상 판정으로 구분하며, 문단 연결과 제목에 같은 기준을 적용한다. `내 실물 유심`·`저의 분실 유심`·`나의 물리 유심`처럼 소유격과 대상 사이에 수식어가 있어도 본인 문의로 구분한다. `내 가족`·`제 형`·`저의 동료`는 명시한 가족·형·동료의 문의로 유지한다.
- 같은 유심의 `본인 신분증`·`본인 확인`·`본인 방문`과 `본인이 매장에 방문` 등 지원하는 준비물·방문자 조건은 소유자 변경으로 해석하지 않는다. 소유격 표현은 대상 명사를 확인하고, 주어 표현은 직접 이어지는 대상 명사구와 방문·준비물 조건을 구분한다. 모든 자유로운 문장을 해석하는 기능은 아니다.
- 접속 조사·쉼표·가운뎃점으로 함께 명시한 대상은 제목에 언급 순서대로 보존한다. 예를 들어 `큰형과 작은형`은 `큰형·작은형 유심 재발급`으로 표시한다. 같은 대상 집합을 다시 명시하면 순서가 바뀌어도 한 문의로 묶지만, 일부 사람이나 모호한 지시어로 되물으면 공통 안내를 그 사람의 안내로 임의 연결하지 않는다. 원답변이 여러 사람 중 일부에게만 답한 경우까지 보완하는 기능은 아니다.
- 같은 문장의 중복 제거는 같은 문의 안에서만 한다. 다른 대상에게 같은 비용을 안내했다면 각 대상 문단에 보존한다. 문맥에 필요한 지시어·조건 문장은 유지한다.
- 제목은 실제 문의에서 만들고, 안내 앞의 중간 처리 표식은 최종 본문에서 제거한다. 일부 방문 요청 표현은 기록형으로 바꾸지만 안내 전체를 AI로 다시 쓰지는 않는다.
- 가입 기간은 비용·무료 조건의 이유로 임의 연결하지 않는다. 가족·회선의 주체나 정정 관계가 명확하지 않으면 해당 기간 발화를 인용한다.
- 이전 안내를 대체하는 처리는 요금제·요금/청구 분류에서 명시적인 이전 안내 철회가 확인되는 경로에 적용한다. 모든 주제의 정정을 자동 해결한다고 보장하지 않는다.
- 최종 원문 복원은 대화와 원문 문단 순서를 따른다. 모델의 선택 순서 때문에 최신 정정이 과거 안내보다 먼저 처리되지 않도록 한다. 따로 나뉜 조건 응답은 저장된 조건 연결이 있을 때만 원래 문의로 복원한다.
- 남은 사항은 `ChatEndSummaryPendingResolver`가 미확인 조건·답변 근거·실행 상태에서 만든다. 지역 미확인과 본인·대리인 미확인은 별도로 보존한다. 필수 확인 항목을 화면에서 8개로 자르지 않는다.
- `ChatEndSummaryResolution`이 같은 하위 요청의 되묻기·사용자 응답·최종 답변을 저장된 조건 연결로 확인한다. 입력 준비와 최종 남은 사항 구성에서 동일한 판정을 사용한다.
- 요청이 `DONE`이고 미확인·거절 조건이 없으며 연결된 사용자 응답에 최종 `GROUNDED` 답변이 있으면 해결된 되묻기를 제외한다. 원래 질문에 직접 달린 답변뿐 아니라 조건 응답 뒤의 답변도 사용한다. 답변 뒤에 추가 되묻기나 근거 없음 안내가 있으면 완료 표시만으로 제외하지 않는다.
- 매장 결과는 일반 답변과 달리 근거 표시가 비어 있을 수 있다. 같은 조건 응답 뒤의 `STORE_RESULT`와 실제 저장된 매장 목록이 확인되면 정상 안내로 인정한다. 목록이 비어 있거나 검색 실패 안내만 있으면 해결 처리하지 않는다. 저장된 근거 표시와 고객용 응답 필드는 바꾸지 않는다.
- 상담 요청이 없는 주제 확인은 바로 이어진 유효 사용자 질문이 같은 주제·대상·회선 범위로 구체화되고 정상 답변까지 완료된 경우에만 제외한다. 일반적인 요금 확인은 요금제·청구 안내로 구체화할 수 있다. 다른 문의를 건너뛰어 뒤의 답변을 연결하거나 주제가 불분명한 확인 요청까지 일괄 해소하지 않는다.
- 같은 일반 주제를 여러 번 되묻는 경우에는 저장된 요청·조건 상태가 없는 중간 주제 확인만 순서대로 따라가 최종 상담 상태를 확인한다. `요금이요`와 `요금 알려줘`처럼 지원하는 동일 주제 표현도 연결한다. 중간에 다른 문의·대상·회선이나 주제 외의 확인 질문이 있으면 연결을 중단한다.
- 지원하는 별칭·구체화는 `가입 → 신규 가입`, `개통 → 신규 개통`, `휴대폰·핸드폰·단말·단말기·기기`, `청구·청구서`, `eSIM·이심`이다. 문장 전체가 일반 주제일 때만 중간 확인을 연결한다. 신규 조건을 일반 가입으로 넓히거나 납부·청구, 할부·기기, 부가서비스·멤버십을 같은 업무로 묶지 않는다. 명시한 신규 조건은 최종 구체화 질문에도 유지되어야 한다.
- 중간 발화에 연결된 실제 요청·조건은 주제 확인이라는 이유로 건너뛰지 않는다. 실행 실패·취소, 최종 미완료 요청, 검색 실패와 미확인 조건은 기존 해결 판정에서 그대로 보존한다. 한 주제의 반복 확인이 해결돼도 별도 매장 문의의 지역 조건은 유지한다.
- 이 예외는 구체적인 조건이 없는 일반 주제 질문에만 적용한다. 재발급 비용과 준비물, 변경 횟수와 적용 시점처럼 대분류가 같아도 세부 질문이 다르면 대신 해결 처리하지 않는다. 부모님·친구 등 다른 대상 표현도 구분하며, 원래 질문 뒤에 저장된 확인 요청만 연결한다.
- 일반 주제는 FAQ 카테고리 10종과 매장을 대상으로 한다. `번호이동 알려줘`, `가입 문의드려요`, `요금이요` 등의 표현을 지원하며, 구체화한 질문의 저장 의도·유효한 버전의 FAQ 분류를 사용한다. 문장 전체가 지원하는 주제 표현과 일치해야 하며 모든 자유로운 표현을 지원한다는 뜻은 아니다.
- 청구서·납부·할부·멤버십·부가서비스처럼 한 카테고리 안에서도 범위가 나뉘는 주제는 후속 질문의 대상 표현도 확인한다. 예를 들어 멤버십 문의를 매장 영업시간 안내로, 청구서 문의를 요금제 변경 시점 안내로 해결하지 않는다. `말고`·`대신`·`아니라`로 주제를 명시적으로 바꾼 발화도 자동 해결에서 제외한다.
- 주제 확인 문구는 `ChatTopicClarification`에서 생성과 요약 인식이 함께 사용한다. 문구 일부의 일치나 사용자 인용만으로 주제 확인으로 분류하지 않는다.
- 같은 조건의 재질문은 현재 저장된 질문·응답 연결을 사용한다. 하위 문의 번호가 없는 과거 복합 기록이나 연결이 누락·모호한 기록은 다른 문의의 답변으로 해결 처리하지 않는다. 유실된 과거 연결 전체를 복원하는 기능은 아니다.
- 지역 확인 중 취소된 단일 매장 요청은 바로 다음 단일 요청이 같은 저장 의도와 검색 문의로 재시작돼 완료된 경우에만 요약상 해결로 연결한다. 요청의 취소 상태를 데이터베이스에서 변경하지 않으며, 고객용 응답 구조도 바꾸지 않는다.
- 이전 지역 확인 메시지의 연결과 이후 조건 응답·실제 매장 목록을 확인한다. 이미 확인한 업무·방문자 조건이 달라지거나 이전 조건을 새 요청에서 확인하지 않았다면 제외하지 않는다. 목록이 없거나 검색에 실패한 경우, 다른 사람·회선·업무, 명시적 중단, 중간에 끼어든 별도 문의도 이전 요청의 해결로 쓰지 않는다.
- 이 매장 예외는 바로 다음 요청의 정상 완료에 한정한다. 여러 취소 요청을 건너뛰거나 검색 문의가 달라진 기록을 추측해 연결하지 않으며, 취소된 모든 요청을 일괄 해결하지 않는다.
- 복합 문의는 미해결 하위 요청과 조건을 유지한다. 조건 응답에 새 문의가 함께 있으면 그 요청도 별도로 판단한다. 단답형 응답을 단어만 보고 숨기지 않는다.
- 같은 사용자 응답을 여러 하위 요청이 공유하면 통합 `GROUNDED` 상태만으로 모두 해결됐다고 판단하지 않는다. 개별 답변 연결이 불명확하면 답변 상태 확인 대상으로 남길 수 있다.
- 연결된 조건 응답 뒤 검색 실패·범위 밖 안내가 나오면 원래 문의의 미답변·범위 밖 사유로 남긴다. 원래 문의가 확인된 단답형 응답을 별도 미해결 문의로 중복 표시하지 않는다.
- 답변 실패·취소와 미확인 조건이 함께 있으면 중단 사유와 조건을 함께 남길 수 있다. 다른 문의·사람·회선·세션의 답변으로 미해결 항목을 제거하지 않는다.
- `DONE`, `COMPLETED`, 상담 종료는 신청 접수·업무 처리 완료의 근거가 아니다. `WAITING_RESPONSE`도 신청 처리 대기를 뜻하지 않는다.

| `remaining.kind` | 의미 |
| --- | --- |
| `NEEDS_CONFIRMATION` | 지역·방문자 등 추가 확인이 남음 |
| `UNANSWERED` | 근거 있는 답변을 확인하지 못함 |
| `OUT_OF_SCOPE` | 상담 범위에 해당하는 안내를 받지 못함 |
| `INTERRUPTED` | 답변 실행이 실패·취소되어 마치지 못함 |
| `WAITING_RESPONSE` | 답변 완료 여부를 확인하지 못함 |

## 긴 대화와 작업 한도

- 짧은 상담은 한 번에 처리하고, 긴 상담은 질문·답변 묶음을 나눠 각 선택 결과를 검증하고 서버에서 원본 연결을 병합한다.
- 모델에 전달하는 안내 구간은 최대 480자, 한 호출에서 제공·선택하는 번호는 최대 8개다. 문단이 길면 문장·공백 경계를 우선해 나누고, 더 긴 단일 문장도 문자 경계를 보존해 나눈다. 원문을 잘라 버리거나 새로 쓰지 않는다.
- 한 질문·답변의 안내만으로 입력·개수 한도를 넘으면 같은 문의와 출처를 유지한 채 여러 호출로 나눈다. 각 호출의 3072 추정 입력 토큰·출력 768 예산은 유지한다.
- 최종 단계에서는 검증된 선택과 마지막 답변 출처를 사용해 원래 문단 전체를 복원한다. 최종 고객용 문단을 480자로 자르지 않는다. 같은 문의는 후속 단계에서 한 문단으로 묶는다.
- 전체 보존 대상은 고유 원문 문단 64개·원문 합산 32,768자까지다. 상한 초과는 모델 호출 전에 `WORK_LIMIT`으로 종료하며 일부 안내를 전체 상담 요약으로 제공하지 않는다. 같은 원문이 여러 대상에 연결돼 최종 문의 문단 수가 늘어나는 경우와 구분한다.
- 부분 결과는 개수·입력 길이에 관계없이 검증된 원문·출처를 서버에서 합친다. 병합을 위한 모델 호출이나 안내 재선택을 하지 않아 병합 입력 초과와 재선택 누락을 피한다. 전체 상태·출처·개인정보를 다시 검사하며 호출별 선택 8개와 최종 원문 한도는 유지한다.
- 단일 묶음·구간 수·입력·작업 기한을 넘으면 일부를 전체 상담 요약처럼 제공하지 않는다. 원래 답변 실행을 요약 작업이 강제로 종료하지 않는다.
- 모델 호출 중 DB 잠금과 트랜잭션을 유지하지 않는다. 세션당 요청 행은 하나이며 소유권이 바뀐 작업의 늦은 결과는 저장하지 않는다.
- 이벤트 유실·큐 포화·작업 중단은 DB 주기 점검으로 회복한다. 실행기는 1개 스레드와 대기 20개를 사용하고 같은 세션의 중복 제출을 방지한다. 외부 모델 호출까지 정확히 한 번을 보장하지는 않는다.

## API

### 종료

`PATCH /api/v1/chat/sessions/{sessionId}/close`

- 기존 인증·게스트 쿠키·소유권 검사, 200 응답과 `CLOSED` 상태를 유지한다. 종료 성공은 요약 생성 완료를 뜻하지 않는다.
- 반복 종료는 새 작업을 만들거나 완료 결과를 초기화하지 않는다. 요청 기록이 없는 과거 상담을 소급 생성하지 않는다.

### 조회

`GET /api/v1/chat/sessions/{sessionId}/summary`

- 본인 상담만 조회한다. 로그인 승계는 현재 세션 소유권으로 판단한다.
- 정상 조회는 200, `CustomResponse.result`, `Cache-Control: no-store`를 사용한다. 다른 사용자·없는 상담은 기존 상담 조회 오류 계약을 따른다.
- 조회는 새 모델 호출·재시도·상담 변경을 하지 않는다. 새로고침·재접속에서도 저장 결과를 읽는다.

| 응답 필드 | 의미 |
| --- | --- |
| `sessionId` | 대상 상담 |
| `sessionStatus` | 현재 상담 상태 |
| `summaryStatus` | 아래 생성 상태 |
| `summary` | 완료 시 아래 5개 필드를 가진 객체. 미완료는 null |
| `generatedAt` | 검증된 결과 저장 시각. 미완료는 null |
| `message` | 상태 안내 |

| `summary` 필드 | 구조와 의미 |
| --- | --- |
| `topics` | 기존 주요 문의 문자열 배열 |
| `guidance` | 기존 안내 문자열 배열 |
| `pendingItems` | 기존 남은 사항 문자열 배열 |
| `inquiries` | 문의별 `{title, text}` 배열. 같은 문의로 묶은 답변 본문 |
| `remaining` | 남은 사항별 `{title, text, kind}` 배열 |

`CustomResponse.result.summary` 형식 예시다. 설명용 합성 문구이며 실제 실행 결과나 요금 정책을 나타내지 않는다.

```json
{
  "topics": ["유심 재발급", "방문 매장 위치"],
  "guidance": ["신분증을 지참해 매장을 방문하는 절차를 안내받았습니다."],
  "pendingItems": ["매장 안내를 위한 방문 지역은 아직 확인되지 않았습니다."],
  "inquiries": [
    {"title": "유심 재발급", "text": "신분증을 지참해 매장을 방문하는 절차를 안내받았습니다."}
  ],
  "remaining": [
    {"title": "방문 매장 위치", "text": "매장 안내를 위한 방문 지역은 아직 확인되지 않았습니다.", "kind": "NEEDS_CONFIRMATION"}
  ]
}
```

| 생성 상태 | 의미 |
| --- | --- |
| `NOT_REQUESTED` | 요청 기록 없음 또는 기능 비활성 |
| `PENDING` | 답변 처리 종료 또는 작업 순서 대기 |
| `GENERATING` | 요약 생성 중 |
| `COMPLETED` | 검증된 결과 저장 |
| `EMPTY` | 요약할 상담 내용 없음 |
| `FAILED` | 생성·검증·작업 한도 실패 |

### 프론트 담당자와 맞출 표시 계약

- 제안 화면은 상담 요약 카드 하나 안에 ‘문의 내용 및 답변’과 ‘남은 사항’을 둔다. `inquiries` 항목별로 제목·본문을 표시하고, `remaining`이 없으면 해당 영역을 숨긴다. 이번 문서 정리는 프론트 구현 변경이 아니다.
- 이전 저장 결과는 재생성하지 않는다. 제목·상태 메타데이터가 없는 과거 결과는 기존 문자열 배열에 내용이 있어도 `inquiries`·`remaining`이 비어 있을 수 있다. 기존 배열을 표시하는 대체 처리가 필요하며, 새 배열이 비었다고 내용 없음으로 판단하지 않는다.
- 남은 사항이 없다는 이유로 `모두 해결됨`이나 `신청 완료`를 추가하지 않는다. 조회 실패·화면 대기 종료도 빈 상담이나 서버 생성 실패로 단정하지 않는다.
- 준비 중에만 정기 조회하고 완료·빈 상담·실패에서 멈추는 표시를 협의한다. 과거 로컬 검증 화면의 조회 주기를 운영 프론트 계약으로 고정하지 않는다.

## 저장과 설정

- 기존 `chat_session_end_summaries`에 원본 연결·작업 소유권·실패 상태·시각과 결과를 저장한다. 부모 세션으로 소유권을 확인하며 사용자·게스트 ID를 중복 저장하지 않는다.
- 저장 JSON의 최상위는 기존 `topics`, `guidance`, `pendingItems`를 유지한다. 문의별 안내에 `title`, 남은 사항에 `title`·`kind`를 함께 저장해 조회 DTO를 구성한다. 내부 출처 번호는 고객용 본문으로 노출하지 않는다.
- 기존 `V31__add_chat_session_end_summary.sql`로 마련된 저장 구조를 사용한다. 되묻기 해결 판정은 기존 `consult_conditions`의 `asked_message_id`·`answered_message_id`를 조회한다. 새 테이블·Flyway 마이그레이션과 고객용 응답 필드 변경은 없다.
- 내부 문맥 요약·기존 채팅 메시지·질문 통계에 새 요약 메시지를 추가하지 않는다. 기존 마이그레이션 적용 후 기능 설정을 활성화한다.

종료 요약만 사용하기 위해 판정기의 `llm.bedrock.enabled`를 함께 바꿀 필요는 없다.
엑사원 기본 호출과 베드락 장애 시 대체 호출은 기존 `ollama.url`을 사용하고 모델·시간 제한·문맥 크기는 위 요약 전용 설정을 사용한다.

토큰 계산은 시스템·사용자 프롬프트의 추정치이며 모델의 실제 토큰 수나 최대 문맥 길이와 다르다.
3072는 서비스가 정한 호출별 입력 예산이다. 모델 변경만으로 이 제한이 해제되지는 않는다.
실제 실행 문맥에서 출력 예산·추가 오버헤드와 여유를 확보하고, 메모리·지연을 측정한 뒤 조정한다.
모델 호출 재시도·선택 번호 재요청·작업 회복 횟수는 서로 별개다.

## 생성 실패와 검증 범위

### 기간 정정·문의 연결 보완의 범위 분리 후 로컬 검증

- 저장 전 유사도·추가 핵심 조건 검사와 임베딩 재시도 연결을 후속 작업으로 분리한 상태에서 검증했다. 해당 기능의 원본·테스트·기존 비교 결과는 별도로 보존한다. 이 단계의 기본 생성 모델은 엑사원이다.

## 계약과 최소 보완

기존 BE 저장·소유권·이력 커서·runningExecutionId·근거 API를 재사용했다. 상담 조건은 DB에서만 판단한다. FE는 대화 문구를 해석해 조건을 만들거나 상담 완료를 저장하지 않는다.

- 브라우저에는 백엔드 주소별 세션 ID만 보관한다. 메시지·상담 조건·회원/게스트 식별자는 저장하지 않는다. 페이지 재접속 시 기존 쿠키로 이력을 다시 조회해 권한을 확인한다. 기억한 ID는 접근 권한이 아니다.
- 이력 커서를 따라 전체 기록을 가져오고 messageId로 중복을 제거하며 sequenceNo 순서로 표시한다. 서버에서 읽은 내용으로 교체하며 모델 생성 중 내용 null을 완료 답변으로 표시하지 않는다.
- runningExecutionId가 있으면 기존 GET 이력을 완료·실패까지 다시 조회한다. 페이지 복원·온라인 복구 시 POST나 입력 재전송을 하지 않는다. 오류 시 전송을 막고 이력 재조회/새 상담을 제공한다. 접근 실패 시 이전 표시 기록도 비운다.
- 완료 답변의 근거는 기존 `/api/v1/chat/messages/{messageId}/sources`로 다시 읽는다. 오류·취소·타임아웃 상태는 완료 답변과 구분한다. 프런트 3분 조회 제한은 서버 취소를 의미하지 않는다.
- 기존 105의 설명은 ANSWER이고 기존 PENDING 질문은 그대로다. 프런트가 마지막 메시지 타입으로 대기 질문을 새로 정하지 않는다. 다음 입력은 서버의 기존 상담·조건에 반영된다.

실제 화면에서 발견된 것은 FE 세션 ID 소실·복원 시 실행 중 결과 추적 누락·저장 근거 미조회다. FE 해당 경로만 보완했다. BE 기능·API/SSE 형식·Guard·Router·모델·검색·프롬프트·평가·스키마는 변경하지 않았다. 기존 데모 ID는 검사 도구의 purity 오류를 피하도록 이벤트 안의 증가 카운터로 생성한다. 데모 응답은 계속 별도다.

## 시나리오별 기대와 실제 결과

브라우저의 실제 페이지 reload를 사용했다. 화면 안의 ‘이력 새로고침’ 버튼으로 대체하지 않았다. 합성 질문만 입력하고 화면·서버 저장·실행 trace·조건을 대조했다.

| 사례 | 기대 | 실제 결과·식별자 |
| --- | --- | --- |
| A 첫 되묻기 후 reload | 같은 세션·가입월 질문, 후속 입력으로 다음 조건 | 세션 761/상담 565, 실행 1252/질문 2608 보존. 지난달 입력 후 같은 상담에서 변경 이력 질문 |
| B 조건 하나 후 reload | 가입월 값·변경 이력 대기 유지, 아니요 후 완료 | 실행 1253/질문 2610, 가입월 아니요 유지. 실행 1254에서 두 값 아니요·DONE, 최종 2612 |
| C 설명 후 reload | 설명 복원·원래 질문에 후속 입력 | 세션 762/상담 566, 설명 실행 1256/메시지 2616 복원. 응답 2617은 질문 2614에 저장됨. 설명을 질문으로 사용하지 않고 변경 이력 질문 2618로 진행 |
| D 최종 답변 후 reload | 같은 답변·FAQ 한 번 표시, 로딩 종료 | 메시지 2612의 본문 동일, FAQ 357/1387/1462 동일. DB 답변 1건, 화면도 1건. 검증 전 생성문을 표시하지 않음 |
| E 접수 후 페이지 이탈·재접속 | 기존 실행 복원, 자동 재전송 없음 | 세션 763/실행 1259/입력 2621/최종 2622. 시작 09:14:33.352401 UTC < 이탈 09:14:33.367 UTC < 완료 09:14:36.478990 UTC. RUNNING 관찰 후 완료 복원, 로딩 종료 |

E의 첫 타이밍 시도는 이탈 전에 이미 완료돼 RUNNING 검증으로 세지 않았다. 동일 질문을 **수동으로 한 번 더 전송**해 이탈 시점의 RUNNING을 확인했다. 따라서 세션 763에는 두 수동 입력·실행·답변이 있으며 각각 한 번 표시된다. 세 번째 자동 실행·답변은 없다. 실제 네트워크/Wi-Fi 자체를 끈 시험은 아니며 페이지 이탈로 해당 페이지 연결을 종료한 시험이다.

FAQ 357(BILLING-0001)은 월 1회·가입월 변경 불가·다음 달부터 가능, 1387(BILLING-0015)은 월 1회·가입월 변경 불가, 1462(BILLING-0106)은 월 1회·이번 달 이미 변경한 경우 다음 달·가입월 제한을 명시한다. 각 실행의 실제 검색 결과·순서·점수는 공유 JSON에 별도로 보존했다. 서로 다른 실행의 FAQ를 동일 근거로 섞지 않는다.

## 자동 검증과 재사용

BE 전용 JDK21/PostgreSQL/PostGIS/pgvector 전체 build: **1,498건 중 통과 1,496건, 실패·오류 0건, 평가 프로브 스킵 2건**. 활성 Chat 통합은 기존 68건에 복원 요청·조건 불변·설명 연결·최종 이력·타인 접근 거절 사례 1건을 더한 69건이다. 이 검증은 모델/검색 대체이며 실제 모델 브라우저 사례와 구분한다.

TELME-92/93의 Guard 검증 후 전송, 정상/수정/안전 안내 저장·조회 동일성, 생성 중 내용 null, 실패·타임아웃·취소, 중복 완료, 저장 후 전송 실패, 종료 실행 SSE 재구독 회귀를 재사용했다. 98·104·105의 후속 입력·정정·조건 동시 입력·설명 후 상담 재개도 같은 전체 실행에 포함한다. 기존 선택/전체 수치를 합산하지 않는다.

FE `check:chat`: lint·TypeScript·production build 성공, 기존 응답 5건 + 복원 6건 = **11건 통과, 실패 0건**. 복원 단위 검증은 저장 포인터/오염값·커서/중복·RUNNING→완료·실패 종료·네트워크/소유권 오류·취소/손상 커서를 다룬다. PR 비교 기준 브랜치에서도 CI가 실행되도록 FE 워크플로와 BE의 105 대상 필터를 준비했다. 최신 게시 HEAD CI 결과는 해당 PR 체크에서 확인한다.

## 남은 범위

- 팀 실제 채팅 화면이 아직 없어 팀 develop 화면의 복원·표시는 미검증이다. 이 PR은 기존 테스트 화면에서 확인한 범위다.
- 브라우저 SSE 소비·완료 이벤트→기록 조회·EventSource 종료는 미검증이다. BE SSE 자동 회귀 통과와 동일시하지 않는다. 팀 화면은 92/93의 기존 계약을 연결해야 한다.
- 물리적 오프라인 복구, 3분 UI 조회 타임아웃, 실제 실패 실행의 재접속 화면은 미검증이다. 실패 상태와 자동 재전송 금지는 자동 테스트로 확인했다.
- 로그인 전환/쿠키 상실/서버 재시작 후 게스트 접근은 별도 환경 검증이 필요하다. 세션 포인터 보존만으로 인증 복구를 주장하지 않는다. 상담 조건은 서버 DB에 남아도 게스트 HttpSession이 사라지면 기존 권한 없이 접근할 수 없다.
- 상담 목록은 여전히 메모리 목록이며 전체 서버 상담 목록 UI를 새로 만들지 않았다. 현재 선택한 API 세션의 복원을 보완한 범위다.
- 모델 품질·전체 환각률 개선은 측정하지 않았다. 화면 복원 성공을 해당 지표로 표현하지 않는다.

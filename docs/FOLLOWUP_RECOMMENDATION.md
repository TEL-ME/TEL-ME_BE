# 후속 질문 추천 설계와 오프라인 검증

## 1. 배경

답변 아래에 "다음에 물어볼 만한 질문" 버튼을 띄운다. 버튼을 누르면 그 문장이 질문으로 그대로 전송된다.

구현 시작 당시 develop(`45c152d`) 기준 상태는 다음과 같았다. 이후 구현 결과는 12절에 정리한다.

| 구분 | 상태 | 위치 |
| --- | --- | --- |
| 저장 칸 | 있음 | `chat_messages.follow_ups` (JSONB) |
| 답변 객체 필드·저장 | 있음 | `ChatAnswer.followUps`, `ChatExecutionService` |
| 대화 이력 API 노출 | 있음 | `ChatMessageHistoryItemResponse.followUps` |
| 정상 답변의 추천 생성 | **없음** | `RagSearchResultAnswerGenerator`가 항상 빈 목록 |
| 답변 완료 SSE 이벤트 | **없음** | `ChatOutputMessage`에 필드 없음 |
| 고정 추천 | 3곳 | 의도 파악 실패·복합 질문 → `요금제 알려줘`/`가까운 매장 찾아줘`, 매장 요청 → `고객센터 연결` |

이 문서는 추천을 **어떻게 고를지**를 오프라인 실험으로 비교하고, 채택한 방식과 그 근거, 구현 결과를 남긴다.

## 2. 요약

- **정상 답변 추천은 "정책 연결표 + 정책별 대표 질문"으로 만든다.** 처음 보는 FAQ 50개씩 세 라운드에서 독립 채점 기준 새정보 비율 **84.7%**(2차 연결표, 61/72), **82.9%**(3차, 58/70), **92.5%**(채택안 4차, 62/67), 중복 0 ~ 1건이다(7절)
- 위 수치는 **추천 단계만** 잰 것이다. 사용자 질문 자리에 FAQ 질문을 넣어 검색이 맞는 FAQ를 찾았다고 가정했다. 실제 사용자 말투 질문(선택용 180)으로 검색 단계를 따로 재면, 답변 가능 110문항 중 67개가 검색을 통과하고 통과한 67개 모두 1위 FAQ의 정책이 정답 정책이었다(7.1절)
- **노출 범위(상한)**: 검색·연결표만 적용한 정책 칩 노출 상한은 답변 가능 질문의 44.5%(49/110)다. 라우팅과 `GROUNDED` 판정까지 적용하면 실제 노출률은 이보다 낮아질 수 있다. 이전 두 독립 라운드의 보수적인 정밀도 약 83%를 적용하면 좋은 정책 칩의 상한은 약 37%(41/110)다(채택안 4차의 92.5%는 쓰지 않았다, 매장 칩 별도). 정확도를 위해 추천이 없는 답변을 허용한 결과다
- **실제 채팅 경로 확인 완료**(7.2절): 대표 질문 32개 모두 누르면 자기 FAQ로 답한다(처음 29/32, 매장 찾기로 빠지거나 LLM이 답하지 않던 3개를 교체). 표본 20건에서 앱 결과가 검증한 추천과 모두 같았고, 생성 답변 기준 1차 판정은 16건 중 적합 14건이다. 4차 연결표 독립 검증도 통과했다
- **실행 조건**: 답변이 `GROUNDED`이고 검색 1순위 FAQ에 연결표에 있는 정책 ID가 있을 때만 만든다. 연결표 추천은 최대 2개다. 매장 칩 플래그를 켜면 기준 FAQ 답변이 매장을 언급할 때 매장 칩을 첫 번째에 놓아 전체 최대 3개가 된다(8절, 10절)
- **채택안인 4차 연결표는 새 기준 FAQ 50개 독립 검증을 통과했다**(62/67 = 92.5%, 중복 1건). 기능 플래그 기본값은 꺼져 있고, 켜는 결정만 남았다(12.1절)
- **LLM은 쓰지 않는다.** 직접 생성하면 버튼 72%가 FAQ에 없는 질문이고(5.4절), 로컬 7.8B 판정은 좋고 나쁜 버튼을 구분하지 못한다(9절)
- 같은 정책 안에서 고르면 **중복 62%**다. 같은 정책 FAQ는 같은 사실을 묻는 방식만 바꾼 것이라, 새 정보는 다른 정책에 있다(5.2절)
- 일관된 약점은 **문제 상황(TROUBLE) 질문**이다(약 68%). 이 유형은 같은 업무의 다음 단계 버튼만 남긴다(8절)
- 칩은 항상 **실제 FAQ 질문**으로 만든다. 없는 내용을 지어내지 않는다. 대표 질문 32개는 실제 채팅 경로에서 모두 자기 FAQ가 1위인 `GROUNDED` 답변으로 이어진다(7.2절)
- 고객센터 버튼은 최후순위로 둔다. 챗봇 안에서 먼저 유도한다(3절)

## 3. 범위

좋은 추천 버튼의 조건은 세 가지다.

1. **누르면 답이 나온다.** "안내드릴 수 있는 정보가 없습니다"로 끝나지 않는다
2. **이미 말한 내용이 아니다.** 방금 "3개월"이라고 답했는데 [번호이동 가능 기간]을 띄우지 않는다
3. **사용자 상황에 맞는다.** 번호이동 질문에 [로밍 요금]을 띄우지 않는다

| 상황 | 추천 | 상태 |
| --- | --- | --- |
| 정책 메타데이터가 있는 정상 FAQ 답변 (`GROUNDED`) | 이어서 물을 질문 최대 2개 (매장 칩이 붙으면 전체 최대 3개) | 구현 완료 (12.1절) |
| 위 답변 + 기준 FAQ에 "매장" 언급 | 매장 찾기 칩(업무 포함)을 먼저 배치 | 구현 완료 (10절, TELME-124), 기본 꺼짐 |
| 근거 없음, 비슷한 후보 있음 | "혹시 이런 내용을 찾으셨나요?" + 임계값 아래 FAQ 1개 (`Q_A` 0.60 이상) | 하한 측정 완료 (11.1절) |
| 넓은 질문 ("로밍 관련 질문 있어") | 검색 결과 없음과 같은 규칙 (FAQ 1개) | 측정 완료 (11.2절) |
| 의도 모름 | 카테고리 칩 | 설계 완료 (11절) |
| 직접 요청 또는 반복 실패 | 고객센터 | 최후순위 확정 |

## 4. 데이터 구조

FAQ 1,150건은 **정책 45개를 기준으로 질문 유형 5종과 페르소나 3종을 조합해** 생성했다(`FAQ_TAXONOMY.md`). 정책마다 생성된 FAQ 수는 13 ~ 33건이다. DB와 `faq_full_1150.json`은 `slot_id` 기준으로 1:1 일치한다.

- **정책(`policy_ref`)**: 사실 덩어리. 예: `PORTING-03` 번호이동 제한 조건(개통 3개월, 명의변경 1개월)
- **질문 유형**: FACT, PROCEDURE, CONDITION, TROUBLE, COMPARE
- **상황(`trigger`)**: 생성 시나리오. 예: 분실, 침수, 액정 파손, 기기변경 희망. 원본 JSON에만 있고 DB에는 없다

같은 정책의 FAQ는 **같은 사실을 묻는 방식만 바꾼 것**이다. 이 구조가 5절 결과의 열쇠다.

## 5. 정상 답변 추천 방식 비교

### 5.1 비교한 방식

| 방식 | 후보 선택 | LLM |
| --- | --- | --- |
| A | 같은 정책, 다른 질문 유형, 가장 짧은 질문 | 없음 |
| A′ | 같은 정책, 다른 질문 유형, 기준 FAQ와 질문 벡터가 가장 가까운 것 | 없음 |
| B | LLM(EXAONE 3.5 7.8B)이 후속 질문을 직접 작성 | 생성 |
| C′ | A′ 후보를 LLM이 새정보·중복·무관으로 판정 | 판정 |
| A″ | 같은 카테고리, **다른 정책**, 질문 벡터가 가장 가까운 정책 | 없음 |
| A‴ | **정책 연결표**(사람 작성)에서 이어지는 정책의 **대표 질문** | 없음 |

### 5.2 같은 정책에서 고르기 (A, A′)

| 방식 | 칩 2개 이상 | 서로 다른 칩 | 답변 절반 이상 겹침 |
| --- | ---: | ---: | ---: |
| A | 1,150 (100%) | 180 | 11.5% |
| A′ (질문 유사도 상한 0.78) | 1,136 | 716 | 15.8% |

- A는 칩이 일반적이고 상황이 어긋난다. 예: 입대 당일 해지 → [해외 체류 중 온라인 해지 절차]
- A′는 상황은 맞아지지만 중복이 늘어난다. 예: 유심 새로 받을 때 뭘 챙겨가요? → [유심 재발급 시 필요한 서류]
- A′ 후보 50쌍을 블라인드로 라벨링하면 **중복 31 / 새정보 14 / 무관 5**다. 같은 정책은 같은 사실을 반복한다

**벡터 유사도로 중복을 거를 수 없다.** 답변 벡터(bge-m3) 유사도 기준 중복 쌍은 0.75 ~ 0.88, 적절한 쌍은 0.72 ~ 0.93으로 범위가 겹친다.

### 5.3 다른 정책으로 넘어가기 (A″)

같은 기준 FAQ 25개 × 2, 블라인드 라벨.

| 결과 | 값 |
| --- | ---: |
| 새정보 | 24/50 (48%) |
| 중복 | **0** |
| 무관 | 26/50 |

- 다른 정책이라 같은 사실을 반복할 수 없다
- 대신 관계없는 정책으로 넘어간다. 예: 소액결제 한도 → [청구서 수령 방법]
- 카테고리 편차가 크다. PLAN·PORTING 5/6, BILLING 1/6, SERVICE 0/6(멤버십·증명서·명의도용·매장 시간을 모은 카테고리)
- 유사도 기준값을 올려도 정밀도는 약 62%에서 멈춘다

관계 판단은 FAQ 단위가 아니라 **정책 단위**다. 정책은 45개, 같은 카테고리 안의 정책 쌍은 84개뿐이라 사람이 표로 정할 수 있다. 이것이 A‴다.

### 5.4 LLM 생성 (B)

카테고리별 5건, 기준 FAQ 50건 × 2 = 100개 생성 후 앱과 같은 기준(이중 벡터, `QUESTION_ONLY` 0.88 / `Q_A` 0.72)으로 검색했다.

| 결과 | 값 |
| --- | ---: |
| 검색 통과 | **28/100** |
| └ 원래 FAQ로 되돌아감 | 4 |
| 검색 미통과 | 72/100 |
| 생성 지연 | 중앙값 0.7초 |

- 통과한 28개도 상당수가 엉뚱한 FAQ에 걸린다. 맞는 답으로 이어지는 것은 약 15개다(눈대중)
- 사용자에게 되묻는 문장("데이터를 얼마나 사용하시나요?"), 맥락 없는 문장("언제까지 확인 가능한가요?"), FAQ에 없는 내용("분실 보험 적용 여부")이 나온다
- LLM은 FAQ에 무엇이 있는지 모른다. 프롬프트로 고칠 문제가 아니다
- 한계: 대화 맥락으로 질문을 다시 쓰는 단계 없이 원문 그대로 검색했고, 생성 답변 대신 FAQ 답변을 썼다

### 5.5 LLM 판정 (C′)

A′ 후보 50쌍(5.2절 라벨)을 로컬 EXAONE에 판정시켰다.

| 방식 | 통과 | 정밀도 |
| --- | ---: | ---: |
| 판정형 ("새정보/중복/무관") | 42/50 | 14/42 = 33% |
| 추출형 ("기준 답변만 보고 후보 질문에 답해 봐라") | 19개 남김 | 8/19 = 42% |

판정형은 이유에 "이미 제공된 정보와 동일한 내용"이라고 쓰고도 새정보로 판정했다. 추출형은 답변에 없는 내용을 추측해 채웠다.

## 6. 검증 방법

- **블라인드**: 점수, 정책 ID, 출처를 숨기고 쌍 순서를 섞는다
- **독립 채점**: 연결표를 만든 사람이 채점하면 편향된다. 1차 연결표를 작성자가 직접 채점하면 78%였다. 2차부터는 연결표를 만들지 않은 별도 채점자가 채점했다
- **처음 보는 기준 FAQ**: 라운드마다 카테고리별 5개, 50개를 새로 뽑고 이전 라운드 기준과 겹치지 않게 한다
- **과적합 주의**: 검증 결과를 보고 연결표를 고치면 그 검증셋으로 잰 수치는 다음 버전에 쓰지 않는다

라벨 정의:

| 라벨 | 의미 |
| --- | --- |
| 새정보 | 사용자 상황에서 자연스럽게 이어 물을 만하고, 버튼 답변이 챗봇 답변에 없는 정보를 준다 |
| 중복 | 버튼 질문이 묻는 내용을 챗봇 답변이 이미 답했다 |
| 무관 | 버튼 질문이 사용자와 다른 상황·대상에 관한 것이다 |

## 7. 검증 결과

| 라운드 | 연결표 | 채점 | 정밀도 | 중복 | 좋은 칩 1개 이상 받은 기준 | 칩 없는 기준 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 0 | 1차 | 작성자(편향) | 32/41 = 78% | 0 | | 4/25 |
| **1** | **2차** | 독립 채점, 새 50개 | **61/72 = 84.7%** | 0 | 38/50 | 9/50 |
| **2** | **3차** | 독립 채점, 새 50개 | **58/70 = 82.9%** | 1 | 37/50 | 9/50 |
| **3** | **4차 (채택안)** | 독립 채점, 새 50개 | **62/67 = 92.5%** | 1 | 38/50 | 9/50 |

- 정밀도 칸은 **독립 채점 기준 새정보 비율**이다. 채점자 1명의 라벨이고 다수결이 아니다. "새정보" 판정 12건은 작성자가 무작위로 다시 확인했다(모두 납득할 수준)
- 같은 정책과 대표 질문이 여러 행에 반복되어 각 행이 독립 표본이 아니다. 독립을 가정한 95% 구간(±8.3%, ±8.8%)은 실제보다 좁으므로 참고값이다
- 1·2라운드 차이는 그 참고 구간 안이다. 연결표를 더 고쳐도 얻는 것이 적다
- **3라운드(4차 연결표)**: 문제 상황(TROUBLE) 기준 FAQ는 5/7, 그 외는 57/60이다. 약했던 대안·관련 정보 연결을 문제 상황에서 뺀 효과가 보인다. 남은 실패 5건 중 하나가 "로밍 요금이 너무 많이 나와요 → [로밍 신청 창구]"다
- **알려진 제한: ROAMING-01 → ROAMING-02(신청 창구) 연결**. 2·3라운드의 문제 상황 질문 2건("보름 동안 로밍을 썼는데 요금이 생각보다 많이 나왔습니다", "로밍 요금이 너무 많이 나와요")에서 모두 무관이었고, 같은 연결이 비교 질문 1건("일주일 출장을 가는데 어떤 로밍이 싼가요?")에서는 새정보였다. 연결 자체보다 이미 요금이 나온 문제 상황에서 맞지 않는 문제다. 독립 검증을 마친 4차 연결표를 바꾸면 추가 검증이 필요하므로 이번 버전에서는 알려진 제한으로 남긴다. 다음 버전에서는 문제 상황 로밍 요금 질문에 [로밍 요금 자동 차단 기준] 버튼(`ROAMING-03`)을 연결하는 방안을 검증한다. 2라운드 채점에서 "보름 동안 로밍을 썼는데 요금이 생각보다 많이 나왔습니다 → [자동 차단 기준]"은 새정보였다
- 1·2·3라운드 모두 같은 채점자가 채점했다. 4차 92.5%는 "채택안이 통과 기준을 넘었다"는 근거로 쓰고 정확한 성능값으로 쓰지 않는다
- 3라운드 검증셋은 자격 조건 불가 목록 확정(16건) 전 단어 검색 목록으로 만들었지만, 확정 목록으로 다시 계산해도 검증 쌍은 바뀌지 않았다
- **2라운드 파일은 75행이다.** 새 기준 50개의 70행에, 1라운드 기준 FAQ에서 3차 수정으로 새로 생긴 쌍 5행을 라벨을 받기 위해 섞었다. 5행은 이미 본 기준 FAQ라 새 50개 수치에서 뺐다. 5행 결과는 새정보 4, 무관 1이고 75행 전체는 62/75 = 82.7%다. 아래 유형별·종류별 집계도 70행 기준이다
- 2차 연결표(연결 72개) 검토에서 N 7개가 나왔다. 검토자는 빠진 연결 3개도 제안했다

질문 유형별(1·2라운드):

| 기준 FAQ 유형 | 1라운드 | 2라운드 |
| --- | ---: | ---: |
| TROUBLE 제외 | 51/58 = 87.9% | 49/56 = 87.5% |
| TROUBLE | 10/14 | 9/14 |

연결 종류별(두 라운드 합):

### 7.1 실제 사용자 질문의 검색 단계

위 라운드는 **추천 단계만** 잰 것이다. 사용자 질문 자리에 FAQ 질문 자체를 넣었으므로 검색이 맞는 FAQ를 찾는다고 가정했다. 실제 품질은 대략 "검색 1위가 맞는 정책일 확률 × 추천 품질"이다. 그래서 사용자 말투로 따로 쓴 선택용 180문항(정답 FAQ 라벨 있음)으로 검색 단계를 쟀다.

앱과 같은 규칙을 재현했다. bge-m3 질문 임베딩, 질문 벡터 상위 3개 중 0.88 이상과 `Q_A` 상위 3개 중 0.72 이상을 질문 벡터 결과 먼저 병합, 상위 3개(`FaqSearchAnswerProvider` top-K 3)다.

| 항목 | 결과 |
| --- | --- |
| 답변 가능 110문항 중 검색 통과 | 67 (60.9%) |
| 통과 중 1위 FAQ가 정답 FAQ | 52/67 (공식 라벨), 60/67 (다중 정답 라벨) |
| **통과 중 1위 FAQ의 정책이 정답 정책** | **67/67** (두 라벨 모두) |
| 통과하고 칩이 붙는 문항 (4차) | 49 |
| 무관 70문항 중 검색 통과 | 8 (모두 칩이 붙는 정책) |

| 유형 | 검색 통과 | 통과 중 1위 정책 정답 |
| --- | ---: | ---: |
| SIMILAR | 36/40 | 36/36 |
| VARIANT | 6/40 | 6/6 |
| ANSWER | 25/30 | 25/25 |

- **엉뚱한 정책으로 추천이 나가는 경우는 이 데이터에서 없었다.** 1위가 정답 FAQ와 달라도 같은 정책의 다른 FAQ였다. 추천은 정책 기준이라 결과가 같다. 67건 표본이라 대략 5% 이하로 본다
- **빈틈은 추천이 아예 붙지 않는 경우다.** 답변 가능 질문의 39%(43/110)가 검색을 통과하지 못한다. 말을 많이 바꾼 질문(VARIANT)은 6/40만 통과한다. 이 구간은 11절(답 못 할 때 추천)과 검색 개선의 몫이다
- 검색을 통과한 무관 질문 8개는 "eSIM 비용 2,750원에 부가세 포함인가요?"처럼 FAQ 주제와 붙어 있지만 답이 없는 질문이다. 1위 정책은 주제상 맞다. LLM이 근거 없음으로 답하면 `GROUNDED` 조건 때문에 칩이 붙지 않는다
- 한계: DB의 HNSW 대신 전체 정확 계산을 했고, 라우팅과 LLM 답변의 `GROUNDED` 여부는 반영하지 않았다
- **이 측정이 확인한 것은 검색 통과 여부와 1위 정책 정답 여부뿐이다.** 다음은 확인하지 못했다
    - LLM이 2·3순위 FAQ 내용을 중심으로 답하는 경우 → 7.2절에서 확인
    - LLM에는 상위 3개 FAQ가 함께 전달되므로, 생성 답변이 추천 대상 정책의 내용까지 이미 답해 버튼이 중복되는 경우. 7절 채점은 FAQ 답변을 "챗봇 답변"으로 놓고 했으므로 실제 생성 답변에서 그대로 유지된다고 보장할 수 없다 → 7.2절에서 확인
    - 부분 근거인데 `GROUNDED`로 판정되어 부적절한 추천이 붙는 경우
    - 라우팅과 질문 재작성 이후에도 같은 검색 결과가 나오는지
- **그래서 전체 E2E 평가셋은 만들지 않되, 활성화 전에 실제 채팅 경로 표본 15 ~ 20건으로 확인한다.** 일반 질문, TROUBLE, 근거가 여러 개인 질문을 섞고, 로컬(`LLM_PROVIDER=ollama`)에서 기능 플래그를 켠 채 실제 채팅 API로 답변을 생성한다. 표시된 추천을 생성 답변 기준으로 새정보·중복·무관으로 확인하고, `NO_EVIDENCE` 답변에 추천이 붙지 않는지도 확인한다. 결과는 7.2절
- 검색 임계값·검색 구성·연결표를 바꿀 때마다 이 측정을 다시 돌린다

### 7.2 실제 채팅 경로 확인

구현 뒤 로컬에서 플래그를 켜고(`LLM_PROVIDER=ollama`, EXAONE 7.8B) 실제 채팅 API로 확인했다. 스크립트는 `scripts/check_suggested_questions_live.py`다(13절).

**대표 질문 32개**: 버튼은 질문 문자열로 다시 전송되어 라우팅·검색·답변 생성을 모두 거친다. 처음에는 29/32였다.

| 정책 | 처음 대표 질문 | 실제 결과 | 바꾼 질문 |
| --- | --- | --- | --- |
| `ROAMING-02` | 로밍 신청 창구를 알려주세요. | 라우터가 매장 찾기로 보냄 | 로밍은 어떻게 신청해요? (`ROAMING-0022`) |
| `SERVICE-03` | 매장 방문은 언제 가능한가요? | 라우터가 매장 찾기로 보냄 | 평일이랑 토요일 운영시간이 어떻게 다른가요? (`SERVICE-0058`) |
| `TERMINATE-02` | 약정 중간에 해지하면 위약금이 얼마나 나오나요? | 검색 1위는 맞지만 LLM이 근거 없음으로 답함(3회 같음) | 약정 반환금 계산 절차를 알려주세요. (`TERMINATE-0034`) |

- 세 버튼은 FAQ 158개(중복 포함)의 추천에 쓰이던 문장이다. 오프라인 측정은 검색까지만 봐서 잡지 못했다
- **대표 질문 기준을 더했다.** "매장", "창구", "어디서"가 들어간 질문은 매장 찾기로 분류되고, FAQ에 비율만 있는데 금액을 묻는 질문은 LLM이 답하지 않는다. 같은 정책의 후보 중 "로밍 신청은 어디서 해요", "매장 몇 시까지 해요", "직영 매장 토요일 영업시간을 알려주세요"도 같은 이유로 실패했다
- 교체 후 **32/32**가 `GROUNDED`이고 자기 FAQ가 검색 1위다. 교체한 질문은 같은 정책 FAQ라 버튼을 눌렀을 때의 내용은 독립 검증 때와 거의 같다. 버튼 문장 자체는 검증 뒤 바뀌었다

**표본 20건**: 실제 말투 질문(선택용 180)에서 추천이 붙어야 하는 16건(10개 카테고리, SIMILAR·VARIANT·ANSWER, TROUBLE 포함)과 붙지 않아야 하는 4건(연결 없는 정책, 경계 무관, 완전 무관 2)을 보냈다. `EVAL-121`, `EVAL-122`는 판정기 프롬프트 예시와 같아 쓰지 않았다.

| 항목 | 결과 |
| --- | --- |
| 추천이 붙어야 하는 16건 | 16건 모두 `GROUNDED`, 앱 결과가 검증한 기대 추천과 같음 |
| 생성 답변 기준 1차 판정 (작성자 판정, 독립 아님) | 적합 14, 일부 중복 1, 상황에 약함 1 |
| 붙지 않아야 하는 4건 | 이 기능의 추천 0건. 매장 운영시간 질문은 매장 찾기로, 날씨·병원은 의도 모름 고정 버튼 |
| 경계 무관 "5G 요금제를 LTE 폰에서 쓰면 요금이 달라지나요?" | LLM이 `GROUNDED`로 답해 요금제 버튼 2개가 붙음 |

- 일부 중복: "폰 값 다 안 갚았는데 할부 또 되나요" → 생성 답변이 이미 "개통 6개월 후"를 말했는데 [기기변경 신청 가능 시점과 할부금 처리 기준]이 붙었다. LLM이 상위 3개 FAQ를 함께 보고 답해 생기는 중복이다
- 상황에 약함: "법인 담당자인데 제 신분증으로는 개통이 안 된다고 합니다"(TROUBLE) → [신규 개통은 매장이랑 온라인 중 어디가 더 빠른가요?]
- 처음 실행 때 깨진 버튼 2건(태블릿 로밍 → 신청 창구, 일시정지 → 위약금)은 대표 질문 교체 뒤 다시 돌려 정상 버튼으로 바뀐 것을 확인했다
- 생성 답변 자체가 틀린 경우도 보였다(만 13세 개통 가능, 반환금을 "돌려받는다"). 추천과 별개인 답변 생성 품질 문제다
- 한계: 20건이고 판정은 작성자 1인이다. 켜기 전에 다른 사람이 검토표(`build/suggested_questions_sample.csv`)를 보면 독립 판정이 된다

**검색 1순위와 실제 답변 근거**: 추천은 LLM에 넘긴 검색 결과 1순위 FAQ의 정책을 기준으로 한다. 모델이 2·3순위를 중심으로 답하면 버튼이 답변과 어긋날 수 있다. 이 문제는 1 ~ 3위에 다른 정책이 섞여 있을 때만 생긴다. 같은 정책이면 어느 FAQ를 근거로 쓰든 버튼이 같다.

| 확인 | 결과 |
| --- | --- |
| 검색 통과한 답변 가능 질문 67개 중 1 ~ 3위가 모두 같은 정책 (7.1절과 같은 계산) | 65 (97%) |
| 다른 정책이 섞인 2건을 실제 앱으로 확인 | 핵심 근거가 1순위와 다른 경우 0건 |
| 그중 다른 정책 내용이 답변에 섞인 경우 | 1건 |

- `EVAL-017` "미납 요금이 조금 있어도 번호이동이 되나요?": 1·3위 번호이동, 2위 명의변경(`NAME_CHANGE-02`). 두 번 실행해 두 번 모두 번호이동 내용으로만 답했고, 추천 [번호이동 처리 절차와 소요 시간], [개통 후 얼마나 지나야 번호이동할 수 있나요?]도 답변과 겹치지 않았다
- `EVAL-048` "폰 값 아직 다 안 갚았는데 액정이 나가서 새로 사야 합니다. 할부 또 되나요": 1·2위 할부(`DEVICE-01`), 3위 기기변경(`DEVICE-02`). 답변의 핵심은 1위(할부 기간·금리)였지만 3위의 "개통 6개월 후"도 섞여, 기기변경 버튼과 일부 중복됐다(위 표본의 일부 중복 1건)
- 결론: 1순위를 기준으로 쓰는 방식에서 버튼이 답변 주제와 어긋난 경우는 없었다. 남는 위험은 다른 정책 내용이 섞여 생기는 일부 중복이고, 생길 수 있는 범위는 약 3%(2/67)다

## 8. 채택 방식 (연결표 4차)

**실행 조건**: 답변이 `GROUNDED`이고 검색 1순위 FAQ에 연결표에 있는 정책 ID가 있을 때만 후속 질문을 만든다. `NO_EVIDENCE`·`OUT_OF_SCOPE`는 11절 방식이 검증되기 전까지 빈 목록이다. 검색 결과가 있어도 답변이 근거 없음으로 끝나면(`RagAnswerGenerator`가 `NO_EVIDENCE`로 판정) 정상 추천을 붙이지 않는다.

1. 기준 FAQ = **LLM에 전달한 검색 결과 중 1순위 FAQ.** 저장되는 출처는 LLM에 넘긴 검색 결과 전체이고(모델이 실제로 참고한 근거는 알 수 없다, `RagAnswerGenerator`), 순서는 이중 벡터 병합 순위(질문 벡터 결과 먼저, 그다음 `Q_A`)다. 모델이 실제로 사용한 근거와 같다는 보장은 없다. 기준 FAQ의 정책 → 연결표에서 이어지는 정책, 앞에서부터. 2순위 이하 결과는 쓰지 않는다
2. 칩 문장은 그 정책의 **대표 질문**. 상황이 섞이지 않은 실제 FAQ 질문이고, 4차 기준 연결 69개에 32개가 쓰인다. 매장 찾기로 분류되는 단어(매장, 창구, 어디서)와 FAQ에 없는 금액을 묻는 질문은 쓰지 않는다(7.2절)
3. 연결 종류: **다음 단계**(같은 업무를 이어감), **대안**, **관련 정보**
4. 규칙
   - 기준 FAQ의 답변이 **자격 조건 때문에 할 수 없다**고 안내한 경우(미성년자 간 명의변경, 만 65세 미만 시니어 요금제, 회선 5개 한도 등) **다음 단계 연결을 뺀다.** 기간이 지나면 풀리는 경우(개통 6개월 전 기기변경, 3개월 전 번호이동, 가입한 달 요금제 변경)는 미리 준비하려는 사용자를 위해 다음 단계 연결을 유지한다. 대상은 사람이 확정한 16건이며 FAQ 메타데이터로 저장한다(실행 중 문자열 검사 없음). 생성 답변이 아니라 FAQ 답변 기준이라 프롬프트 변경에 흔들리지 않는다. 단어 검색으로 고른 35건 중 조건부 가능·정보 안내·기간 조건을 빼고, 단어 검색이 놓친 자격 조건 2건을 더했다
   - 근거 FAQ가 TROUBLE이면 **다음 단계 연결만 남긴다**
   - `DEVICE-02/03/04`는 상황(`trigger`)에 따라 연결을 나눈다. 예: 침수·액정이면 수리, 분실이면 유심 재발급
   - 매장 운영 시간 연결은 기준 질문에 "매장"이 있을 때만
5. 연결 없음: `SERVICE` 5개 정책, `BILLING-04`, `BILLING-06`, `PORTING-04`
6. 개수와 순서: 현재 구현은 연결표 추천을 연결 종류와 관계없이 **최대 2개** 반환하고, 같은 문장은 하나만 남긴다. 매장 칩이 붙으면 첫 번째에 두고 연결표 추천 최대 2개를 그대로 더해 **전체 최대 3개**가 된다(10절). 예: [유심 재발급 가능한 매장을 알려주세요.], [유심 재발급 시 필요한 서류를 알려주세요.], [평일이랑 토요일 운영시간이 어떻게 다른가요?]

| 지표 | 2차 | 3차 | 4차 |
| --- | ---: | ---: | ---: |
| 칩 2개 | 781 | 715 | 588 |
| 칩 1개 | 245 | 264 | 327 |
| 칩 없음 | 124 (11%) | 171 (15%) | 235 (20%) |

4차 수치는 확정한 자격 조건 16건 기준이다.

- 4차는 두 검증셋의 라벨을 재사용하면 110/117 = 94%다. **검증셋을 보고 정한 규칙이라 낙관치이며 보고에 쓰지 않는다.** 보고용 수치는 7절의 독립 검증 수치(4차 92.5%)다
- **4차 독립 검증 통과**: 이전 라운드와 겹치지 않는 새 기준 FAQ 50개에서 62/67 = 92.5%, 중복 1건으로 통과 기준(새정보 비율 약 83% 이상, 중복 1건 이하)을 넘었다(7절 3라운드)
- 애매한 연결을 빼서 정확도를 얻고 커버리지를 내줬다. 매장 칩(10절)이 연결표 추천이 없던 FAQ 15건을 메운다
- 실행 비용: 답변당 DB 조회 2회(`policy_ref`, 대표 FAQ의 현재 질문)와 메모리 연결표 조회다. 유사도 쿼리는 쓰지 않는다. 현재 구현 기준 지연은 별도로 측정하지 않았다

## 9. LLM 사용 검토

| 용도 | 결과 | 판단 |
| --- | --- | --- |
| 추천 질문 생성 | 검색 통과 28% (5.4절) | 사용 안 함 |
| 중복 판정 (판정형) | 42/50 통과, 정밀도 33% (5.5절) | 사용 안 함 |
| 도움 판정 (문제 상황용, 독립 라벨 142쌍) | "예" 12/142, 좋은 칩 119개 중 108개 버림 | 사용 안 함 |

로컬 판정은 같은 모델이 **프롬프트 문구에 따라 거의 다 통과시키거나 거의 다 거절했다.** 도움 판정에서 좋은 칩에 "예"는 9%, 나쁜 칩에 "예"는 4%로 구분력이 거의 없다.

남은 선택지: 큰 모델(기존 채점 스크립트의 Bedrock `gpt-oss-120b`)로 TROUBLE FAQ 222건의 칩을 미리 골라 두는 방식. 같은 142쌍으로 구분력을 먼저 확인해야 하고 외부 API 비용이 든다. 효과는 전체 몇 % 포인트 수준이다.

참고: 근거 적합성 판정기(`EvidenceRelevanceChecker`, 기본 꺼짐)도 같은 로컬 모델로 "답할 수 있는가"를 판단한다. 위 관찰을 판정기를 켤지 정할 때 참고할 수 있다. 질문 형식과 데이터가 달라 그대로 옮겨 말할 수는 없다.

검색 통과를 늘리는 "임계값 하향 + 판정기" 조합은 `SEARCH_THRESHOLD_060_AND_ANSWER_QUALITY.md`에 130문항 측정이 있다(0.6 + EXAONE 엄격 판정: 같은 정책 근거 전달 37 → 69, 답변 불가 통과 3 → 7). 이중 벡터 이전 구성이고 1회 측정이므로 현재 구성으로 다시 재야 한다. 판정기를 잴 때 주의할 점이 두 가지 있다.

- 코드의 판정 프롬프트(`evidence-check-v2`)는 "애매하면 true"이고, 위 측정은 "애매하면 false" 변형이다
- 판정 프롬프트의 예시 두 개("eSIM 2,750원 부가세 포함인가요?", "카드로 결제되나요?")가 평가셋 무관 문항 `EVAL-121`, `EVAL-122`와 같다. 이 두 문항은 판정기 측정에서 뺀다

임계값을 낮추면 1위에 다른 정책 FAQ가 올라올 수 있으므로, 구성이 정해지면 7.1절 측정을 판정기 통과 결과 기준으로 다시 돌린다.

## 10. 매장 칩 (TELME-124)

매장 방문이 필요한 답변 뒤에 그 업무가 되는 매장 찾기로 바로 이어지게 한다. 플래그 기본값은 꺼짐이다.

- **붙는 조건**: 정상 추천과 같은 조건(`GROUNDED`, 검색 1순위 FAQ)에서 기준 FAQ 답변에 "매장"이 있을 때. "매장 방문 없이", "매장에 가지 않아도", "매장이 아니라", "매장을 방문하지 않아도", "매장에 갈 필요가 없습니다", "매장 방문은 필요하지 않습니다", "매장 방문이 필수는 아닙니다", "매장에 꼭 갈 필요는 없습니다"처럼 매장에 갈 필요가 없다는 표현은 언급으로 보지 않는다(정규식, 데이터 원본에 있음). 관리자 FAQ에도 적용되어 원본에 없는 표현까지 잡고, "매장에서 확인하지 않으면"처럼 매장과 무관한 부정은 걸리지 않게 했다. "않", "안 가"는 "않아도", "안 가도"처럼 허용 뜻일 때만 잡아, "매장에 가지 않으면 처리할 수 없습니다", "매장 방문이 필수입니다"처럼 방문이 필요하다는 답변에는 칩이 붙는다. 1,150건 중 "매장"이 든 140건에서 이런 답변 3건(`TERMINATE-0057`, `TERMINATE-0077`, `DEVICE-0087`)을 빼 137건(11.9%)이고, 그중 15건은 연결표 추천이 없는 FAQ다. 검색 결과에 담긴 답변으로 판단해 DB를 더 읽지 않고, 관리자 등록 FAQ에도 적용된다
- **개수**: 매장 칩은 첫 번째에 두고 연결표 추천 최대 2개를 그대로 더해 전체 최대 3개다. 매장 칩은 행동 버튼, 연결표 추천은 정보 버튼이라 자리를 나누지 않는다. 전체 최대 2개로 하면 연결표 추천이 2개인 FAQ 76건에서 검증한 추천 하나를 잃는다. 프론트 `FollowUps`는 최대 3개를 그린다
- **문장**: 기준 FAQ 카테고리별로 업무를 넣는다. 다른 추천 버튼(실제 FAQ 질문)과 같은 존댓말로 쓴다

| 카테고리 | 칩 문장 | 매장 업무 | FAQ 수 |
| --- | --- | --- | ---: |
| `USIM` | 유심 재발급 가능한 매장을 알려주세요. | `USIM_REISSUE` | 33 |
| `SUBSCRIBE` | 신규 개통 가능한 매장을 알려주세요. | `NEW_LINE` | 30 |
| `NAME_CHANGE` | 명의변경 가능한 매장을 알려주세요. | `NAME_CHANGE` | 26 |
| `PORTING` | 번호이동 가능한 매장을 알려주세요. | `PORT_IN` | 4 |
| 그 외 | 가까운 매장을 알려주세요. | 없음 | 44 |

- 문장에 "근처"를 넣지 않는다. 라우터가 "근처"를 지역 이름(`location`)으로 받아 되묻기 대신 지역 검색을 하기 때문이다("유심 재발급 가능한 근처 매장 찾아줘" 3/3)
- "~할 수 있는 매장 있어?" 모양은 라우터 규칙("매장에서 처리 가능한지는 FAQ")에 걸려 FAQ로 분류된다(2/2). "~가능한 매장을 알려주세요." 모양을 쓴다
- 업무 표현은 라우터의 업무 규칙(`유심.*재발급`, `신규.*개통`, `번호.*이동`, `명의.*변경`)에 맞춘다. "신규 가입"은 이 규칙에 맞지 않는다
- 버튼을 누르면 지역 되묻기 → 지역 이름 입력(TELME-112) 또는 [현재 위치 사용] 버튼(프론트 TELME-4)으로 매장 카드가 나온다

### 10.1 라우터 업무 추출 보완

매장 찾기 질문에서 라우터 LLM이 업무(`serviceType`)를 유심만 뽑았다. 버튼만이 아니라 사용자가 직접 "번호이동 가능한 매장 찾아줘"라고 물어도 같아서, 그 업무를 하지 않는 매장이 5곳 중 1 ~ 2곳씩 섞였다.

| 측정 (로컬 EXAONE 7.8B, 강남역 좌표) | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 유심 재발급 가능한 매장 찾아줘 | 4/4 | 2/2 |
| 신규 개통·번호이동·명의변경 가능한 매장 찾아줘 | **0/12** | **6/6** |
| 위 4종 존댓말 문장("~ 가능한 매장을 알려주세요.") | – | 되묻기 12/12, 업무 필터 12/12 |

- 원인: 라우터 프롬프트를 로컬 모델에 직접 보내도 `extractedConditions`가 비어서 왔다. 검증에서 버려진 게 아니라 처음부터 뽑지 않았다. 프롬프트 예시 중 업무가 들어간 매장 찾기 예시가 유심 하나뿐인 영향으로 보인다. 문장을 예시와 비슷하게 바꿔도(대리점, 가능 매장 등 6가지) 0건이었다
- 수정(`QueryRoutingService.withRuleServiceType`): 의도가 `STORE`인데 LLM이 업무를 비우면 현재 질문의 업무 규칙(`RuleBasedRoutingFallback`)으로 채운다. 이 규칙은 LLM이 준 업무를 검증할 때 쓰던 것과 같다. `BOTH`는 FAQ 쪽 표현 때문에 매장 업무가 잘못 걸릴 수 있어 채우지 않는다. "번호이동 말고 신규 개통"처럼 업무 표현이 여럿이면 어느 쪽인지 알 수 없어 채우지 않는다(필터 없이 검색). LLM이 업무를 직접 준 경우도 같은 기준으로 검증해, 업무 표현이 여럿인 문장에서는 LLM 값을 버린다. LLM 호출이 실패했을 때 쓰는 규칙 분류(`classify`)는 기존 우선순위 동작을 유지한다
- 영향: 조건은 `STORE` 하위 질문에만 붙어 FAQ 검색·답변에 닿지 않는다. 라우팅 평가 130개를 같은 LLM 응답으로 수정 전후 비교하면 의도·처리 방식·검색 문장이 130개 모두 같다(FAQ 117 / STORE 2 / UNKNOWN 11)
- 기존 테스트 기대값 변경 1건(`currentServiceTypeOverridesHistoricalServiceType`): 이전 대화가 유심이고 현재 질문이 "그거 번호이동 매장 알려줘"일 때, 전에는 잘못된 유심을 버리고 업무 없음이었고, 지금은 현재 질문의 번호이동으로 채운다

### 10.2 실제 채팅 경로 확인

추천·매장 칩 플래그를 켠 로컬 앱에서 매장을 언급하는 FAQ 질문을 보내고, 붙은 매장 칩을 그대로 다시 보낸 뒤 지역 되묻기에 "강남역"으로 답했다(카카오 REST 키 사용).

| FAQ 질문 | 붙은 버튼 (기대값과 같음) | 매장 칩 → 되묻기 → 강남역 |
| --- | --- | --- |
| 기기변경 시 유심 재발급 택배 소요 기간을 알려주세요. | 유심 매장 칩 + 연결표 2개 | 매장 5곳, 업무 불일치 0 |
| 신규 개통은 매장이랑 온라인 중 어디가 더 빠른가요? | 신규 개통 매장 칩 + 연결표 2개 | 5곳, 불일치 0 |
| 번호이동 철회는 어떻게 신청하나요? | 번호이동 매장 칩 1개 (연결표 추천 없는 정책) | 5곳, 불일치 0 |
| 명의변경 시 필요한 서류를 정리해서 알려주세요. | 명의변경 매장 칩 + 연결표 2개 | 5곳, 불일치 0 |
| 6개월이 지난 뒤 기기변경은 어떤 절차로 진행되나요? | 가까운 매장 칩 + 연결표 2개 | 5곳 |
| 요금 납부 방법에는 어떤 게 있나요? (매장 언급 없음) | 매장 칩 없음, 연결표 1개 | – |

### 10.3 켜기 전 확인

- **[현재 위치 사용] 경로(TELME-103 쪽)**: 지역 되묻기 뒤 [현재 위치 사용] 버튼("현재 위치에서 가까운 매장을 찾아줘" + 좌표)을 누르면 라우터가 `location="현재 위치"`를 뽑는다(로컬 5/5). 명시 지역 우선 규칙 때문에 좌표 대신 지역 검색을 해서, 카카오 키가 없으면 실패하고 있으면 "현재트윈빌아파트"처럼 이름이 비슷한 장소 주변 매장이 나온다. 매장 칩과 별개로 그쪽에서 고치기로 했고, 고쳐진 뒤 매장 칩을 켠다
- 지역 이름 입력은 시·구를 함께 쓰는 편이 안전하다. "해운대구"만 쓰면 위치를 찾지 못했다("부산 해운대구"는 동작)
- 라우터 결과는 LLM에 따라 달라질 수 있어 운영 모델로 켜기 전에 매장 칩 문장 5개를 다시 확인한다

| 1. 검색 결과 없음 | "혹시 이런 내용을 찾으셨나요?" + FAQ 질문 **1개** | 임계값 아래라 버려지던 후보 중 `Q_A` 0.60 이상 1위 (11.1절) |
| 2. 넓은 질문 ("로밍 관련 질문 있어") | 1번과 같음. 별도 판별 없음 | 대부분 검색에 실패해 1번 규칙으로 처리된다 (11.2절) |
| 3. 근거는 찾았지만 LLM이 답 못 함 | 이미 찾은 근거 FAQ 질문 | 임계값을 넘은 후보 |
| 4. 의도 모름 (UNKNOWN) | 카테고리 칩 | 고정 |
| 5. 복합 질문 | 라우터가 나눈 하위 질문 | `UnsupportedCompoundQuestionException`이 버리는 하위 질문. #75 결과에 따라 결정 |

- 같은 정책·질문 유형 후보는 하나로 묶는다
- 칩 문장은 경험자 페르소나 질문으로 바꾼다
- 측정 계획: 1번은 측정 완료(11.1절). 2번은 측정 완료(11.2절), 1번 규칙으로 처리한다. 3번은 이슈 구현 후 실제 채팅 경로 표본에서 확인한다(LLM 답변이 있어야 알 수 있다). 4번은 고정 칩이라 측정하지 않는다. 5번은 #75 결과 이후 정한다
- 고객센터는 후보가 없고 카테고리 칩으로도 안 될 때, 또는 사용자가 직접 요청할 때만 띄운다

### 11.1 검색 결과 없음 측정 (하한 선택)

현재 검색(질문 벡터 0.88 / `Q_A` 0.72, 상위 3)을 통과하지 못한 질문에 임계값 아래 후보를 보여줄 때의 하한을 쟀다. 후보는 `Q_A` 점수 순으로 서로 다른 정책에서 고른다. 선택용 180과 경계 무관 홀드아웃 90을 썼다.

| 그룹 | 검색 실패 | 버튼이 뜨면 |
| --- | ---: | --- |
| 답변 가능 | 43/110 | 맞는 FAQ로 유도해야 한다 |
| 완전 무관 (날씨, 영화 등, `EVAL-081` ~ `096`) | 16/16 | 무조건 잘못이다 |
| 통신 주변 무관 (집전화 설치, 통신사 앱 로그인 등, `EVAL-097` ~ `120`) | 24/24 | 대체로 잘못이다 |
| 경계 무관 (`EVAL-121` ~ `130`, 보강 20, 홀드아웃 90) | 22/30, 70/90 | 관련 FAQ로 안내하는 것이라 대체로 괜찮다 |

| 하한 | 버튼 | 답변 가능 43개 중 맞는 정책 버튼 | 버튼 정밀도 | 완전 무관 표시 | 통신 주변 무관 표시 |
| --- | --- | ---: | ---: | ---: | ---: |
| **0.60** | **1개** | **33 (77%)** | **87%** | **0/16** | 14/24 |
| 0.60 | 2개 | 37 (86%) | 54% | 0/16 | 14/24 |
| 0.64 | 1개 | 25 (58%) | 86% | 0/16 | 7/24 |
| 0.66 | 2개 | 24 (56%) | 73% | 0/16 | 1/24 |

- **채택: 하한 0.60, 버튼 1개.** 완전 무관 질문의 `Q_A` 최고 점수는 0.59 이하라 0.60 이상에서는 버튼이 뜨지 않는다. 1번째 후보는 87%가 맞는 정책이지만 2·3번째는 대부분 틀려서 1개만 보여준다
- **알려진 제한: 통신 주변 무관 질문.** 0.60에서 24개 중 14개에 버튼이 뜨고 대부분 엉뚱하다(집전화 설치 → [번호이동 신청], 스팸 문자 차단 → [청구서가 안 와요]). 답변 가능 질문과 점수 구간(0.60 ~ 0.70)이 겹쳐 하한으로는 거르지 못한다. 0.66으로 올리면 1/24로 줄지만 유도율이 약 50%로 떨어진다. "혹시 이런 내용을 찾으셨나요?"는 조심스러운 제안이라 틀렸을 때 피해가 정상 답변 버튼보다 작다고 보고 유도율을 택했다
- 한계: 같은 데이터로 하한을 골라 실제 효과는 이보다 낮을 수 있다. 칩 문장은 후보 FAQ 질문 그대로 셌으므로, 구현할 때 같은 정책·질문 유형의 경험자 페르소나 문장으로 바꾼다. 라우팅은 반영하지 않았다(완전 무관 질문은 의도 분류에서 먼저 걸러질 가능성이 크다)

### 11.2 넓은 질문 측정

FAQ와 검색 결과를 보지 않은 별도 작성자가 쓴 넓은 질문 30개(카테고리 10개 × 말투 3종, 예: "해외 로밍 관련해서 문의드립니다", "유심 얘기 좀 하려고요")로 쟀다.

| 항목 | 결과 |
| --- | ---: |
| 지금 검색 통과 | 3/30 |
| 검색 실패 27개 중 1번 규칙 버튼 표시 | 25/27 |
| 그중 맞는 카테고리 FAQ | **20/25 (80%)** |

- **넓은 질문은 따로 판별하지 않고 1번 규칙으로 처리한다.** 대부분 검색에 실패해 1번 경로로 들어가고, 버튼 80%가 맞는 카테고리로 이어진다. 예: "해외 로밍 관련해서 문의드립니다" → [로밍은 어떻게 신청해요?]. 틀린 예: "명의 바꾸는 것 좀 여쭤봅시다" → 번호이동 FAQ
- **넓은 질문 전용 응답("로밍과 관련해 어떤 점이 궁금하신가요?")은 이번 범위에서 뺀다.** 검색 후보가 한 카테고리의 여러 정책에 퍼져 있는지로 판별해 봤지만, 가장 나은 설정에서도 넓은 질문 27개 중 7 ~ 9개를 잡는 동안 검색 실패한 답변 가능 질문 43개 중 5 ~ 6개를 넓은 질문으로 잘못 잡았다. 필요하면 라우터(의도 분류)에서 판별해야 한다
- 검색을 통과한 3개 중 "휴대폰 요금 얘기 좀 하려고요"는 소액결제 한도 FAQ로 답한다. 넓은 질문이 구체적인 답으로 이어지는 경우로, 검색 쪽 문제라 이 기능 범위 밖이다
- 한계: 질문 30개, 작성자 1명이다. 하한은 11.1절 값을 그대로 썼고 이 데이터로 다시 고르지 않았다

### 12.1 구현 내용 (TELME-120, TELME-124)

| 기대값 | `src/test/resources/suggested-question/expected-recommendations.json` | FAQ 1,150개별 기대 추천과 매장 칩. FAQ 하나를 한 줄로 쓴다. 코드 결과와 비교하는 테스트가 있음 |

- 이름: 코드의 `Followup*`(`FollowupContextService` 등)은 되묻기 뒤 사용자의 다음 입력을 뜻한다. 혼동을 피해 이 기능은 `SuggestedQuestion*`으로 지었다. 저장 필드는 기존 `followUps`다
- 관리자 등록 FAQ(`slotId` 없음): 연결표는 적용하고, 상황(`trigger`)을 모르므로 상황별로 나눈 연결(`DEVICE-02/03/04`)은 붙이지 않는다. 문제 상황·자격 조건 규칙은 해당 없음으로 본다
- 검증 때 있던 `TERMINATE-02 → TERMINATE-04`의 "TROUBLE이 아닐 때만" 조건은 공통 TROUBLE 규칙과 결과가 같아 뺐다
- 전달: 답변 완료 SSE에는 답변 본문이 없고, 프론트는 대화 기록 API로 답변을 받는다. 같은 응답의 `followUps`에 추천이 들어간다. 프론트(TEL-ME_FE develop)의 `FollowUps` 컴포넌트가 가장 최근 답변 아래에 최대 3개를 버튼으로 그리고, 누르면 그 문장을 질문으로 보낸다. SSE 변경은 필요 없다
- 프론트 확인 필요: 종료된 대화에서도 마지막 답변의 추천 버튼이 그대로 보인다. 종료된 대화는 입력을 막기로 했으므로 버튼도 숨기거나 비활성화해야 한다

### 12.2 구현 시 고려 (설계 당시)


- **연결표 저장**: 설정 파일(JSON·YAML) 또는 DB 테이블. 테이블이면 Flyway 마이그레이션이 필요하다 → 리소스 JSON으로 결정(12.1절)
- **상황·질문 유형 매핑**: `trigger`, `question_type`은 원본 JSON에만 있다. `slot_id` 기준 매핑을 따로 두거나 컬럼을 추가한다 → `faq-rules.json`에 `slot_id` 기준으로 둠
- **관리자 등록 FAQ**: 등록 요청(`AdminFaqSaveRequest`)의 `policyRef`는 선택 입력이다. 연결표에 있는 정책 ID가 들어 있으면 연결표만 적용하고, 상황·질문 유형 규칙은 건너뛴다. 비어 있거나 연결표에 없는 값이면 정상 답변 추천을 생성하지 않는다
- **검색 결과가 여러 개일 때**: LLM에 전달한 검색 결과 1순위 FAQ만 기준으로 쓴다(8절). 저장 순서가 병합 순위와 같은지 테스트로 고정한다
- **실행 조건**: `answerBasis`가 `GROUNDED`일 때만 연결표 추천을 만들고, `NO_EVIDENCE`·`OUT_OF_SCOPE`는 빈 목록이다
- **채울 위치**: `RagSearchResultAnswerGenerator`의 빈 `followUps`. 추천 계산은 별도 클래스로 분리하고 기존 파일에는 호출만 둔다
- **겹치는 작업**: 상담 흐름 파일을 TELME-103(채팅 매장 찾기), TELME-104(후속 입력), #75(복합 질문)가 함께 고친다. 머지 순서를 확인한다
- **실시간 표시**: SSE `complete`에 `followUps`를 실을지, 프론트가 이력을 다시 조회할지 chat 담당·프론트와 정한다 → 기존 대화 기록 API로 전달(12.1절)
- **기능 플래그**: 기본값이 꺼져 있다. 4차 독립 검증과 실제 채팅 경로 표본 확인(7.2절)은 완료했으며, 독립 재검토 여부를 정한 뒤 활성화한다
- **테스트**: 연결표 조회, 불가 FAQ 규칙, TROUBLE 규칙, 상황 조건, 검색 결과 1순위 선택, 정책 ID 없는 FAQ, `GROUNDED`가 아닌 답변, 최대 2개와 중복 제거를 단위 테스트로 둔다(매장 칩 포함 최대 3개는 TELME-124에서 추가). 검증한 연결표의 FAQ별 추천 목록을 기대값으로 삼아 코드 결과와 비교하는 테스트도 둔다
- **검색 단계 재측정**: 검색 임계값·검색 구성(리랭커, 판정기 등)·연결표를 바꾸면 7.1절 측정(검색 통과율, 1위 정책 정답률, 무관 통과)을 다시 돌린다
- **대표 질문 회귀 테스트**: 버튼은 FAQ ID가 아니라 질문 문자열로 다시 전송되어 라우팅과 검색을 거친다. 임계값 변경, 재임베딩, FAQ 추가·수정·비활성화, 라우팅 변경에 결과가 바뀔 수 있으므로, 대표 질문 32개를 실제 채팅 경로로 보내 기대 FAQ가 근거로 나오는지 확인한다 → `check_suggested_questions_live.py representatives`(7.2절, 32/32). 실행 중에는 대표 FAQ가 숨겨지거나 수정되면 검색과 같은 조건으로 걸러 현재 질문을 쓴다(12.1절)

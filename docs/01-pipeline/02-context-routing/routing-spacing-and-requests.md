# TELME-132 질문 분해와 검색어 의미 보존

## 목표와 처리 방식

띄어쓰기 차이로 같은 질문을 여러 요청으로 나누거나 고객이 묻지 않은 조건을 검색어에 추가하지 않도록 한다. 답변에 필요한 FAQ 개수와 고객이 요청한 항목 수는 구분한다.

1. 라우팅 입력에서 한글 주변의 가로 공백만 통일한다. 저장된 고객 메시지는 바꾸지 않는다.
2. 모델이 FAQ 하위 질문을 여러 개 제안한 경우에만 별도 판정으로 `SINGLE`, `COMPARISON`, `MULTIPLE`과 요청 수를 확인한다. 비교와 하나의 처리 순서는 한 요청이고, 명시적으로 물은 서로 다른 업무나 항목은 여러 요청이다.
3. 단일 또는 비교 요청에는 고객 원문 전체를 사용한다. 여러 요청에는 각 `requestQuote`의 원문 근거, 순서와 중복 여부를 검증한다. 모델이 `필요한 서류`를 `필요서류`로 줄인 경우에는 원문에서 이어진 구간을 확인한 뒤 복구한다.
4. 하위 질문의 검색 문구가 원문에 없는 대상이나 조건을 보태거나 의미 판정에 실패하면 검증된 원문 인용구로 되돌린다. 요청 수가 충돌하거나 원문 인용을 검증할 수 없으면 확인 안내로 끝내며 상담 요청을 일부만 저장하지 않는다.

`번호이동 하고싶어요`는 한 요청이고, `eSIM과 유심 중 어느 쪽이 편해`는 한 비교 요청이다. `부가서비스 가입이랑 해지는 어떻게 해요`는 서로 다른 두 업무다. `해지 서류`의 대상을 원문에 없는 `로밍`으로 확정해서는 안 된다.

## 검증 결과

2026-10-08 현재 코드로 로컬 EXAONE 3.5 7.8B와 bge-m3, 실제 Spring 경로, FAQ와 임베딩 1,152건이 있는 별도 PostgreSQL 평가 DB를 사용해 재실행했다. 라우팅 일치 수는 사전에 작성한 요청 유형과 개수 기준에 대한 회귀 검사다. 답변 정확도나 환각률은 아니다.

| --- | ---: | --- |
| Spring 라우팅 195회 | 채점 대상 165/165 일치 | 의도와 요청 수. 대상이 모호한 FAQ 30건은 채점 제외 |
| 실제 채팅 153회 | 구조 검사 144건 통과, 9건 확인 안내 | FAQ 되묻기를 끈 상태. 9건은 라우팅 전에 문맥 확인 안내로 종료되어 답변 검증 대상에서 제외 |
| 실제 채팅 11회 | 10건 통과, 1건 확인 안내 | 비교와 복합 요청을 포함한 별도 사례 |

이전 라우팅 자료와 같은 입력 순서로 비교하면 요청 유형과 개수가 바뀐 것은 채점 제외 문항 `NAME_CHANGE-0085` 한 건이다. 저장 검색어는 66회 달라졌지만 모델 출력 차이와 코드 변경이 함께 작용하므로 전부 코드 효과로 해석하지 않는다.

기본 설정에서는 FAQ 되묻기가 켜져 있다. 이를 켠 채 실행한 첫 3건은 최종 답변 대신 미납 여부를 물었고 상담 요청이 `WAITING_CONDITION`이었다. 기존 153건 스크립트는 곧바로 `DONE`이 되어야 한다고 가정하므로, 위 153건 비교에서는 FAQ 되묻기만 껐다. 기본 설정의 최종 답변 완료율로 해석하면 안 된다.

153건 중 확인 안내 9건은 `ChatQuestionResolver`가 라우팅 전에 문맥 확인을 요구해 상담 요청이 생성되지 않은 경우다. `H_PAYMENT_CONDITION` 2건, `H_PAYMENT_COMPOUND`, `TERMINATE-0100`, `TERMINATE-0105`, `PLAN-0046`, `PLAN-0102`, `BILLING-0100`, `BILLING-0128`이다. 기본 `REGEX_GATED` 모드에서 `IMPLICIT` 패턴이 `요금이 밀렸는데 유심 재발급 받을 수 있어요`처럼 대상이 드러난 질문까지 문맥 의존 후보로 잡고, 이전 고객 발언이 없으면 모델 판단 전에 확인 안내로 끝낸다. 따라서 이 9건은 이번 질문 분해 개선의 성공 사례가 아니라 별도로 해결해야 할 오탐이다. `H_PAYMENT_CONDITION`의 띄어쓰기 변형 2건도 모두 확인 안내로 끝났다.

`INDEPENDENT-03`은 실제 채팅에서 요청 3건이 모두 `DONE`으로 저장되고 답변 한 건과 SSE가 일치했다. 그러나 `필요한 서류` 검색어에서 번호이동 대상이 빠져 해당 항목이 안내 불가로 나왔다. 번호이동 서류 FAQ는 후보에 있었지만 생성 근거로 채택되지 않았다. **요청 분해 성공과 각 항목의 답변 성공은 별개**다.

이전 답변 실험에서 발견한 근거 밖 단정, 검색 근거가 있어도 안내 불가, 답변 가드 예외와 내용 누락은 이 평가의 구조 검사만으로 해결 여부를 판단할 수 없다. 각 답변과 FAQ를 사람이 대조하거나 별도 품질 평가로 확인해야 한다.

## 범위와 남은 한계

- 공개 API와 DB 스키마는 바꾸지 않는다. FAQ와 매장이 섞인 질문의 매장 답변 결합은 이 작업 범위 밖이다.
- 원문 구간의 존재와 순서는 확인하지만 두 질문의 의미가 완전히 같은지는 증명하지 못한다. 하위 질문의 대상과 조건은 모델 판단에도 영향을 받는다.
- 최초 라우팅이 단일 질문으로 판단하면 독립 요청 재확인은 실행하지 않는다. 여러 요청으로 판단하면 요청 수 확인과 검색어 의미 검증으로 모델 호출이 최대 두 번 더 늘어난다.
- 대상이 모호하고 검색 근거까지 없는 질문은 현재 FAQ 되묻기로 처리되지 않는다. 근거에서 조건을 추출할 수 있는 경우와 구분해 별도 설계가 필요하다.
- 문맥 없이 완결된 질문이 확인 안내로 빠지는 9건은 `ChatQuestionResolver`의 문맥 판정 문제로 별도 이슈에서 수정한다. 수정 후에는 독립적인 요금 질문과 실제 후속 질문을 같은 Spring 채팅 경로에서 재검증해야 한다. 복합 요청에서 첫 항목의 대상을 나머지 검색어에 안전하게 전달하는 문제는 별도 검색 품질 작업이다.

## 설계 근거

- [CheckList, ACL 2020 본문 2.2절](https://aclanthology.org/2020.acl-main.442.pdf)은 의미와 정답을 유지하는 입력 변형에서 예측도 유지되는지 검사한다. TEL-ME에서는 띄어쓰기 변형의 의도와 요청 수를 비교하는 기준으로 사용했다.
- [Break It Down, TACL 2020 본문 2절](https://aclanthology.org/2020.tacl-1.13.pdf)은 복합 질문의 하위 의미 단위와 관계를 명시한다. TEL-ME에서는 고객이 요구한 항목과 답변 작성에 필요한 정보를 구분하는 데 참고했다. 이 논문이 TEL-ME의 특정 모델 호출 방식이나 한국어 성능을 검증한 것은 아니다.

## 하위 질문 검색어 띄어쓰기 복원 (TELME-225)

라우팅은 한글 사이 공백을 지운 발화로 모델의 인용(`requestQuote`)을 검증하고, 모델 검색어를 믿지 못하면 그 인용을 검색어로 쓴다. 그래서 복합 질문의 하위 질문 검색어가 "번이철회하면제회선은어떻게돼요"처럼 붙여 쓴 문장이 됐고, 앱 검색 점수가 크게 낮아졌다("번이 철회하면 제 회선은 어떻게 돼요" 0.854 → 0.740, 하한 0.80 아래). 붙여 쓴 검색어가 원문에 있으면 원문 구간의 띄어쓰기로 되돌린다(`IndependentQuestionPolicy.withOriginalSpacing`). 모델이 띄어 쓴 검색어와 원문에 없는 말은 그대로 둔다. 라우팅 모델의 입력과 판정은 바꾸지 않는다.

채팅 API로 develop(`86c9df2a`)과 비교했다. 블라인드 문장은 구현을 보지 않은 에이전트가 FAQ 표본 100개만 보고 썼다.

| 블라인드 46문장, 각 3회 | develop | 이 변경 |
| --- | --- | --- |
| 한 업무 여러 항목(K, 42회) 모든 부분 답함 | 29 | 37 |
| 서로 다른 두 업무(M, 24회) | 24 | 21 |
| 목적 진술 + 매장 요청(P, 30회) 매장 하나로 처리 | 20 | 17 |
| FAQ만 묻는 대조군(F, 24회) | 18 | 18 |
| FAQ와 매장 대조군(B, 18회) | 15 | 14 |
| 띄어쓰기 없는 FAQ 검색어 | 100 | 0 |

| 품질셋 307턴, 각 1회 | develop | 이 변경 |
| --- | --- | --- |
| 답하지 못한 부분이 있는 턴 | 116 | 112(좋아짐 12, 나빠짐 9) |

- P·B 그룹과 품질셋에서 나빠진 턴의 대부분(9턴 중 6턴)은 질문을 나눌지, 매장으로 볼지 하는 라우팅 판정이 회차마다 달라진 경우다. 이 변경은 판정 뒤 검색어만 바꾼다.
- M06 "듀얼번호 쓰면 돈 더 나와요? 담주에 일주일 출장가는데 로밍은 뭐가 제일 싸요"는 띄어쓰기를 되살리자 맞는 FAQ를 0.887로 찾았지만 생성된 답("7일 기간권이 39,000원으로 가장 저렴합니다")을 근거 정책 검사가 막아 3회 모두 근거 없음으로 끝났다. 근거와 맞는 답인데 막힌 이유는 확인하지 않았다.

**시도했다가 뺀 것**
- 라우팅 프롬프트에 "목적 진술 + 매장 요청 → 매장 하나" 예시: 목적 진술 매장 요청은 20 → 29/30으로 좋아졌지만 "명의변경 수수료 있나요? 부산 서면역 근처 매장 어디예요"(FAQ와 매장) 같은 질문이 3회 모두 "나누어 처리하기 어려워요"로 바뀌고(develop 0/3), 하위 질문을 셋 이상으로 나누는 경우가 늘었다(14 → 18).
- 주제가 빠진 뒤쪽 조각("신청방법", "얼마예요")에 질문의 유일한 업무 이름 붙이기: 효과가 드러나지 않았고, "유심 깨진 김에 이심으로 갈아타고 싶은데… 얼마예요?"에 "유심"을 붙이는 오작동이 있었다(유심과 이심이 같은 주제로 묶임).

결과 파일은 `scripts/spacing-routing-evaluation/results/telme225/`에 있다. `captures.tar.xz`는 캡처 16개(`m225-d2-*` develop, `m225-b3-*` 이 변경, `m225-b2-*` 위 두 시도를 넣은 판), `blind-sentences.json.gz`는 블라인드 문장과 입력, `scores.json.gz`는 `score_compound_capture.py` 채점 결과다.

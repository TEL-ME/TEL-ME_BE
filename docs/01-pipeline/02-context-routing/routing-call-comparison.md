# 라우팅 LLM 호출별 EXAONE·gpt-oss 비교

라우팅 단계의 LLM 호출을 호출 순서대로 하나씩 EXAONE 3.5 7.8B와 Bedrock gpt-oss-120b로 바꿔 보고, 호출마다 어느 모델을 쓸지 정하는 작업(TELME-175)의 정리다. "이득이 없는 호출은 바꾸지 말자"는 팀 의견에 따라 호출별 근거를 남긴다. 앞 단계에서 정한 모델은 다음 단계에서 고정한다.

| 단계 | 호출 | 언제 도는가 | 상태 |
| --- | --- | --- | --- |
| 1 | 의도 분류 (`ROUTING_SYSTEM_PROMPT`) | 새 질문마다 | **gpt-oss 확정** |
| 2 | 요청 개수 판정 (`REQUEST_INVENTORY_PROMPT`) | 의도 분류가 FAQ 하위 질문을 2개 이상 만들었을 때 | **의도 분류가 gpt-oss면 끔**(`telme.routing.request-inventory-enabled`), 켤 때는 프롬프트 v4 |
| 3 | 검색어 검증 (`FAQ_QUERY_FAITHFULNESS_PROMPT`) | 복합 하위 질문, 원문 검색 결과가 없어 다시 검색할 때, 문맥 복원 단일 질문 | **gpt-oss 확정**, 재검색 후보에만 단일 검색어용 프롬프트 |
| 4 | 후속 분석 (`FOLLOW_UP_SYSTEM_PROMPT`) | 되물은 질문에 고객이 답했을 때 | **gpt-oss 확정**, 프롬프트 v4(되물은 질문 함께 전달, 상황으로 답한 것도 답)와 규칙 보완 |

판정 기준은 호출마다 더 나은 쪽이다. 호출마다 다른 모델을 써도 된다. 차이가 실행 간 흔들림 범위 안이면 서빙을 하나로 줄일 수 있는 gpt-oss를 고른다. 이 기준은 팀 확인이 남아 있다. 1·3·4단계는 gpt-oss가 분명히 낫다. 2단계는 호출만 따로 떼면 앱 흐름 기준으로 EXAONE이 낫지만, 의도 분류가 gpt-oss면 이 호출을 끄는 쪽이 둘보다 낫다(2단계 마지막 절).

## 측정 방식

- 앱 코드의 라우팅 서비스(`QueryRoutingService`)를 그대로 쓰는 프로브([RoutingEvaluationProbe](../../../src/test/java/com/telme/probe/RoutingEvaluationProbe.java))로 잰다. 호출마다 보낼 주소를 따로 정할 수 있다(`TELME_ROUTING_INTENT_URL`, `TELME_ROUTING_INVENTORY_URL`, `TELME_ROUTING_FAITHFULNESS_URL`, `TELME_ROUTING_FOLLOWUP_URL`, 나머지는 `TELME_ROUTING_BASE_URL`). 확정한 호출의 기본 주소는 gpt-oss 라우터다.
- 2단계부터는 앱의 해당 호출 메서드(`requestInventory`, `findUnsafeFaqQueries`, `requestFollowUpAnalysis`)를 그대로 불러 그 호출만 잰다(`TELME_ROUTING_STEP`). 앱에서 그 호출 앞에 도는 규칙도 같은 순서로 적용한다. 요청 개수 판정을 끈 라우팅 전체 경로는 `TELME_ROUTING_SKIP_INVENTORY=true`로 잰다.
- EXAONE은 로컬 Ollama, gpt-oss는 평가용 라우터(`scripts/judge-serving-evaluation/judge_router.py --chat bedrock --judge bedrock`, 도쿄)로 보낸다.
- gpt-oss 요청 조건(라우터): 추론 강도 low, 온도는 요청 값(라우팅 호출은 0). 라우터는 앱의 Ollama 형식 요청을 Bedrock Converse로 바꾸면서 두 가지를 더한다. 사용자 메시지 끝에 "응답은 유효한 JSON 객체 하나만 출력하세요."를 붙이고, 출력 한도를 최소 512로 올린다(gpt-oss는 내부 추론도 출력 한도를 쓴다).
- 앱의 Bedrock 클라이언트(`BedrockClient`, `BedrockRequestConverter`)는 추론 강도 low로 같지만 JSON 지시를 붙이지 않고 요청의 출력 한도를 그대로 쓴다(요청 개수 판정·검색어 검증 256, 후속 분석 300, 의도 분류 768). 그래서 1~4단계의 gpt-oss 3회를 앱 클라이언트로 한 번 더 돌렸다(아래 "앱 클라이언트 재확인").
- gpt-oss는 같은 입력에도 결과가 흔들려 3회를 동시에 돌린다(`TELME_ROUTING_REPEATS=3`). EXAONE은 1·2단계는 1회, 3·4단계는 3회다.
- 1단계 채점은 앱의 UNKNOWN 재확인(#145)을 재현한다. 모델이 UNKNOWN이라 한 질문을 검색 테스트 API로 다시 검색해 걸리면 FAQ로 본다. 검색 임계값은 확정값 0.69/0.80이다.
- 원시 결과는 단계마다 `scripts/routing-call-comparison/results/<단계>/results.json.gz` 하나에 실행별로 담는다.

## 통합 평가셋 (365문항)

라우팅 평가 자료가 여러 파일로 나뉘어 있어 하나로 모았다([eval_routing_unified.json](../../../scripts/data/eval_routing_unified.json), 생성 스크립트 [build_eval_set.py](../../../scripts/routing-call-comparison/build_eval_set.py)). 출처는 검색 평가 180문항, 라우팅 32·홀드아웃 20·문맥 3, FAQ+매장 복합 16, 띄어쓰기·요청 개수(#120), 비교 14, 복합 FAQ 7이다.

| 의도 | 문항 | tuning | holdout | general |
| --- | --- | --- | --- | --- |
| FAQ | 210 (여러 요청 57) | 86 | 63 | 61 |
| STORE | 52 | 9 | 43 | 0 |
| BOTH | 51 | 25 | 26 | 0 |
| UNKNOWN | 52 | 9 | 25 | 18 |

- tuning은 라우팅 프롬프트를 고칠 때 보던 문장, holdout은 보지 않은 문장, general은 검색 평가용으로 만든 문장이다.
- 뺀 문항 235개와 이유는 파일의 `excluded`에 있다.
  - 띄어쓰기만 달라 모델 입력이 같은 문장: 26개. 앱이 라우팅 전에 한글 주변 공백을 지운다.
  - 프롬프트 예시와 같은 문장: 20개.
  - 뜻과 표현이 같은 쌍: 2개.
  - FAQ 비율 축소: 187개. 검색 평가 문항과 #120 FAQ 변형만 유형·업무 분류별 층화 무작위(seed 175)로 줄였다. 모델 결과를 보고 고르지 않았다.
- 새로 쓴 문항 137개는 holdout이다. STORE·BOTH·UNKNOWN 보강 77, 맥락 9, FAQ 복합 질문 30, 요청 개수 프롬프트 확인용 21이다. 라벨은 사람 검토 전이다(`TELME-175 신규(사람 검토 전)` 태그).
- 정답이 둘 이상일 수 있는 13문항은 `acceptable_intents`, `acceptable_request_counts`로 허용 정답을 적었다. 채점은 이 값으로 한다. 예: 지역 없는 "매장은 보통 몇 시까지"는 FAQ·STORE 모두 정답. 액세서리 추천 2문항(아이폰 케이스, 블루투스 이어폰)은 FAQ로 보내도 근거 없음 안내로 끝나 UNKNOWN·FAQ 모두 정답이다(PR #160 리뷰).
- 맥락 문항은 요약 문장이 아니라 이전 고객 발언(`previous_questions`)과 연결 여부(`context_linked`)로 적었다. 라우팅 프롬프트는 상담 요약을 쓰지 않고, 앱은 문맥 해석이 이전 발언을 연결했을 때만 그 발언과 복원 질문을 라우팅에 넘기기 때문이다.

## 1단계: 의도 분류 → gpt-oss

나머지 라우팅 호출은 EXAONE으로 두고 의도 분류만 바꿨다. 보정 후 정답 수다.

| | 전체 365 | FAQ 210 | STORE 52 | BOTH 51 | UNKNOWN 52 | holdout 157 |
| --- | --- | --- | --- | --- | --- | --- |
| EXAONE | 337 | 208 | 50 | 47 | **32** | 147 |
| gpt-oss | 362 / 361 / 360 | 208 | 52 / 51 / 50 | 50 | **52** | 156 / 155 / 154 |

| 오류 (실행당 건수) | EXAONE | gpt-oss |
| --- | --- | --- |
| 무관한 질문에 답하려 함 (UNKNOWN→FAQ) | 20 | 0 |
| 통신 질문을 거절 (→UNKNOWN) | 1 | 2~3 |
| 복합 질문 한쪽 누락 (BOTH→FAQ, 응답 형식 오류 포함) | 4 | 1 |
| FAQ·매장 혼동 | 3 | 0~1 |

- EXAONE은 김치찌개, 파이썬, 노트북 추천, 주택담보대출 같은 질문을 FAQ로 보낸다. gpt-oss는 0건이다.
- gpt-oss가 거절한 통신 질문은 "제가 못 가서 동생을 보내려는데 제가 가는 것보다 오래 걸릴까요"(EXAONE 포함 네 실행 모두)와 "멤버십 VIP면 영화 할인도 받을 수 있나요?"(3회 중 2회)다.
- 맥락 문항 "로밍 신청 방법도 알려주고 거기 몇 시까지 하는지도요"(이전 발언 "인천공항 매장 위치 알려줘")는 네 실행 모두 FAQ로만 분류했다. 문장에 "로밍"이라는 대상이 있어 문맥 해석이 이전 발언을 연결하지 않고, 라우팅은 "거기"가 어디인지 모른 채 질문만 받는다. 모델이 아니라 앱 흐름의 빈틈이다.

## 2단계: 요청 개수 판정 → 의도 분류가 gpt-oss면 끔 (켤 때는 gpt-oss, 프롬프트 v4)

의도 분류는 gpt-oss로 고정했다. 이 호출의 입력은 질문 하나뿐이다. 앱 흐름에서는 1단계가 나눈 문항에만 돌아서(gpt-oss 기준 365문항 중 51문항) 대부분 진짜 여러 요청이고, 합쳐야 하는 경우는 거의 시험되지 않는다. 그래서 FAQ 210문항 전체에 이 호출만 직접 보내 나누기와 합치기를 모두 시험했다. 프로브는 앱의 `requestInventory`를 그대로 불러 같은 응답 검증과 개수 보정(SINGLE·COMPARISON은 1)을 거친다.

### 요청 개수 기준 (팀 결정)

같은 업무를 이어 물어도 두 번째 질문의 답이 첫 질문의 답에 들어 있지 않은 다른 정보면 요청을 나눈다. 첫 질문 답의 일부를 다시 확인하는 것만 합친다.

- 합침: "개통 신분증은 어떤 걸 가져가나요? 면허증도 가능해요?" (프롬프트 예시)
- 나눔: "개통 취소 가능 기간이 언제까지예요? 그리고 취소하면 위약금 있어요?"

합치면 두 번째 질문에 맞는 FAQ가 없을 때 답에서 조용히 빠진다. 위 예에서 합친 문장으로 검색하면 철회 기간 FAQ만 나오고, "개통 취소 위약금"은 따로 검색해도 결과가 없다. 나누면 앱이 그 부분을 찾지 못했다고 알려 준다.

### 프롬프트 v4

`REQUEST_INVENTORY_PROMPT`에 규칙 문장만 넣었다(평가 문항과 닮은 예시는 넣지 않음). 버전은 `routing-request-inventory-v4`.

- 고객이 묻지 않았는데 답변에 필요한 설명 항목과, 고객이 직접 나열해 물은 정보(비용, 서류, 방법, 기간, 위약금, 가능 기종)를 구분한다. 후자는 정보마다 요청이다.
- '각각'이 붙어도 종류나 구성을 소개해 달라는 목록 설명은 한 요청이다.
- 같은 업무를 이어 물어도 다른 정보면 MULTIPLE이다. 첫 질문 답의 일부 확인만 SINGLE이다.
- 한 업무를 처리하는 방법이나 경로(온라인, 매장, 전화)를 함께 묻는 것은 한 요청이다.

### 결과 (FAQ 210문항, 여러 요청 57 / 한 요청 153)

| | 전체 | 한 요청 | 여러 요청 | 앱 흐름 대상 51 |
| --- | --- | --- | --- | --- |
| EXAONE v3 | 193 | 148 | 45 | 42 |
| gpt-oss v3 | 199 / 197 / 198 | 153 / 151 / 152 | 46 / 46 / 46 | 43 / 44 / 44 |
| EXAONE v4 | 200 | 145 | 55 | 51 |
| **gpt-oss v4** | **203 / 204 / 202** | **153 / 153 / 153** | 50 / 51 / 49 | 46 / 47 / 46 |

- 앱 흐름 대상은 1단계에서 gpt-oss가 FAQ 하위 질문을 2개 이상 만든 문항이다.
- gpt-oss v4는 한 요청을 잘못 나눈 경우가 3회 모두 0건이다. 남은 오류는 전부 여러 요청을 합친 것이다.
- EXAONE v4는 여러 요청은 잘 나누지만 한 요청을 잘못 나누는 경우가 7건으로 늘었다.
- 앱 흐름 대상(51문항, 그중 50이 여러 요청)에서는 EXAONE v4가 51로 gpt-oss v4(46~47)보다 낫다. gpt-oss는 의도 분류가 맞게 나눈 질문을 10%쯤 다시 하나로 합친다. gpt-oss의 전체 우세는 한 요청을 잘못 나누지 않는 데서 나오는데, 앱에서 이 호출은 의도 분류가 이미 나눈 질문에만 돌아 그런 문항이 거의 들어오지 않는다. 그래서 이 호출을 끄는 경우를 따로 쟀다(아래).

### 판정 호출을 끄면 (앱 라우팅 전체 경로)

요청 개수 판정은 #120에서 EXAONE 의도 분류가 너무 자주 나누던 것을 막으려고 넣은 장치다(1단계에서 EXAONE은 94번 나눴고 그중 61번이 잘못 나눈 것). 의도 분류가 gpt-oss면 이 역할이 거의 필요 없어, 호출을 끄고 의도 분류가 나눈 개수를 그대로 쓰는 경우를 쟀다. 끄더라도 하위 질문마다 서로 다른 원문 근거가 있는지 보는 확인(`IndependentQuestionPolicy`), 비교 질문 규칙, 3단계 검색어 검증은 그대로 돈다.

FAQ 210문항을 앱의 `routeSingleConsult`로 끝까지 돌려 최종 하위 질문 개수를 채점했다([run_request_count_skip_check.sh](../../../scripts/routing-call-comparison/run_request_count_skip_check.sh), [score_request_count_skip.py](../../../scripts/routing-call-comparison/score_request_count_skip.py)). 응답 시간은 모델이 하위 질문을 나눈 문항의 라우팅 전체 시간 중앙값이다.

| 구성 | 여러 요청 맞음 (57) | 합침 | 복합 질문 안내 | 한 요청 잘못 나눔 (153) | 응답 시간 |
| --- | --- | --- | --- | --- | --- |
| EXAONE 전체, 판정 켬 (지금 develop) | 51 | 2 | 4 (+ 한 요청 2) | 2 | 1.80초 |
| gpt-oss, 판정 켬 (라우터) | 45 / 48 / 47 | 12 / 8 / 10 | 0 | 0 | 1.85~2.09초 |
| **gpt-oss, 판정 끔 (라우터)** | **52 / 52 / 53** | 4 / 5 / 3 | 0 / 0 / 1 (+ 한 요청 1 / 0 / 0) | **0** | **1.41~1.61초** |
| gpt-oss, 판정 켬 (앱 클라이언트) | 47 / 48 / 48 | 8 / 8 / 8 | 1 / 1 / 1 | 0 | 1.78~1.86초 |
| **gpt-oss, 판정 끔 (앱 클라이언트)** | **52 / 53 / 53** | 3 / 2 / 4 | 1 / 1 / 0 | 0 / 2 / 1 | **1.57~1.73초** |

- 판정을 끄면 맞게 나뉜 질문을 다시 합치는 일이 3회 합계 24~30건에서 9~12건으로 준다. 남은 합침은 의도 분류가 처음부터 하나로 낸 것이다("7,700원 내면 택배로도 받을 수 있어요? 며칠 걸려요?" 등).
- 끄면 한 요청을 잘못 나누는 경우가 앱 클라이언트 3회에서 3건 생겼다. "요금제 변경하려는데 온라인이나 매장에서 하는 절차를 알려줘"(2회)와 "요금제 종류를 저가형, 무제한형으로 나눠서 각각 소개해줘"(1회)로, v4 판정 규칙(처리 경로, 목록 소개는 한 요청)이 잡던 유형이다. 나뉘어도 답이 두 부분으로 나올 뿐 내용이 빠지지는 않는다. 합침은 한쪽 질문에 맞는 FAQ가 답에서 빠질 수 있다.
- EXAONE 전체 구성은 나누기 정확도는 비슷하지만, 하위 질문의 원문 근거가 맞지 않아 복합 질문 안내로 끝나는 경우가 6건이다(고객이 다시 물어야 한다). EXAONE도 "저가형, 무제한형으로 나눠서 각각 소개해줘"를 판정 호출이 있는데도 나눴다.
- 결론: 의도 분류가 gpt-oss면 판정 호출을 끈다. TELME-182까지는 의도 분류가 EXAONE이라 설정 기본값을 켬(`ROUTING_REQUEST_INVENTORY_ENABLED=true`)으로 두었다가, TELME-194에서 라우팅을 기본 gpt-oss로 바꾸면서 기본을 끔(`false`)으로 바꿨다. 끄면 엑사원이 대신 판정하는 것이 아니라 이 호출 자체를 하지 않는다.

## 3단계: 검색어 검증 → gpt-oss, 재검색 후보에만 단일 검색어용 프롬프트

검색어 검증은 모델이 다듬은 검색어가 고객 원문의 뜻을 바꿨는지(unsafe) 판정한다. 복합 FAQ 하위 질문마다, 단일 FAQ의 원문 검색이 0건일 때 재검색 후보에, 그리고 문맥을 복원한 단일 질문(`groundedSingleFaqQuery`, 의도 분류가 이전 발언을 복원해 하위 질문을 나눴는데 요청 개수 판정이 한 요청으로 본 경우)에 돈다. 뜻이 바뀐 검색어를 통과시키면 다른 FAQ로 답할 수 있고(위험), 멀쩡한 검색어를 막으면 원문으로 검색할 뿐이다(손해가 작다). 문맥 복원 질문은 원문이 "그럼 신청 방법은?" 같은 짧은 후속 질문이라 막으면 손해가 더 크다.

### 평가셋 (검색어 321개)

[eval_routing_faithfulness.json](../../../scripts/data/eval_routing_faithfulness.json), 생성 스크립트 [build_faithfulness_set.py](../../../scripts/routing-call-comparison/build_faithfulness_set.py).

- 실제 입력 241개: 1단계 gpt-oss 1회차 의도 분류 출력에서 앱 코드로 만든 입력이다(복합 하위 질문 98, 재검색 후보 143). 앱이 모델을 부르지 않거나 입력이 다른 9건(업무 대상 규칙이 먼저 거절 4, 맥락 복원 단일 질문 3, 원문이 프롬프트 예시 2)은 뺐다.
- 일부러 뜻을 바꾼 검색어 30개(`SYN`): 실제 입력에는 뜻이 바뀐 검색어가 14개뿐이라 조건·부정 빠뜨리기, 없는 대상 넣기, 상황을 해결책으로 좁히기, 비교를 한쪽으로 바꾸기, 복합 질문에서 앞 대상 붙이기를 만들었다.
- 확인용 30개(`CHK`): 프롬프트를 고치기 전에 정답을 정해 쓰고 수정에는 쓰지 않았다.
- 문맥 복원 20개(`GRD`, PR #160 리뷰로 추가): 이전 발언과 짧은 후속 질문, 복원한 검색어다. 맞게 복원한 것 10개(리뷰 예시 "로밍 요금제는 어떻게 골라요?" → "그럼 신청 방법은?" → "로밍 요금제 신청 방법" 포함)와 현재 조건을 빠뜨리거나 이전 발언의 별도 요청·업무로 바꾼 것 10개다. 앱은 검색어의 단어가 모두 현재 발화나 이전 발언에 있을 때만 모델을 부르므로 그런 검색어만 썼다.
- 정답은 뜻 바뀜 64, 멀쩡함 249, 판단이 갈림 8(어느 판정이든 맞음)이다. 모델 결과를 보기 전에 붙였고 사람 검토 전이다.

### 프롬프트 수정

조건을 하나씩 대조하는 순서를 넣었다. 원문의 조건(~인데, ~하면, 사람·나이·금액·기간, 경로, 부정)을 찾아 검색어에 남았는지 대조하고, 검색어에만 있는 대상·기준과 좁힌 말을 찾고, 판단이 서지 않으면 unsafe로 본다.

이 순서를 모든 검색어에 쓰면 복합 하위 질문에서 다른 하위 질문의 요청을 빠진 조건으로 읽어 멀쩡한 하위 검색어를 100개 중 13~26개 막았다. 그래서 재검색 후보에만 쓴다(`FAQ_SINGLE_QUERY_FAITHFULNESS_PROMPT`, 버전 `routing-faq-faithfulness-single-v3`).

처음에는 하위 질문 개수(1개)로 골라서 문맥 복원 단일 질문에도 이 순서가 쓰였다. 이 경로는 이전 발언에서 복원한 대상이 검색어에 들어가 "검색어에만 있는 대상"으로 읽힌다. 문맥 복원 20개로 재 보니 맞게 복원한 검색어 10개 중 7~8개를 막았다(리뷰 예시도 3회 중 2회). 그래서 호출 목적으로 나눠(`findUnsafeFaqQueries`의 `searchCandidate`) 재검색 후보에만 쓰고, 복합 하위 질문과 문맥 복원 단일 질문은 원래 프롬프트(`routing-faq-faithfulness-v2-single-search`)를 쓴다.

## 4단계: 후속 분석 → gpt-oss, 프롬프트 v4

후속 분석은 되묻는 중인 조건 이름(`agent_visiting` 같은 영문 키)과 고객 답변을 받아, 답변 종류(조건 답변·보류·새 질문)와 조건 값(FILLED·DECLINED)을 낸다. v3부터는 앱이 실제로 되물은 질문 문장과 선택지도 함께 받는다.

### 평가셋 (70개)

[eval_routing_followup.json](../../../scripts/data/eval_routing_followup.json), 생성 스크립트 [build_followup_set.py](../../../scripts/routing-call-comparison/build_followup_set.py).

- 실제 입력 16개: TELME-174 대화 흐름 실행 DB(`consult_conditions`)에 남은 조건 이름과 고객 답변, 그리고 마지막 확인(채팅 API)에서 후속 분석이 놓친 입력 2개(CL-04 3회차 `FU-69`, CO-02 `FU-70`)다.
- 새로 쓴 34개: 지역·업무·예아니요 조건, 거절, 보류, 새 질문.
- 확인용 20개: 프롬프트를 고치기 전에 쓴 설명이 붙은 부정 답, 진짜 거절·보류, 유심 새로 받기와 신규 개통 구분.
- 모든 케이스에 앱이 되물은 질문과 선택지(`asked_questions`)를 적었다. 실제 입력은 DB에 남은 문장이다. 같은 조건 이름이라도 앱이 다른 문장으로 물은 경우는 그 문장을 쓴다(`FU-70`: "양도인과 양수인이 함께 매장에 오실 수 있나요?").
- 답변 종류가 맞고 정답에 적힌 조건이 모두 맞아야 정답이다. 정답은 사람 검토 전이다.

### 수정

- `FOLLOW_UP_SYSTEM_PROMPT` v2(`routing-follow-up-v2`): "아니요", "없어요", "아직 안 됐어요"처럼 부정하거나 부정 뒤에 사정을 덧붙인 답도 값(FILLED)이다. DECLINED는 대답 자체를 하지 않겠다고 할 때만이다. 유심이나 eSIM을 새로 받거나 바꾸는 것은 USIM_REISSUE, NEW_LINE은 새 회선을 개통할 때만이다.
- v3(`routing-follow-up-v3`): 되물은 질문 문장과 선택지를 함께 넘긴다(`askedConditionsOf`가 되물은 메시지의 마지막 줄과 `follow_ups`를 읽는다). 프롬프트에는 "되물은 질문이 있으면 고객 답변이 그 질문에 답하는지로 판단하고, 다른 사정을 덧붙여도 답이 들어 있으면 FILLED"를 더했다. 조건 이름만 받을 때는 "대리인이 대신 받으러 오실 예정이신가요?"(`agent_collecting`)에 "유심을 잃어버렸고 제가 직접 매장에 갈 거예요"라고 답하면 30번 중 5번을 보류나 새 질문으로 읽었다.
- v4(`routing-follow-up-v4`, PR #160 리뷰): 되물은 질문에 예·아니요로 딱 맞게 답하지 않고 자기 계획이나 상황(누가 가는지, 무엇이 있는지)을 말한 것도 답(FILLED)이고, 그런 답은 보류가 아니라고 적었다. 보류 예시에 "아직 못 정했어요"를, 보류에 "왜 묻는지 되묻는 것"을 더했고, 이 경우를 보여 주는 예시 하나(가족 방문 질문에 "저 혼자 갈 거예요")를 넣었다. CO-02 입력("양도인과 양수인이 함께 매장에 오실 수 있나요?" → "직접 매장에 가요")을 v3는 90번 중 7번만 답으로 읽었다(보류 66, 새 질문 16). 4단계 평가셋의 비슷한 케이스(`FU-11`)는 질문에 "직접"이 들어 있어 통과했다.
- v4 문구는 평가셋을 보며 네 번 고쳤다. 처음 문구는 보류를 좁게 적어 "그건 왜 물어보시는 거예요?"를 새 질문으로 읽었고, "value에는 고객 답변"을 업무 조건에도 적용해 업무 코드 대신 문장을 넣었다. 평가셋에 맞춘 면이 있어 마지막 확인(채팅 API)으로 다시 봤다.
- 규칙(`RuleBasedRoutingFallback.serviceTypeOfShortReply`): 업무를 묻거나 지역을 묻는 중 "명의변경이라고", "유심 재발급이요"처럼 업무 이름에 어미만 붙은 짧은 답은 모델 없이 업무 조건으로 읽는다. 전에는 버튼 문구와 글자가 같을 때만 읽어서, gpt-oss가 이런 답을 새 질문으로 보고 상담을 끊는 경우가 있었다. "하려고요"처럼 동사가 붙거나 다른 말이 섞인 답은 지금처럼 모델이 읽는다.

- 고치기 전 gpt-oss는 "아뇨 제가 직접 갈 거예요", "아니요 둘 다 직접 가요"를 3회 모두 거절로 읽었다. 앱의 `FaqClarificationAnswers`는 "아니요"·"없어요"만 단독으로 올 때만 값으로 바로잡아서, 설명이 붙은 답은 거절로 남았다.
- 진짜 거절("대답하기 싫어요", "개인정보라 말씀 못 드려요")과 보류("아직 정하지 못했어요", "그건 왜 물어보시는 거예요?")는 v4에서도 거절·보류로 처리한다.
- EXAONE은 부정하는 답을 대부분 거절로, "동생이 대신 갈 거예요"처럼 멀쩡한 답을 보류로 읽는다. v4로 50에서 57~59가 됐지만(2·3회차는 "아니요 작년에 가입했어요", "아직 1년 안 됐어요"도 거절로 읽었다) gpt-oss와 차이는 여전히 크다.
- 69~70개 결과의 버전 간 차이는 1~2개로 작다. 실패율이 높지 않은 입력은 3회 실행에서 잘 드러나지 않아, 실제로 놓친 입력은 같은 입력 반복으로 따로 쟀다(`co02-repeat-*` 키).

### 되묻기 흐름의 다시 묻기 (모델과 무관, 별도 이슈)

TELME-174에서 gpt-oss가 이미 답한 조건을 다시 물은 것은 후속 분석 모델 때문이 아니다. 조건 뽑기가 조건을 2개 만들면 앱은 하나씩 묻고, 후속 분석은 지금 묻는 조건 하나만 받는다. 그래서 같은 답에 들어 있던 두 번째 조건의 답을 버리고 다시 묻는다.

- "두 분이 모두 직접 오실 수 있나요?" → "둘 다 직접 매장에 갈 거예요" → "대리인으로 방문하실 예정인가요?"
- "개통 후 6개월이 지났나요?" → "1년 넘었고 남은 할부금은 없어요" → "남은 할부금을 모두 결제하셨나요?"

후속 분석에 아직 묻지 않은 조건까지 질문 문장과 함께 넘기거나, 조건 뽑기가 같은 정보를 두 조건으로 나누지 않게 해야 한다.

## 마지막 확인: 채팅 API 대화 흐름 22개

라우팅 호출 4개를 포함한 모든 LLM 호출을 gpt-oss로 두고, 이 브랜치 코드로 TELME-174의 대화 흐름 22개를 실제 채팅 API로 끝까지 진행했다. 마지막 답변을 근거 FAQ 원문과 대조해 판정했다(판정과 이유는 `results/step5-chat-flows/results.json.gz`의 `verdicts`). 앞서 판정한 실행과 턴별 응답 종류·근거 FAQ가 같은 대화는 그 판정을 쓰고, 처음 나온 결과만 새로 판정했다. 검색 임계값은 TELME-174와 같은 앱 기본값(0.72/0.88)이다. 후속 분석 v4와 검색어 검증 경로 분리를 넣은 코드로 돌린 결과가 기본이고, 그 전 코드는 `-v3`(후속 분석 v3)와 `-v2` 키에 있다.

| --- | --- | --- | --- | --- | --- | --- |
| 되묻기 완주 (8) | 6 | 6 / 5 / 7 | 6 / 6 / 4 | 5 / 5 / 7 | 6 / 6 / 5 | 7 / 4 / 7 |
| 복합 FAQ·비교 (5) | 4 | 3 / 3 / 3 | 3 / 3 / 3 | 3 / 3 / 3 | 3 / 3 / 4 | 3 / 3 / 3 |
| FAQ+매장 복합 (4) | 4 | 2 / 3 / 2 | 3 / 3 / 3 | 4 / 2 / 3 | 3 / 4 / 3 | 3 / 3 / 2 |
| 멀티턴 (5) | 2 | 2 / 2 / 3 | 3 / 3 / 3 | 3 / 3 / 3 | 2 / 3 / 2 | 3 / 3 / 3 |
| 합계 (22) | 16 | 13 / 13 / 15 | 15 / 15 / 13 | 15 / 13 / 16 | **14 / 16 / 14** | 16 / 13 / 15 |

- 합계 차이는 실행 간 흔들림 범위다.
- 요청 개수 판정을 끈 실행(`inventory-off-*` 키, `ROUTING_REQUEST_INVENTORY_ENABLED=false`)도 같은 범위다. 복합 FAQ 5개는 켠 실행과 같은 결과이고, 실패 원인도 켠 실행과 같은 되묻기 흐름·문맥 해석·검색 문제다.
- MT-01(인터넷 해지·장비 반납)과 MT-02(번호이동 수수료)는 FAQ에 답이 없어 정답을 근거 없음으로 고쳤다(TELME-174 판정도 같이 고침). 모든 구성이 매번 근거 없음으로 답했다.
- TELME-174 대비 좋아진 것: "유심 재발급 비용 알려주고 근처 매장도 찾아줘"(ST-01)는 TELME-174에서 3회 중 2회 FAQ 쪽을 정보 부족으로 답했는데 TELME-175에서는 9회 중 8회 7,700원과 매장을 안내했다.
- 라우팅 호출이 원인인 실패
  - CO-02("양도인과 양수인이 함께 매장에 오실 수 있나요?" → "직접 매장에 가요")는 v3까지 후속 분석(4번 호출) 문제였다. v3는 함께 오는지가 답에 없다고 보고 같은 질문을 다시 물었다. v4에서는 3회 모두 답으로 받는다. 그래도 앱이 두 번째 조건(대리인 방문·위임장)을 더 물어 서류 안내 없이 끝나서 대화는 실패다. 이 부분은 아래 되묻기 흐름 문제다.
  - CL-04("대리인이 대신 받으러 오실 예정이신가요?" → "유심을 잃어버렸고 제가 직접 매장에 갈 거예요")는 v2에서 3회 중 1회 다시 물었고 v3부터 맞는다(4단계 같은 입력 반복).
  - v4 코드로 돌린 결과에는 라우팅 호출이 원인인 실패가 없다.
- 라우팅 밖의 실패
  - 되묻기 흐름(실행마다 4~5건, 남은 실패의 대부분): 같은 답에 들어 있던 다음 조건을 다시 묻거나(CO-01, CL-01, CL-06, ST-03), 답한 뒤에도 두 번째 조건을 더 물어 답변 없이 끝난다(CL-07 위임장, CL-02 신분증, CO-02). 4단계 마지막 절의 별도 이슈로 고친다.
  - 문맥 해석: MT-03 "그럼 데이터 다 쓰면 어떻게 돼요?"(앞 질문 로밍)는 9회 모두 "데이터"를 대상으로 보고 앞 발언과 연결하지 않아 국내 요금제 FAQ(400kbps)로 답했다. 로밍 데이터 소진 FAQ는 없다. MT-04 "택배로도 받을 수 있나요?"(앞 질문 유심 재발급 비용)는 v4 3회 중 2회 문맥 해석이 앞 발언과 연결하지 않아 라우팅 전에 주제 확인으로 끝났다(v2·v3 6회는 모두 맞음).
  - 검색·근거 판정: MT-05 "미성년자 자녀한테도 돼요?"는 v4 3회 중 2회 검색이 "미성년자 사이 명의변경 불가" 쪽 FAQ를 가져와 "미성년자와는 명의변경이 안 된다"고 답했다. FAQ에는 어른이 미성년자에게 넘기는 건 된다는 답(NAME_CHANGE-0036, 0024)이 있어 사실과 반대다. 나머지는 되물음으로 끝났다.
- 대화 한 턴의 응답 시간(중앙값)은 v4에서 첫 턴 3.8초, 이어지는 턴 2.5초다. TELME-174 gpt-oss(3.8초, 2.7초)와 EXAONE(4.3초, 2.5초)보다 길지 않다.

## 앱 클라이언트 재확인

라우터와 앱 클라이언트의 요청 차이(JSON 지시, 출력 한도)로 결과가 달라지는지 보려고, 1~4단계의 gpt-oss 3회를 앱의 `BedrockClient`로 직접 다시 돌렸다(`TELME_ROUTING_GPTOSS_CLIENT=bedrock`, [run_app_client_check.sh](../../../scripts/routing-call-comparison/run_app_client_check.sh), 결과 `results/app-client-check/results.json.gz`). 설정은 운영 값(`llm.bedrock`: 추론 강도 low, 시간 제한 8초, 재시도 없음)과 같고 지역만 도쿄다. 1단계는 각 단계와 같이 의도 분류만 gpt-oss다.

| 단계 | 라우터 | 앱 클라이언트 |
| --- | --- | --- |
| 1 의도 분류 (보정 후, 365) | 362 / 361 / 360 | 358 / 359 / 357 |
| 2 요청 개수 판정 (210) | 203 / 204 / 202 | 203 / 203 / 204 |
| 2 중 앱 흐름 대상 (51) | 46 / 47 / 46 | 47 / 47 / 49 |
| 3 검색어 검증 (321) | 304 / 303 / 300 | 307 / 307 / 307 |
| 4 후속 분석 (70) | 70 / 70 / 70 | 70 / 69 / 70 |

- 출력 한도 256에서도 빈 응답이나 잘린 JSON은 없었다(클라이언트 오류 `INVALID_RESPONSE` 0건).
- 요청 개수 판정에서 8초 시간 초과가 3회에 1건씩 있었다. 앱은 이때 질문 분해를 보류하고 복합 질문 안내로 끝낸다.
- 1단계는 앱 클라이언트가 3~4개 적다. 응답 형식 오류는 없고, 경계에 있는 문항 몇 개의 판단이 달라졌다(예: "회사 심부름으로 매장에 갔는데 제 주민등록증만으로는 안 된다고 돌려보냈어요"를 UNKNOWN으로, "택배 배송 조회는 어디서 해요?"를 FAQ로). 반대로 앱 클라이언트만 맞힌 문항도 있다. EXAONE(337)과의 차이에 비하면 작아 결론은 같다.
- 2~4단계는 실행 간 흔들림 범위 안이다.

## 호출당 응답 시간

프로브 기록의 중앙값이다. EXAONE 칸은 로컬 GPU에서 잰 1회차 값이라 판단에 쓰지 않는다(엑사원 시간은 배포 환경에서 따로 잰다). 3·4단계 2·3회차는 1회차보다 10배 넘게 느려 측정 조건이 달랐던 것으로 보여 넣지 않았다. gpt-oss는 Bedrock 도쿄이고 3회를 동시에 돌린 값이라 실제보다 조금 높을 수 있다. 대화 한 턴 전체의 시간은 위 채팅 API 확인에 있다.

| 호출 | EXAONE (로컬) | gpt-oss |
| --- | --- | --- |
| 요청 개수 판정 | 143ms | 365ms |
| 검색어 검증 | 100ms | 575ms |
| 후속 분석 | 390ms | 616ms |

준비물(Ollama EXAONE, Bedrock 라우터, 검색 앱 실행 방법)은 각 스크립트 머리말에 있다. 1~4단계 채점 스크립트는 모두 결과 파일에 저장된 모델 판정을 지금 평가셋의 정답과 대조해 다시 계산한다. 라벨 검토로 정답을 고치면 평가셋만 다시 만들고(`build_*.py`) 채점 스크립트를 다시 돌리면 되며, 모델을 다시 부를 필요는 없다. 결과 파일의 `-v3`(2단계), `-v2`(3단계), `-v1`·`-v2`·`-v3`(4단계), `-v2`·`-v3`(마지막 확인) 키는 프롬프트를 고치기 전 결과다. 3단계의 `-grounded-single-prompt` 키는 문맥 복원 20개를 단일 검색어 프롬프트로 판정한 비교(앱 클라이언트, `TELME_ROUTING_GROUNDED_PROMPT=single`), 4단계의 `co02-repeat-*` 키는 CO-02 입력 90번 반복이다. 3·4단계의 `exaone-2`, `exaone-3` 키는 EXAONE 2·3회차다(`exaone`이 1회차). 2단계의 `exaone-full`, `route-*` 키는 판정 호출 켬/끔을 라우팅 전체 경로로 잰 결과, 마지막 확인의 `inventory-off-*` 키는 판정 호출을 끈 대화 흐름, `context-v32-inventory-off-*`·`context-v32-rules-inventory-off-*` 키는 여기에 #156의 1차·2차 보완을 넣은 대화 흐름, `exaone-context-v32-*` 키는 #156 1차 코드로 모든 호출을 EXAONE으로 둔 대화 흐름이다.

## 남은 일과 확인할 것

- 되묻기 흐름의 다시 묻기는 별도 이슈로 고친다(4단계 마지막 절). 마지막 확인에서 남은 실패의 대부분이 이것이다(CO-02 포함).
- 적용(TELME-182, 기본값은 TELME-194): `ROUTING_BEDROCK`(`telme.routing.bedrock`, 기본 `true`)이 라우팅 호출 4개를 gpt-oss로 부른다. Bedrock 호출이 실패하면 그 호출만 EXAONE으로 대체한다. 요청 개수 판정은 기본으로 하지 않는다(`ROUTING_REQUEST_INVENTORY_ENABLED=false`, 2단계 마지막 절). 의도 분류를 EXAONE으로 되돌리면(`ROUTING_BEDROCK=false`) 요청 개수 판정을 true로 켠다. 다른 호출의 전환 상태는 [gpt-oss-switch.md](../../04-operations/gpt-oss-switch.md)에 있다.
- 문맥 판정도 gpt-oss로 바꾸면 `CHAT_QUESTION_RESOLUTION_STABILITY_GUARDS=true`로 흔들림 보완을 켠다([context-resolution.md](context-resolution.md)). 문맥 판정의 출력 한도(최소 512)는 플래그와 관계없이 적용된다. 라우팅(256)·조건 뽑기 등 다른 호출의 출력 한도는 전환 PR에서 Bedrock 요청 쪽에서 함께 정한다. 같은 PR에서 문맥 판정 프롬프트의 비용 항목 목록(`위약금` 없음)과 1차의 요금 규칙이 위약금 질문에 미치는 영향을 확인한다([context-resolution.md](context-resolution.md)).
- 마지막 확인은 #156(문맥 해석 보강, TELME-165) 없이 돌렸다. #156을 넣고 요청 개수 판정을 끈 구성으로 다시 돌린 결과는 1차 보완(`context-v32-inventory-off-*` 키) 16 / 15 / 15, 2차 보완(`context-v32-rules-inventory-off-*` 키) 14 / 15 / 15로, 넣기 전(16 / 13 / 15)과 흔들림 범위 안에서 같다. 멀티턴은 모두 3 / 3 / 3이다. 같은 1차 코드로 모든 호출을 EXAONE으로 둔 결과(`exaone-context-v32-*` 키)는 16 / 16 / 17이다. MT-03 "데이터 다 쓰면"은 여전히 앞 발언과 연결하지 않고, MT-05는 검색 문제라 그대로다(자세한 내용은 [context-resolution.md](context-resolution.md)).
- 라우팅과 별개로 볼 것: MT-05처럼 반대 뜻의 FAQ로 답하는 검색·근거 판정 문제, 대상 같은 단어("데이터", "거기")가 있으면 앞 발언을 연결하지 않는 문맥 해석 문제, MT-04처럼 문맥 해석이 실행마다 연결 여부가 흔들리는 문제.
- 팀 확인
  - 판정 기준 "호출마다 더 나은 쪽, 흔들림 범위 안이면 gpt-oss".
  - 새로 쓴 137문항의 라벨, 3단계 검색어 정답(문맥 복원 20개 포함), 4단계 케이스 정답.
  - 액세서리 추천(아이폰 케이스, 블루투스 이어폰)과 상담원 채용·대리점 창업 4문항은 FAQ에 다루는 내용이 없어 UNKNOWN으로 정했다. 액세서리 2문항은 FAQ로 보내도 근거 없음 안내로 끝나 FAQ도 정답으로 본다. 해당 FAQ가 생기면 FAQ로 바꾼다.
- 별도로 볼 것
  - 대상 업무가 있는 문장 안의 "거기" 같은 지시어는 문맥 해석이 연결하지 않아 라우팅에서 풀리지 않는다(1단계 맥락 문항).
  - 요청 개수 판정에서 "각각" 없는 정보 나열과 같은 업무 이어 묻기는 gpt-oss v4에서도 합치는 경우가 남는다.
  - 검색어 검증은 복합 하위 질문의 앞 대상 붙이기와 전체 조건 빠뜨리기를 거의 못 잡는다.
  - 문맥 복원 단일 질문의 검색어 검증에서 gpt-oss는 맞게 복원한 검색어를 10개 중 2~4개 막는다(EXAONE 0~1개).
  - 후속 분석 v4는 평가셋을 보며 문구를 고쳐서 평가셋 밖의 답변에서도 같은지는 실제 사용 기록으로 다시 본다.

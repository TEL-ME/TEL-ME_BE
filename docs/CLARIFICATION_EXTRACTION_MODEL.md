# 되묻기 조건 뽑기 모델 비교 — 불필요한 되묻기 줄이기 (TELME-176)

작성 2026-10-16. 구조 설명은 `condition-extraction.md`에 있고, 이 문서는 **불필요한 되묻기를 줄이려고 한 분석과 모델 비교**를 기록한다.
수치는 모두 이 브랜치에서 로컬로 잰 값이다. Bedrock은 실행마다 결과가 조금씩 달라 **1회 측정**이면 잡음이 섞인다(2.3절).

## 요약

- **문제**: 정답 근거를 찾고도 안 물어도 되는 것을 되묻는 경우가 많다. 평가셋 32건 중 26건이 해당했고 엑사원은 그중 25건을 되물었다.
- **원인**: 불필요한 조건을 **모델이 처음부터 내고**, 걸러내기가 거의 못 걸렀다. 불필요한 되묻기는 모두 모델이 낸 조건에서 나왔다.
- **결론**: **조건 뽑기를 Bedrock(gpt-oss-120b)으로 바꾼다.** 평가셋 22% → 75%, 기존 평가 77% → 87~89%, 실제 채팅 흐름 32건의 되묻기 31 → 14개.
- **적용**: 설정 `telme.consult.faq-clarification.bedrock-extraction`(기본 **꺼짐**). 켜면 Bedrock으로 뽑고 실패하면 엑사원으로 대체한다.
- **대화 시나리오**: 플래그를 켠 33개 중 27개가 통과했고 나이 중복 질문 4건은 판정을 보강해 해결했다. 나머지 2건은 모델마다 달라지는 가정이라 엑사원 전용으로 표시했다(3.4절).
- **접은 것**: 뽑은 조건을 한 번 더 검증하는 단계(엑사원·Bedrock 모두 필요한 되묻기도 지워 이득이 없었다), 새로 쓴 gpt용 프롬프트(오히려 나빠졌다).

## 1. 문제

정답 근거를 찾았는데도 되묻기(`CLARIFICATION`)로 끝나는 질문을 모아 유형을 나눴다.

| 유형 | 예 |
| --- | --- |
| 질문에 이미 조건이 있음 | "요금을 **안 내면**…"에 "요금을 납부하셨나요?" |
| 엉뚱하거나 질문을 되돌림 | "처리 시간은?"에 "처리 시간이 얼마나 걸리나요?" |
| 일반 답을 먼저 줘도 됨 | 근거가 방법과 순서를 이미 안내하는데 "6개월이 지난 후 기기변경 절차는?"에 "할부금을 완납하셨나요?" |
| 되묻는 게 맞음 | "다른 통신사로 번호를 가져가려면?"에 미납 여부 |

앞의 세 유형은 바로 답해도 되는 질문이고, 되묻기가 답을 늦추고 고객을 귀찮게 한다.

## 2. 평가 방법

### 2.1 세 가지 평가

| 평가 | 위치 | 무엇을 보나 |
| --- | --- | --- |
| **평가셋 32건** | `src/test/resources/condition-eval/grading-cases.json`, `ClarificationGradingEval` | 질문과 근거 FAQ를 **직접 넣고** 조건 뽑기와 걸러내기만 본다. 검색과 판정기를 거치지 않는다 |
| **기존 평가 47건** | `condition-eval/cases.json`, `ConditionExtractionEval` | 검색 결과로 조건을 뽑는다. 필요한 되묻기를 유지하는지 본다 |
| **실제 채팅 흐름** | 로컬 스크립트(레포 밖) | 평가셋의 질문을 실제 API로 보낸다. 판정기와 조건 뽑기를 모두 거친다 |

평가셋 32건은 원래 180문항 평가셋(`eval_questions_180_multigold.json`)에서 답할 수 있는 질문 중, 정답 근거를 찾고도 되묻기로 끝난 질문을 모은 것이다.
대화 시나리오(로컬, 33개)는 되묻기 → 고객 답 → 최종 답변까지 흐름이 끊기지 않는지 따로 본다(3.4절).

### 2.2 평가셋 라벨

점수는 **조건 개수**로 센다.

| 종류 | 기대 | 개수 |
| --- | --- | ---: |
| 불필요(UNNECESSARY) | 조건 0개 | 26 |
| 필요(NEEDED) | 조건 1개 이상 | 6 |

라벨은 질문과 근거 FAQ를 읽고 정했고, 애매한 문항은 아래처럼 판단했다.

| 문항 | 판단 | 이유 |
| --- | --- | --- |
| EVAL-043 | 필요 | "지난달에 한 번 바꿨는데 **이달에** 또 바꿔도…"는 이번 달 변경 여부가 질문에 없다 |
| 007, 030, 047, 036 | 바로 답 | 근거가 방법·순서·한도를 이미 다 안내한다 |
| 050, 133 | 바로 답 | 정답 FAQ가 질문에 직접 답한다(부결이면 진행 불가, 인증하면 바로 적용) |
| 013 | 필요 | 근거가 "이번 달 2번까지"라 횟수 확인이 핵심이다 |

아래 시도 표에서 "구 라벨"이라고 적은 값은 불필요 20 · 필요 5 · 점수 제외 7 기준이고, 최종 비교(3.2절 첫 표)만 불필요 26 · 필요 6 기준이다.

### 2.3 Bedrock의 변동

같은 프롬프트를 두 번 재도 결과가 달랐다(둘 다 temperature 0, reasoning `low`).

| | 평가셋(구 라벨) | 기존 평가 |
| --- | ---: | ---: |
| 1회 | 72% (불필요 7) | 87% (맞음 41) |
| 2회 | 80% (불필요 5) | 89% (맞음 42) |

- 평가셋은 **±2개**, 기존 평가는 **±1개** 정도를 잡음으로 본다. 경계 질문(조건을 낼지 말지 애매한 것)만 뒤집힌다.
- 엑사원(올라마)은 같은 입력에 같은 결과가 나온다.
- 원인은 확정하지 못했다. 모델의 추론 과정이나 호출 환경의 계산 차이로 추정한다.

### 2.4 기준선 주의

기존 평가는 검색 결과로 조건을 뽑으므로 DB와 검색 상태에 따라 값이 달라진다. 엑사원 기준선이 67%였다가 검색이 비던 5문항이 점수에 들어와 분모가 42에서 47이 되면서 77%가 됐다. **같은 상태에서 잰 값끼리만 비교한다.**

## 3. 분석과 결과

### 3.1 원인 확인

평가셋 32건을 엑사원으로 돌려 모델 원본 응답과 걸러내기 결과를 비교했다.

- 불필요한 조건은 **모델이 처음부터 냈다.** 걸러내기가 일부라도 거른 것은 3건(042, 141, 145)이었고 그래도 불필요한 조건이 하나씩 남았다.
- 기존 걸러내기(`alreadySaid` 5글자 겹침, `known` 겹침, 근거 확인)는 **표현이 다르면 못 잡는다.** "안 내면"과 "납부하셨나요"는 글자가 겹치지 않는다.

| 유형 | 예 |
| --- | --- |
| 질문 전제를 되묻는다 | "요금을 안 내면…" → "요금을 납부하셨나요?", "대리인이 가면…" → "대리인이 방문하시는 건가요?" |
| `known`에 적고도 되묻는다 | `known`="할부금이 남아 있다" → "남은 할부금을 모두 납부하셨나요?" |
| 질문을 되돌린다 | "처리 시간은?" → "처리 시간이 얼마나 걸리나요?" |
| 질문과 무관한 조건 | "3개월 기준이 개통일이에요?" → "명의 변경을 하셨나요?" |
| 문장 문제 | 선호 질문("택배로 받으시겠습니까?"), 설명이 섞인 질문("(예: 30일 이내인지 확인 필요)") |

### 3.2 시도와 결과

**최종 비교** (평가셋은 최종 라벨, 조건 뽑기 모델만 다르다. 프롬프트는 같은 v1.9)

| 조건 뽑기 | 평가셋 32건 | 기존 평가 47건 | 평가 평균 시간 |
| --- | ---: | ---: | ---: |
| 엑사원(운영 기본) | 22% (불필요 25) | 77% | 약 2.8~3.6초 |
| **Bedrock** | **75%** (불필요 8) | **87~89%** | 약 1.5~1.8초 |

- 불필요한 되묻기가 26건 중 25건에서 **8건**으로 줄었고, 필요한 되묻기 6건은 모두 유지했다(놓침 0).
- 기존 평가는 1회차 87%, 2회차 89%라 범위로 적는다.

**시도 전체** (구 라벨 기준 평가셋과 기존 평가. 값이 다른 시도끼리 직접 비교하지 않는다)

| 시도 | 평가셋 | 기존 평가 | 판단 |
| --- | ---: | ---: | --- |
| 검증 없음(엑사원) | 20% | 77% | 기준선 |
| 엑사원 + 조건 검증, "버릴지" 직접 질문 | 20% | – | 모델이 전부 KEEP, 효과 없음 |
| 엑사원 + 검증, 질문에서 말을 복사 | 92% / 68% | 49% | 필요한 조건까지 지움 |
| 엑사원 + 검증, 조건에 직접 답 | 44% | 62% | 둘 다 애매 |
| 엑사원 + 검증 + 복사 확인 규칙 | 44% | 60% | 이득이 작고 호출이 늘어 접음 |
| Bedrock + 검증, 조건에 직접 답 | 64% | 55% | 평가셋은 좋아졌으나 기존 평가는 나빠짐 |
| **Bedrock 조건 뽑기, 프롬프트 v1.8** | **76%** | **81%** | 채택 방향 |
| **Bedrock 조건 뽑기, 프롬프트 v1.9** | **72~80%** | **87~89%** | **채택** |
| Bedrock 조건 뽑기, gpt용으로 새로 쓴 프롬프트 | 64% | 79% | 헛짚음이 1에서 5건으로 늘어 접음 |
| Bedrock 조건 뽑기, v1.9 + 규칙 보강(gpt-v1.1) | 80% | 87% | 놓침 4에서 5건, 효과 없음 |

- **검증 단계**는 불필요한 되묻기를 줄이면 필요한 되묻기도 같이 지웠다. 모델이 "질문에 답이 있다"를 주제어 수준에서 판단해("미성년자도 가입돼요?"의 "미성년자"를 나이 조건의 답으로 복사) 둘을 구별하지 못했다. 엑사원은 프롬프트를 바꿀 때마다 한쪽이 좋아지면 다른 쪽이 나빠졌고, Bedrock으로 바꿔도 같은 패턴이었다.
- **조건 뽑기 자체를 Bedrock으로** 바꾸는 편이 두 점수 모두 가장 좋았다. 검증 단계 없이 처음부터 불필요한 조건을 덜 낸다.
- v1.9는 v1.8에 "답변(A)이 경우별로 다른 내용을 나열하면 어느 경우인지 말하지 않았을 때 그 구분을 조건으로 적는다"는 규칙 한 문장을 더한 것이다. 기존 평가의 놓침이 7건에서 4건으로 줄었다.

### 3.3 실제 채팅 흐름

플래그를 켠 백엔드(조건 뽑기 Bedrock + 판정기)로 평가셋 32건의 질문을 보냈다.

| | 엑사원 조건 뽑기 | **Bedrock 조건 뽑기** |
| --- | ---: | ---: |
| 되묻기 | 31 | **14** |
| 바로 답변 | 1 | 18 |

| 라벨 | 엑사원 | Bedrock |
| --- | --- | --- |
| 불필요 26건 | 25건이 되묻기로 남음 | **8건 남음**(005, 010, 048, 050, 078, 133, 145, 148) |
| 필요 6건 | 6건 모두 되묻기 유지 | **6건 모두 되묻기 유지** |

- 평가셋 측정(불필요 5~8건 남음)과 실제 흐름(8건 남음)이 비슷해 평가셋이 실제를 잘 반영한다.
- 조건 뽑기 호출 30회 중 1회가 실패했고 **엑사원으로 대체**되어 그대로 진행됐다.
- Bedrock 호출은 판정기 81회 + 조건 뽑기 30회 = 111회였다(`llm_generations` 기준). 질문당 약 3~4회다.

### 3.4 대화 시나리오

되묻기 → 고객 답 → 최종 답변까지 이어지는 시나리오 33개를 플래그를 켠 백엔드(조건 뽑기 Bedrock + 판정기)로 1회씩 실행했다.
이전에 엑사원 조건 뽑기로 3회씩 99회 돌렸을 때는 99/99였다. 횟수가 달라 직접 비교하지 않는다.

| | 결과 |
| --- | --- |
| 통과 | 27/33 (81%) |
| 하드 실패(응답 없음, 엉뚱한 상담 연결, 같은 질문 반복, 오류) | 0건 |

통과하지 못한 6건과 처리 결과다.

| 시나리오 | 내용 | 처리 |
| --- | --- | --- |
| `faq-minor-*` 4건 | "미성년자도 가입가능한가요?"에 "만 14세 이상이신가요?"를 묻고 고객이 답한 뒤 **"만 18세 이하이신가요?"를 또 물었다.** FAQ에 나이 기준이 둘이라 Bedrock이 조건을 둘 냈다 | **수정**: 같은 대상의 나이 기준(`만 N세`)은 이상·이하로 나눠도 같은 사실로 보도록 `asksTheSame`에 규칙을 더했다. 다시 돌려 **4/4 통과** |
| `compound-docs-and-plan` | 복합 질문에서 "예"로 답한 뒤 최종 답변에 "요금제"가 없다 | 고장이 아니다. 엑사원은 요금제 변경에 조건을 묻고 번호이동을 먼저 답했는데, Bedrock은 요금제 변경을 바로 답하고 번호이동에 미납 조건을 물었다. 시나리오가 엑사원의 순서를 가정한 것이라 **엑사원 전용으로 표시** |
| `choice-docs-button` | "유심 재발급 받으려면 서류 뭐 필요해요"에 본인·대리인 버튼이 붙지 않는다 | 고장이 아니다. 엑사원은 "본인 직접 방문하시나요? 아니면 대리인이…"로 선택지를 냈고 Bedrock은 "본인 직접 받으시겠습니까?"를 예/아니요로 냈다. 버튼은 모델이 낸 선택지로 만들어지므로 **엑사원 전용으로 표시** |

- 나이 시나리오 재실행의 Bedrock 호출은 판정기 24회 + 조건 뽑기 4회 = 28회였다. 최초 33개 실행은 판정기 157회 + 조건 뽑기 26회 = 183회였고 조건 뽑기 1회가 실패해 엑사원으로 대체됐다(`llm_generations` 기준).
- 엑사원 전용 시나리오 2개는 `--bedrock` 옵션으로 건너뛴다. 수정 뒤 전체 시나리오를 한 번에 다시 돌려 확인하지는 않았다(나이 4건만 재실행).

## 4. 적용

| 설정 | 동작 |
| --- | --- |
| `telme.consult.faq-clarification.bedrock-extraction=false`(기본) | 조건 뽑기를 엑사원으로 한다. 지금 운영과 같다 |
| `true` | Bedrock(`llm.bedrock`)으로 뽑는다. 호출이 실패하거나 Bedrock이 꺼져 있으면 엑사원으로 뽑는다 |

- 환경 변수는 `CONSULT_FAQ_CLARIFICATION_BEDROCK`이다. 프롬프트는 두 모델이 같은 v1.9를 쓴다.
- `FallbackLlmClient`가 Bedrock 실패 시 같은 요청을 엑사원으로 다시 보낸다.
- Bedrock 키는 `AWS_BEARER_TOKEN_BEDROCK` 또는 AWS 기본 자격 증명을 쓴다(판정기와 같다).
- 조건 뽑기가 Bedrock이 되면 FAQ 근거가 있는 모든 질문에서 Bedrock을 한 번 더 부른다. 판정기는 점수가 애매한 질문에만 부르지만 조건 뽑기는 근거가 있으면 매번 부른다.

## 5. 한계

- **놓침이 4~5건 남는다.** "로밍 요금제 얼마예요", "요금 안 냈는데 정지되나요", "폰 새로 만들려는데 뭐 챙겨야 해요?"처럼 근거가 경우별 내용을 나열하는 질문이다. 모델이 "모두 나열해 답하면 된다"고 본다. 규칙을 구체화하고 예시를 넣어도(gpt-v1.1) 바뀌지 않았다. 조건 없이 전체를 안내하는 것이라 틀린 답은 아니다.
- **불필요한 되묻기가 8건 남는다.** 평가셋 기준으로 010, 048, 050, 059, 078, 145, 148, 154이고 질문과 무관한 조건이 대부분이다. 048은 두 번째 조건이 합리적일 수 있어 라벨이 애매하다.
- **실행마다 달라진다.** 경계 질문은 같은 설정에서도 조건이 나왔다 안 나왔다 한다(일시정지와 해지, 개통 4개월 번호이동 등).
- **질문 모양이 모델마다 다르다.** Bedrock은 선택형 질문("A인가요, B인가요")을 예/아니요로 내서 선택지 버튼이 안 붙을 수 있다. 같은 대상의 나이 기준은 하나로 합쳤지만 다른 종류의 조건이 여러 개 나오는 경우는 합치지 않는다(3.4절).
- **추론 강도는 `low`다.** `llm.bedrock.reasoning-effort`가 모든 Bedrock 호출에 같이 적용된다(판정기와 조건 뽑기). `medium` 이상은 재지 않았다.
- **1회 측정이다.** 평가셋 32건은 1~2건이 점수 3~6%p라 작은 차이는 구별하지 못한다.
- 평가셋 라벨은 한 사람이 정했고 애매한 문항(048 등)은 다르게 볼 수 있다.
- 평가 호출은 `executionId`가 없어 `llm_generations`에 남지 않는다. 호출 수는 `CountingLlmClient`가 센다.

## 6. 재현

평가셋과 기존 평가는 `LLM_PROVIDER=ollama`일 때만 돈다.

```bash
# 엑사원 (무료)
LLM_PROVIDER=ollama TELME_DB_TESTS=true POSTGRES_PORT=5432 \
  ./gradlew test --tests '*ClarificationGradingEval' --tests '*ConditionExtractionEval' -i

# Bedrock (유료. 호출 수는 BEDROCK_CALLS 줄에 찍힌다)
AWS_BEARER_TOKEN_BEDROCK=<Bedrock API 키> EVAL_EXTRACTOR=bedrock LLM_BEDROCK_ENABLED=true \
  LLM_PROVIDER=ollama TELME_DB_TESTS=true POSTGRES_PORT=5432 \
  ./gradlew test --tests '*ClarificationGradingEval' --tests '*ConditionExtractionEval' -i
```

- `EVAL_ONLY=질문앞부분|질문앞부분`(기존 평가)로 일부 질문만 돌릴 수 있다.
- 한 번 재면 평가셋 32회, 기존 평가 47회 안팎의 Bedrock 호출이 나간다.

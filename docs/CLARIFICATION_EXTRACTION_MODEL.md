# 되묻기 조건 뽑기 모델 비교 — 불필요한 되묻기 줄이기 (TELME-176)

작성 2026-10-16. 구조 설명은 `condition-extraction.md`에 있고, 이 문서는 **불필요한 되묻기를 줄이려고 한 분석과 모델 비교**를 기록한다.
수치는 모두 이 브랜치에서 로컬로 잰 값이다. Bedrock은 실행마다 결과가 조금씩 달라 **1회 측정**이면 잡음이 섞인다(2.3절). 그래서 최종 비교는 엑사원과 Bedrock 모두 **3회씩** 반복해 범위로 적었다(3.2절, 7절).

## 요약

- **문제**: 정답 근거를 찾고도 안 물어도 되는 것을 되묻는 경우가 많다. 평가셋 32건 중 26건이 해당했고 엑사원은 그중 25건을 되물었다.
- **원인**: 불필요한 조건을 **모델이 처음부터 내고**, 걸러내기가 거의 못 걸렀다. 불필요한 되묻기는 모두 모델이 낸 조건에서 나왔다.
- **결론**: **조건 뽑기를 Bedrock(gpt-oss-120b)으로 바꾼다.** 평가셋 22% → 72~81%, 기존 평가 77% → 85%(각 3회), 실제 채팅 흐름 32건의 되묻기 31 → 14개(TELME-176, 1회).
- **적용**: 설정 `telme.consult.faq-clarification.bedrock`(기본 **켜짐**). Bedrock으로 뽑고 실패하면 엑사원으로 대체한다. TELME-185에서는 기본을 꺼짐으로 두었다가 TELME-194에서 켜짐으로 바꿨다. 키 이름은 TELME-194에서 `bedrock-extraction`에서 `bedrock`으로 통일했고 환경 변수는 그대로다.
- **대화 시나리오**: 플래그를 켠 33개 중 27개가 통과했고 나이 중복 질문 4건은 판정을 보강해 해결했다. 나머지 2건은 모델마다 달라지는 가정이라 엑사원 전용으로 표시했다(3.4절).
- **접은 것**: 뽑은 조건을 한 번 더 검증하는 단계(엑사원·Bedrock 모두 필요한 되묻기도 지워 이득이 없었다), 새로 쓴 gpt용 프롬프트(오히려 나빠졌다).

## 1. 문제

정답 근거를 찾았는데도 되묻기(`CLARIFICATION`)로 끝나는 질문을 모아 유형을 나눴다.

| 유형 | 예 |
| --- | --- |
| 질문에 이미 조건이 있음 | "요금을 **안 내면**…"에 "요금을 납부하셨나요?" |
| 엉뚱하거나 질문을 되돌림 | "처리 시간은?"에 "처리 시간이 얼마나 걸리나요?" |
| 일반 답을 먼저 줘도 됨 | 근거가 방법과 순서를 이미 안내하는데 "6개월이 지난 후 기기변경 절차는?"에 "할부금을 완납하셨나요?" |
| 되묻는 게 맞음 | "다른 통신사로 번호를 가져가려면?"에 미납 여부 |

앞의 세 유형은 바로 답해도 되는 질문이고, 되묻기가 답을 늦추고 고객을 귀찮게 한다.

## 2. 평가 방법

### 2.1 세 가지 평가

| 평가 | 위치 | 무엇을 보나 |
| --- | --- | --- |
| **평가셋 32건** | `src/test/resources/condition-eval/grading-cases.json`, `ClarificationGradingEval` | 질문과 근거 FAQ를 **직접 넣고** 조건 뽑기와 걸러내기만 본다. 검색과 판정기를 거치지 않는다 |
| **기존 평가 47건** | `condition-eval/cases.json`, `ConditionExtractionEval` | 검색 결과로 조건을 뽑는다. 필요한 되묻기를 유지하는지 본다 |
| **실제 채팅 흐름** | 로컬 스크립트(레포 밖) | 평가셋의 질문을 실제 API로 보낸다. 판정기와 조건 뽑기를 모두 거친다 |

평가셋 32건은 원래 180문항 평가셋(`eval_questions_180_multigold.json`)에서 답할 수 있는 질문 중, 정답 근거를 찾고도 되묻기로 끝난 질문을 모은 것이다.
대화 시나리오(로컬, 33개)는 되묻기 → 고객 답 → 최종 답변까지 흐름이 끊기지 않는지 따로 본다(3.4절).

### 2.2 평가셋 라벨

점수는 **조건 개수**로 센다.

| 종류 | 기대 | 개수 |
| --- | --- | ---: |
| 불필요(UNNECESSARY) | 조건 0개 | 27 |
| 필요(NEEDED) | 조건 1개 이상 | 5 |

TELME-218에서 되묻기 정책을 바꿔 EVAL-043을 필요에서 불필요로 옮겼다(9절). 3~8절의 수치는 바꾸기 전 라벨(불필요 26, 필요 6) 기준이다.

라벨은 질문과 근거 FAQ를 읽고 정했고, 애매한 문항은 아래처럼 판단했다.

| 문항 | 판단 | 이유 |
| --- | --- | --- |
| EVAL-043 | 불필요(TELME-218, 이전에는 필요) | 근거 "이번 달에 아직 안 바꾸셨으면 됩니다. 한 달에 한 번입니다"를 그대로 전하면 답이 된다. 이전 판단은 "이번 달 변경 여부가 질문에 없다"였다 |
| 007, 030, 047, 036 | 바로 답 | 근거가 방법·순서·한도를 이미 다 안내한다 |
| 050, 133 | 바로 답 | 정답 FAQ가 질문에 직접 답한다(부결이면 진행 불가, 인증하면 바로 적용) |
| 013 | 필요 | 근거가 "이번 달 2번까지"라 횟수 확인이 핵심이다 |

아래 시도 표에서 "구 라벨"이라고 적은 값은 불필요 20 · 필요 5 · 점수 제외 7 기준이고, 최종 비교(3.2절 첫 표)만 불필요 26 · 필요 6 기준이다.

### 2.3 Bedrock의 변동

같은 프롬프트로 세 번 재도 Bedrock은 결과가 달랐다(모두 temperature 0, reasoning `low`). 엑사원은 세 번 모두 사례별로 같았다.

| Bedrock | 평가셋 | 기존 평가 |
| --- | ---: | ---: |
| 1회 | 72% (불필요 9) | 85% (맞음 40) |
| 2회 | 81% (불필요 6) | 85% (맞음 40) |
| 3회 | 78% (불필요 7) | 85% (맞음 40) |

- 평가셋은 **±3개**(불필요 6~9건)를 잡음으로 본다. 기존 평가는 점수가 같아도 틀린 질문이 1~2개씩 달라진다. 경계 질문(조건을 낼지 말지 애매한 것)만 뒤집힌다.
- 엑사원(올라마)은 같은 입력에 같은 결과가 나온다. 3회 모두 사례별 결과가 같았다.
- 원인은 확정하지 못했다. 모델의 추론 과정이나 호출 환경의 계산 차이로 추정한다.
- TELME-176 초판의 값(Bedrock 평가셋 75%, 기존 평가 87%, 89%)은 같은 코드와 같은 평가로 재현되지 않아 이 6회로 교체했다(7절).

### 2.4 기준선 주의

기존 평가는 검색 결과로 조건을 뽑으므로 DB와 검색 상태에 따라 값이 달라진다. 엑사원 기준선이 67%였다가 검색이 비던 5문항이 점수에 들어와 분모가 42에서 47이 되면서 77%가 됐다. **같은 상태에서 잰 값끼리만 비교한다.**

## 3. 분석과 결과

### 3.1 원인 확인

평가셋 32건을 엑사원으로 돌려 모델 원본 응답과 걸러내기 결과를 비교했다.

- 불필요한 조건은 **모델이 처음부터 냈다.** 걸러내기가 일부라도 거른 것은 3건(042, 141, 145)이었고 그래도 불필요한 조건이 하나씩 남았다.
- 기존 걸러내기(`alreadySaid` 5글자 겹침, `known` 겹침, 근거 확인)는 **표현이 다르면 못 잡는다.** "안 내면"과 "납부하셨나요"는 글자가 겹치지 않는다.

| 유형 | 예 |
| --- | --- |
| 질문 전제를 되묻는다 | "요금을 안 내면…" → "요금을 납부하셨나요?", "대리인이 가면…" → "대리인이 방문하시는 건가요?" |
| `known`에 적고도 되묻는다 | `known`="할부금이 남아 있다" → "남은 할부금을 모두 납부하셨나요?" |
| 질문을 되돌린다 | "처리 시간은?" → "처리 시간이 얼마나 걸리나요?" |
| 질문과 무관한 조건 | "3개월 기준이 개통일이에요?" → "명의 변경을 하셨나요?" |
| 문장 문제 | 선호 질문("택배로 받으시겠습니까?"), 설명이 섞인 질문("(예: 30일 이내인지 확인 필요)") |

### 3.2 시도와 결과

**최종 비교** (평가셋은 최종 라벨, 조건 뽑기 모델만 다르다. 프롬프트는 같은 v1.9, 각 3회)

| 조건 뽑기 | 평가셋 32건 | 기존 평가 47건 | 평가 평균 시간 |
| --- | ---: | ---: | ---: |
| 엑사원(운영 기본) | 22% (불필요 25), 3회 모두 같음 | 77%, 3회 모두 같음 | 약 3.7~3.8초 (로컬 Ollama, 판단에 쓰지 않음) |
| **Bedrock** | **72~81%** (불필요 6~9) | **85%** (3회 모두) | 약 1.5~1.7초 |

- 엑사원 시간은 로컬 Ollama에서 잰 값이다. 배포 환경(vLLM)에서는 따로 재야 해서 모델 선택에는 쓰지 않았다.
- 불필요한 되묻기가 26건 중 25건에서 **6~9건**으로 줄었고, 필요한 되묻기 6건은 모두 유지했다(놓침 0, 3회 모두).
- 기존 평가는 3회 모두 85%(맞음 40)지만 틀린 질문은 회차마다 조금 다르다. 3 대 3 비교표와 회차별 결과는 7절에 있다.

**시도 전체** (구 라벨 기준 평가셋과 기존 평가. 값이 다른 시도끼리 직접 비교하지 않는다)

| 시도 | 평가셋 | 기존 평가 | 판단 |
| --- | ---: | ---: | --- |
| 검증 없음(엑사원) | 20% | 77% | 기준선 |
| 엑사원 + 조건 검증, "버릴지" 직접 질문 | 20% | – | 모델이 전부 KEEP, 효과 없음 |
| 엑사원 + 검증, 질문에서 말을 복사 | 92% / 68% | 49% | 필요한 조건까지 지움 |
| 엑사원 + 검증, 조건에 직접 답 | 44% | 62% | 둘 다 애매 |
| 엑사원 + 검증 + 복사 확인 규칙 | 44% | 60% | 이득이 작고 호출이 늘어 접음 |
| Bedrock + 검증, 조건에 직접 답 | 64% | 55% | 평가셋은 좋아졌으나 기존 평가는 나빠짐 |
| **Bedrock 조건 뽑기, 프롬프트 v1.8** | **76%** | **81%** | 채택 방향 |
| **Bedrock 조건 뽑기, 프롬프트 v1.9** | **72~80%** | **87~89%** | **채택** (176 당시 값. 최종 3회는 7절) |
| Bedrock 조건 뽑기, gpt용으로 새로 쓴 프롬프트 | 64% | 79% | 헛짚음이 1에서 5건으로 늘어 접음 |
| Bedrock 조건 뽑기, v1.9 + 규칙 보강(gpt-v1.1) | 80% | 87% | 놓침 4에서 5건, 효과 없음 |

- **검증 단계**는 불필요한 되묻기를 줄이면 필요한 되묻기도 같이 지웠다. 모델이 "질문에 답이 있다"를 주제어 수준에서 판단해("미성년자도 가입돼요?"의 "미성년자"를 나이 조건의 답으로 복사) 둘을 구별하지 못했다. 엑사원은 프롬프트를 바꿀 때마다 한쪽이 좋아지면 다른 쪽이 나빠졌고, Bedrock으로 바꿔도 같은 패턴이었다.
- **조건 뽑기 자체를 Bedrock으로** 바꾸는 편이 두 점수 모두 가장 좋았다. 검증 단계 없이 처음부터 불필요한 조건을 덜 낸다.
- v1.9는 v1.8에 "답변(A)이 경우별로 다른 내용을 나열하면 어느 경우인지 말하지 않았을 때 그 구분을 조건으로 적는다"는 규칙 한 문장을 더한 것이다. 기존 평가의 놓침이 7건에서 4건으로 줄었다.

### 3.3 실제 채팅 흐름

플래그를 켠 백엔드(조건 뽑기 Bedrock + 판정기)로 평가셋 32건의 질문을 보냈다.

| | 엑사원 조건 뽑기 | **Bedrock 조건 뽑기** |
| --- | ---: | ---: |
| 되묻기 | 31 | **14** |
| 바로 답변 | 1 | 18 |

| 라벨 | 엑사원 | Bedrock |
| --- | --- | --- |
| 불필요 26건 | 25건이 되묻기로 남음 | **8건 남음**(005, 010, 048, 050, 078, 133, 145, 148) |
| 필요 6건 | 6건 모두 되묻기 유지 | **6건 모두 되묻기 유지** |

- 평가셋 측정(불필요 5~8건 남음)과 실제 흐름(8건 남음)이 비슷해 평가셋이 실제를 잘 반영한다.
- 조건 뽑기 호출 30회 중 1회가 실패했고 **엑사원으로 대체**되어 그대로 진행됐다.
- Bedrock 호출은 판정기 81회 + 조건 뽑기 30회 = 111회였다(`llm_generations` 기준). 질문당 약 3~4회다.

### 3.4 대화 시나리오

되묻기 → 고객 답 → 최종 답변까지 이어지는 시나리오 33개를 플래그를 켠 백엔드(조건 뽑기 Bedrock + 판정기)로 1회씩 실행했다.
이전에 엑사원 조건 뽑기로 3회씩 99회 돌렸을 때는 99/99였다. 횟수가 달라 직접 비교하지 않는다.

| | 결과 |
| --- | --- |
| 통과 | 27/33 (81%) |
| 하드 실패(응답 없음, 엉뚱한 상담 연결, 같은 질문 반복, 오류) | 0건 |

통과하지 못한 6건과 처리 결과다.

| 시나리오 | 내용 | 처리 |
| --- | --- | --- |
| `faq-minor-*` 4건 | "미성년자도 가입가능한가요?"에 "만 14세 이상이신가요?"를 묻고 고객이 답한 뒤 **"만 18세 이하이신가요?"를 또 물었다.** FAQ에 나이 기준이 둘이라 Bedrock이 조건을 둘 냈다 | **수정**: 같은 대상의 나이 기준(`만 N세`)이 둘 이상이면 하나를 버리지 않고 "나이가 어떻게 되시나요?" 한 질문(직접 입력)으로 합친다. 하나를 버리면 남은 기준(예: 65세)이 확인되지 않기 때문이다. 처음에는 중복으로 판정해 버렸고 그때 다시 돌려 4/4 통과했다. 합치는 방식으로 바꾼 뒤에는 단위 테스트와 4건 1회 재실행(질문 "나이가 어떻게 되시나요?" 후 나이를 답하게 바꿈)으로 **4/4 통과**를 확인했다 |
| `compound-docs-and-plan` | 복합 질문에서 "예"로 답한 뒤 최종 답변에 "요금제"가 없다 | 고장이 아니다. 엑사원은 요금제 변경에 조건을 묻고 번호이동을 먼저 답했는데, Bedrock은 요금제 변경을 바로 답하고 번호이동에 미납 조건을 물었다. 시나리오가 엑사원의 순서를 가정한 것이라 **엑사원 전용으로 표시** |
| `choice-docs-button` | "유심 재발급 받으려면 서류 뭐 필요해요"에 본인·대리인 버튼이 붙지 않는다 | 고장이 아니다. 엑사원은 "본인 직접 방문하시나요? 아니면 대리인이…"로 선택지를 냈고 Bedrock은 "본인 직접 받으시겠습니까?"를 예/아니요로 냈다. 버튼은 모델이 낸 선택지로 만들어지므로 **엑사원 전용으로 표시** |

- 나이 시나리오 재실행의 Bedrock 호출은 판정기 24회 + 조건 뽑기 4회 = 28회였다. 최초 33개 실행은 판정기 157회 + 조건 뽑기 26회 = 183회였고 조건 뽑기 1회가 실패해 엑사원으로 대체됐다(`llm_generations` 기준).
- 엑사원 전용 시나리오 2개는 `--bedrock` 옵션으로 건너뛴다. 수정 뒤 전체 시나리오를 한 번에 다시 돌려 확인하지는 않았다(나이 4건만 재실행).

## 4. 적용

| 설정 | 동작 |
| --- | --- |
| `telme.consult.faq-clarification.bedrock=true`(기본) | Bedrock(`llm.bedrock`)으로 뽑는다. 호출이 실패하거나 Bedrock이 꺼져 있으면 엑사원으로 뽑는다 |
| `false` | 조건 뽑기를 엑사원으로 한다 |

- 환경 변수는 `CONSULT_FAQ_CLARIFICATION_BEDROCK`이다. 기본값은 켜짐이다. 프롬프트는 두 모델이 같은 v1.9를 쓴다(8절에서 모델별 후보를 시도했지만 나은 것이 없어 분리하지 않았다).
- `FallbackLlmClient`가 Bedrock 실패 시 같은 요청을 엑사원으로 다시 보낸다.
- Bedrock 키는 `AWS_BEARER_TOKEN_BEDROCK` 또는 AWS 기본 자격 증명을 쓴다(판정기와 같다).
- 조건 뽑기가 Bedrock이 되면 FAQ 근거가 있는 모든 질문에서 Bedrock을 한 번 더 부른다. 판정기는 점수가 애매한 질문에만 부르지만 조건 뽑기는 근거가 있으면 매번 부른다.

## 5. 한계

- **놓침이 5~6건 남는다.** "로밍 요금제 얼마예요", "요금 안 냈는데 정지되나요", "폰 새로 만들려는데 뭐 챙겨야 해요?"처럼 근거가 경우별 내용을 나열하는 질문이다. 모델이 "모두 나열해 답하면 된다"고 본다. 규칙을 구체화하고 예시를 넣어도(gpt-v1.1) 바뀌지 않았다. 조건 없이 전체를 안내하는 것이라 틀린 답은 아니다.
- **불필요한 되묻기가 6~9건 남는다.** 평가셋 기준으로 3회 모두 남는 것은 010, 048, 050, 059, 148, 154이고, 회차마다 달라지는 것은 007, 133, 145이다. 질문과 무관한 조건이 대부분이다. 048은 두 번째 조건이 합리적일 수 있어 라벨이 애매하다.
- **실행마다 달라진다.** 경계 질문은 같은 설정에서도 조건이 나왔다 안 나왔다 한다(일시정지와 해지, 개통 4개월 번호이동 등).
- **질문 모양이 모델마다 다르다.** Bedrock은 선택형 질문("A인가요, B인가요")을 예/아니요로 내서 선택지 버튼이 안 붙을 수 있다. 같은 대상의 나이 기준은 하나로 합쳤지만 다른 종류의 조건이 여러 개 나오는 경우는 합치지 않는다(3.4절).
- **추론 강도는 `low`다.** `llm.bedrock.reasoning-effort`가 모든 Bedrock 호출에 같이 적용된다(판정기와 조건 뽑기). `medium` 이상은 재지 않았다.
- **회차 사이에 Bedrock 평가셋이 9%p 흔들린다(72~81%).** 평가셋 32건은 1~2건이 점수 3~6%p라 작은 차이는 구별하지 못한다. 엑사원과 Bedrock의 차이(22% 대 72~81%)는 이 흔들림보다 훨씬 크다.
- 평가셋 라벨은 한 사람이 정했고 애매한 문항(048 등)은 다르게 볼 수 있다.
- 평가 호출은 `executionId`가 없어 `llm_generations`에 남지 않는다. 호출 수는 `CountingLlmClient`가 센다.

## 6. 재현

평가셋과 기존 평가는 `LLM_PROVIDER=ollama`일 때만 돈다.

```bash
# 엑사원 (무료)
LLM_PROVIDER=ollama TELME_DB_TESTS=true POSTGRES_PORT=5432 \
  ./gradlew test --tests '*ClarificationGradingEval' --tests '*ConditionExtractionEval' -i

# Bedrock (유료. 호출 수는 BEDROCK_CALLS 줄에 찍힌다)
AWS_BEARER_TOKEN_BEDROCK=<Bedrock API 키> EVAL_EXTRACTOR=bedrock LLM_BEDROCK_ENABLED=true \
  LLM_PROVIDER=ollama TELME_DB_TESTS=true POSTGRES_PORT=5432 \
  ./gradlew test --tests '*ClarificationGradingEval' --tests '*ConditionExtractionEval' -i
```

- `EVAL_ONLY=질문앞부분|질문앞부분`(기존 평가)로 일부 질문만 돌릴 수 있다.
- 한 번 재면 평가셋 32회, 기존 평가 47회 안팎의 Bedrock 호출이 나간다.

## 7. 반복 측정 (TELME-185)

엑사원과 Bedrock을 **3회씩** 같은 조건으로 다시 재서 사례별 결과를 모두 남겼다. TELME-176 초판의 엑사원 1회, Bedrock 2회 값은 사례별 기록이 없어 이 측정으로 교체했다.

### 7.1 조건

- 코드는 TELME-176 머지 커밋(`0f7d7612`)이라 프롬프트는 v1.9(통신사 이름 `LG U+`)다. 로컬 DB와 평가셋도 176과 같다. 이후 프롬프트의 이름을 `TELME`로 바꾸고 버전을 올렸지만(`condition-extract-v1.10`) 이 측정에는 쓰지 않았다.
- Bedrock은 176 재현 명령 그대로라 리전 기본값(`us-east-1`), 추론 강도 `low`다. 호출은 회차마다 평가셋 32회, 기존 평가 47회이고 실패, 응답 읽기 실패, 엑사원 대체는 0건이었다.
- Bedrock 3회차는 평가셋과 기존 평가를 따로 실행했다(평가셋 78%, 기존 평가 85%). 호출은 Bedrock 합계 237회다. 토큰 수와 비용은 평가 코드가 기록하지 않아 알 수 없다.

## 9. 되묻기 정책 변경 (TELME-218)

### 9.1 결정

### 9.9 되묻기 중 매장 요청(후속 분석 v8)
지역이 아닌 조건을 되묻는 중에 고객이 매장을 찾아 달라고 하면 후속 분석 모델이 이를 되묻기의 답으로 읽었다("회사 근처에서 처리하고 싶은데 여의도 쪽에 매장 있어요?"를 담당자 방문 조건의 답으로 채움).

- 처음(v7)에는 "location이 아닌 조건을 되묻는 중 매장을 찾으면 NEW_QUESTION"이라는 규칙을 시스템 프롬프트에 넣었다. 리뷰에서 업무(serviceType)를 되묻는 중에도 이 규칙이 걸린다는 지적이 있었고, 실제로 "명의변경 할 건데 매장 어디 있어요?" 같은 답을 새 질문으로 읽거나 출력이 잘렸다. 새 질문이 되면 기다리던 매장 상담이 취소돼 앞서 받은 지역이 이어지지 않는다.
- `routing-follow-up-v8`은 시스템 프롬프트를 v6로 되돌리고, 매장 조건(location, serviceType)이 아닌 조건을 되묻는 중일 때만 사용자 프롬프트에 이 규칙과 예시를 붙인다(`RoutingPromptTemplates.followUpUserPrompt`).

후속 분석 호출만 Bedrock으로 3회 비교했다.

### 9.10 사용량을 묻는 중 나이 정정(S14)
요금제 추천에서 사용량을 묻는 중 "아 잘못말했다 19살이요"처럼 나이를 고치면 나이가 바뀌지 않고 같은 사용량 질문만 다시 나갔다. 후속 분석은 기다리는 조건(사용량)과 매장 조건만 받아 나이를 버렸고(`QueryRoutingService.toExtractedConditions`), 받더라도 대기 중 정정 처리가 매장 상담만 대기 상태로 이어 갔다.

**처음 고친 것의 문제(리뷰).** 처음에는 나이 정정 규칙을 사용량 규칙보다 먼저 돌리고, 정정하는 말("잘못", "오타")과 숫자 하나만 있어도 나이로 읽었다. 리뷰에서 지적한 문장을 실제 메서드에 넣어 보니 아래처럼 사용량 답이 나이를 덮어썼다. 앞선 블라인드의 사용량 답에 "정정하는 말 + 단위 없는 숫자" 모양이 없어 측정에서 놓쳤다.

| "대학생인데 잘 모르겠어요", "25살인데 무제한이요" | 나이 정정, 사용량 다시 물음 | 모름, 무제한 |

| "아 잘못 말했다 95년생이요" | 95살, 시니어 | 모델로 넘김 |

**지금 규칙.**
- 사용량 규칙을 먼저 돌리고, 사용량을 읽지 못한 답에서만 나이 정정을 찾는다.
- 사용량 단위("50G", "50개" 포함)나 사용 정도("무제한", "모르겠어요", "거의 안 써요")가 있으면 나이로 읽지 않는다. 학년("중3"), 매장을 찾는 말이 있으면 둘 다 읽지 않고 모델에 넘긴다.
- 살·세 없이 숫자 하나로 고친 답은 "나이"라는 말이 있을 때만 나이로 읽는다("나이 47로 바꿔주세요"). 숫자 뒤에 년, 개월, 원 같은 다른 단위가 붙으면 읽지 않는다.
- 부정하며 고친 답("15살 아니고 21살이에요", "30 아니라 39요")은 부정한 쪽이 나이일 때 마지막 부정 표현 뒤의 나이를 읽는다. 사용량을 부정하며 고친 답("10기가 아니고 20기가요")은 뒤의 양을 사용량으로 읽는다.
- 나이를 바꾸면 "나이대를 만 19~64세로 바꿨어요."를 먼저 알리고 같은 사용량 질문을 다시 보낸다(`ConsultChatPersistenceService.withReceivedAge`).
- FAQ 상담에서 다른 조건만 고치면 고친 조건을 저장하고 기존 질문을 그대로 기다린다(`ConsultTurnPreparationService.keepWaiting`).
- 함께 고친 사용량 파서: "24개월"의 "개"를 문자 수로, "3만원"의 3을 데이터 3GB로 읽던 것.

채팅 API로 나이 → 사용량 질문 → (나이 정정, 사용량 답, 부정 표현 정정, 매장 요청 각 3개) → 사용량 답 흐름 12개를 돌렸다(블라인드 6차 문장, 부정 표현 처리를 넣기 전). 나이 정정 3개는 바꾼 나이대를 알리고 같은 질문을 유지한 뒤 고친 나이로 추천했고, 사용량 답 3개는 나이를 바꾸지 않고 추천했고, 매장 요청 3개는 매장 찾기로 넘어갔다. 부정 표현 정정 3개는 그때 모델로 넘어가 범위 밖 답이나 못 찾음으로 끝나, 위의 부정 표현 처리를 넣었다.

### 9.11 FAQ 1,152개 전수 분류
"지금 FAQ에는 되물을 조건이 거의 없다"(9.8)는 FAQ 174개 표본을 본 에이전트의 판단이었다. 전체로 확인하려고 Judge 후보 모델 두 개(Qwen3 235B, DeepSeek V3.2)에 FAQ마다 정책 9.1로 되물어야 하는지 판정하게 했다(`faq_ask_census.py`, 질문과 답만 주고 고객은 자기 상황을 말하지 않았다고 본다). 두 모델이 모두 되물어야 한다고 본 FAQ는 102개, 판정이 갈린 FAQ는 168개, 둘 다 바로 답이라고 본 FAQ는 882개다.

판정이 걸린 270개는 구현을 보지 않은 에이전트가 답의 모양으로 나눴다. 정책을 해석하지 않고 모양만 보게 했다.

| 답의 모양 | 둘 다 되물어야(102) | 판정 갈림(168) | 정책 9.1로 보면 |
| --- | --- | --- | --- |
| 갈리지 않음 | 17 | 51 | 바로 답 |
| 결과만 다른 두 경우("기본 30만 원, 인증하면 100만 원") | 27 | 28 | 바로 답 |
| 고객이 고르는 방법이나 상품 나열 | 20 | 37 | 바로 답(선호는 묻지 않는다) |
| 한 경우만 적힌 답("14일 이내라면 철회") | 12 | 17 | 되물어도 다른 경우의 근거가 없다 |
| 준비물이나 절차가 다른 두 경우("분실이면 정지, 파손이면 서비스센터") | 25 | 35 | 해석이 갈린다 |
| 셋 이상 | 1 | 0 | 되묻는다 |

- 정책 해석에 따라 되물을 수도 있는 모양은 "절차가 다른 두 경우" 60개와 "셋 이상" 1개를 더한 61개(5.3%)다. 이 61개도 모든 경우가 답에 적혀 있어(두 경우는 두세 문장, 셋 이상인 FAQ 55번은 세 문장) 되묻지 않고 답 하나로 함께 안내할 수도 있다. 되물을지 함께 안내할지가 해석이 갈리는 부분이다.
- 모양 분류는 에이전트의 판단이고, 조건 문장의 표현에 기대는 경계는 갈릴 수 있다.

조건 뽑기를 켠 품질셋 캡처(9.4, low)에서 되물은 33턴의 1위 FAQ를 위 모양에 맞춰 보면 다음과 같다.

| 되물은 FAQ | 턴 |
| --- | --- |
| 두 모델 모두 바로 답이라고 본 FAQ | 17 |
| 결과만 다른 두 경우, 나열, 갈리지 않음, 한 경우만 | 7 |
| 절차가 다른 두 경우 | 9 |

넓은 기준으로도 되물을 만한 FAQ에서 되물은 것은 33턴 중 9턴(27%)이다. 1위 FAQ가 절차가 다른 두 경우였던 14턴 중 5턴은 되묻지 않았다. 켜 두어도 되물을 곳을 골라 묻지 못해 9.8대로 끈다.

### 9.12 재현
- 채팅 API 캡처: `run_chat_pipeline_eval --capture-only --record-raw`. 환경은 `AWS_PROFILE`, `POSTGRES_PORT=5440`(질문 벡터 1,152개 DB), `LLM_BEDROCK_ENABLED=true`, `SEARCH_GRAYZONE_ENABLED=true`, `TELME_CONSULT_FAQCLARIFICATION_ENABLED=true`, `ROUTING_REQUEST_INVENTORY_ENABLED=false`, `TELME_SUBSCRIPTION_DEMO_MODE=true`이고, 조건 뽑기를 켠 비교는 `CONSULT_FAQ_CLARIFICATION_EXTRACT_CONDITIONS=true`를 더한다. 엑사원 답변 생성이 들어가 캡처는 하나씩 돌렸다. 채점은 `score_capture.py`.
- 근거 직접 입력: `ClarificationGradingEval`에 `EVAL_EXTRACTOR=bedrock`, 다른 문항은 `EVAL_CASES`, 1위 FAQ만은 `EVAL_TOP1=true`.
- 후속 분석: `RoutingEvaluationProbe`에 `TELME_ROUTING_STEP=followup`, `TELME_ROUTING_GPTOSS_CLIENT=bedrock`, `TELME_ROUTING_REPEATS=3`, `TELME_ROUTING_INPUT`(문항은 `followup-compare.json.gz`와 `review-fixes.json.gz`의 `followupCases`).
- 나이 정정 규칙: `review-fixes.json.gz`의 `harness`를 `src/test/java`에 임시로 넣고 `CHECK_CASES`(줄마다 `그룹|기다리는 조건|고객 답|문항 ID`)로 돌린다. 모델은 부르지 않는다.
- FAQ 전수 분류: `faq_ask_census.py`.

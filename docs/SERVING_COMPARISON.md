# EXAONE·임베딩 서빙 비교 (Ollama vs vLLM + TEI)

TELME-187. 배포 GPU EC2에서 EXAONE 3.5 7.8B와 bge-m3를 무엇으로 띄울지 정하려고, 배포 구성(앱 EC2 → GPU EC2, us-east-1 Bedrock)을 그대로 만들어 앱(채팅 API)으로 쟀다. 결과에 따라 **vLLM(EXAONE AWQ) + TEI(bge-m3)로 정한다.**

TELME-180·182 뒤 EXAONE은 평소 대화 요약·세션 제목만 맡고, Bedrock이 실패하면 답변 경로 호출을 대신 받는다(`FallbackLlmClient`). 그래서 **Bedrock 장애 순간에 몰리는 호출을 버티는지**를 기준으로 비교했다.

## 판단

- **Bedrock이 바로 실패하는 장애(S1)에서 vLLM이 처리량 3배, 턴 시간 3분의 1이다.** 동시 대화 5개부터 Ollama는 분당 약 18턴에서 막히고 턴 p95가 28초(N=5)~77초(N=20)로 늘었다. vLLM은 분당 약 54턴, p95 9초(N=5)~24초(N=20)다.
- 차이는 엑사원 호출 하나의 시간에서 나온다. 동시 요청이 4~5개가 되면 Ollama는 호출당 시간이 3배가 되고(의도 분류 p50 2.0초 → 6.1초), vLLM은 거의 그대로다(1.9초 → 2.1초).
- **임베딩을 TEI로 바꿔도 검색은 그대로다.** 질문 100개에서 Ollama 벡터와 코사인 유사도 최소 0.99979, 검색 1위 FAQ 100/100 같음. DB의 FAQ 벡터와 검색 기준값(0.72)을 그대로 쓴다.
- 평상시(S0)에는 두 서빙이 같다(gpt-oss가 답한다).

## 결과

### S1 Bedrock 즉시 장애 (질문 100개, 모두 성공)

| N | Ollama p50 / p95 / 최대 | Ollama 처리량 | vLLM p50 / p95 / 최대 | vLLM 처리량 |
|---|---|---|---|---|
| 1 | 4.3 / 9.2 / 18.0초 | 12.1턴/분 | 3.7 / 6.5 / 7.9초 | 15.0턴/분 |
| 5 | 15.6 / 27.6 / 33.1초 | 18.1턴/분 | **5.2 / 8.8 / 10.4초** | **54.0턴/분** |
| 10 | 32.2 / 43.6 / 58.9초 | 17.5턴/분 | **10.4 / 14.6 / 16.5초** | **53.8턴/분** |
| 20 | 64.0 / 77.0 / 88.7초 | 17.9턴/분 | **21.0 / 24.5 / 26.3초** | **54.1턴/분** |

엑사원 호출당 시간(p50, 호출 기록 `llm_generations`):

| 작업 | Ollama N=1 → N=5 → N=20 | vLLM N=1 → N=5 → N=20 |
|---|---|---|
| 의도 분류(ROUTING) | 2.0 → 6.1 → 6.1초 | 1.9 → 2.1 → 2.1초 |
| 근거 검증(EVIDENCE_CHECK) | 1.1 → 3.1 → 3.4초 | 0.9 → 1.1 → 1.1초 |
| 답변 생성(RAG_ANSWER) | 1.0 → 2.9 → 3.5초 | 1.0 → 1.1 → 1.1초 |

- **N=5부터 처리량이 더 늘지 않는 것은 앱의 동시 처리 제한 때문이다.** 앱은 채팅 턴을 동시에 4개까지만 처리한다(`ChatProcessingDispatcher` 스레드 4, 대기열 100). N=5와 N=20의 호출당 시간이 같은 것도 엑사원이 받는 동시 요청이 그 이상 늘지 않아서다. 그 안에서 Ollama는 GPU 쪽이 먼저 막혔고(분당 18턴), vLLM은 앱 제한(턴당 약 4.4초 × 4개 ≈ 분당 54턴)까지 갔다. vLLM의 실제 한계는 이보다 높다.
- N이 커질수록 늘어난 턴 시간은 대부분 앱 대기열에서 기다린 시간이다.

### S0 평상시 (Bedrock 정상, 질문 100개, 모두 성공)

| N | Ollama p50 / p95 | 처리량 | vLLM p50 / p95 | 처리량 |
|---|---|---|---|---|
| 1 | 5.7 / 10.5초 | 10.4턴/분 | 6.0 / 10.0초 | 10.2턴/분 |
| 10 | 14.7 / 20.1초 | 39.3턴/분 | 13.8 / 19.8초 | 41.1턴/분 |

- 두 서빙이 같다. 엑사원은 요약·제목만 맡는다.
- 혼자 쓸 때 gpt-oss 경로(5.7~6.0초)가 엑사원 대체 경로(3.7~4.3초)보다 느리다. 서울에서 us-east-1을 부르는 왕복과 gpt-oss 응답 시간이다. 근거 없음 답은 gpt-oss가 14~16개, 엑사원이 33~38개다.
- Bedrock 호출 2,252건은 모두 성공했다. 답변 생성 5건이 `MODEL_ERROR`로 기록됐는데, 호출 실패가 아니라 답변 가드가 gpt-oss 답을 막은 것이다(가드 예외가 호출 기록에 `MODEL_ERROR`로 남는다). 가드가 막은 답은 안내 문장으로 바뀌고 엑사원으로 대체되지 않는다.

|---|---|---|---|
| 1 | 10 | 30.9 / 83.1 / 83.1초 | 26.4 / 78.5 / 78.5초 |
| 5 | 20 | 45.3 / 92.3 / 97.5초 | 32.8 / 74.9 / 79.3초 |
| 10 | 20 | 83.8 / 129.1 / 129.8초 | 63.7 / 102.7 / 130.0초 |

- **서빙과 관계없이 턴이 1~2분 걸린다.** 한 턴의 Bedrock 호출마다 8초를 기다린 뒤 대체되기 때문이다. CloudFront(30초)·ALB(60초) 기본 시간 제한을 넘는다.
- Bedrock 대체 경로에 차단 장치(연속 실패하면 일정 시간 Bedrock을 건너뛰고 바로 엑사원)가 필요하다. 팀원 대체 작업에 넘긴다.

### S3 15분 쉰 뒤 장애 (S1, N=5, 질문 20개, 모두 성공)

| 구성 | p50 / p95 / 최대 | 의도 분류 호출 p50 / p95 |
|---|---|---|
| Ollama `KEEP_ALIVE` 기본(10분) | 16.4 / **49.3 / 61.7초** | 5.6 / 23.2초 |
| Ollama `KEEP_ALIVE=-1` | 15.8 / 36.3 / 42.3초 | 3.1 / 9.6초 |
| vLLM | 4.5 / 9.0 / 11.0초 | 2.1 / 3.3초 |

- Ollama는 기본값이면 쉬는 동안 EXAONE을 GPU에서 내리고, 장애 첫 요청들이 모델을 다시 올리는 동안 기다린다. 모델을 다시 올리는 데 약 52초가 걸렸다(컨테이너를 새로 띄운 뒤 첫 호출). `KEEP_ALIVE=-1`이면 대부분 사라진다.
- vLLM은 모델을 내리지 않아 쉬었다가도 같다.

### T2 임베딩 회귀 (Ollama bge-m3 vs TEI bge-m3)

질문 100개를 두 서버로 임베딩하고, 각 벡터로 DB의 FAQ 벡터(Ollama로 만든 것)를 검색했다.

| 항목 | 결과 |
|---|---|
| 코사인 유사도 | 최소 0.999790, 평균 0.999989 |
| Q_A 벡터 검색 | 1위 같음 100/100, 상위 5개 순서까지 같음 98/100 |
| 질문 벡터 검색 | 1위 같음 100/100, 상위 5개 순서까지 같음 98/100 |

TEI는 한 번에 받는 문장 수에 상한이 있다(`--max-client-batch-size 64`). 앱의 FAQ 재임베딩은 50개씩 보내 걸리지 않는다.

### T4 정확도 (아직 채점하지 않음)

S1 N=1에서 같은 질문 100개에 대한 답의 종류(답변·되묻기·근거 없음)가 두 서빙에서 같은 것은 **67개**다. vLLM이 되묻기가 조금 많다(Ollama가 답한 11개를 되물음, 반대 6개). 같은 EXAONE이라도 양자화(GGUF Q4_K_M / AWQ)와 실행기가 달라 결과가 꽤 다르다. 어느 쪽이 맞는지는 답 내용을 채점해야 알 수 있는데, 이번 측정은 답 길이만 저장했다. `load_chat.py`가 이제 답 내용도 남기므로, 배포 인프라에서 S1 N=1을 한 번 더 돌려 TELME-180 Judge로 채점한다. 엑사원은 대체 모델이라 이 결과가 서빙 결정을 바꾸지는 않지만, 대체 때 답 품질을 알려면 필요하다.

## 배포에 반영할 것

1. GPU EC2는 `scripts/serving-comparison/gpu-compose.yml`의 `vllm` 프로필(vLLM + TEI)로 띄운다. 앱은 `LLM_PROVIDER=vllm`, `VLLM_URL`, `EMBEDDING_PROVIDER=tei`, `EMBEDDING_URL`.
2. 앱의 동시 처리 턴 수(지금 코드에 4로 고정)를 설정으로 빼고 예상 동시 사용자 수에 맞춘다. 지금은 vLLM보다 이 제한이 먼저 걸린다.
3. Bedrock 대체 경로의 차단 장치(S2)와 짧은 연결 시간 제한. GPU EC2를 스팟으로 두면 회수 직후에도 같은 문제가 생긴다.
4. 질문 임베딩 CPU 대체(TEI CPU, 앱 EC2). GPU EC2가 스팟이면 회수되는 동안 임베딩이 끊기기 때문이다.
5. GPU EC2 고정 주소(VPC 안 Route 53 이름 등). 스팟을 다시 띄우면 사설 IP가 바뀐다. vLLM + TEI는 모델을 받는 데까지 포함해 약 2분 10초 만에 준비됐다.

## 한계

- 묶음마다 1회 측정이다. S2·S3는 질문이 10~20개라 p95·최대는 몇 턴에 좌우된다.
- 단일 턴 질문만 보냈다. 멀티턴·되묻기 답변은 포함하지 않았다.
- 앱 EC2에 앱·Postgres·부하 스크립트를 함께 올렸다. RDS가 아니고, 앱 EC2는 배포 예정보다 크다(m6i.xlarge). 두 서빙에 같은 조건이라 비교에는 영향이 없다.
- ALB·CloudFront를 거치지 않았다. S2의 1~2분 턴이 그 시간 제한에 끊기는지는 배포 뒤 실제 경로로 한 번 확인한다.

## 재현

```bash
# GPU EC2 (g6.xlarge): 한 프로필만 띄운다
docker compose -f gpu-compose.yml --profile ollama up -d   # 또는 --profile vllm
# 앱 EC2: 측정 DB 복원, bedrock.env(서명 방식 자격 증명)를 둔 뒤 시나리오 하나 또는 여러 개
GPU_HOST=<GPU 사설 IP> DB_HOST=<DB 주소> bash run.sh <ollama|vllm> <S0|S1|S2> <N> <질문 수> [라벨 덧붙임]
GPU_HOST=... DB_HOST=... nohup setsid bash series.sh vllm "S1 1 100" "S1 5 100" > series-vllm.log 2>&1 < /dev/null &
python3 embed_check.py --ollama http://<GPU>:11434 --tei http://<GPU>:8080   # T2, 두 서버를 함께 띄운 상태
python3 load_chat.py --summarize results/*.jsonl
```

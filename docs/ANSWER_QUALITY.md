# RAG 답변 품질 측정과 개선 보고서

---

## 1. 배경

### 1.1 대상

검색이 찾아준 FAQ를 근거로 LLM이 답변을 만드는 단계. 검색이 근거를 못 찾은 경우는 이 단계가 실행되지 않는다.

```
질문 → [검색] → 근거 → [답변 생성] → 답변
                        └ 이 문서의 대상
```

### 1.2 무엇을 재는가

답변 문장이 **근거 안에 있는 내용인지**만 본다. 문장 단위로 셋 중 하나로 판정한다.

| 판정 | 뜻 |
| --- | --- |
| supported | 근거에 있는 내용 |
| unsupported | 근거에 없거나 근거와 다른 내용 (= 환각) |
| irrelevant | 인사말, 근거에 정보가 없다고 밝히는 문장 등 사실을 주장하지 않는 문장 |

환각율 = unsupported / 전체 문장.

### 1.3 측정 원칙

- 운영 기본값은 답변이 매번 달라져 전후 비교가 불가능하므로 측정 중에는 `temperature=0`으로 고정한다. 두 번 돌려 결과가 글자까지 동일함을 확인했다.
- 호출 기록(`llm_generations`)을 남기지 않아 측정이 운영 통계를 더럽히지 않는다.
- 개선 전후는 같은 질문·같은 FAQ·같은 Judge로만 비교한다.

## 2. 평가셋

| 파일 | 건수 | 용도 |
| --- | --- | --- |
| `scripts/data/eval_questions_130.json` | 130 | 검색 품질 측정용 (검색 담당) |
| `scripts/data/eval_answer_quality_20.json` | 20 | 환각 유도용 (이번 이슈에서 추가) |

### 2.1 20건을 따로 만든 이유

130건의 긍정 질문 80건은 전부 FAQ **질문**을 변형한 것이다. 근거를 그대로 옮겨 쓰면 정답이 되므로 모델이 지어낼 이유가 없다. 실제로 이전 30건 평가에서 43문장 중 unsupported가 1건(2.3%)에 그쳐 개선 여지를 측정할 수 없었다.

근거를 그대로 쓸 수 없는 질문을 유형별로 4건씩 만들었다.

| 유형 | 내용 | 예 |
| --- | --- | --- |
| CALCULATION | 근거에 단가만 있고 합계를 물음 | 무제한 로밍 5일이면 총 얼마예요? |
| CONDITION | 근거가 조건부인데 조건을 안 물음 | 소액결제 한도 얼마까지 돼요? |
| COMPARISON | 근거에 각 값만 있고 우열은 없음 | 5G랑 LTE 중 뭐가 더 싸요? |
| MIXED | 근거에 있는 것과 없는 것을 함께 물음 | 유심 재발급 비용 얼마고, 카드 할부도 되나요? |
| MISSING_INFO | 근거에 없는 절차·기간·비용을 물음 | 유심 재발급하면 택배비는 따로 내나요? |

20건 모두 임계값 0.72에서 근거가 검색되는 것을 확인했다. 검색이 막으면 모델이 답할 기회가 없어 측정이 되지 않기 때문이다. 처음 만든 6건이 검색 0건이라 표현을 바꿨다.

## 3. Judge 선정

### 3.1 로컬 모델을 쓰지 않은 이유

처음에는 서비스와 같은 EXAONE 3.5 7.8B로 채점했다. 정답을 아는 문장 11개로 검증하니 **8/11**이었고, 틀린 3건이 전부 환각을 supported로 통과시킨 쪽이었다. 자기 답변을 자기가 채점하는 구조이기도 했다.

### 3.2 사용한 모델

`openai.gpt-oss-120b-1:0`. 기존 `bedrock-runtime` 엔드포인트에 Bedrock API 키를 Bearer로 얹어 호출한다.

```
POST https://bedrock-runtime.us-east-1.amazonaws.com/model/openai.gpt-oss-120b-1:0/converse
Authorization: Bearer <BEDROCK_API_KEY>
```

### 3.3 Judge 정확도

채점 결과 중 unsupported 33건 전체와 supported 24건을 근거와 직접 대조했다.

| 구분 | 결과 |
| --- | --- |
| unsupported 33건 | 맞음 26 / 오판 3 / 애매 4 |
| supported 24건 | 놓침 1 (조건 누락) |
| 합계 | 약 49/57, **85% 일치** |

판정 기준을 한 번 보완했다. 초기 프롬프트가 "위약금은 안내에 없습니다" 같은 **정직한 문장을 환각으로 세고 있었다.** 개선 방향이 바로 그런 문장을 늘리는 것이라, 고치지 않으면 잘 고칠수록 점수가 나빠지는 구조였다.

보완 후에도 경계 사례 3건이 새로 틀렸다. 추가 조정은 하지 않았다. 전후 비교는 같은 Judge를 쓰므로 일정한 오차는 상쇄되고, 계속 조정하면 기준선을 다시 채점해야 한다.

> 이 85%는 절대 정확도가 아니라 **검토자와의 일치율**이다. 근거 포함 여부 판정은 사람끼리도 경계 사례에서 갈린다.

### 3.4 Judge 실행 방법

```bash
python3 -m scripts.chat_judge.judge_answers .measure/baseline-<시각>.json
```

`temperature=0`, `reasoning_effort=low`로 고정한다. 기본값은 판정 전에 생각을 길게 해 토큰을 다 쓰고 답을 못 내는 경우가 있었다.

## 4. 측정 결과

### 4.1 단계별 환각 수

150건(130 + 20) 전체를 매 단계 다시 돌려 같은 Judge로 채점했다.

| 단계 | 문장 | supported | unsupported | irrelevant | 환각율 |
| --- | --- | --- | --- | --- | --- |
| 기준선 | 129 | 95 | 26 | 8 | 20.2% |
| 안내 창구 규칙 | 117 | 93 | 17 | 7 | 14.5% |
| + 수치·비교 규칙 | 110 | 89 | 14 | 7 | 12.7% |
| **최종** (비교 목록에서 "보다" 제외) | 111 | 91 | **12** | 8 | **10.8%** |

**환각 26건 → 12건, 54% 감소.**

문장 수가 줄어든 것은 가드가 지어낸 문장을 걷어냈기 때문이다.

### 4.2 운영 설정의 영향

측정은 `temperature=0`이지만 운영 기본값은 0.2였다. 같은 코드에서 온도만 바꿔 두 번 측정했다.

| temperature | 문장 | unsupported | 환각율 |
| --- | --- | --- | --- |
| 0.2 (1회) | 111 | 19 | 17.1% |
| 0.2 (2회) | 110 | 20 | 18.2% |
| 0.0 | 111 | 12 | 10.8% |

**0.2에서 환각이 1.7배**였다. FAQ 상담은 표현을 바꿀 이유가 없어 `RAG_ANSWER` 기본값을 0으로 낮췄다. 같은 질문에 항상 같은 답변이 나온다. ROUTING은 이미 0이고 되묻기·요약·세션 제목은 그대로 둔다.

## 5. 효과가 있었던 것 — AnswerGuard

### 5.1 근거에 없는 안내 창구 차단

모델이 존재하지 않는 안내처를 만들어낸다. FAQ 1,150건에 `샵`과 `이벤트`는 **한 번도 나오지 않는데** 답변에는 `샵 이벤트 페이지`가 등장했고, `샵샵샵샵 이벤트 페이지`처럼 글자가 반복되기도 했다.

```
전  유심 재발급 비용은 7,700원입니다. 자세한 할부 조건은샵 이벤트 페이지를 확인해 주세요.
후  유심 재발급 비용은 7,700원입니다.
```

검사 대상 단어는 데이터를 세어 정했다. `매장` 159건, `고객센터` 74건처럼 FAQ에 흔한 단어가 있어 무조건 막을 수 없으므로, **그 답변에 딸려온 근거에 없을 때만** 막는다. 고객이 질문에 쓴 말도 통과시킨다.

금액과 달리 답변 전체를 막지 않고 해당 문장만 걷어낸다. 나머지 문장은 근거대로인 경우가 많기 때문이다. 전부 걷히면 근거 없음으로 돌린다.

**26건 → 17건.**

### 5.2 근거에 없는 수치 차단

기존 `verifyAmounts`는 "원"만 검사해 다음이 통과했다.

```
근거  기본 월 30만 원 → 최대 월 100만 원
답변  원래 한도의 약 3.3배까지 증가합니다 (100만 원 ÷ 30만 원 = 약 3.3배)
```

단위를 `배 % 일 개월 시간 분 GB 회 년`으로 넓혔다. `배`는 FAQ에 0건이라 답변에 나오면 무조건 지어낸 값이다. 나머지는 FAQ에 흔해 근거와 대조한다.

추가 검토에서 `3영업일`, `2~3 영업일` 같은 표현이 기존 수치 검사에 포함되지 않는 것을 확인해, 영업일과 범위의 양쪽 값을 검사하도록 보완했다. 수정 후 동일한 150건을 다시 생성한 결과 기존 답변과 모두 동일했고, 추가 차단이나 정상 답변 오차단은 발생하지 않았다. 이번 평가셋의 품질 수치에는 변화가 없었으며, 운영 중 잘못된 영업일 수치가 생성될 가능성을 막기 위한 안전장치 보완이다.

### 5.3 근거에 없는 비교 표현 차단

근거에 각 값만 있고 우열 판단이 없는데 모델이 비교한다.

```
근거  우편은 월 500원, 이메일은 무료입니다
답변  이메일 청구서는 무료이며, 즉시 확인이 가능해 빠르고 편리합니다
```

`제일 가장 유리 저렴 비싸 빠릅 편리 나은 낫습 우수`를 검사한다. `보다`는 처음에 넣었다가 뺐다. "이보다 오래 걸린다면"처럼 우열 비교가 아닌 쓰임이 많아 멀쩡한 문장을 걷어냈다.

**17건 → 12건.**

### 5.4 걷힌 문장 검증

최종 상태에서 걷힌 6문장을 근거와 대조했다. 5건은 제대로 걷혔고, 1건은 3.3배가 든 답변이 통째로 막히면서 근거대로인 첫 문장이 함께 사라졌다. 수치 규칙은 금액과 마찬가지로 답변 전체를 막는 방식이라 그대로 두었다.

## 6. 효과가 없었던 것

### 6.1 프롬프트 규칙 추가

시스템 프롬프트에 규칙 4개를 더했다. 근거 없는 단정 금지, 비교 금지, 조건 함께 쓰기, 뜻 뒤집기 금지.

| | 문장 | unsupported | 환각율 |
| --- | --- | --- | --- |
| 규칙 추가 전 | 117 | 17 | 14.5% |
| 규칙 추가 후 | 120 | 20 | 16.7% |

**오히려 악화되어 되돌렸다.** 5건이 해결되고 8건이 새로 생겼다.

```
"근거를 뒤집지 마십시오" 추가
  전  이번 달에 아직 변경하지 않으셨다면 변경이 가능합니다.     supported
  후  이번 달에 요금제를 바꾸는 것은 불가능합니다.             unsupported

"없다고 단정하지 마십시오" 추가
  전  영업일 여부에 따른 구분은 명시되어 있지 않습니다.         irrelevant (정답)
  후  정확한 영업일 수는 확인이 필요하지만, 일반적으로 회사의... unsupported
```

단정을 피하라고 하니 애매하게 돌려 말하면서 근거 밖 추측을 덧붙였다.

### 6.2 답변 길이 축소

"3~5문장"을 "2~3문장"으로 줄였다. 환각이 답변 뒷부분에 몰려 있어 덧붙일 여지를 줄이려는 의도였다.

| | 문장 | unsupported | 환각율 |
| --- | --- | --- | --- |
| 3~5문장 | 111 | 12 | 10.8% |
| 2~3문장 | 108 | 16 | 14.8% |

**악화되어 되돌렸다.** 길이는 평균 75자에서 69자로 거의 줄지 않았고, 대신 문장을 합치면서 근거에 없는 내용을 끼워 넣었다. 근거에 정보가 없다고 밝히는 문장을 쓸 여유가 없어져 `NO_EVIDENCE`가 2건에서 0건이 되었다.

### 6.3 관찰

프롬프트 수정은 두 번 다 악화됐고, 코드 가드는 세 번 다 개선됐다. 프롬프트에는 이미 "근거에 없는 웹사이트, 페이지, 고객센터를 쓰지 마십시오"라는 규칙이 있었는데도 안내 창구 환각이 9건 발생했다. **7.8B 모델에게 지시로 막는 데에는 한계가 있고, 생성된 결과를 사후에 검증하는 쪽이 통했다.**

## 7. 구현했으나 기본값을 끈 것 — 근거 적합성 판정

### 7.1 문제

검색은 문장 전체의 유사도로 거르기 때문에, FAQ와 단어를 많이 공유하지만 묻는 항목은 다른 질문이 통과한다.

```
질문  유심 재발급 비용은 카드로 결제할 수 있나요?   (점수 0.7868, 통과)
근거  유심 재발급 비용이 얼마예요? → 7,700원입니다
답변  네, 현금이나 카드로 결제 가능합니다          ← 근거에 결제 수단 언급 없음
```

환각이 숫자도 창구 이름도 아닌 **사실 주장**이라 문자열 규칙으로 걸러지지 않는다. 프롬프트 보강도 6.1에서 실패했다.

### 7.2 구현

검색 결과를 LLM에 넘기기 전에 "이 FAQ로 이 질문에 답할 수 있는가"를 먼저 묻고, 아니면 생성을 건너뛰고 근거 없음으로 끝낸다.

| 항목 | 값 |
| --- | --- |
| 클래스 | `EvidenceRelevanceChecker` |
| 설정 | `rag.evidence-check.enabled` (기본 `false`) |
| 판정 실패 시 | 답변을 막지 않고 통과 |

### 7.3 검증

정답을 아는 20건(막아야 할 5건 + 답해야 할 15건)으로 같은 프롬프트를 두 모델에 물렸다.

| 모델 | 정확도 | 틀린 방향 |
| --- | --- | --- |
| EXAONE 3.5 7.8B (서비스 모델) | **12/20** | 막아야 할 3건 통과, 답해야 할 5건 차단 |
| GPT OSS 120B | **18/20** | 막아야 할 2건 통과, 잘못 막은 것 0건 |

로컬 모델은 틀린 방향이 양쪽으로 흩어져 있다. 잡아야 할 것은 놓치고 건드리면 안 되는 것은 막았다. 실제 150건 측정에서도 엄격한 프롬프트로는 답할 수 있는 질문 12건을 막았고, 완화하면 목표 3건을 놓쳤다.

**판정 로직이 아니라 모델 크기가 원인**이다. 같은 프롬프트로 큰 모델은 멀쩡한 답변을 하나도 막지 않았다.

기본값을 끄고 코드는 남긴다. 더 큰 모델을 로컬에서 쓸 수 있게 되면 설정 한 줄로 켜서 재측정하면 된다. 판정만 외부 API로 돌리는 방안은 서비스가 AWS 없이 동작하지 못하게 되어 채택하지 않았다.

## 8. 남은 환각의 원인 — 모델 크기

남은 12건이 파이프라인 한계인지 모델 한계인지 가르기 위해, 검색·프롬프트·가드를 모두 그대로 두고 **답변 생성 모델만** 교체해 측정했다.

| 생성 모델 | 문장 | unsupported | 환각율 | 가드 발동 |
| --- | --- | --- | --- | --- |
| EXAONE 3.5 7.8B | 111 | 12 | 10.8% | BLOCKED 4, NO_EVIDENCE 2 |
| GPT OSS 120B | 90 | **1** | **1.1%** | BLOCKED 0 |

**열 배 차이가 났고 가드는 한 번도 발동하지 않았다.** 큰 모델은 애초에 지어내지 않아 걷어낼 것이 없었다. 문장 수가 적은 것은 근거에 있는 만큼만 말하고 끝냈기 때문이다.

틀린 1건은 이번에 추가한 함정 질문이다.

```
질문  유심 재발급하면 택배비는 따로 내나요?
근거  7,700원입니다. 온라인 신청 시 택배로 2~3 영업일 걸립니다.
답변  7,700원에 포함되어 있어 별도의 택배비는 없습니다.
```

서비스 모델 교체를 제안하는 것은 아니다. 모든 질문마다 외부 API를 호출하게 되고 네트워크 장애에 서비스가 멈춘다. **남은 환각의 성격을 규명한 측정 결과로만 기록한다.**

---

## 9. 측정 범위 밖 — 검색 단계

환각율 10.8%는 **답변이 생성된 60건 안에서의 비율**이다. 150건 전체로 보면 답변 자체가 나오지 않은 경우가 더 많다.

| 구분 | 건수 |
| --- | --- |
| 평가 질문 | 150 |
| 검색 0건으로 답변 없음 | 90 |
| 답변 생성 | 60 |

130건만 놓고 보면 답할 수 있어야 하는 80건 중 **43건(54%)** 이 검색 0건이었다. 검색 담당 문서의 `Recall@3 0.375`와 같은 현상이다.

임계값을 0으로 두고 다시 검색해 원인을 나눴다.

| 구분 | 건수 | 뜻 |
| --- | --- | --- |
| 정답이 top3에 있음 | 25 | 순위는 맞고 점수만 0.61~0.72 |
| 상위 10건에도 없음 | 13 | 임베딩 단계에서 밀림 |
| 4~9위로 밀림 | 5 | |

점수가 낮은 이유를 한 건 추적했다.

```
질문  eSIM이 무엇인가요?          (실제 답변: "안내드릴 수 있는 정보가 없습니다")

  FAQ 질문만 "eSIM이 뭐예요"와 비교     0.9862
  FAQ 답변만과 비교                    0.3719
  질문+답변 합친 현재 방식              0.6269
```

FAQ 벡터가 질문과 답변을 합쳐 만들어지므로, 짧은 질문과 비교할 때 답변 부분이 유사도를 끌어내린다. 답변이 모두 200자 미만이라 청킹은 해당 사항이 없다.

**이 단계는 이번 이슈의 범위 밖이다.** 원인과 후속 과제는 검색 담당 문서의 미해결 항목 6번(리랭커 또는 하이브리드 검색)을 따른다. 질문별 목록과 순위는 검색 담당에게 전달했다.

```bash
# 1. 사전 조건
```

## 12. 미해결 항목

| # | 항목 | 현황 | 선행 조건 |
| --- | --- | --- | --- |
| 1 | 근거 적합성 판정 비활성 | 로컬 7.8B로 12/20 | 더 큰 로컬 모델 또는 외부 API 사용 합의 |
| 2 | 가드 차단 시 이미 전송된 토큰 | 금액 환각에서 32토큰(50자)이 SSE로 나간 뒤 차단됨 | 문장 단위 검사로 옮기거나 프론트에서 error 시 표시 내용 제거 |
| 3 | 근거를 정반대로 읽는 환각 | 2건 (수수료 없음 → 있음) | 문자열 규칙으로 판별 불가. 모델 교체 또는 판정 단계 |
| 4 | Judge 경계 사례 오판 | 검토 57문장 중 3~4건 | 정답 라벨을 더 모아 재검증 |
| 5 | 검색 단계 미응답 | 답할 수 있는 80건 중 43건 | 검색 담당 문서 미해결 6번 |

영업일 수치 검사를 보완한 뒤 동일한 최종 답변 111문장을 다시 채점했을 때 unsupported가 12건에서 13건으로 달라졌다. 답변 자체는 이전 측정과 글자까지 동일했으며, 기존에 supported로 판정됐던 택배비 포함 문장이 재채점에서는 unsupported로 판정됐다. 이는 코드 변경에 따른 품질 변화가 아니라 동일 답변에 대한 Judge 판정 변동 사례다.

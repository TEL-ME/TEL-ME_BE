# 이중 벡터와 리랭커 비교 (TELME-84)

## 1. 배경

검색 품질 개선 수단이 두 개 나와 있다.

- **이중 벡터**: `Q_A` 벡터에 `QUESTION_ONLY` 벡터를 병행한다. develop에 들어가 있다(TELME-76, 79, 83). 도입 결과는 `SEARCH_TUNING.md` 15절
- **리랭커**: 벡터 검색 후보를 리랭커 모델로 다시 매긴다. 코드는 공개되지 않았고 로컬 실험 결과만 있다(`rerank-multigold-experiment.md`)

리랭커 문서는 이중 벡터가 develop에 들어가기 전 커밋(`c8634c2`) 위에서 측정해 단일 벡터와만 비교했다.
이 문서는 두 수단을 같은 질문·같은 라벨·같은 임계값 선택 규칙으로 놓고 **효과, 겹침, 부작용, 비용**을 비교해 그 판단 근거를 남긴다.

## 2. 요약

답변 가능 110 / 무관 70. 임계값은 3.3절 규칙으로 골랐다.

| 구성 | 임계값 | 공식 라벨 | 다중 정답 라벨 | 무관 통과 | 지연 평균 / p95 |
| --- | --- | ---: | ---: | ---: | --- |
| 단일 벡터 (현행) | `Q_A` 0.72 | 52 | 59 | 8 | 기준 |
| 이중 벡터 | `QUESTION_ONLY` 0.88 | **59** (+7) | **64** (+5) | 8 | ×1.09 / ×1.15 |
| 리랭커 | 0.82 | **61** (+9) | **70** (+11) | 7 | ×6.9 / ×6.5 |
| 리랭커 + 이중 벡터 (오프라인 시뮬레이션) | 리랭커 0.82 + `QUESTION_ONLY` 0.90 | 64 (+12) | 72 (+13) | 7 | 미측정 |

- **리랭커 우위의 크기는 라벨에 달렸다.** 공식 라벨에서는 +9 vs +7로 비슷하고, 다중 정답 라벨에서는 +11 vs +5다(4.2절)
- **리랭커는 지연이 약 7배다.** 이중 벡터는 지연이 사실상 그대로다
- **이중 벡터가 살린 문항은 대부분 리랭커도 살린다.** 이중 벡터만 살리는 문항은 두 라벨 모두 `EVAL-013` 1건이다(5절)
- **리랭커는 기존 정답을 놓치고 무관 질문을 교체한다.** 이중 벡터는 놓친 문항과 새로 통과한 무관 질문이 실측상 0건이다(7절)
- **둘을 합치면 리랭커 단독보다 +2 ~ 3이다.** 단 질문 벡터 임계값을 0.90으로 다시 골라야 한다(6절)
- 리랭커 적용 여부는 **지연 허용치와 배포 환경**에 달렸다. 이 문서의 수치만으로는 정하지 않는다(9절)

## 3. 평가 기준

### 3.1 데이터

| 이름 | 파일 | 구성 | 역할 |
| --- | --- | --- | --- |
| 기존 130 | `eval_questions_130.json` | 답변 가능 80(질문 변형) + 무관 50 | 기존 평가 세트 |
| 보강 50 | `eval_questions_supplement_50.json` | 답변형(`ANSWER`) 30 + 경계 무관 20 | 기존 130에 없던 위험 유형 보강(TELME-69) |

| 검색 확인용 60 | `eval_questions_holdout_60.json` | 경계 무관(`ADJACENT_HARD`) 60, 카테고리당 6 | 검색 임계값의 독립 확인과 0.87 ~ 0.92 구간의 구분력 확보(13.1절) |

- **공식 라벨**: 위 두 파일의 정답. 대부분 질문당 FAQ 1건
- **다중 정답 라벨**: `eval_questions_180_multigold.json`(TELME-75). 같은 내용으로 답하는 FAQ를 정답으로 추가했다. 검색팀 검토 전 후보 라벨이다
- 추가 라벨 278건 중 163건은 LLM 판정만 거쳤다(`multigold-label-additions.md`). 이 문서의 `[검토]` / `[LLM]` 표시를 FAQ 질문 문장으로 `slot_id`에 대응시켜(278건 모두 대응) 163건을 빼고 다시 채점해도, 네 구성(단일 벡터 0.72, 이중 벡터 0.88, 리랭커 0.82, 병합 0.82 + 0.90)에서 정답으로 인정되는 문항이 하나도 바뀌지 않았다. 이 문서의 다중 정답 수치는 사람이 검토한 라벨만으로도 성립한다. 다만 라벨 파일에는 검토 여부 필드가 없어 이 확인은 아직 자동으로 재현되지 않는다(13절)
- 보강 50은 검증용으로 떼어 둔 세트가 아니다. 기존 130만으로는 답변형 손실과 경계 무관 통과를 볼 수 없어 임계값 선택에 쓰려고 만들었다. 그래서 180 전체를 선택에 쓰고, 독립 확인은 검색 확인용 세트로 따로 한다

### 3.2 측정

| 항목 | 이중 벡터 | 리랭커 |
| --- | --- | --- |
| 측정 | 로컬 API 실측, 2026-09-29 | YJ720 제공 앱 실측 파일(`app_raw_20260929/`), 2026-09-29 |
| 설정 | `Q_A` 0.72 + `QUESTION_ONLY` 합친 뒤 top-3 | `Q_A` 상위 20개를 리랭커로 정렬, 점수 기준 이상, top-3 |
| 기준선 | `--vector QA` 실측 | 리랭커를 끈 실측(`cos_t072_top3.json`) |

- **두 기준선은 같다.** 리랭커 쪽 기준선과 이 문서의 `--vector QA` 실측은 180문항 전부 반환 결과가 동일했다. 문항 단위로 비교할 수 있다
- 채점: 답변 가능 질문은 반환된 top-3에 정답 `slot_id`가 하나라도 있으면 성공. 무관 질문은 결과가 1건이라도 오면 통과(오답)
- 임계값별 결과는 임계값 없이 받은 원시 결과(`--vector` 원시 결과, `rerank_k20_t000_top10.json`)를 잘라 계산했다. 리랭커 파일을 0.76으로 자르면 0.76 실측과 180문항 모두 같다
- 리랭커 결과 파일은 레포에 없다. 코드도 공개되지 않아, 리랭커 수치는 이 파일로만 재현된다

### 3.3 임계값 선택 규칙

모든 구성에 같은 규칙을 적용한다.

1. 선택용 180, **공식 라벨**로 고른다. 다중 정답 라벨 결과는 같은 임계값으로 함께 보고한다
2. 기존 130의 무관 50건 통과가 현행(3건) 이하, 보강 50의 경계 무관 20건 통과가 현행(5건) 이하
3. 답변형 30건의 정답 전달 수가 현행 아래로 떨어지지 않는다
4. 위 조건을 만족하는 값 중 전체 정답 전달이 가장 많은 값. 같으면 더 높은 임계값
5. 조합은 각 구성요소의 단독 선택값을 고정하고, 추가한 쪽 임계값만 다시 고른다
6. 기준선에서 맞혔다가 놓친 문항은 개수와 별개로 목록을 남긴다(7절)

무관 통과를 두 구간으로 나눠 제한하는 이유: 합계만 보면 한 구간의 증가가 다른 구간의 감소로 가려진다. 리랭커 0.76이 그 예다(4.1절).

### 4.1 리랭커 임계값

다중 정답 라벨 기준 곡선이다(YJ720 제공 `score_summary.json`의 `threshold_selection`).

| 리랭커 임계값 | 정답 110 | 무관 70 통과 | 무관 50 통과 (현행 3) | 무관 20 통과 (현행 5) |
| ---: | ---: | ---: | ---: | ---: |
| 0.72 | 77 | 9 | 4 | 5 |
| 0.74 | 75 | 8 | 4 | 4 |
| 0.76 | 74 | 8 | **4** | 4 |
| 0.78 | 71 | 8 | 4 | 4 |
| **0.80 ~ 0.82** | **70** | **7** | **3** | 4 |
| 0.85 | 69 | 7 | 3 | 4 |
| 0.90 | 63 | 6 | 2 | 4 |

- 리랭커 문서의 측정 설정 0.76은 무관 통과 합계가 8로 현행과 같지만, **기존 무관 50에서는 3 → 4로 늘고** 보강 무관 20에서 5 → 4로 줄어 상쇄된 것이다. 3.3절 규칙 2를 어긴다
- 규칙을 지키는 값 중 정답이 가장 많은 구간은 0.80 ~ 0.82이고, 더 높은 0.82를 쓴다. 공식 라벨로 골라도 같은 구간이다
- 0.80과 0.82는 일부 문항의 반환 개수만 다르고 정답·무관 수는 두 라벨 모두 같다

### 4.2 라벨에 따라 리랭커 우위가 달라지는 이유

리랭커는 원래 정답과 **같은 내용의 다른 FAQ**를 자주 올린다. 공식 라벨은 이를 오답으로, 다중 정답 라벨은 정답으로 센다.

| eval_id | 질문 | 공식 정답 | 리랭커 top-3 (0.82 이상) |
| --- | --- | --- | --- |
| EVAL-015 | 알뜰 미니 요금제는 얼마인가요? | `PLAN-0025` | `PLAN-0035`, `PLAN-0115`, `PLAN-0065` |
| EVAL-039 | 유심을 새로 받으면 예전 유심도 계속 쓸 수 있나요? | `USIM-0092` | `USIM-0088`, `USIM-0044`, `USIM-0008` |

- 두 문항 모두 리랭커가 올린 세 FAQ가 다중 정답 라벨에서는 전부 정답이다. 단일 벡터는 공식 정답을 3위에 두어 공식 라벨로 맞혔다
- 그래서 공식 라벨은 리랭커를 과소평가한다. 다중 정답 라벨은 LLM 판정 라벨의 영향은 없지만(3.1절) 사람 검토분도 한 사람이 확정해 교차 검토 전이므로, 실제 효과는 두 값 사이로 본다
- 기존 130의 정답 80만 보면 공식 라벨에서 이중 벡터와 리랭커가 모두 37이다. 공식 라벨 기준 리랭커의 추가 이득은 답변형 +2다

## 5. 겹침

| 이중 벡터가 살린 문항 | 라벨 | `Q_A` 원순위 / 점수 | 리랭커도 살림 |
| --- | --- | --- | :-: |
| EVAL-006 | 공통 | 1위 / 0.703 | ✅ |
| EVAL-007 | 공식만 | 6위 / 0.758 | ✅ |
| EVAL-013 | 공통 | 1위 / 0.674 | ❌ (빈 결과) |
| EVAL-014 | 공식만 | 6위 / 0.758 | ✅ |
| EVAL-025 | 공통 | 1위 / 0.691 | ✅ |
| EVAL-037 | 공통 | 1위 / 0.627 | ✅ |
| EVAL-040 | 공통 | 1위 / 0.718 | ✅ |

- 공식 라벨에서는 7건 중 6건, 다중 정답 라벨에서는 5건 중 4건을 리랭커도 살린다. EVAL-007, 014는 다중 정답 라벨에서 단일 벡터가 이미 맞히는 문항이다
- **겹치는 이유는 구조다.** 이중 벡터가 살린 문항은 전부 `Q_A` 후보 안에 정답이 이미 있었고, 점수가 0.72에 못 미쳤거나 3위 밖이었다. 리랭커도 같은 `Q_A` 후보를 받아 다시 판정한다. 두 수단이 같은 문제(임계값 컷)를 다른 신호로 푼다
- **순위만 보면 리랭커 이득은 작다.** 임계값 없이 top-3에 정답이 있는지 보면 벡터 대 리랭커(후보 20개)가 공식 라벨 84 대 87, 다중 정답 라벨 99 대 102다(`score_summary.json`). 리랭커 효과 대부분은 순위가 아니라 임계값 판정을 대신한 데서 나온다
- EVAL-013은 실제 앱 리랭커에서도 정답(`PLAN-0118`)이 1위지만 점수가 0.440으로 기준값 0.82에 크게 못 미친다(후보 10 / 20 / 30개 모두 같다). 경계 문항이 아니라 현재 구성(`Q_A` 후보)에서는 리랭커 임계값으로 살아나지 않는 문항이다. 질문 벡터는 같은 정답을 0.955로 잡는다

리랭커가 살린 문항을 유형별로 나누면 다음과 같다(다중 정답 라벨).

| 유형 | 이중 벡터 구제 | 리랭커 구제 |
| --- | ---: | ---: |
| SIMILAR | 5 | 7 |
| VARIANT | 0 | 5 |
| ANSWER | 0 | 3 |

- `ANSWER`(답변에만 있는 값으로 묻는 질문)는 리랭커만 푼다. 질문 벡터는 FAQ 답변을 모르므로 구조적으로 돕지 못한다

## 6. 리랭커 + 이중 벡터 (오프라인 시뮬레이션)

리랭커 결과와 질문 벡터 결과를 각자의 임계값으로 자른 뒤 합쳤다. 점수는 섞지 않고 중복 제거 → 우선순위 → top-3로 합친다(`DualVectorMerger`와 같은 방식). 리랭커 입력(`Q_A` 후보 20개)은 바뀌지 않으므로 리랭커를 다시 돌리지 않고 두 결과 파일로 계산할 수 있다.

| 구성 | 공식 라벨 | 다중 정답 라벨 | 무관 50 / 20 통과 | 규칙 |
| --- | ---: | ---: | --- | :-: |
| 리랭커 0.82 단독 | 61 | 70 | 3 / 4 | ✅ |
| + `QUESTION_ONLY` 0.88 | 64 | 72 | **4** / 4 | ❌ |
| **+ `QUESTION_ONLY` 0.90** | **64** | **72** | 3 / 4 | ✅ |
| + `QUESTION_ONLY` 0.92 | 63 | 71 | 3 / 4 | ✅ |
| + 현행 이중 벡터 전체(`QUESTION_ONLY` 0.88 + `Q_A` 0.72) | 67 | 75 | **5 / 6** | ❌ |

- 리랭커 단독보다 공식 라벨 +3(EVAL-013, 015, 036), 다중 정답 라벨 +2(EVAL-013, 036)
- EVAL-036("한동안 안 쓸 예정인데 일시정지하려면 어떻게 하나요?")은 리랭커가 놓친 문항이다. 질문 벡터가 정답(`TERMINATE-0044`)을 0.907로 되살린다
- **질문 벡터 임계값은 조합에서 다시 골라야 한다.** 0.88이면 무관 질문 EVAL-122("유심 재발급 비용은 카드로 결제할 수 있나요?")가 질문 벡터 0.886으로 통과한다. 이중 벡터 단독에서는 이 문항이 어차피 `Q_A`로 통과하던 문항이라 드러나지 않았다. 리랭커가 이를 막으면서 질문 벡터 쪽 통과가 새로 생긴다
- 0.90의 여유는 작다. 무관 EVAL-122가 0.886, 정답 EVAL-036이 0.907이다
- 합치는 순서(질문 벡터 먼저 / 리랭커 먼저)는 결과에 영향이 없었다
- 현행 이중 벡터 전체를 합치면 리랭커가 놓친 문항은 되살아나지만, 리랭커가 막았던 무관 질문 4건도 `Q_A`로 되살아난다
- **한계**: 오프라인 계산이다. 리랭커 결과는 YJ720 DB, 질문 벡터 결과는 이 문서 측정 DB의 것이다(`Q_A` 결과는 두 DB에서 180문항 모두 같았다). 지연은 측정하지 않았다. 리랭커 지연에 DB 조회 1회(이중 벡터 기준 약 +4ms)가 더해지는 수준으로 추정한다

이중 벡터 후보를 리랭커에 넣어 다시 판정하는 구성(질문 벡터 후보 → 리랭커 판정)은 리랭커 코드가 있어야 측정할 수 있다. 현재 `Q_A` 후보 기준 EVAL-013 정답 점수는 0.440으로, 후보 10 / 20 / 30개에서 모두 같았고 기준값 0.82와의 차이(0.38)가 후보 구성에 따른 관측 최대 변화(0.22)보다 크다. 구제 가능성은 작아 보이지만, 질문 벡터 후보가 섞이면 후보 구성이 달라지므로 실제 구성에서 다시 확인해야 한다.

## 9. 판단

- **이중 벡터는 유지한다.** 공식 라벨 +7, 놓침 0(실측), 무관 통과 변화 없음, 지연 +4ms. 리랭커 도입 여부와 상관없이 지금 켜 둘 이유가 충분하다
- **리랭커 적용 여부는 이 문서로 정하지 않는다.** 효과는 공식 라벨 +9, 다중 정답 라벨 +11이고 `ANSWER`를 푸는 유일한 수단이지만, 지연 7배와 모델 배포는 서비스 지연 목표와 배포 환경이 정해져야 판단할 수 있다
- **리랭커를 도입해도 이중 벡터의 몫은 남는다.** 병합 시뮬레이션에서 +2 ~ 3이고, 그중 EVAL-036은 리랭커가 놓친 문항을 되살린 것이다. 비용은 DB 조회 1회뿐이다

리랭커 도입을 검토한다면 먼저 확인할 것:

1. **실제 조합 측정.** 6절 병합 방식을 구현하거나, 이중 벡터 후보를 리랭커에 넣는 구성으로 다시 잰다. 리랭커 코드가 있어야 한다
2. **무관 통과 교체(7.2절).** 근거 적합성 판정을 켠 상태에서 EVAL-175 같은 문항이 걸러지는지
3. **배포 환경 지연과 메모리.** 로컬 CPU 422ms가 배포 환경에서 얼마인지
4. **시뮬레이션과 앱의 차이.** 0.76 근처 4문항에서 결과가 달랐고 원인이 확인되지 않았다. 임계값 근처 판정이 구현에 따라 바뀔 수 있다
5. **후보 수에 따른 점수 변화.** 같은 질문·FAQ 쌍이라도 리랭커에 넣는 후보 수(10 / 20 / 30개)에 따라 점수가 달라진다. 대부분 같지만(중앙값 0, p90 0.001 이하) 최대 0.22까지 차이 난다(`score_summary.json`). 임계값 근처 문항은 후보 수만 바꿔도 통과 여부가 바뀔 수 있다

## 10. 질문 벡터 임계값 0.88 근거

0.88은 TELME-69에서 선택용 180으로 골랐다(`EVAL_SET_SUPPLEMENT.md` 6절). 기존 130만으로 고르면 다른 값이 나온다.

| t | 기존 130: 정답 80 | 기존 130: 무관 50 통과 | 보강 50: 무관 20 통과 |
| ---: | ---: | ---: | ---: |
| 현행(`Q_A` 단독) | 30 | 3 | 5 |
| **0.85** | **40** | 3 | **7** |
| 0.87 | 37 | 3 | 6 |
| **0.88** | 37 | 3 | **5** |

(공식 라벨)

- 기존 130만 보면 **0.85**가 선택된다. 기존 무관 50의 통과를 지키면서 정답이 가장 많기 때문이다(30 → 40)
- 그러나 0.85는 보강 50의 경계 무관 2건(EVAL-162 0.851, EVAL-175 0.877)을 통과시킨다. 기존 130에는 경계 무관 질문이 10건뿐이고 답변형 질문이 없어, 이 위험을 볼 수 없었다
- 그래서 180 전체로 고른 0.88이 맞다. 3.3절 규칙으로 다시 골라도 0.88이다(공식 라벨에서 동점 없음)
- 대신 180은 선택에 썼으므로 **0.88의 독립 검증이 아니다.** 최종 확인은 검색 확인용 세트로 한다(13절)
- 다중 정답 라벨로 고르면 0.88 ~ 0.92가 동점이다. EVAL-007, 014가 단일 벡터로 이미 맞혀져 0.88과 0.90의 차이가 사라진다. 선택을 공식 라벨로 하는 이유다
- **0.88은 사실상 EVAL-175 한 건이 정한 값이다.** 무관 70건 중 질문 벡터 최고점이 0.85 ~ 0.95인 문항은 경계 무관 6건뿐이다(EVAL-162 0.851, 123 0.852, 166 0.859, 177 0.863, 175 0.877, 122 0.886). 0.886 위로는 무관 문항이 없어 0.89 ~ 0.92는 무관 쪽에서 구분되지 않는다. 6절 병합에서 0.90으로 올린 것도 EVAL-122 한 건 때문이다

## 12. 재현

```bash
# 측정용 서버 (실제 임계값 그대로)
FAQ_SEARCH_TEST_API_ENABLED=true java -jar build/libs/telme-0.0.1-SNAPSHOT.jar --server.port=18090

# 다중 정답 라벨로 단일 / 이중 벡터 실측
for v in QA DUAL; do
  python3 scripts/measure_search_quality.py scripts/data/eval_questions_180_multigold.json \
    --api-url http://localhost:18090/api/v1/faq/search --vector $v \
    --dump-json .measure/live-mg180-$v.json
done
```

- 임계값 선택: `scripts/README.md`의 이중 벡터 임계값 재탐색 절차로 임계값 0 원시 결과를 벡터별로 모은다. 이중 벡터는 `simulate_dual_vector.py`가 3.3절 규칙으로 고른다(130건과 보강 50건 원시 결과를 파일별로 넣으면 평가셋별 무관 제한이 적용된다)
- 겹침(5절), 병합(6절), 부작용(7절): 원시 결과와 리랭커 결과 파일을 `eval_id`별로 맞춰, 임계값으로 자른 top-3에 정답 `slot_id`가 있는지로 채점한다
- 리랭커 결과 파일은 YJ720에게 받아야 한다(레포에 없음)

### 13.1 검색 확인용 세트

목적은 Recall 재확인보다 **임계값 근처의 구분력**을 만드는 것이다. 선택용 180에서 질문 벡터 최고점이 0.85 ~ 0.95 구간에 들어오는 문항, 즉 t 선택이 실제로 가르는 문항은 다음과 같다.

| 유형 | 구간 안 / 전체 |
| --- | ---: |
| `UNRELATED` / `ADJACENT_HARD` | **6 / 30** |
| `UNRELATED` / `ADJACENT` | 0 / 24 |
| `UNRELATED` / `OFF_DOMAIN` | 0 / 16 |
| `SIMILAR` | 23 / 40 |
| `VARIANT` | 3 / 40 |
| `ANSWER` | 4 / 30 |

무관 쪽은 6건뿐이라 0.88(EVAL-175 한 건)과 0.90(EVAL-122 한 건)이 표본 한 건에 걸려 있다. 새 세트는 0.87 ~ 0.92 구간에 무관 문항을 채워야 한다.

"검색 결과를 보지 않고 작성"과 "임계값 근처 문항 확보"는 한 단계로는 함께 만족할 수 없다. 점수를 알려면 검색을 돌려야 하기 때문이다. 두 단계로 나눈다.

1. **작성.** 검색 결과를 보지 않는다. 기존 FAQ의 주제 목록만 주고, 주제는 같지만 묻는 조건이 달라 답이 없는 질문(`ADJACENT_HARD` 정의)과 단독 답변 가능 질문을 만든다. 유형별 목표 건수와 합격 기준을 먼저 고정한다
2. **점검.** 질문을 고치지 않는다. 작성이 끝난 뒤 질문 벡터 점수 분포만 보고 0.85 ~ 0.95 구간에 들어온 건수를 센다. 부족하면 1단계와 같은 방식으로 문항을 더 만들고, 이미 만든 질문이나 임계값은 건드리지 않는다

이후 설정 변경 없이 적용하고, 결과를 보고 임계값을 다시 고치지 않는다.

#### 확정된 구성

`scripts/data/eval_questions_holdout_60.json` - 경계 무관(`ADJACENT_HARD`) **60건**, 카테고리 10종 x 6건. 이 세트는 처음 보는 경계 무관 질문의 거부 성능만 확인한다. 답변 가능 질문의 독립 Recall 검증은 포함하지 않으며, 기존 180건으로 정답 전달 회귀를 계속 확인한다.

| 항목 | 내용 |
| --- | --- |
| 유형 | `UNRELATED` / `ADJACENT_HARD` 만. 주제는 FAQ에 있으나 묻는 조건은 FAQ가 답하지 않는 질문 |
| 필드 | `eval_id`, `category`, `type`, `unrelated_kind`, `question`, `expected_slot_id`(null), `related_slot_id`, `note` |
| `related_slot_id` | 주제가 겹치는 FAQ 2건. `note`에 그 FAQ가 무엇까지만 답하는지 적었다 |
| 검증 | `check_eval_questions.py` 정적 검사 통과 |

**답변 가능 문항은 넣지 않았다.** 이유는 두 가지다.

- 초안의 답변 가능 30건 중 **22건이 기존 180건과 정답 `slot_id`가 0.30 이상 겹쳤다**(다중 정답 라벨 기준, 최대 1.00). 카테고리가 10종이고 카테고리당 정책이 3 ~ 7종뿐이라 기존 110건이 답변 가능 영역을 이미 조밀하게 덮었다. 겹치지 않는 질문을 짜내면 "이 값이 무엇을 가리키나" 식의 부자연스러운 문장이 된다
- 겹치는 문항을 빼면 카테고리 대칭이 깨져 `check_eval_questions.py`가 실패한다(카테고리별 `SIMILAR` = `VARIANT`, 카테고리 간 동수를 요구). 대칭을 맞추려면 겹치는 문항을 억지로 채워야 한다

답변 가능 쪽 회귀는 기존 180건으로 계속 본다. 이 세트의 목적은 위 표대로 경계 무관 구분력이다.

#### 제외 규칙과 적용 결과

초안 80건에 아래 규칙을 **점수를 보기 전에** 정하고 적용했다.

| # | 규칙 | 제외 |
| --- | --- | ---: |
| 1 | 기존 180건 중 어느 문항과 질문 텍스트 유사도 0.35 이상 | 7건 |
| 2 | 답변 가능 문항으로서 기존 180건과 정답 `slot_id` 겹침 0.50 이상 | 13건 |
| 3 | 1 / 2에 안 걸려도 질문 의도가 기존 문항과 같음 | 3건 |

- 규칙 3으로 뺀 3건: `H-033`(EVAL-165와 같은 의도 - 유심 연락처 이전), `H-041`(EVAL-178 - 로밍 수신만 해도 과금), `H-046`(EVAL-120 / 179 - 매장 방문 예약)
- 유사도는 어절 앞 2 ~ 3글자 n-gram의 Jaccard다. 임베딩을 쓰지 않아 검색 점수를 보지 않고 계산된다
- 계산은 `scripts/check_eval_overlap.py`로 재현한다

```bash
python3 scripts/check_eval_overlap.py scripts/data/eval_questions_holdout_60.json \
  --against scripts/data/eval_questions_130.json scripts/data/eval_questions_supplement_50.json \
  --multigold scripts/data/eval_questions_180_multigold.json
# 겹침 검사 통과 (텍스트 0.35 / 정답 0.5 미만). 최대 텍스트 유사도 0.318 (H-009)
```

같은 명령을 초안 80건에 돌리면 위 표의 규칙 1 · 2 제외 20건이 그대로 재현된다
- 제외 후 남은 무관 40건에 같은 규칙을 지키는 20건을 새로 써서 카테고리당 6건으로 맞췄다
- 최종 60건의 기존 180건 대비 최대 텍스트 유사도는 **0.318**(H-009), 파일 내부 중복 0건

**2차 검토에서 2건을 더 교체했다.** 수치에는 안 걸렸으나 질문 의도가 기존과 같았다(규칙 3).

| eval_id | 기존 문항 | 교체 후 |
| --- | --- | --- |
| `H-013` | `EVAL-176` 기기변경 시 보상 판매 | 기기변경 시 기존 폰의 사진 · 연락처 이전 지원 여부 (기존 대비 0.158) |
| `H-037` | `EVAL-171` 명의변경 시 약정 승계 | 명의변경 접수 후 완료 전 취소 가능 여부 (기존 대비 0.188) |

`H-030`("가입자가 사망한 경우 해지 서류")은 `EVAL-172`("돌아가신 부모님 명의 회선 변경 서류")와 상황은 같으나
묻는 업무가 해지와 명의변경으로 달라 정책 범위(`TERMINATE-01` 대 `NAME_CHANGE-01`)가 다르므로 유지했다.

#### 새로 쓴 20건의 라벨 검증

"답이 없다"를 FAQ 본문 검색으로 확인했고, **초안 단계에서 만든 5건은 실제로 FAQ가 답하고 있어 교체했다.**

| 교체한 문항 | 답하고 있던 FAQ |
| --- | --- |
| 납부 기한 25일이 주말이면 밀리나요 | `BILLING-0051` / `0079` / `0142`가 "다음 영업일에 출금"이라고 답함 |
| 요금제를 바꾸면 이월 데이터가 유지되나요 | `PLAN-0078`이 같은 질문을 다룸 |
| 듀얼번호로 로밍 데이터를 같이 쓸 수 있나요 | `ROAMING-0079`가 듀얼번호와 나눠쓰기를 구분해 답함 |
| 20만 원 차단 후에도 전화가 되나요 | `ROAMING-0048`이 "데이터만 차단, 통화·문자는 그대로"라고 답함 |
| 부가서비스 해지도 바로 되나요 | `SERVICE-0011` / `0016` / `0031`이 "신청한 달 말일까지"라고 답함 |

**키워드 검색만으로는 부족하다.** 위 5건은 관련어 동시 등장으로 걸러진 뒤 FAQ 답변을 직접 읽어서야 오답 라벨임이 드러났다. 남은 문항도 사람 검토 때 같은 방식으로 본다.

#### 경위와 한계

- **1차 초안에 프롬프트 예시 누출이 있었다.** 생성 프롬프트의 `ADJACENT_HARD` 정의 예시로 `EVAL-175`를, JSON 형식 예시의 `related_slot_id` / `note`로 `EVAL-122` 관련 내용을 그대로 넣은 탓에, 초안에 `EVAL-175`와 글자까지 같은 문항(`H-014`)과 유심 재발급 비용 경계 문항(`H-031`)이 섞였다. 둘 다 0.88과 0.90을 정한 문항이라 규칙 1로 제외했다
- `H-031`의 기존 쌍둥이는 하나가 아니다. `EVAL-123`(0.40), `EVAL-122`(0.31), `EVAL-166`(0.24)로, 유심 재발급 비용 FAQ는 기존 세트에서 이미 경계 문항이 밀집한 지점이다
- **초안은 임계값 선택에 참여하지 않은 외부 작성자가 만들었으나, 제외와 보강은 임계값을 고른 검색 쪽이 했다.** 수정은 위 수치 규칙으로만 집행했고 검색 점수는 보지 않았다. 완전한 독립성은 아니므로, 측정 결과가 경계에 걸리면 이 사실을 함께 본다

#### 적용 규칙

- **`simulate_dual_vector.py`에 넣어 임계값을 다시 고르지 않는다.** 확인용 세트다
- 현행 설정(`Q_A` 0.72 + `QUESTION_ONLY` 0.88) 그대로 `--vector DUAL`로 **한 번** 측정한다
- 합격 기준은 **60건 중 44건 이상 거부**(거부율 73.3% 이상)하고, 어느 한 카테고리에서도 3건 이상 통과시키지 않는 것이다. 같은 유형인 기존 `ADJACENT_HARD` 30건의 거부 결과 22 / 30(73.3%)과 카테고리 균형을 함께 기준으로 삼았다
- 결과가 나빠도 이 세트로 임계값을 고치지 않는다. 고칠 근거가 되면 그것은 별도 재선택이고 새 확인용 세트가 필요하다

#### 1차 적용 결과

교체를 마친 60건을 현행 설정(`Q_A` 0.72 + `QUESTION_ONLY` 0.88, `--vector DUAL`)으로 한 번 측정했다.

| 항목 | 합격 기준 | 실측 | |
| --- | --- | --- | --- |
| 거부 | 44건 이상 (73.3%) | **55 / 60 (0.917)** | 통과 |
| 한 카테고리 최대 통과 | 3건 미만 | **2건** (PLAN) | 통과 |
| 참고: 선택용 180의 무관 거부율 | - | 0.886 (62/70) | - |

- **0.88이 선택용 평가셋에만 맞춘 값이 아니라는 1차 증거다.** 처음 보는 경계 무관 60건에서 거부율이 오히려 조금 높다
- 통과한 5건 중 **4건은 `Q_A` 벡터가 통과시켰다**(0.721 ~ 0.802). 질문 벡터가 통과시킨 것은 `H-087`(0.896) 1건뿐이다. 이중 벡터가 만든 누수가 아니라 단일 벡터 시절부터 있던 유형이다

| eval_id | 카테고리 | 통과 점수 | 통과시킨 벡터 |
| --- | --- | ---: | --- |
| `H-087` | PORTING | 0.896 | `QUESTION_ONLY` |
| `H-083` | PLAN | 0.802 | `Q_A` |
| `H-092` | USIM | 0.781 | `Q_A` |
| `H-009` | PLAN | 0.751 | `Q_A` |
| `H-003` | BILLING | 0.721 | `Q_A` |

**다만 구간 구분력은 부족하다.** 질문 벡터 최고점 분포가 이렇다.

| 구간 | 건수 |
| --- | ---: |
| 0.92 이상 | 0 |
| **0.87 ~ 0.92** | **1** (`H-087` 0.896) |
| 0.85 ~ 0.87 | 0 |
| 0.85 미만 | 59 |

0.87 ~ 0.92를 가르는 문항이 1건뿐이라 **거부율은 확인되지만 0.88과 0.90 중 어느 쪽이 안전한지는 이 세트로 판정할 수 없다.** 13.1절 첫 문단의 목표는 10건 이상이었다.

원인은 문장 방식이다. 구간에 들어온 문항은 FAQ 질문과 어휘가 거의 같고 묻는 조건만 다르다.

```
H-087 "번호이동 접수를 취소하면 바로 다시 신청할 수 있나요?"  <-  FAQ "번호이동 취소할 수 있어요?"   0.896
```

나머지 59건은 조건은 FAQ 밖이지만 문장이 FAQ 질문과 멀어 0.75 ~ 0.84에 머물렀다.

라벨 교체가 구간 문항을 줄인 면도 있다. 교체 전 `H-098`("멤버십 등급은 언제 다시 산정돼요?")이 질문 벡터 0.942로 0.92 이상 구간에 있었고, 그때 거부율은 0.883(53/60)이었다. 라벨이 맞지 않아 교체한 판단은 맞지만 구간 문항이 2건에서 1건으로 줄었다.

#### 2차 보강

| 항목 | 내용 |
| --- | --- |
| 방식 | **FAQ 질문 문장을 거의 그대로 쓰고 묻는 조건만 바꾼다.** 조건이 FAQ 답변 밖이어야 한다 |
| 건수 | 카테고리당 2 ~ 3건, 총 20 ~ 30건. 목표는 0.87 ~ 0.92 구간 10건 이상 |
| 검증 | 라벨은 FAQ 답변을 직접 읽어 확인한다. 키워드 검색만으로는 부족하다(위 교체 5건이 그 사례) |
| 기록 | 1차 60건은 이미 측정했으므로 확인용으로 다시 쓸 수 없다. 2차 추가분만 새 확인분이다 |

- 1차 작성 방식의 구간 적중률은 신규 20건 중 2건이었고 그중 1건이 라벨 문제로 교체되어 최종 1건만 남았다. 같은 방식으로 늘리면 200건이 더 필요하다. 방식을 바꾸는 쪽이 맞다
- 기존 세트의 `EVAL-175`(0.877), `EVAL-122`(0.886)가 구간에 있는 이유도 같다. FAQ를 보고 그 지점을 노려 쓴 문항이다
- **라벨 정확성과 구간 적중을 같이 만족해야 한다.** 어휘를 FAQ에 붙이면 점수는 올라가지만 FAQ가 실제로 답해 버릴 위험도 함께 올라간다

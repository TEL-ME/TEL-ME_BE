# TELME-98 요금제 변경 되묻기 오류 보완

## 범위와 검증 기준

가입월·당월 변경 이력을 확인하는 요금제 변경 상담 1개의 마무리를 보완한다. 전체 상담 지원·모델 자체 품질·전체 환각률 개선을 뜻하지 않는다.

원래 작업본은 `52df227`에 최초 되묻기 미커밋 변경이 포함된 상태였다. 최초 실험 `metadata.json`의 소스 지문과 이번 수정 전 소스가 모두 일치했다. 보고서 작성 후 이미 해결됐다고 볼 추가 수정은 없었다. 기존에 정상인 미확인 값 없음 저장, 저장 후 SSE 전송, 중복 질문 메시지 방지, 상담 소유권 검증은 유지했다.

최종 준비본은 PR #85 `47cbbe5`를 기준으로 한다. 최신 develop `c4f4458`, 병합된 #74 Guard·#83 저장·조회 보완을 포함한다. 기존 되묻기 작업본과 다른 작업 폴더를 보존하고 별도 복사본에 관련 변경만 적용했다. 로컬 merge/rebase·커밋·푸시·PR 게시·GitHub 리뷰 답변·머지는 하지 않았다.

활성 경로는 `ChatProcessingDispatcher → ConsultChatProcessingService → 라우팅/후속 분석 → ConsultTurnPreparationService → DialogueService → FaqSearchAnswerProvider → RagAnswerGenerator → 기존 AnswerGuard → 최종 답변 저장 → SSE`다. 대화 기록 조회 API와 DB 원문도 함께 확인했다.

## 재현한 실패와 원인

- **PLAN-006 모름:** `DECLINED`/값 없음은 보존됐지만 확정 조건만 전달하는 변환 과정에서 모름 상태가 생성 입력에서 빠졌고, 기존 “판단 범위” 안내는 변경 **가능** 확정만 금지했다. 같은 모델 재현에서도 변경 불가·다음 달 초 안내를 생성했다. 기존 Guard는 이 상담 상태에 따른 개인 판단까지 검증하지 못했다.
- **PLAN-010 거절:** “알려주고 싶지 않아요”가 기존 거절 규칙에 없었다. 모델의 거절 라벨도 실제 발화 규칙 검증에서 제거되어 보류·대기로 남았다. 명시적 거절을 검증된 규칙 결과로 보완한다.
- **PLAN-002/007 가입월:** 저장된 `joinedThisMonth=예` 자체는 맞았다. 원래 실험에는 ‘가입한 지 한 달’, 이번 재현에는 ‘가입한 지 얼마 되지 않아서’가 나타났다. 생성에서 달력상 가입월을 경과 기간으로 바꾼 문제이며 단순 값 저장 오류가 아니다.
- **PLAN-003 제한 안내 누락:** 원래 실험에는 Guard 전 원문이 없어 당시 정확한 원인은 미확정이다. 같은 질문·응답·FAQ·모델 옵션으로 재현한 원문은 “정보가 없습니다”로 시작했고 Guard가 그 뒤를 잘랐다. 이 재현은 생성기의 오거절이었다. 정상 생성문을 통과시키려고 Guard를 완화하지 않았다.
- 추가 반례: “바꾼 적이 없어요”가 긍정 변경 이력으로 추출되는 문제, ‘언제’가 포함된 개인 질문의 일괄 제외, 최신 정정·불명확한 두 달·가정·타인 조건 처리도 보완했다.

## 변경 내용과 처리 계약

`PlanChangeConditions`가 명시적 절을 순서대로 읽어 최신 정정과 부정 이력을 반영한다. 가정·타인·애매한 문구를 예·아니요로 채우지 않는다. 미확인으로 정정하면 이전에 채워진 값도 제거된다. 개인 질문은 ‘언제’·‘조건’ 단어 하나로 제외하지 않는다.

후속 모델 결과는 사용자 발화에서 검증된 조건·거절·보류와 대조한다. 해당 요금제 대기 상담에만 보완을 적용한다. 초기 의도 enum/라우팅 JSON 계약, 기존 매장 후속 처리에는 새 조건을 임의로 적용하지 않는다.

모델 프롬프트에는 별도 `[요금제 상담 적용 기준]`을 전달한다. 미확인은 고객의 예·아니요가 아니며, 달력상 가입월을 30일·한 달 경과·다음 달 초로 바꾸지 않도록 설명한다. 기존 v3 시스템 지시는 유지하고 버전은 `rag-answer-v3-plan-v2`다. 상담 적용 기준을 사용자 조건으로 DB에 저장하지 않는다.

**프롬프트 보완만으로 최종 답변을 보장하지 않는다.** 중간 실제 모델 실험에서 모름 뒤 단정이 남았다. 이 상담의 확인된 두 제한과 조건 상태에 대한 최종 문장은 서버가 구성한다. 근거가 없으면 구성하지 않고 기존 답변 불가 경로를 유지한다. 구성한 답변도 동일한 Answer Guard 검사를 통과해야 한다. 모델 오류·취소에서는 정상 완료를 만들지 않는다. 일반 FAQ에 이 응답 구성기를 적용하지 않는다. 일반 요금제 변경 기준 질문은 동일한 정책 근거로 개인 질문 없이 기준을 안내한다.

- 미확인이고 확정된 제한도 없음: 조건별 기준과 개인 가능 여부 미확정 안내.
- 확인된 가입월 또는 당월 변경 이력과 해당 FAQ 제한 있음: 그 제한을 안내. 다른 미확인 조건 때문에 전체 거절하지 않음.
- 두 조건 모두 아니요이고 두 제한 근거 있음: 두 기준에 한정한 변경 가능 안내. 전체 가입 자격·변경 권한 충족을 확정하지 않음.
- ‘다음 달부터’는 실제 FAQ 답변에 있는 경우만 안내. 날짜·경과 기간을 계산하지 않음.
- ‘한 번’ 근거를 새 숫자 ‘1회’로 바꿔 기존 수치 Guard가 오차단하는 일을 피하도록 근거 표기를 유지.

이 작업에서 `AnswerGuard.java`·`AnswerClaimRelations.java`, 모델 설정, 검색 임계값·Top-K·리랭커, Judge 기준·평가셋은 변경하지 않았다. 새로운 상담 유형·DB 테이블·조건 상태도 추가하지 않았다. 정책 근거가 필요한 기준 질문에는 기존 정책 보완 검색을 재사용하며, 검색 문구·추가 여부는 실행 추적에 남는다.

### 반복 입력 종료

기존 정책은 동일 대기 질문 메시지를 중복 생성하지 않았지만 해석 불가 응답의 종료 상한은 없었다. 최초 질문은 조건별 1회, 추가 질문 메시지는 0회다. 같은 대기 조건의 해석 불가 응답이 **2회**면 값을 채우지 않고 일반 기준 안내로 종료한다. 한 번의 애매한 입력은 정정할 기회를 남기며 무기한 대기는 막기 위한 값이다. 명시적 보류, 추출 가능한 정정, 새 상담 전환은 실패 횟수에 포함하지 않는다. 기존 메시지·실행 연결로 계산하며 새 카운터 테이블은 없다.

남은 `PENDING` 조건이 있어도 요금제 상담에서 다른 확정 제한으로 종료하거나 값 없는 미확인으로 일반 안내를 종료한 경우에만 상담을 완료한다. 미답변 기록을 예·아니요로 위조하지 않는다. 매장 위치 등 다른 대기 조건의 완료 금지는 유지한다.

## 근거와 로컬 모델 비교

근거: BILLING-0001(357), BILLING-0015(1387), BILLING-0106(1462)의 가입월 제한·월 1회, BILLING-0092(1451)·BILLING-0057(395)의 한 달에 한 번이다. 실제 근거 문구와 사례별 사용 FAQ는 [공유 검증 자료](evidence/telme98-clarification-fixes-20261001.json)에 포함했다.

실행은 EXAONE `exaone3.5:7.8b`(digest `c7c4e3d…ba8fbf03`), temperature 0, num_ctx 8192, num_predict 1024, bge-m3, Q_A 0.72/QUESTION_ONLY 0.88/Top-3, 근거 적합성 추가 모델 검사 비활성 조건이다. 검색·생성·후속 라우팅은 실제 로컬 호출이다. 최초 SQL 스냅샷과 시험 DB FAQ 1,152건의 관련 필드를 대조했으며 변경은 0건이다. 원본 사용자 DB에는 쓰지 않았다.

기존 10문항의 질문·합성 사용자 응답을 유지하고 추가 11개 대화를 실행했다. 최종 21개 대화·50개 사용자 턴에서 21개 최종 답변의 DB·조회 API·trace·SSE 문자열이 일치했다. 최종 SSE token은 실행당 한 번이었다. 상담은 의도한 DONE 또는 새 주제의 이전 상담 CANCELLED로 종료했다. 보류·첫 애매한 입력에는 새 출력이 없었다. 이것은 소규모 선택 사례 검증이다.

비교 조건 차이를 숨기지 않는다. 최종 준비본은 이미 병합된 최신 #74 Guard를 포함하며 최초 실험의 Guard 해시와 다르다. 이번에 Guard 규칙을 수정한 것은 아니다. PLAN-005는 일반 기준에 필요한 정책 보완 검색으로 최종 FAQ가 달라졌다. PLAN-010은 기존에 최종 생성 자체가 없어 같은 최종 근거의 전후 비교가 성립하지 않는다. 나머지 PLAN 문항의 최종 FAQ ID·답변은 최초 기록과 일치했다. 수정 전 신규 원문 재현은 핵심 5문항에서 수행했다.

원시 생성문에는 여전히 오거절·개인 단정이 나타날 수 있다. 최종 답변은 검증된 상담 정책 응답과 Guard를 통해 보호된 결과이며, 이를 모델 자체 품질 개선이나 Guard 단독 효과로 표현하지 않는다. 기존 Bedrock Judge 원본은 보존했고 이번 유료 재채점은 실행하지 않았다. 이전 PLAN-006의 ‘다음 달 초’도 Judge는 supported로 기록했으므로 Judge 라벨과 근거 대조를 구분한다. 아래 결과는 근거 대조·계약 확인 초안이며 사람 확정 라벨은 아니다.

직접 JDBC를 사용하는 DB 테스트는 `POSTGRES_PORT` 등의 환경변수를 읽는다. Spring datasource 설정뿐 아니라 환경변수도 같은 전용 시험 DB로 지정해야 한다.

## 추가 확인: 조건 재사용·두 조건 동시 입력

이번 추가 요청에서 기능 코드 수정은 필요하지 않았다. `PlanChangeClarificationPolicy.userConditions`는 저장된 최신 조건을 먼저 사용하고 원문 조건은 비어 있는 키에만 보완한다. 후속 라우팅은 실제 발화에서 확인된 두 조건을 모두 전달하고, `FollowupConditionConverter`는 현재 상담 ID를 확인한 뒤 대기 중인 키 외의 유효한 조건도 함께 저장한다.

## 재현 자료·PR 의존 관계·남은 확인

이 문서와 공유 JSON은 PR 변경에 포함할 자료다. 전체 원시 대화·SSE·trace·DB 상태·로컬 프록시 원문은 별도 `local-experiments/2026-10-01-clarification-fixes/`의 `before/`, 중간 실행 폴더, `final/`에 보존했다. PR만 내려받으면 전체 원본은 생기지 않는다. 더 자세한 비교가 필요하면 해당 실행 원본을 작성자에게 요청한다. 원문은 합성 실험 발화에만 한정해 loopback 프록시로 수집했고, 운영 로그·DB에 Guard 전 생성문을 일괄 추가하지 않았다.

필수 선행 기반은 #82 안전 전송·#83 저장/조회·#84 실패 처리·#85 실행 추적이다. #82/#83은 병합됐으며 최종 기준 `47cbbe5`에는 미병합 #84/#85도 포함되어 있다. #85의 V17은 그대로 재사용하고 적용된 V15/V16은 수정하지 않았다. 게시 전 최신 병합 상태를 확인해 선행 변경이 PR diff에 포함되는 범위를 설명해야 한다. `develop`을 대상으로 게시해야 기존 CI가 실행된다. 현재 로컬 준비 단계이므로 새 PR의 GitHub CI는 아직 실행되지 않았다.

#75 복합 질문과 #86 프롬프트 관계 생성 방지는 별도 미병합 작업이며 임의로 합치지 않았다. 용재님과 두 조건의 값 계약, 복합 하위 상담의 대기 선택, 로컬 GPU의 다른 모델 조건을 맞춰야 한다. #86 적용 시 `rag-answer-v3-plan-v2`의 상담 블록과 v4.1 시스템 지시를 함께 보존하고 다시 검증해야 한다.

실제 브라우저 화면과 배포 DB는 미검증이다. API 테스트를 화면 새로고침 완료로 해석하지 않는다. 프론트에서는 아래를 확인한다.

1. 되묻기 표시가 한 번이고 새로고침 후 기존 질문·이력이 유지되는지.
2. Guard 전 토큰이 화면에 나타나지 않고 최종 답변이 한 번만 표시되는지.
3. 모름·거절 후 기준 안내가 표시·저장되고 새로고침 후 동일한지.
4. 보류/첫 애매한 응답의 `complete`와 출력 없음에서 기존 질문을 유지하고 로딩이 종료되는지.
5. 정정과 새 주제 전환에서 과거 조건·질문이 새 상담에 적용되지 않는지.
6. 오류·타임아웃·취소 화면에서 부분 원문이나 정상 완료 상태가 보이지 않는지.

다음 우선순위는 실제 프론트 검증, 복합 상담과의 연결, 다양한 표현·정책 변경/상충 FAQ에 대한 상담 정책 검토다. 이번처럼 유한 정책 답변을 기존 Guard 전에 구성하는 결정, 2회 미해결 응답 종료 기준은 팀 공통 `decisions.md`에 반영할 필요가 있다. 다른 작업 폴더의 미커밋 decisions 문서는 수정하지 않았다.

# 최근접 매장 거리 계산 방식 결정 및 쿼리 실측 (TELME-68)

> **읽기 전에**
> - 측정 도구(`scripts/measure_store_nearby.py`, `src/benchmark`의 벤치마크 코드와 `./gradlew store*` 태스크)는 저장소에 넣지 않았다. 이 문서의 명령과 파일 이름은 측정 당시 도구 이름이고, 도구는 담당자가 따로 보관한다(10절).
> - 측정 중에는 마이그레이션을 V8(좌표)·V9(업무 조합 부분 인덱스, 검토안)·V10(태그)로 나눴다. 최종 이력에는 채택한 것만 `V15__add_store_geography.sql`(좌표, 영업 중 매장 공간 인덱스)과 `V16__add_store_tags.sql`(태그 배열, 태그 공간 인덱스)로 남겼다. 업무 조합 부분 인덱스는 검토안이라 저장소에 없다.

## 1. 배경

요구사항 FR-C2(현재 위치 기준 최근접 매장 계산)를 구현하면서, 기술 스택 표에 "담당자 비교 후 확정"으로 비어 있던 **거리 계산 방식**을 정한다. 이후 제휴 매장이 더해져 매장이 크게 늘고, 업무 종류·영업 중 같은 필터가 붙는 경우까지 고려했다.

- 후보: Haversine 공식 SQL / PostgreSQL `earthdistance` 확장 / PostGIS
- 판단 기준: 정확도, 설치 부담(로컬·CI·RDS), 규모별 성능, 필터가 붙을 때의 최악 시간
- 성능 목표: 최근접 매장 조회 300ms 이내(NFR-1.2). 이 문서는 **쿼리 단위**까지만 잰다. API 전체 응답시간은 사용자용 매장 API 작업에서 확인한다

결론부터: **거리 계산은 모두 PostGIS로 하고, 검색은 KNN이다.** 필터가 없으면 영업 중 매장 인덱스에서, 정적 조건(업무 종류와 앞으로 더할 매장 속성)이 있으면 매장 태그 배열과 위치를 함께 담은 인덱스 하나(`(geog, tags)`, V16)에서 가까운 곳을 꺼낸다. 동적 조건(영업 중)은 인덱스로 만들 수 없어 가까운 후보부터 확인하고 모자라면 반경 안을 모두 확인한다. 규모는 전국 최대 4만 곳, 반경 10km 안 최대 6천 곳으로 고정이고, 이 결정의 근거와 규모별 극단 케이스 실측은 11절에 모았다. 아래 문장은 검토안 2(업무 조합 부분 인덱스) 이전의 판정 과정이다. 필터가 없으면 반경 없이 순수 KNN, 있으면 반경(최대 10km) 안에서 조건 맞는 매장을 모두 계산한다. 국내 서비스 지역 밖이면 조회하지 않는다. 엣지케이스 19가지 중 18가지는 가상 100만 곳에서 가장 느린 값까지 300ms 안이었고, 업무 여러 개를 고르는 필터 경로는 여유가 부족해 개선안을 검토 중이다(7.4).

## 3. 정확도

`scripts/measure_store_nearby.py --accuracy-only`로 국내 좌표 무작위 2,000쌍을 거리 구간별로 만들어 WGS84 타원체 기준 Vincenty 거리와 비교했다.

| 거리 구간 | Haversine 최대 오차 | 평균 | earthdistance 최대 오차 | 평균 |
| --- | --- | --- | --- | --- |
| 0.1–1km | 0.257% | 0.142% | 0.370% | 0.156% |
| 1–10km | 0.259% | 0.141% | 0.372% | 0.154% |
| 10–50km | 0.257% | 0.142% | 0.369% | 0.162% |

10km 거리에서 최대 26m 차이다. 매장 카드에 m 단위로 보여 주는 거리로서 충분하다. 거리가 0.3% 안쪽으로 붙은 두 매장은 방식에 따라 순서가 바뀔 수 있다(100만 건 측정에서 `ST_Distance`만 4·5번째 순서가 달랐다).

## 4. 필터 없는 쿼리 실측

### 4.1 측정 방법

- 스크립트: `scripts/measure_store_nearby.py --postgis`
- 규모마다 측정용 테이블(`bench_stores`, `stores`와 같은 컬럼 타입)을 트랜잭션 안에서 만들고 ROLLBACK 한다. 크기마다 psql 세션을 새로 연다(같은 세션에서 PostGIS 확장을 ROLLBACK 후 다시 만들면 `no spatial operator found` 에러가 난다)
- 가상 매장 분포: 60%는 9개 도시 중심 주변(표준편차 약 9km), 40%는 전국 균등, 2%는 폐업
- 기준점: 밀집(강남, 서면), 중간(대전), 희박(강원 산간). 반경 10km·50km, `LIMIT 5`
- 값: `EXPLAIN (ANALYZE)`의 Planning + Execution Time. 조건마다 워밍업 5회 후 30회, 전체 3회 반복
- 환경: Apple M4, Podman(4 CPU, 6GB), PostgreSQL 16.14, PostGIS 3.6.4, `shared_buffers` 128MB, JIT 켬(기본값). 절대값은 RDS와 다르므로 **방식 간 상대 비교**로 읽는다

### 4.2 결과 (강남 · 반경 50km, 3회 중앙값, 단위 ms)

| 방식 | 150건 | 2,000건 | 100만 건 | 100만 건 읽은 행 |
| --- | --- | --- | --- | --- |
| Haversine + 사각형 선필터 | 0.08 | 0.52 | 92 (p95 111) | 1,000,000 |
| earthdistance + GiST | 0.43 | 2.55 | 1,133 | 약 239,000 |
| PostGIS `ST_DWithin` → `ST_Distance` 정렬 | 0.06 | 0.42 | 160 | 약 240,000 |
| PostGIS KNN (`<->`, 5개 먼저 뽑고 반경으로 거름) | 0.03 | 0.03 | 0.31 | 5 |

- 150건·2,000건에서는 모든 방식이 3ms 이하다. 이 규모에서 PostGIS를 쓸 성능상 이유는 없다
- 100만 건에서는 KNN만 규모와 무관하게 빠르다. 반경으로 먼저 거르는 PostGIS(`ST_DWithin`)는 오히려 Haversine보다 느리다
- **KNN은 `ORDER BY`가 `<->` 하나일 때만 동작한다.** `ORDER BY geog <-> pt, store_id`처럼 동점 정렬을 붙이면 전체 정렬로 바뀌어 100만 건에서 약 135ms가 된다
- KNN도 완전히 일정하지는 않다. 강남 기준 방문한 인덱스 페이지가 2,000건 8개, 100만 건 37개였다(0.03 → 0.31ms). 밀집 지역일수록 확인할 인덱스 영역이 많다

## 5. 필터가 붙을 때

필터 측정은 스크래치 스크립트로 1회만 돌렸다(저장소 미포함). 100만 건, 강남, 반경 50km, JIT 끔, 조건마다 5~7회 중앙값이다.

### 5.1 KNN은 필터를 먼저 적용할 수 없다

공간 인덱스에는 위치만 있어서, KNN은 가까운 매장을 꺼내며 필터를 확인하고 안 맞으면 버린다. 조건에 맞는 매장이 드물거나 주변에 없으면 멀리까지 훑는다.

- 반경 없는 KNN: 주변에 조건 맞는 매장이 없으면 **약 1.5초**(87만 행 확인)
- KNN + 반경: 반경이 탐색 범위를 묶어 폭발하지는 않지만, 주변이 전부 조건에서 빠지면 반경 안을 다 훑는다. 강남 50km 안 약 24만 곳 → **약 470ms**. 활성 비율과 관계없이 "반경 안 매장 수"로 정해진다
- 옵티마이저에 맡기면 공간 조건의 선택도를 크게 틀린다(강남 50km 안 매장을 100곳으로 추정, 실제 약 24만 곳). 활성 10%에서 KNN이면 1ms인 쿼리에 "필터 먼저" 계획을 골라 87ms(JIT 켜면 187ms)가 됐다

### 5.2 필터 먼저는 조건에 맞는 매장 수에 비례한다

조건에 맞는 매장만 모아 거리를 구하는 방식. 분포와 관계없이 맞는 매장 수로 시간이 정해진다.

| 조건에 맞는 매장 | 필터 먼저 |
| --- | --- |
| 50만 곳 | 129–156ms |
| 1만–5만 곳 | 33–52ms |
| 약 2,000곳 | 13–15ms |
| 1,000곳 이하 | 1–2ms |

통과율이 100%인 필터("월요일 12:00 영업 중", 영업시간 테이블 700만 행 조인)에서는 필터 먼저가 PostGIS `<->` 300ms, Haversine 391ms, `ST_Distance` 468ms, earthdistance 1,106ms였다. 같은 조건의 KNN + 반경은 0.26–0.42ms다. 시간의 대부분은 거리 계산이 아니라 영업시간 조인이었다(`<->` 거리 계산만 하면 109ms).

### 5.3 역전 지점

평균적인 분포에서 두 방법은 조건에 맞는 매장 **약 1,000–2,000곳(100만 곳 중 0.1–0.2%)**에서 역전된다. 그보다 적으면 필터 먼저, 많으면 KNN이 빠르다. 최악의 분포(주변만 전부 탈락)에서는 KNN + 반경이 반경 안 매장 수만큼 느려진다.

## 6. 결정

### 6.1 검색 경로

| 경우 | 경로 | 코드 |
| --- | --- | --- |
| 국내 서비스 지역 밖 (위도 33.0~38.7, 경도 124.5~132.0 밖) | DB를 조회하지 않고 빈 목록 | `StoreSearchService` |
| 필터 없음 | 반경 없이 KNN(`<->`). 가까운 순으로 꺼내다 요청 개수를 채우면 멈춘다 | `StoreNearbyQueryRepository.findNearest` |
| 정적 조건만 (업무 종류, 앞으로 더할 매장 속성) | 태그 조건을 인덱스 안에서 거르며 `(geog, tags)` 인덱스(V16)에서 KNN으로 가까운 곳을 꺼낸 뒤 반경으로 거른다 | `StoreNearbyQueryRepository.findNearestMatching` |
| 동적 필터(영업 중)가 섞임 — **구현했지만 꺼 둠**(8.9) | ① 가까운 후보(요청 개수×10)를 KNN으로 꺼내며 조건 확인, 요청 개수를 채우면 끝 ② 못 채우면 반경 안에서 조건 맞는 매장을 모두 모아 정렬 | ① `findNearestCandidatesMatching` ② `findMatchingWithinRadius` |

- 필터가 없을 때와 있을 때를 나눠, 필터가 있는 경로만 따로 최적화할 수 있게 했다
- 필터 없는 KNN은 반경을 보지 않으므로 주변에 매장이 없으면 멀리 있는 매장이 나온다. 지도를 확대해도 화면 밖 매장이 결과에 들어갈 수 있다
- "필터 없음"이어도 영업 중(`status = 'OPEN'`) 조건은 항상 붙는다. 고정 조건이라 공간 인덱스를 영업 중 매장만 담는 부분 인덱스로 만들어 KNN이 폐업 매장을 건너뛸 필요가 없게 했다(주변 5만 곳 폐업 시 65 → 4.6ms)
- 해외 좌표에서는 반경 없는 KNN이 인덱스를 거의 전부 훑었다(뉴욕 약 1.5초). 그래서 서비스 지역 밖이면 조회하지 않는다. 지역 안의 끝자락(독도, 해상 모서리)은 1ms 미만이었다
- 필터 있는 경로는 반경 상한 덕분에 읽는 양이 "반경 안 매장 수"로 묶인다. 규모별 전략(SMALL/LARGE, `store.search.scale`)을 두었다가 없앴다(7.2, 7.3). 비교에 쓴 SQL은 벤치마크 코드에만 남겼다
- 조건이 있는 쿼리는 `OFFSET 0`으로 KNN 탐색으로 바뀌지 못하게 고정한다(5.1). KNN 쿼리의 안쪽 `ORDER BY`는 `<->` 하나만 둔다(4.2)

### 6.2 검색 반경 상한 10km

10km는 사람이 매장을 찾아 이동할 만한 최대 거리로 정한 값이다(측정으로 정한 값이 아니다).

- 반경은 필터가 있는 검색에만 적용한다. 지도 화면(카카오 지도 SDK)은 현재 축척에 맞는 반경을 넘긴다. 확대하면 10km보다 작아지고, 축소해도 10km를 넘지 않는다
- 축척을 넘기지 않는 호출(채팅 매장 안내 등)은 기본값 10km를 쓴다
- 검색 시간은 반경 안 매장 수에 비례하므로(7.3) 10km가 성능상 최악이다. 10km에서 목표 안이면 더 작은 반경은 자동으로 목표 안이다

### 6.3 필터

- 지금은 거의 안 바뀌는 속성인 **업무 종류**만 지원한다. 여러 개를 고르면 모두 처리할 수 있는 매장만 남긴다
- (검토안 1) 업무마다 `EXISTS`를 하나씩 뒀다. `IN (… GROUP BY … HAVING count(*) = n)` 형태는 후보 매장마다 집계를 다시 돌아 10만 곳에서 24초가 걸렸다(수정 후 17.8ms). 매장마다 업무 행을 한 번에 세는 상관 `count` 형태도 비교했지만 더 느렸다(100만 곳 강남, 업무 4개 314ms 대 244ms, psql 직접 실행)
- (검토안 2, 채택 안 함) 매장별 가능 업무를 비트값 `stores.service_mask`로 두고 업무 조합 15가지마다 공간 부분 인덱스를 뒀다. 조건 종류가 하나 늘 때마다 인덱스가 두 배가 되어(10종이면 1,023개) 정적 조건이 늘어날 서비스에 맞지 않았다(11절)
- (채택, V16) 정적 조건마다 태그 번호를 두고(`StoreTag`: NEW_LINE 1, PORT_IN 2, NAME_CHANGE 3, USIM_REISSUE 4) 매장별 태그 배열 `stores.tags int[]`를 트리거가 맞춘다. 조건은 `s.tags @> '{2,4}'::int[]` 하나로, 여러 정적 조건을 골라도 한 조건으로 묶인다. 인덱스는 `gist (geog, tags gist__int_ops) WHERE status = 'OPEN'` 하나(`intarray` 확장)다. 정적 조건을 더하면 태그 번호와 `store_tags()`의 원천만 늘리고 인덱스는 그대로다
- 조건이 공간 인덱스를 갖는지(`backedBySpatialIndex`)로 경로를 고른다. 영업 중처럼 요청 시각마다 달라지는 조건은 인덱스로 만들 수 없어 후보 확인 → 반경 전체 확인 경로로 간다(8.9)
- 필터는 `StoreSearchCondition`으로 추가한다. 조건은 매장 별칭 `s`의 `store_id`만 참조하고 다른 테이블을 조회해 판단한다. 영업 중 조건(`OpenNowCondition`)은 SQL의 `now()` 대신 서비스가 한국 시각으로 정한 요일·시각을 파라미터로 넘긴다. 후보 확인과 반경 전체 확인이 같은 시각으로 판단하고, 테스트에서 시각을 고정할 수 있다

### 6.4 PostGIS 도입 범위

- `V15__add_store_geography.sql`: `postgis` 확장, `stores.geog`(위경도에서 계산되는 생성 컬럼), 영업 중 매장만 담는 GiST 부분 인덱스(`WHERE status = 'OPEN'`). 관리자 파트의 매장 등록·수정 코드는 바꿀 필요가 없다
- 로컬: `docker compose up -d --build`로 한 번 다시 빌드해야 한다. 빌드하지 않으면 V15에서 앱 기동이 실패한다. 태그 인덱스(V16)는 `intarray` 확장을 쓰는데 PostgreSQL 기본 배포(contrib)에 들어 있어 이미지 변경은 없다. RDS 적용 절차는 `docs/STORE_SEARCH_OPERATIONS.md` 1절
- CI: 서비스 컨테이너에 `postgresql-16-postgis-3`을 설치하는 단계를 추가했다

### 6.5 쿼리 타임아웃

- 매장 검색 쿼리에만 타임아웃을 건다(`store.search.query-timeout`, 기본 2초). 전용 `JdbcTemplate`이라 다른 도메인 쿼리에는 영향이 없다
- 넘으면 PostgreSQL이 쿼리를 취소하고(SQLState 57014) `STORE503-0`("검색 범위를 좁혀 다시 시도해 주세요")으로 응답한다
- 극단 조건이 목표를 넘는 것 자체보다, 느린 쿼리가 DB를 오래 붙잡아 다른 요청까지 느려지는 것을 막는 장치다

## 7. 운영 코드 실측 (`./gradlew storeBenchmark`)

`src/benchmark/java/com/telme/store/benchmark/StoreSearchBenchmark.java`가 운영 저장소·서비스 코드를 그대로 호출한다. 가상 매장을 실제 `stores`에 넣고 업무를 `store_services`로 부여한 뒤 롤백한다(측정 전후 `VACUUM ANALYZE`). 시간은 JDBC 왕복을 포함한 앱 체감 시간이고, 조건마다 워밍업 2회 후 7회 중앙값(ms)이며 전체 1회 실행이다. 모든 결과에 반경, 반경 안 OPEN 매장 수, 그중 조건 맞는 수를 함께 기록한다. 모든 조건에서 방법끼리 같은 매장을 같은 순서로 돌려줬다. 환경은 Apple M4, Podman(4 CPU, 6GB), PostgreSQL 16.14, PostGIS 3.6.4, JIT 켬(기본값)이다.

### 7.1 필터 없음 (강남, 반경 10km)

| 매장 수 | Haversine | earthdistance | PostGIS(반경 안 전부 계산) | PostGIS KNN |
| --- | --- | --- | --- | --- |
| 149 (시드) | 0.56 | 0.96 | 0.54 | 0.44 |
| 2,121 | 0.81 | 1.83 | 0.52 | 0.39 |
| 98,156 | 15.5 | 32.0 | 4.99 | 0.48 |
| 980,122 | 90.9 | 381 | 78.3 | 0.66 |

같은 일을 해도 PostGIS가 Haversine과 같거나 빠르고, earthdistance보다 빠르다. KNN은 규모와 거의 무관하다.

### 7.2 합치기 전 비교: SMALL/LARGE (강남, 반경 10km)

SMALL은 지금의 "필터 있음" 경로와 같다. LARGE는 조건 맞는 매장 수를 2,001곳까지 세서 2,000곳 이하면 필터 먼저, 초과면 가까운 5만 곳 후보 안에서 조건을 적용하던 경로다.

| 전체 매장 | 조건 | SMALL | LARGE |
| --- | --- | --- | --- |
| 98,156 | 통과율 100% | 8.34 | 21.1 |
| 98,156 | 가까운 절반 전부 탈락 | 6.28 | 17.8 |
| 980,122 | 통과율 100% | 146 | 258 |
| 980,122 | 가까운 절반 전부 탈락 | 112 | 205 |

| 조건 맞는 매장 (100만 곳) | 필터 먼저 | KNN 후보 상한 | LARGE |
| --- | --- | --- | --- |
| 2,000 | 2.19 | 134 | 4.25 |
| 5,000 | 6.57 | 120 | 140 |
| 100,000 | 80.7 | 181 | 181 |
| 500,000 | 155 | 234 | 234 |

- 10만 곳에서 SMALL이 한계에 닿지 않았고, 100만 곳에서도 SMALL이 LARGE보다 빨랐다
- 2,000곳을 넘겨 KNN 후보 경로로 바꾸면 오히려 느려졌다. KNN 후보 경로가 이긴 곳은 희박 지역뿐이고, 거기서는 SMALL도 2.55ms다
- 그래서 전환 수치를 고치는 대신 LARGE를 없애고 한 경로로 합쳤다

### 7.3 비용 모델: 반경 안 매장 수 × 1곳당 단가

반경을 1 · 2.5 · 5 · 10km로 바꿔(지도 축척을 바꾸는 것과 같다) 100만 곳 강남에서 쟀다. 반경 안 매장 수는 578 · 3,762 · 14,566 · 50,109곳이다.

| 경로 | 1km | 2.5km | 5km | 10km | 1곳당 단가 |
| --- | --- | --- | --- | --- | --- |
| 필터 없음 KNN | 0.47 | 0.46 | 0.54 | 0.81 | 거의 0 |
| 필터 있음(업무 1개), 통과율 100% | 1.73 | 10.4 | 66.9 | 148 | 2.92µs |
| 필터 있음(업무 1개), 주변 전부 탈락 | 1.45 | 7.34 | 26.1 | 103 | 2.07µs |
| KNN 후보 상한(없앤 경로), 주변 전부 탈락 | 2.18 | 12.7 | 51.9 | 216 | 4.35µs |
| 필터 없음, 반경 안 전부 계산(비교용) | 1.23 | 6.07 | 20.7 | 90.0 | 1.81µs |

- 시간을 결정하는 변수는 전체 매장 수가 아니라 **반경 안 매장 수**다. 필터 있음(업무 1개, 통과율 100%)은 약 6ms + 2.92µs × 반경 안 매장 수다. 업무를 더 고르면 조건(`EXISTS`)이 늘어 단가가 커진다(7.4)
- KNN 후보 상한은 후보를 하나씩 꺼내 조건을 확인해서 1곳당 4.35µs로, 같은 조건의 반경 먼저(2.07µs)보다 비싸다
- 반경이 작을수록 빠르므로 10km가 성능상 최악이다

**기준 계산 (필터 있음, 업무 1개, 이 환경)**: 기준 = (DB 쿼리 예산 − 고정비) ÷ 단가

| DB 쿼리 예산 | 버티는 반경 안 매장 수 |
| --- | --- |
| 100ms | 약 3.2만 곳 |
| 150ms | 약 4.9만 곳 |
| 200ms | 약 6.6만 곳 |

재검토 기준은 "전체 매장 수"가 아니라 **"반경 10km 안 최대 매장 수"**와 **"한 번에 고를 수 있는 업무 수"**다.

**기준 수치의 근거를 쌓는 순서**

1. 시간을 결정하는 변수를 찾고, 모든 측정에 함께 기록한다(여기서는 반경 안 매장 수)
2. 변수를 3~4단계로 바꿔 단가와 고정비를 잰다
3. 예산을 정하고 (예산 − 고정비) ÷ 단가로 기준을 계산한다. 예산(목표 300ms 중 DB 몫)은 팀이 정한다
4. 실행 환경(스테이징 RDS)에서 `./gradlew storeBenchmark`로 단가만 다시 재면 같은 공식으로 기준이 다시 나온다
5. 운영 데이터로 매장마다 반경 10km 안 매장 수를 세서 최댓값이 기준에 가까워지면 재검토한다

## 8. 요청 분포 기반 판정 (`./gradlew storeWorkloadBenchmark`)

7절은 조건 하나씩(최악 포함)을 잰다. 이 절은 "실제로 들어올 요청들"이 목표를 지키는지를 본다. 극단 조건은 실패해도 되지만, 흔한 요청이 느리면 안 되기 때문이다.

### 8.3 측정 방법

1. **요청 분포 벤치마크 (주 판정)**: 8.1의 가정대로 요청 2,000건(워밍업 200건 별도)을 뽑아 운영 `StoreSearchService`로 실행한다. 단건과 동시 8건 두 번 돈다. 필터 요청 4건 중 1건은 측정이 끝난 뒤 반경 안 매장 수를 따로 세서 밀도별로 나눠 본다
2. **엣지케이스 (상한 확인)**: 7.4. 목표가 아니라 "타임아웃 안에 끝나는가, 결과가 맞는가"로 본다
3. **부하 테스트 (미진행)**: API(T3)가 생기면 k6 등으로 API 전체 기준을 잰다

측정 데이터는 측정 전용 DB(`telme_workload`)에 한 번 적재하고 계속 쓴다. 개발 DB와 분리돼 있고, DB 이름에 `workload`가 없으면 적재를 거부한다.

### 8.5 개선안 시제품: 업무 조합별 부분 인덱스 + KNN

매장별 가능 업무를 비트값(`service_mask`)으로 두고, 업무 4개의 조합 15가지마다 "그 업무를 모두 하는 영업 매장"만 담은 공간 부분 인덱스를 만든다. 요청 조합의 인덱스에서 KNN으로 가까운 5곳을 뽑은 뒤 반경으로 거른다. 인덱스에 조건 맞는 매장만 있어서 KNN이 버릴 매장이 없고, 반경 안에서 가까운 5곳과 결과가 같다. 같은 300만 곳 데이터에 복사본 테이블을 만들어 psql로 잰 값이다(4회 중 첫 회 제외 중앙값, ms).

| 기준점 | 업무 | 반경 | 지금 방식 | 시제품 | 결과 일치 |
| --- | --- | --- | --- | --- | --- |
| 강남 | 1개 | 10km | 1,807–1,851 | 0.76–1.06 | 일치 |
| 강남 | 2개 | 10km | 3,060 | 0.62 | 일치 |
| 강남 | 4개 | 10km | 3,285 | 0.71 | 일치 |
| 서울 중심 | 1~4개 | 1 · 5 · 10km | 39–1,445 | 0.45–1.13 | 일치 |
| 강원 | 1~4개 | 1 · 5 · 10km | - | 0.11–0.23 | - |

- 모든 조합·반경·밀도에서 1.1ms 이하였다
- 반경 조건(`ST_DWithin`)을 KNN과 같은 WHERE에 넣으면 옵티마이저가 "반경 안 전부 모아 정렬"을 골라 100~165ms가 됐다. KNN 5곳을 먼저 뽑고 반경으로 거르는 형태여야 한다
- 비용: 300만 곳에서 인덱스 15개가 약 1.8GB(기존 공간 인덱스 209MB의 약 9배), 만드는 데 1분 32초. 매장·업무가 바뀔 때마다 해당 인덱스들이 갱신된다
- 업무 종류가 늘면 조합이 2배씩 늘어난다(5종 31개, 6종 63개). 그때는 업무별 인덱스 + 나머지 비트 확인으로 바꾼다
- 부분 인덱스는 조건 값이 SQL에 상수로 있어야 쓰인다. 비트값을 바인드 파라미터로 넘기면 준비문의 일반 계획에서 인덱스를 못 쓸 수 있어, 열거형에서 만든 상수로 SQL에 넣어야 한다
- 영업 중 같은 시간 조건은 요청 시각마다 달라져 인덱스에 미리 넣을 수 없다. 그 조건이 붙으면 다른 설계가 필요하다

### 8.6 결론 (가상 데이터 기준)

- 8.1의 가정(300만 곳, 반경 10km 안 최대 65만 곳, 요청 절반이 필터 사용)에서 **지금 설계는 p95 기준 불합격**이다. 필터 없는 경로는 합격이고, 필터 있는 경로가 반경 안 매장 수에 비례해 느려지는 것이 원인이다
- 업무 조합별 부분 인덱스로 바꾸면 필터 있는 경로도 1ms 수준이 된다(시제품). 대가는 인덱스 저장 공간(약 9배)과 비트값 컬럼 동기화(트리거)다
- **재검토 조건**: 실제 제휴 매장 데이터의 반경 10km 안 최대 매장 수가 약 5만 곳(7.3의 150ms 예산 기준)을 넘으면 개선안을 적용한다. 넘지 않으면 지금 설계로 충분하다

### 8.9 동적 필터(영업 중): 구현했지만 꺼 둠 (`./gradlew storeOpenNowBenchmark`)

동적 필터는 당분간 제공하지 않는다. 설정 `store.search.open-now-filter-enabled`(기본 `false`)로 꺼 두었고, 요청에 `openNow=true`가 오면 `STORE400-4`로 거부한다. 조건을 조용히 빼면 영업 종료 매장이 "영업 중" 결과처럼 보이기 때문이다.

**왜 인덱스로 만들 수 없나.** 부분 인덱스 조건에는 `now()` 같은 시각 함수도, 다른 테이블(`store_hours`)도 쓸 수 없다. 시각별 인덱스를 스케줄러로 교체하는 방식은 인덱스 하나 72~85ms로 빠르지만(제휴 규모, 트랜잭션 롤백 실측), 매시간 교체로는 10:30·19:30 같은 시각에 최대 59분 틀리고, 업무 조합 15개 × 시각만큼 인덱스가 늘어 쓰지 않는다.

**판단 방식.** 요청 시각(서버 UTC 시계를 한국 시각으로 바꾼 값)의 요일·시각으로 `store_hours`를 조회한다.
- `close_time <= open_time`이면 다음 날 `close_time`까지 영업이다(18:00~02:00). 자정 이후는 전날 행도 본다. 00:00~00:00은 24시간이다
- 여는 시각은 포함, 닫는 시각은 제외한다. 휴무(`is_closed`), 행 없음, 시각 비어 있음은 영업 중이 아니다
- `day_of_week IN (오늘, 전날)`로 기본키 `(store_id, day_of_week)`에서 두 행만 읽는다

**경로.** 반경 안을 모두 확인하는 방식만 쓰면 낮에도 밀집 지역에서 수천 곳을 매번 확인한다. 그래서 두 단계로 나눈다.
1. 업무 조건(인덱스 있음)으로 가까운 후보를 KNN으로 꺼내며 영업 중·반경을 확인하고, 요청 개수를 채우면 바로 멈춘다. 후보는 요청 개수의 10배까지 본다. 그 안에서 채웠다면 더 가까운 매장은 모두 후보 안에 있었으므로 결과가 정확하다
2. 못 채우면(밤, 휴무일) 반경 안에서 조건 맞는 매장을 모두 확인한다. 업무 조건이 있으면 그 조합의 부분 인덱스로 후보를 줄인다

반경·영업 중 조건을 KNN과 같은 층에 두면 옵티마이저가 반경 안을 모두 모아 정렬하는 계획을 골랐다(서울시청 15:00, 17~20ms). 강제로 KNN을 쓰게 해도 반경 조건이 인덱스 조건이 아니라 필터로 붙어, 반경 안에 조건 맞는 매장이 적으면 인덱스를 끝까지 읽는다. 그래서 후보 층(LIMIT)과 확인 층을 나눴다.

## 9. 확인이 필요한 것

| 항목 | 이유 |
| --- | --- |
| 가상 분포와 실제 밀도 | 시간은 반경 안 매장 수로 정해진다(7.3). 실제 서울의 반경 10km 안 매장 수가 가상 분포보다 많으면 더 느리다 |
| DB 쿼리 예산 | 7.3의 기준 계산에 쓸 예산(목표 300ms 중 DB 몫)을 팀이 정해야 한다 |
| 요청 분포 가정과 합격 기준 | 8.1의 필터 사용 비율·업무 개수·반경 비율과 8.2의 백분위 기준을 기획과 합의해야 한다 |
| 연결별 첫 KNN 검색 | 새 DB 연결의 첫 KNN 검색은 인덱스 전체를 읽는다(8.8, 원인 추정). 인덱스가 커지면 연결 생성 시 검색을 한 번 미리 실행하는 방법(`connectionInitSql`)을 측정해 본다 |
| 실제 매장 분포 | 11절은 합의한 규모(전국 최대 4만 곳, 반경 10km 안 최대 6천 곳)를 공공데이터 좌표로 만든 것이다. 실제 제휴 매장 데이터가 생기면 같은 절차로 다시 판정한다 |
| 정적 조건 추가 | 인덱스는 그대로다. `StoreTag`에 새 번호를 더하고, V11 이후 마이그레이션에서 `store_tags()`에 원천 테이블을 더하고 그 테이블에 같은 트리거를 건다. 쓴 번호는 바꾸지 않는다 |
| RDS의 확장 설치 | V15가 `postgis`, V16이 `intarray` 확장을 만든다. RDS에서는 마스터 계정으로 먼저 설치하기로 했다. 절차는 `docs/STORE_SEARCH_OPERATIONS.md` 1절 |
| JIT 설정 | 짧은 조회에 JIT 컴파일이 붙어 최대 약 100ms가 더해졌다. RDS 파라미터 그룹의 `jit` 값 확인 필요 |
| RDS의 PostGIS 버전과 권한 | 로컬은 3.6.4. Flyway 계정에 `CREATE EXTENSION` 권한이 있는지 |
| 영업 중 필터 켜기 전 | 공휴일·임시 휴무를 `store_hours`로 표현할 수 없다(요일 7행뿐). 영업시간 데이터 품질(빈 행 비율)과 함께 확인 후 `store.search.open-now-filter-enabled`를 켠다(8.9) |
| 동시 처리량 | 모든 측정은 단건 쿼리다. 100만 곳에서 Haversine은 쿼리 하나에 병렬 워커 3개를 쓴다 |

## 10. 재현 절차

측정 도구는 저장소에 없다. 아래 명령은 도구를 되돌려 놓았을 때(벤치마크 소스를 `src/benchmark`에, `build.gradle`에 벤치마크 태스크를 추가) 쓰는 명령이다. 도구와 측정 결과(JSON)는 담당자가 로컬에 보관하고, 필요하면 공유한다.

```bash

./gradlew storeBenchmark

# 요청 분포 판정 (8절). 공공데이터 CSV는 직접 받아 저장소 밖 폴더에 둔다

createdb -h localhost -U telme telme_workload   # 또는 psql로 CREATE DATABASE
POSTGRES_DB=telme_workload ./gradlew storeWorkloadLoad -PworkloadCsvDir=<시도별 CSV 폴더>   # 한 번만. 다시 넣으려면 -PworkloadForce=true
POSTGRES_DB=telme_workload ./gradlew storeWorkloadBenchmark   # 결과: build/benchmark/workload-store-search.json

# 제휴 매장 규모 판정 (8.8). 실제 좌표의 1.44% 표본
POSTGRES_DB=telme_workload_partner ./gradlew storeWorkloadLoad -PworkloadCsvDir=<시도별 CSV 폴더> -PworkloadSampleRate=0.0144
POSTGRES_DB=telme_workload_partner ./gradlew storeWorkloadBenchmark
```

## 11. 최종 결정과 근거: 필터 없음 KNN · 정적 조건 태그 인덱스 KNN · 동적 조건 후보 먼저

### 11.1 전제

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 전국 매장 수 | 150(우리 매장) / 2,000(U+ 매장) / 40,000(제휴 확장) | 기획 합의. 40,000을 넘지 않는다 |
| 가장 밀집한 곳 반경 10km 안 | 최대 6,000곳(전체의 15%) | 기획 합의. 측정 DB는 서울시청 반경 10km 안에 15%를 둔다(150곳 23, 2,000곳 300, 40,000곳 6,000) |
| 반경 상한 | 10km | 6.2절. 지도 축척이 작으면 더 작다 |
| 정적 조건 | 업무 4종 + 앞으로 늘어날 매장 속성 | 측정에서는 가상 속성 30종(보유 90%~0.1%)과 극단용 태그를 더했다 |
| 동적 조건 | 영업 중 | 구현했지만 꺼 둠(8.9) |
| 목표 | p50 100ms, p95 300ms, p99 1초(제안값, 8.2) | 쿼리 단위 |

측정 DB는 공공데이터 277만 곳의 실제 좌표를 md5 순서로 뽑아 만든다(`storeScaleLoad`). 작은 규모가 큰 규모의 부분집합이다. 환경은 4.1절과 같다(Apple M4, Podman, PostgreSQL 16.14, PostGIS 3.6.4).

### 11.2 여기까지 온 과정

| 단계 | 방식 | 결과 | 버린 이유 |
| --- | --- | --- | --- |
| 거리 계산 | Haversine / earthdistance / PostGIS | 100만 곳: Haversine 92ms, earthdistance 1,133ms, PostGIS KNN 0.31ms(4.2) | PostGIS KNN만 규모와 무관 |
| 필터 1 | 반경 먼저 + 업무 `EXISTS` | 실제 277만 곳 p95 395ms, 8스레드 1,421ms(8.7) | 반경 안 매장 수에 비례 |
| 필터 2 | 업무 조합별 부분 인덱스 15개(검토안 2) | 4만 곳 엣지케이스 최대 1.62ms(8.8) | 조건 종류가 늘면 인덱스가 2배씩(10종 1,023개), 15개만으로 50MB |
| 필터 3 | 영업 매장 인덱스 `INCLUDE (service_mask)` | 조건이 테이블 행을 읽은 뒤 적용되는 필터로 붙어, 조건 맞는 매장이 없으면 4만 곳을 모두 읽음. 최악 23ms로 INCLUDE 없는 것과 같음 | 인덱스 안에서 거르지 못함(PostgreSQL 16) |
| **최종** | **태그 배열 + `(geog, tags)` 다중 컬럼 GiST 1개(V16)** | 11.3 | - |

INCLUDE와 다중 컬럼 GiST의 차이는 실행 계획에서 조건이 붙는 자리다. INCLUDE는 `Filter`(테이블 행을 읽은 뒤)이고, 다중 컬럼 GiST는 `Index Cond`(인덱스 안)다. 게다가 GiST 트리의 중간 칸마다 아래 매장 태그의 합집합이 있어, 조건 맞는 매장이 없는 칸은 통째로 건너뛴다.

### 11.7 측정에서 찾아 고친 문제

- **같은 좌표 매장의 경계 동점**: 공공데이터에는 같은 건물(같은 좌표)의 매장이 많다. KNN 안쪽 정렬은 거리 하나라(ID를 더하면 KNN이 꺼진다, 4.2절) 5번째 자리에서 동점이면 어느 매장이 들어갈지 정해지지 않았다. 4만 곳 벤치마크의 결과 비교에서 발견했다. KNN으로 5번째 거리만 구하고, 그 거리(+1cm) 안의 매장을 같은 인덱스로 다시 모아 (거리, ID) 순으로 자르도록 바꿨다. 추가 비용은 0.1ms 안팎이다
- **벤치마크의 가상 영업시간 치우침**: 매장 ID 산술식으로 영업시간을 나눴더니 적재기의 ID 배치 규칙과 맞물려 반경 안 23시 영업 비율이 설계(3%)가 아닌 20%가 됐다. 해시로 바꿨다

# FAQ 다중 정답 라벨링과 리랭커 실험 요약

**검색팀 참고용**. 2026-09-29 기준, develop `c8634c2` 위에서 로컬 실험

## 핵심 결과

이 실험은 **평가 기준 보완**과 **검색 방식 변경**을 따로 비교했다. 먼저 같은 벡터 검색 결과를 다시 채점했을 뿐인데, 기존 정답 라벨보다 같은 정책을 설명하는 FAQ를 더 인정한 라벨에서 Hit@3가 **84/111에서 100/111**로 올랐다. 검색 코드가 좋아진 결과가 아니라 기존 평가가 정답 근거를 놓치고 있었다는 뜻이다.

보완 라벨을 고정한 뒤 검색 방식만 바꾸면, 실제 앱에서 정답 근거 전달이 **59/111에서 74/111**로 올랐다. 무관 질문 통과는 **8/69로 동일**했다. 이 증가분이 리랭커 비교 결과다. 다만 리랭커는 주제가 비슷해도 질문의 핵심 조건을 답하지 못하는 FAQ를 통과시키므로, 답변 가능 여부까지 판단할 수는 없다.

| 실제 앱, 답변 가능 질문 111개 | 기존 정답 라벨 | 보완한 다중 정답 라벨 |
| --- | ---: | ---: |
| 현재 벡터 검색 | 52/111 | **59/111** |
| 리랭커 검색 | 63/111 | **74/111** |

위 표에서 **가로 비교는 같은 검색 결과를 다른 정답 라벨로 채점한 차이**이고, **세로 비교는 같은 라벨로 검색 방식을 바꾼 차이**다. 수치는 임계값을 거친 실제 앱의 정답 근거 전달 건수이며, 아래 Hit@3처럼 임계값을 빼고 순위만 본 수치와 구분해야 한다.

### 1. 다중 정답 라벨링으로 달라진 평가

기존 개발셋의 답변 가능 질문 80개 중 76개는 정답 FAQ를 하나만 지정했다. 검증셋은 답변 가능 질문 30개 모두 복수 정답을 담고 있었지만, 같은 결론으로 답하는 FAQ가 빠져 있었다. 정답 라벨을 보완하고 **검색 결과와 순위를 그대로 둔 채** 다시 채점한 결과는 다음과 같다.

| 임계값 없이 순위만 평가, 답변 가능 질문 111개 | 기존 정답 라벨 | 보완한 다중 정답 라벨 |
| --- | ---: | ---: |
| 벡터 검색 Hit@1 | 68/111 | **88/111** |
| 벡터 검색 Hit@3 | 84/111 | **100/111** |
| 리랭커 Hit@1 | 74/111 | **92/111** |
| 리랭커 Hit@3 | 86/111 | **102/111** |

여기서 **102/111은 답변에 실제 전달된 건수가 아니라**, 벡터 검색 상위 30개를 리랭커로 정렬하고 상위 3개에 정답이 있는지 본 순위 지표다. 점수 기준을 적용하지 않아 낮은 확신의 후보도 포함한다.

반면 실제 앱의 **74/111**은 상위 20개 후보를 다시 정렬하고 리랭커 점수 **0.76 이상**만 반환하는 설정에서, API 응답에 정답 근거가 하나라도 있었던 질문 수다. 후보 수와 점수 기준이 모두 다르므로 102와 74의 차이를 점수 기준 하나만의 영향으로 볼 수는 없다. 이 실제 반환 조건에서는 답변 가능 질문 111개 중 33개가 빈 결과였고, 74개에서 정답 근거를 받았다.

67개 질문에 같은 정책 답변으로 인정할 FAQ 280건을 추가했다. 상위 3개 검색 결과에 영향을 줄 수 있는 후보는 직접 확인하고 18건의 동치 판정을 취소했다. 기존 무관 질문 중 1건도 답변 가능한 질문으로 재분류했다. 따라서 기존 라벨만으로 리랭커나 검색 설정을 평가하면 실제 정답 근거를 실패로 셀 수 있다. 반대로 보완 라벨도 평가셋 전체에 대해 팀이 확정한 정답 목록은 아니므로, 공식 지표로 쓰기 전에 검색팀과 검토해야 한다.

**평가셋 파일**

- 개발셋 130개: [`eval_questions_130.json`](../TEL-ME_BE/scripts/data/eval_questions_130.json). 기준값을 비교하고 선택하는 데 사용했다.
- 검증셋 50개: [`eval_questions_supplement_50.json`](../TEL-ME_BE/scripts/data/eval_questions_supplement_50.json). 개발셋에서 고른 설정을 바꾸지 않고 별도 질문에 적용해 확인했다.

두 파일은 모두 현재 `develop`에 있다. 개발셋에서 무관 질문 통과를 현재 기준선 이하로 유지하는 설정을 고른 뒤, 검증셋에 그대로 적용했다. 리랭커 설정은 후보 20개, 벡터 하한 없음, 리랭커 기준값 0.76이다. 점수 기준은 추가 정답 라벨을 포함한 보완 라벨이다.

## 한계와 비용

- 리랭커는 질문과 FAQ의 관련도를 다시 매긴다. 주제가 같지만 필요한 조건이 빠진 FAQ도 높은 점수로 통과할 수 있다. 예를 들어 “eSIM 발급 비용에 부가세가 포함됐나요?”에 “eSIM은 얼마예요?”가 높은 점수를 받았다. 이 유형은 근거 적합성 판정이나 답변 가드에서 걸러야 한다.
- 실제 앱의 검색 응답 중앙값은 **62ms에서 422ms**, p90은 **77ms에서 511ms**로 늘었다. 로컬 CPU 측정이므로 배포 환경 지연시간은 따로 확인해야 한다.
- JAR는 66MB에서 177MB가 되었고, 모델 파일 545MB를 별도 배치해야 한다. 메모리 사용량은 아직 측정하지 않았다.
- 내용 없는 후속 질문 23개에서는 엉뚱한 FAQ 통과가 0건에서 3건으로 늘었다. 일반적인 후속 질문 71개에서는 통과 수가 늘지 않았고, 정답 근거 전달은 34건에서 47건으로 늘었다. 원문과 재작성 질문의 선택 규칙을 먼저 바꾸는 것이 리랭커 적용의 필수 조건은 아니다.

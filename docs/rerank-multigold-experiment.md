# FAQ 다중 정답 라벨링과 리랭커 실험 요약

**검색팀 참고용**. 2026-09-29 기준, develop `c8634c2` 위에서 로컬 실험

## 핵심 결과

이 실험은 두 가지를 따로 봤다. 하나는 채점 기준(정답 라벨)을 바꾸면 수치가 어떻게 달라지는지, 다른 하나는 채점 기준을 고정하고 검색 방식만 바꾸면 어떻게 달라지는지다.

기존 평가셋은 질문마다 정답 FAQ를 대부분 하나만 인정했다. 같은 내용으로 답하는 다른 FAQ도 정답으로 인정하도록 라벨을 보완하면, 검색 결과는 그대로인데 현재 벡터 검색의 정답 전달이 **52/110에서 59/110**으로 집계된다. 검색이 좋아진 게 아니라 채점 기준이 달라진 차이다. 보완 라벨은 아직 검색팀 검토 전이다.

보완 라벨을 고정한 뒤 검색 방식만 바꾸면, 실제 앱에서 정답 근거 전달이 **59/110에서 74/110**로 올랐다. 무관 질문 통과는 **8/70으로 동일**했다. 이 증가분이 리랭커 비교 결과다. 다만 리랭커는 주제가 비슷해도 질문의 핵심 조건을 답하지 못하는 FAQ를 통과시키므로, 답변 가능 여부까지 판단할 수는 없다.

| 실제 앱, 답변 가능 질문 110개 | 기존 정답 라벨 | 보완한 다중 정답 라벨 |
| --- | ---: | ---: |
| 현재 벡터 검색 | 52/110 | **59/110** |
| 리랭커 검색 | 63/110 | **74/110** |

위 표에서 **가로 비교는 같은 검색 결과를 다른 정답 라벨로 채점한 차이**이고, **세로 비교는 같은 라벨로 검색 방식을 바꾼 차이**다. 수치는 임계값을 거친 실제 앱의 정답 근거 전달 건수이며, 아래 Hit@3처럼 임계값을 빼고 순위만 본 수치와 구분해야 한다.

### 1. 다중 정답 라벨링으로 달라진 평가

기존 개발셋의 답변 가능 질문 80개 중 76개는 정답 FAQ를 하나만 지정했다. 검증셋은 답변 가능 질문 30개 모두 복수 정답을 담고 있었지만, 같은 결론으로 답하는 FAQ가 빠져 있었다. 정답 라벨을 보완하고 **검색 결과와 순위를 그대로 둔 채** 다시 채점한 결과는 다음과 같다.

| 임계값 없이 순위만 평가, 답변 가능 질문 110개 | 기존 정답 라벨 | 보완한 다중 정답 라벨 |
| --- | ---: | ---: |
| 벡터 검색 Hit@1 | 68/110 | **88/110** |
| 벡터 검색 Hit@3 | 84/110 | **99/110** |
| 리랭커 Hit@1 | 71/110 | **89/110** |
| 리랭커 Hit@3 | 87/110 | **102/110** |

여기서 **102/110은 답변에 실제 전달된 건수가 아니라**, 앱을 리랭커 기준값 0으로 돌려 후보 20개를 점수순으로 정렬한 상위 3개에 정답이 있는지 본 순위 지표다. 점수 기준을 적용하지 않아 낮은 확신의 후보도 포함한다.

반면 실제 앱의 **74/110**은 상위 20개 후보를 다시 정렬하고 리랭커 점수 **0.76 이상**만 반환하는 설정에서, API 응답에 정답 근거가 하나라도 있었던 질문 수다. 두 수치는 후보 20개가 같고 기준값 0.76 적용 여부만 다르다. 정답이 상위 3개에 있어도 기준값 때문에 반환되지 않은 질문이 28건이다. 이 실제 반환 조건에서는 답변 가능 질문 110개 중 32개가 빈 결과였고, 74개에서 정답 근거를 받았다.

67개 질문에 같은 정책 답변으로 인정할 FAQ 278건을 추가했다. 상위 3개 검색 결과에 영향을 줄 수 있는 후보는 직접 확인하고 18건의 동치 판정을 취소했다. 직접 확인한 라벨만 인정해 앱 결과를 다시 채점하면 리랭커 순위 지표(Hit@3)만 102에서 101로 1건 줄고, 나머지 수치(벡터 Hit@3 99, 실제 앱 59→74 등)는 같았다. 기존 무관 질문의 분류는 바꾸지 않았다. 따라서 기존 라벨만으로 리랭커나 검색 설정을 평가하면 실제 정답 근거를 실패로 셀 수 있다. 반대로 보완 라벨도 평가셋 전체에 대해 팀이 확정한 정답 목록은 아니므로, 공식 지표로 쓰기 전에 검색팀과 검토해야 한다.

## 한계와 비용

- 리랭커는 질문과 FAQ의 관련도를 다시 매긴다. 주제가 같지만 필요한 조건이 빠진 FAQ도 높은 점수로 통과할 수 있다. 예를 들어 “eSIM 발급 비용에 부가세가 포함됐나요?”에 “eSIM은 얼마예요?”가 높은 점수를 받았다. 이 유형은 근거 적합성 판정이나 답변 가드에서 걸러야 한다.
- 실제 앱의 검색 응답 중앙값은 **62ms에서 422ms**, p90은 **77ms에서 511ms**로 늘었다. 로컬 CPU 측정이므로 배포 환경 지연시간은 따로 확인해야 한다.
- 리랭커 후보를 10개, 20개, 30개로 바꿔 앱을 다시 돌리면 같은 (질문, FAQ) 쌍 4,038개 중 92%는 점수가 0.001 이하로 같았지만, 57개(1.4%)는 0.05 넘게, 최대 0.22까지 달랐다. 원인은 확인하지 못했다. 점수가 기준값 근처인 FAQ는 후보 구성에 따라 통과 여부가 바뀔 수 있다.
- JAR는 66MB에서 177MB가 되었고, 모델 파일 545MB를 별도 배치해야 한다. 메모리 사용량은 아직 측정하지 않았다.
- 내용 없는 후속 질문 23개에서는 엉뚱한 FAQ 통과가 0건에서 3건으로 늘었다. 일반적인 후속 질문 71개에서는 통과 수가 늘지 않았고, 정답 근거 전달은 34건에서 47건으로 늘었다. 원문과 재작성 질문의 선택 규칙을 먼저 바꾸는 것이 리랭커 적용의 필수 조건은 아니다.

## 검색팀에 부탁할 검토

1. 보완 라벨이 실제로 같은 정책 답변으로 볼 수 있는지 평가셋을 검토해 주세요.
2. 정답 전달 향상과 지연시간 및 모델 배포 비용을 함께 보고 리랭커 적용 여부를 판단해 주세요.
3. 비슷한 주제지만 근거가 질문의 세부 조건을 답하지 못하는 사례를 후속 근거 적합성 평가에 포함해 주세요.

위 수치는 리랭커 검색 구현(`search.rerank.enabled`, 기본값 `false`)을 로컬에서 띄운 앱으로 측정했다. 이 구현은 이후 develop에 옵션으로 들어갔고, 기본값이 꺼져 있어 설정을 켜기 전에는 검색 동작이 바뀌지 않는다. 다만 의존성(onnxruntime, tokenizers)은 항상 포함되므로 JAR 크기는 꺼 둬도 커진다.

## 리랭커 켜기

| 설정 | 환경변수 | 기본값 |
| --- | --- | --- |
| `search.rerank.enabled` | `SEARCH_RERANK_ENABLED` | `false` |
| `search.rerank.model-path` | `SEARCH_RERANK_MODEL_PATH` | 없음 (켰는데 비어 있으면 기동 실패) |
| `search.rerank.tokenizer-path` | `SEARCH_RERANK_TOKENIZER_PATH` | 없음 |
| `search.rerank.candidate-k` | `SEARCH_RERANK_CANDIDATE_K` | 20 |
| `search.rerank.vector-floor` | `SEARCH_RERANK_VECTOR_FLOOR` | 0.0 |
| `search.rerank.threshold` | `SEARCH_RERANK_THRESHOLD` | 0.5 |

- 켜면 `Q_A` 벡터 상위 후보만 리랭커로 판정한다. `search.similarity-threshold`와 이중 벡터(`search.dual-vector`)는 쓰지 않는다. 이 문서의 수치는 모두 이 구성으로 쟀다.
- `threshold`의 기본값 0.5는 측정한 값이 아니다. 이 문서는 0.76에서 쟀고 기준값별 결과는 2절 표에 있으니, 켤 때 그 표를 보고 정한다.
- 모델 파일은 아래 "모델 파일 만들기"로 직접 만든다. 레포에는 파일이 없다.

### 모델 파일 만들기

`BAAI/bge-reranker-v2-m3`를 CPU용 동적 INT8(AVX2)로 양자화한 ONNX 파일을 쓴다. 실험에 쓴 파일을 만든 절차이다. 모델 변환에만 Python을 쓰고, 검색과 리랭커 수치는 앱으로 잰다.

**실험 환경**

| 항목 | 값 |
| --- | --- |
| CPU | AMD Ryzen 7 9800X3D (8코어 / 16스레드). AVX2를 지원하는 CPU다 |
| 메모리 | 약 31GB |
| 변환에 쓴 버전 | Python 3.12.14, sentence-transformers 5.7.0, transformers 4.57.6, PyTorch 2.6.0+cpu |
| 앱 쪽 라이브러리 | onnxruntime 1.20.0, DJL tokenizers 0.31.1 (`build.gradle`) |

**변환** (첫 변환은 원본 모델 다운로드와 FP32 내보내기 때문에 디스크가 수 GB 필요하다. 아래 코드는 변환 뒤 FP32 파일을 지운다)

```bash
pip install "sentence-transformers[onnx]>=5.0,<6"
```

```python
import os
from sentence_transformers import CrossEncoder, export_dynamic_quantized_onnx_model

out = "bge_reranker_v2_m3_onnx_int8"

model = CrossEncoder("BAAI/bge-reranker-v2-m3", backend="onnx", device="cpu")
model.save_pretrained(out)
export_dynamic_quantized_onnx_model(
    model=model,
    quantization_config="avx2",
    model_name_or_path=out,
)
for f in ("onnx/model.onnx", "onnx/model.onnx_data"):
    try:
        os.remove(os.path.join(out, f))
    except FileNotFoundError:
        pass
```

**결과 확인**

- `onnx/model_quint8_avx2.onnx`: 571,039,928바이트(약 545MB). 실험에 쓴 파일의 SHA-256은 `eb5fdd0995d4323055cfd6736bb53a1a8adbfc995c8ef2309ab7cece00dc001d`다
- `tokenizer.json`: 17,082,900바이트. SHA-256은 `8bf8afbfd11306bd872018c53bfdf2e160a56f8edbcf49933324404791c148d3`다
- 다시 만든 파일은 라이브러리 버전이나 CPU에 따라 해시가 다를 수 있다. 해시가 같지 않다면 같은 질문의 점수가 실험과 같은지 앱으로 확인한다

**앱에 연결**

```powershell
$env:SEARCH_RERANK_ENABLED = "true"
$env:SEARCH_RERANK_MODEL_PATH = "<폴더>/bge_reranker_v2_m3_onnx_int8/onnx/model_quint8_avx2.onnx"
$env:SEARCH_RERANK_TOKENIZER_PATH = "<폴더>/bge_reranker_v2_m3_onnx_int8/tokenizer.json"
$env:SEARCH_RERANK_THRESHOLD = "0.76"
```

- 기동 로그에 `[OnnxFaqReranker] 리랭커 로드 완료`가 나오면 연결된 것이다
- 파일 이름의 `avx2`는 이 양자화가 AVX2 명령어를 쓰도록 만들어졌다는 뜻이다. CPU가 다르면 그 CPU에서 동작과 지연을 따로 확인해야 한다

# FAQ와 매장 복합 상담

## 처리 방식

`유심 재발급 비용을 알려주고 매장도 찾아줘`를 FAQ 요청과 매장 요청으로 나눠 처리한다. 기존 FAQ 검색과 매장 검색을 재사용하며, FAQ와 매장을 합쳐 한 번에 최대 3개 요청을 받는다.

1. 라우팅에서 서로 다른 하위 질문을 확인하고 상담 요청을 순서대로 저장한다. `BOTH`인데 질문이 없거나 원문 전체를 양쪽에 복제한 결과는 저장 전에 거절한다.
2. 각 매장 요청의 지역과 업무를 그 하위 질문으로 검증한다. FAQ의 업무나 다른 지역을 공통 조건으로 복사하지 않는다. `USIM 재발급`과 `유심 재발급`은 같은 업무로 읽는다.
3. 처리할 수 있는 요청은 바로 답한다. 다른 요청의 지역이나 업무가 빠졌으면 그 요청 하나만 되묻고, 답변과 확인 질문을 같은 메시지에 넣는다. 이미 답한 상담은 `DONE`, 되묻는 상담은 `WAITING_CONDITION`으로 저장한다.
4. 후속 응답은 대기 중인 상담에만 연결한다. 현재 위치 버튼의 좌표는 최신 지역 되묻기에 직접 연결하고, 이미 답한 FAQ는 다시 생성하지 않는다.
5. 되묻기가 없으면 FAQ를 따로 검색하고 매장을 조회해 요청 순서대로 답변을 결합한다. 메시지 하나와 관련 상담 상태를 같은 트랜잭션에서 저장하고, 저장된 최종 본문을 SSE로 전달한다.

모델 호출은 저장 트랜잭션 밖에서 실행한다. 되묻기 저장 중 버전 충돌이 생기면 다른 요청의 조건 변경과 새 메시지도 함께 롤백한다.

## 답변과 실패 처리

| 상황 | 동작 |
| --- | --- |
| FAQ와 매장 검색 성공 | FAQ 안내와 매장 검색 설명을 본문에 넣고 매장 카드를 함께 저장 |
| FAQ 근거 부족 | 해당 FAQ 부분만 안내 불가로 표시하고 매장 결과 유지 |
| 매장 검색 실패 또는 결과 없음 | 매장 부분에 실패 또는 조건 변경 안내를 넣고 FAQ 답변 유지 |
| 지역 제공 거절 | 매장 부분에 대체 안내를 넣고 FAQ 답변 유지 |
| FAQ 생성 또는 저장 오류 | 실행 실패 처리. 일부 답변을 완료 상태로 저장하거나 토큰으로 보내지 않음 |

매장 검색 실패 안내도 그 요청에 대한 응답이므로 상담은 `DONE`으로 완료한다. 다시 검색하려면 새 질문을 보낸다.

## 응답 계약

- 되묻기가 없는 결합 메시지는 `ANSWER`, 일부 답변과 확인 질문이 함께 있으면 `CLARIFICATION`이다. 단일 매장 답변은 기존 `STORE_RESULT`를 유지한다. API 주소와 DB 스키마는 추가하지 않는다.
- `CLARIFICATION`에는 매장 카드가 없으므로 처리한 매장 결과는 본문에 이름으로 안내한다. 매장 카드와 지도는 매장 답변에서 제공한다. 필요한 조건이 빠진 매장 요청이 둘 이상이면 하나씩 나눠 보내도록 안내한다.
- `answerBasis=GROUNDED`는 근거가 있는 FAQ 부분이 있다는 뜻이다. 모든 부분이 답변됐다는 뜻은 아니다. FAQ 근거가 없지만 매장 결과가 있으면 `answerBasis`는 `null`이다.
- FAQ 근거는 결합 답변 메시지에 연결하고 동일 FAQ의 중복 저장은 제거한다.
- 여러 지역의 매장 결과를 합치면 공통 `storeSearchContext`와 `distanceMeters`를 비운다. 각 질문의 검색 기준과 매장 이름은 본문에서 구분하고, 카드의 매장 ID 중복은 제거한다.
- 좌표는 해당 요청에 명시적으로 제공된 경우에 사용한다. 복합 요청에서 특정 지역이 확인된 매장에는 다른 요청의 현재 위치를 덮어쓰지 않는다. 좌표로 지역을 답한 뒤 업무 응답을 보낼 때도 좌표가 필요하다.

## 검증

PostgreSQL 통합 테스트 11개에서 실제 매장 검색, 지역과 업무의 순차 되묻기, 좌표 응답 연결, 두 지역의 조건 분리, FAQ 근거 부족, 매장 장애, 지역 거절, 종료된 요청과 버전 충돌을 검증한다. 테스트의 라우팅 및 FAQ 생성 결과와 지역명 해석은 통제하고 상담 저장 및 매장 DB 검색은 실제로 실행한다.

현재 브랜치의 기존 전체 테스트 보고서는 총 2,563건, 실패 0건, 제외 110건이다. 복합 매장 통합 테스트와 복합 FAQ 테스트 23건도 별도 평가 DB에서 다시 실행해 모두 통과했다. 라우팅을 통제한 테스트 통과는 실제 모델의 분류 성공을 보장하지 않는다.

실제 API에서는 Docker Ollama의 EXAONE 3.5 7.8B와 bge-m3를 사용했다. 독립 DB의 FAQ와 임베딩은 각각 1,152건, 매장은 152건이다. 이 DB에는 이전 평가용 FAQ 2건이 포함되어 있어 FAQ 전체 품질 측정용으로 해석하지 않는다.

### FAQ와 매장 요청의 라우팅 실측

FAQ 한 건과 매장 한 건을 명시한 16문항의 기대값을 `BOTH`로 고정하고 실제 Spring 채팅 API에서 실행했다. 현재 위치 좌표가 있는 5문항과 지역명 또는 지역 미지정 문항을 포함한다. 별도 DB `telme_135_routing_check_20261012`를 사용했다. 동일 입력의 두 실행은 모두 다음 결과였다. 반복 실행은 독립 문항 32개로 계산하지 않는다.

| 최초 처리 결과 | 문항 수 | 의미 |
| --- | ---: | --- |
| FAQ와 매장 요청 모두 보존 | 9/16 | FAQ는 즉시 처리하고 매장 조건만 되묻거나 두 요청을 함께 처리 |
| 나눠 보내기 안내 | 4/16 | 상담 요청 저장 전에 거절 |
| 매장 요청만 처리 | 3/16 | FAQ가 누락됨 |

모든 채팅 실행은 `COMPLETED`였지만, 이는 고객의 두 요청을 모두 처리했다는 뜻이 아니다. 9건의 요청 보존은 답변 정확도도 아니다. 그중 6건의 FAQ 부분은 근거 부족 안내였다. 지명으로 매장을 조회한 1건은 평가 환경의 카카오 키가 더미여서 HTTP 401과 매장 조회 실패 안내가 나왔다. 매장 목록의 실제 검색 성공률은 이 실측으로 판단할 수 없다.

실패한 7건의 원시 모델 출력은 모두 **최상위 `intent=FAQ`인데 하위 질문에는 `FAQ`와 `STORE`가 함께 있는 모순**이었다. 문장을 나누지 못한 것과는 다르다. `QueryRoutingService.normalizeLlmPayload`가 이 모순을 파싱 실패로 처리하면서 유효할 수 있는 하위 질문도 버린다.

- `알려주고`, `그리고` 등이 있는 4건은 규칙 대체가 원문 전체를 FAQ와 STORE에 각각 복제한다. 이후 안전 검사가 이를 거절해 나눠 보내기 안내가 나온다.
- `이랑`으로 연결한 3건은 규칙 대체가 매장 요청 하나만 남긴다. FAQ 질문이 이 단계에서 사라진다.

| ID | 실패 입력 | 결과 |
| --- | --- | --- |
| MIXED-02 | 유심 재발급 비용 알려주고 근처 유심 재발급 매장도 찾아줘 | 나눠 보내기 안내 |
| MIXED-03 | 번호이동 방법이랑 번호이동 되는 매장 알려줘 | 매장만 처리 |
| MIXED-05 | 요금제 변경은 어떻게 해? 그리고 신촌역 매장 위치도 알려줘 | 나눠 보내기 안내 |
| MIXED-08 | 인터넷 해지할 때 장비 반납 방법이랑 근처 매장 알려줘 | 매장만 처리 |
| MIXED-10 | 명의변경 수수료 얼마야? 그리고 가까운 명의변경 매장도 | 나눠 보내기 안내 |
| MIXED-12 | 유심 재발급 방법이랑 서울역 근처 유심 재발급 매장 알려줘 | 매장만 처리 |
| MIXED-15 | 번호이동 하면 위약금 있나요? 그리고 근처 번호이동 매장 찾아주세요 | 나눠 보내기 안내 |

다음 보완 대상은 전체 의도와 하위 의도의 일관성이다. 프롬프트에 두 종류의 하위 요청이 있으면 전체 의도는 `BOTH`임을 명시하고, 서버에서는 검증된 하위 요청으로 전체 의도를 계산하는 방식을 검토한다. 단순히 `FAQ`를 `BOTH`로 바꾸어서는 안 되며 원문 근거, 요청 수, 순서, 각 매장 조건 검증도 통과해야 한다. 대체 경로에서도 질문 일부를 조용히 버리지 않아야 한다. 개선 효과는 같은 16문항과 단일 FAQ, 단일 매장, 복합 FAQ 회귀 사례로 다시 확인해야 한다.

재실측에서는 생성 호출 33회가 모두 HTTP 200이었다. SSE 완료 이벤트의 메시지 ID는 16건 모두 저장 메시지와 일치했고, 토큰이 전송된 답변의 본문도 일치했다. 되묻기와 확인 안내는 토큰 없이 완료 이벤트로 전달될 수 있다.

[압축 원시 자료](../scripts/compound-store-evaluation/routing-results.json.gz)에 질문, 좌표, 기대값, 모델 요청과 원시 응답, 실행 trace, 상담 상태, 저장 답변과 SSE 이벤트를 보관했다. [실행 스크립트](../scripts/compound-store-evaluation/run_routing.py)는 별도 `telme_135_` DB의 서버에서 16문항을 실행한다. 모델 호출 로그를 만드는 프록시 소스도 원시 자료에 포함했다.

## 범위와 한계

- FAQ 정책 조건 되묻기는 공통 복합 상담 경로를 재사용한다. 이 작업에서 추가하는 조건은 매장 지역과 업무다.
- FAQ+매장 실측 16건 중 7건은 라우팅 단계에서 두 요청을 유지하지 못했다. 매장 처리기까지 연결돼 있다는 이유만으로 복합 질문이 안정적으로 처리된다고 판단해서는 안 된다.
- 요청 보존과 검색 성공, 답변의 사실성은 별도 평가 대상이다. 예를 들어 가족결합 질문의 매장 하위 검색어에 원문에 없는 유심을 추가한 출력도 관찰됐다.
- 지역명 검색은 기존 카카오 연동 설정이 필요하다. 실제 API 검증은 좌표 경로를 사용했고, 지역명 경로는 통합 테스트에서 해석 결과를 통제해 매장 DB 검색을 확인했다.
- `이 상품을 취급하는 매장`처럼 FAQ 답변에서 새 검색 조건을 도출하는 의존 작업은 지원하지 않는다. 라우팅이 고객 원문에서 확인한 지역과 등록된 업무 조건으로 검색한다.

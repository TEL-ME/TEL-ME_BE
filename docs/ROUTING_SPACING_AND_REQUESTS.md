# TELME-132 질문 분해와 검색어 의미 보존

## 목표와 처리 방식

띄어쓰기 차이로 같은 질문을 여러 요청으로 나누거나 고객이 묻지 않은 조건을 검색어에 추가하지 않도록 한다. 답변에 필요한 FAQ 개수와 고객이 요청한 항목 수는 구분한다.

1. 라우팅 입력에서 한글 주변의 가로 공백만 통일한다. 저장된 고객 메시지는 바꾸지 않는다.
2. 모델이 FAQ 하위 질문을 여러 개 제안한 경우에만 별도 판정으로 `SINGLE`, `COMPARISON`, `MULTIPLE`과 요청 수를 확인한다. 비교와 하나의 처리 순서는 한 요청이고, 명시적으로 물은 서로 다른 업무나 항목은 여러 요청이다.
3. 단일 또는 비교 요청에는 고객 원문 전체를 사용한다. 여러 요청에는 각 `requestQuote`의 원문 존재 여부, 순서와 중복 여부를 검증한다.
4. 하위 질문의 검색 문구가 원문에 없는 대상이나 조건을 보태면 검증된 원문 표현으로 되돌린다. 판정이 충돌하거나 검증에 실패하면 확인 안내로 끝내며 상담 요청을 일부만 저장하지 않는다.

`번호이동 하고싶어요`는 한 요청이고, `eSIM과 유심 중 어느 쪽이 편해`는 한 비교 요청이다. `부가서비스 가입이랑 해지는 어떻게 해요`는 서로 다른 두 업무다. `해지 서류`의 대상을 원문에 없는 `로밍`으로 확정해서는 안 된다.

## 검증 결과

로컬 EXAONE 3.5 7.8B, 실제 Spring 경로와 별도 PostgreSQL 평가 DB를 사용했다. 라우팅 일치 수는 사전에 작성한 회귀 기준과의 비교다. 사람 확정 정확도는 아니다.

| 검증 | 결과 | 확인 범위 |
| --- | ---: | --- |
| Spring 라우팅 195회 | 채점 대상 165/165 일치 | 의도와 요청 수. 대상이 모호한 FAQ 30건은 채점 제외 |
| 실제 채팅 11회 | 11/11 통과 | 상담 상태, 답변 한 건 저장, SSE와 저장 답변 일치 |
| 실제 채팅 153회 | 실행 검사 실패 0건 | 회귀 60회와 사전 라벨 FAQ 93회. 중복 질문 포함 |
| 153회 답변 근거 유형 | 근거 있음 125, 근거 없음 26, 범위 밖 2 | 답변 정확도나 환각률이 아님 |

153회 중 FAQ 93회에서 같은 `slot_id`의 FAQ가 생성 근거로 전달된 경우는 92회였다. 그중 7회는 최종 답변이 안내 불가였다. 4회는 답변 가드 예외와 `MODEL_ERROR`가 기록됐다. 검색 정답 포함 여부와 답변 성공 여부가 다르다.

저장된 상담 요청 수를 확인하면 단일 요청 136회, 복수 요청 15회, 범위 밖 질문 2회였다. 이는 요청 수 확인 결과이며 하위 질문의 의미나 답변 정확성을 보증하지 않는다.

153회 채팅은 검색어 의미 보존 보완 **이전** 코드로 실행했다. 이 결과를 현재 미커밋 코드의 최종 답변 품질 수치로 사용하지 않는다. 질문별 입력, 검색 근거, 모델 결과와 최종 답변은 압축 원시 자료에서 확인할 수 있다.

## 답변에서 확인한 문제

| 사례 | 확인된 문제 |
| --- | --- |
| `H_PAYMENT_CONDITION` 047~048 | 근거에는 미납 중 유심 재발급 가능 여부가 없는데 가능하다고 단정함 |
| `NAME_CHANGE-0080`, `PORTING-0098`, `PLAN-0141` | 근거 밖 비용, 다른 업무의 신청 방법, 요금제 종류를 주파수 대역으로 잘못 해석한 답변이 가드를 통과함 |
| `PLAN-0035`, `ROAMING-0056`, `DEVICE-0125`, `PLAN-0135` | 생성 뒤 가드 예외로 답변 불가. 검색 근거 누락과 구분해야 함 |
| `TERMINATE-0110`, `TERMINATE-0105`, `TERMINATE-0111` | 해당 FAQ가 생성 근거에 있어도 최종 답변은 안내 불가 |
| `SERVICE-0017`, `NAME_CHANGE-0078`, `PLAN-0123`, `BILLING-0138` | 가드 수정 뒤 목록이 끊기거나 첫 설명 또는 비교 항목이 빠짐 |
| `SUBSCRIBE-0112` | 평가 질문과 FAQ 원문이 서로 다른 가입 대상을 비교함. 정답 라벨 확인 필요 |

띄어쓰기 변형은 요청 수가 같아도 검색 후보와 가드 결과가 달라 최종 답변이 달라질 수 있었다. 라우팅 회귀 검사만으로 답변의 의미 보존을 확인할 수 없으므로 검색과 답변까지 다시 검증해야 한다.

## 범위와 남은 한계

- 공개 API와 DB 스키마는 바꾸지 않는다. FAQ와 매장이 섞인 질문의 매장 답변 결합은 이 작업 범위 밖이다.
- 원문 구간의 존재와 순서는 확인하지만 두 질문의 의미가 완전히 같은지는 증명하지 못한다. 하위 질문의 대상과 조건은 모델 판단에도 영향을 받는다.
- 최초 라우팅이 단일 질문으로 판단하면 독립 요청 재확인은 실행하지 않는다. 여러 요청으로 판단하면 모델 호출이 한 번 더 늘어난다.
- 대상이 모호하고 검색 근거까지 없는 질문은 현재 FAQ 되묻기로 처리되지 않는다. 근거에서 조건을 추출할 수 있는 경우와 구분해 별도 설계가 필요하다.
- 다음 점검은 153회 채팅을 현재 코드로 다시 실행하고, 위 문제 사례에서 검색 근거와 최종 답변을 함께 비교하는 것이다.

## 자료와 재실행

입력 사례는 [평가 스크립트 폴더](../scripts/spacing-routing-evaluation)에 있다. `cases.json`은 띄어쓰기와 요청 관계 40회, `additional-cases.json`은 추가 20회, `faq-csv-cases.json`은 FAQ 원문 123건, `request-objective-cases.json`은 비교와 처리 순서 등 12건이다. 입력 JSON은 기준을 직접 검토하고 수정할 수 있도록 일반 파일로 둔다.

| 자료 | 내용 |
| --- | --- |
| `runs/request-objective-routing.json.gz` | Spring 라우팅 195회의 모델 요청과 응답 |
| `runs/request-objective-chat-153.json.gz` | 채팅 153회의 검색 근거, 실행 상태, 최종 답변 |
| `runs/request-objective-summary.json` | 라우팅 회귀 집계 |
| `runs/request-objective-manifest.json` | 입력과 코드 해시, 모델 및 설정 정보 |
| `runs/history.tar.gz` | 이전 단계의 압축 원시 결과, 요약, 11회 채팅 결과 |

이전 자료의 목록은 `tar -tzf scripts/spacing-routing-evaluation/runs/history.tar.gz`로 확인한다. 새 실험은 `run_full_answer_eval.py`와 `run_request_objective_chat.py`로 별도 평가 DB에서 실행한다. `summarize.py`는 저장된 라우팅 원시 자료만 집계하며 모델을 호출하지 않는다.

## 설계 근거

- [CheckList, ACL 2020 본문 2.2절](https://aclanthology.org/2020.acl-main.442.pdf)은 의미와 정답을 유지하는 입력 변형에서 예측도 유지되는지 검사한다. TEL-ME에서는 띄어쓰기 변형의 의도와 요청 수를 비교하는 기준으로 사용했다.
- [Break It Down, TACL 2020 본문 2절](https://aclanthology.org/2020.tacl-1.13.pdf)은 복합 질문의 하위 의미 단위와 관계를 명시한다. TEL-ME에서는 고객이 요구한 항목과 답변 작성에 필요한 정보를 구분하는 데 참고했다. 이 논문이 TEL-ME의 특정 모델 호출 방식이나 한국어 성능을 검증한 것은 아니다.

# 띄어쓰기와 독립 요청 검증

## 해결할 문제

`번호이동 하고싶어요`와 `번호 이동하고싶어요`는 같은 한 요청이다. 라우팅 모델이 첫 문장을
`번호이동 절차`와 `필요 서류`로 나누면 고객이 묻지 않은 요청이 추가된다.
단어 수, 답변에 필요한 FAQ 수, 비교 대상 수를 고객 요청 수로 사용하지 않는다.

## 처리 방식

1. 고객 메시지는 원문 그대로 저장한다. 라우팅 입력에서만 한글 주변의 가로 공백을 통일한다.
   맞춤법을 새로 생성하는 기능은 아니다. 줄바꿈과 영문 및 숫자 사이 공백은 보존한다.
2. 기존 라우팅 모델은 의도, 검색 질문, 하위 질문별 `requestQuote`를 출력한다.
   `requestQuote`는 현재 질문에서 고객이 요청한 연속된 원문 구간이다.
3. 여러 FAQ 후보가 나오면 원문만 받는 요청 인벤토리 모델을 한 번 호출한다.
   이전 상담, 검색 FAQ, 첫 모델의 답변 계획은 전달하지 않는다.
4. 인벤토리가 입력 전체를 한 요청으로 판정하면 원문 한 건으로 처리한다.
   여러 요청이면 개수와 질문별 인용 구간을 대조한다. 인용은 현재 원문에 존재하고,
   순서대로 서로 겹치지 않아야 한다.
5. 두 판정이 맞지 않거나 출력 검증 및 호출이 실패하면 질문을 다시 확인하는 안내를 반환한다.
   이때 라우팅과 상담 요청을 일부만 저장하지 않는다.

일반 단일 질문은 라우팅 호출 한 번이다. 여러 FAQ 후보는 최대 두 번이며,
요청 인벤토리 판정을 반복 재시도하는 루프는 없다. 라우팅은 temperature `0`, 출력 한도 `768`토큰,
인벤토리는 temperature `0`, 출력 한도 `256`토큰이다. 통신과 관계없는 일반적인 방법 문의는 UNKNOWN이다.

| 현재 질문 | 기대 처리 |
| --- | --- |
| 번호이동 하고 싶어요 | 업무 요청 한 건 |
| 미납 요금이 있는데 번호이동하고 싶어요 | 조건을 포함한 요청 한 건 |
| 번호이동은 안 하고 요금제 변경만 하고 싶어요 | 부정된 업무를 추가하지 않은 요청 한 건 |
| 번호이동 비용과 신청 방법 그리고 필요 서류 알려줘 | 명시적으로 요구한 요청 세 건 |
| eSIM과 유심 중 어느 쪽이 편해 | 비교 요청 한 건 |
| 로밍 신청 방법 알려줘. 5G와 LTE 요금제 비교해줘 | 독립 요청과 비교 요청 두 건 |

## 실측

Docker Ollama의 `exaone3.5:7.8b`를 실제 Spring `QueryRoutingService`로 호출했다.
PostgreSQL 별도 DB `telme_132_routing`에서 라우팅 및 상담 요청 저장을 확인했고,
평가 트랜잭션은 종료 시 롤백했다. 기준 커밋은 `5f7ea49`다.

| 평가군 | 기대 의도와 요청 수 일치 | 띄어쓰기 때문에 결과가 달라진 그룹 | 모델 호출 |
| --- | --- | --- | --- |
| 변경 전 동일 입력 | 31/40 | 4/17 | 40 |
| 변경 후 기존 입력 | 40/40 | 0/17 | 54 |
| 변경 후 추가 입력 | 20/20 | 0/10 | 26 |

기존 입력에는 번호이동 4개 띄어쓰기 변형의 2회 반복이 포함되어 있다.
추가 입력은 eSIM, 로밍 가입, 기기변경, 조건, 부정, 복합, 비교, 매장, 외부 질문을 포함한다.
추가 평가군도 오류 분석에 사용한 회귀 사례이며 독립적인 블라인드 검증셋은 아니다.
위 수치는 **라우팅 의도와 요청 수**의 결과다. 검색 정답률, 최종 답변 정확도, 서비스 전체 품질 수치가 아니다.

같은 40회에서 모델 호출 시간 합계는 변경 전 `35.1초`, 변경 후 `43.1초`였다.
추가 호출, 프롬프트, 출력 한도가 함께 바뀐 소규모 로컬 측정이며 전체 API 지연시간으로 해석하지 않는다.

자동 검증에서는 전체 빌드가 성공했고 1,838개 테스트가 통과했다. 제외된 테스트는 104개다.
직접 라우팅 API 오류 처리까지 포함한 변경 대상 테스트 301개도 별도로 통과했다.

## 범위와 한계

- `requestQuote`는 LLM 내부 출력이다. 공개 응답 DTO와 DB 컬럼은 추가하지 않는다.
- 채팅 경로의 분해 실패는 기존 안내 응답으로 처리한다. 직접 라우팅 API에서 같은 실패가 발생하면
  `422 INTENT422-0`을 반환해 처리되지 않은 예외의 `500` 응답을 방지한다.
- FAQ와 매장이 섞인 BOTH의 기존 안내 및 단일 매장 처리 경계를 유지한다.
- 원문 우선 FAQ 검색과 RAG 답변 생성은 기존 방식이다. 라우팅이 같아도 검색이나 생성 결과가 항상 같다고 보장하지 않는다.
- 원문 인용의 존재는 코드로 확인하지만, 의미상 독립적인 요청인지의 판정은 모델 성능에 영향을 받는다.
  같은 모델의 두 판단을 독립적인 모델 교차 검증으로 해석하지 않는다.
- 초기 모델이 FAQ 한 건으로 판정하면 추가 호출을 하지 않는다. 누락된 복합 요청까지 모두 재검증하는 구조는 아니다.
- 한글 공백이 실제 의미를 바꾸는 동형 문장이나 잘못 끊은 영문 및 숫자의 공백까지 동일 의미로 보정하지 않는다.

## 근거와 적용 부분

- [CheckList, ACL 2020 본문 2.2절, p.4904](https://aclanthology.org/2020.acl-main.442.pdf):
  의미와 정답을 유지하는 입력 변형에서는 예측도 유지되어야 한다는 invariance 테스트를 제시한다.
  TEL-ME에서는 같은 요청의 띄어쓰기 변형별 의도와 요청 수를 비교하는 기준으로 적용했다.
- [Break It Down, TACL 2020 본문 2절, pp.184–186](https://aclanthology.org/2020.tacl-1.13.pdf):
  질문 의미를 분해 표현으로 나타내고 각 단계와 참조 관계를 정의한다.
  TEL-ME에서는 고객 요청의 구조를 답변에 넣을 설명 항목과 구분하는 설계에 참고했다.
  QDMR 전체 연산 체계를 구현한 것이 아니며, 한글 공백 제거와 두 번째 모델 호출은 TEL-ME의 구현 판단이다.

## 자료와 재실행

자료는 [scripts/spacing-routing-evaluation](../scripts/spacing-routing-evaluation)에 모았다.

| 파일 | 용도 |
| --- | --- |
| `cases.json` | 기존 17개 의미 그룹, 40회 입력과 기대 의도 및 요청 수 |
| `additional-cases.json` | 추가 10개 의미 그룹, 20회 입력과 기대 의도 및 요청 수 |
| `runs/baseline.json.gz` | 변경 전 실제 Spring 라우팅 결과 및 모델 요청과 응답 |
| `runs/development.json.gz` | 변경 후 기존 입력 결과, 최초 분류와 추가 판정의 모든 요청 및 응답 |
| `runs/additional.json.gz` | 변경 후 추가 입력 결과 및 모든 모델 호출 |
| `runs/summary.json` | 성공 수, 불일치 그룹, 호출 시간, 원시 자료 SHA-256 |
| `runs/manifest.json` | 기준 코드, 모델 정보와 실행 설정 |
| `summarize.py` | 저장된 원시 자료 집계. 채팅이나 모델을 호출하지 않음 |

모델 평가는 opt-in `SpacingRoutingProbe`로 실행한다. 기존 개발 DB를 사용하지 않고,
새 평가 DB를 준비한 뒤 아래 환경변수를 설정한다.

```powershell
$env:POSTGRES_PORT = '5440'
$env:POSTGRES_DB = 'telme_132_routing'
$env:TELME_SPACING_PROBE = 'true'
$env:TELME_SPACING_CASES = 'scripts/spacing-routing-evaluation/cases.json'
$env:TELME_SPACING_OUT = '.measure/telme132/recheck.json.gz'
.\gradlew.bat test --tests 'com.telme.probe.SpacingRoutingProbe' --rerun-tasks
Remove-Item Env:TELME_SPACING_PROBE
```

실행 환경에 동일한 Ollama 모델과 마이그레이션 가능한 PostgreSQL이 필요하다.
추가 평가에는 `TELME_SPACING_CASES`를 `additional-cases.json` 경로로 바꾼다.

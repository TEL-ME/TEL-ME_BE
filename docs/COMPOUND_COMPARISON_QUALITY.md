# FAQ 복합 질문과 비교 질문 처리

## 무엇을 바꿨나

독립된 FAQ 질문은 각각 검색하고 답한 뒤 하나의 채팅 답변으로 합친다. 비교 질문은 한 질문으로 유지하면서 두 대상의 같은 속성에 대한 근거를 확인한다. 한쪽 정보로 다른 쪽을 추측하거나, 근거 없는 정책을 덧붙이지 않는 것이 목표다. 매장이 섞인 복합 질문은 이번 범위에서 제외한다.

## 어떻게 처리하나

| 질문 유형 | 처리 방식 | 근거가 부족할 때 |
| --- | --- | --- |
| 독립 FAQ 복합 질문 | `ConsultChatProcessingService`가 하위 질문을 요청 순서대로 검색하고 답변 하나로 결합한다. 결합된 답변과 근거를 저장하고 최종 내용만 전송한다. | 해당 하위 질문만 답변 불가로 표시하고 나머지 답변은 유지한다. 생성 오류는 실행 실패로 처리한다. |
| 비교 질문 | 원문 검색 결과를 보존한다. 양쪽 근거가 부족하면 대상별로 임계값 없는 상위 10개 후보를 추가 검색한다. 검증된 FAQ 답변 문장을 두 대상에 연결해 표시한다. | 어느 한쪽이라도 질문한 속성의 근거가 확인되지 않으면 비교 전체를 보류한다. |

독립 FAQ는 한 번에 최대 3개까지 처리한다. 일부 하위 질문만 답한 경우에도 전체 `answerBasis`는 `GROUNDED`이며, 답하지 못한 부분은 본문에서 구분한다. 이 값만으로 모든 하위 질문이 해결됐다고 판단하면 안 된다.

**복합 FAQ의 검색 보완:** 일반 임계값 검색이 비었을 때만 상위 10개 후보를 다시 확인한다. 모델이 고른 FAQ ID가 후보에 존재하고, 인용문이 해당 FAQ 답변 원문에 있는지 검사한다. 질문의 핵심 어휘가 선택한 FAQ의 질문과 답변을 합친 내용에 포함되는지도 확인한다. 인용문을 의역했다면 같은 FAQ에서 정확히 복사하도록 한 번만 재요청한다. 검증을 통과하면 해당 FAQ 답변 원문을 사용한다.

**비교 답변의 근거 검증:** FAQ 질문은 대상 식별에 사용하고, 정책 사실은 FAQ 답변에서만 가져온다. 모델이 제시한 ID와 인용문을 검증하고 인용문이 포함된 원문 문장 전체를 표시한다. 같은 문장이 양쪽 사실을 담으면 한 번만 표시한다. 실제 상담의 이 경로는 자유 생성 문장을 추가하지 않는다.

대상 식별에서는 `5G`처럼 단어 하나만 겹치는 것으로 통과시키지 않고 상품명과 대상의 식별 단어를 모두 확인한다. 판정 모델의 연결 장애나 타임아웃은 실행 실패로 전달한다. 정상 호출에서 읽을 수 없는 JSON이나 검증되지 않은 인용문이 나오면 근거로 사용하지 않는다. 모델 호출 기록에는 하위 상담 ID를 함께 남기며, 프롬프트 버전 이름도 DB 컬럼 길이 안으로 제한한다.

예를 들어 명의 변경 서류와 무료 해외 항공권을 함께 물으면, 명의 변경 서류는 안내하고 항공권 질문에는 `안내드릴 수 있는 정보가 없습니다.`라고 답한다. 두 부분은 하나의 채팅 답변으로 제공한다.

## 왜 이 방식인가

| 확인한 문제 | 적용한 대응 |
| --- | --- |
| 명의 변경 서류 FAQ가 후보에 있지만 유사도 임계값 때문에 답변에서 누락됨 | 복합 FAQ의 빈 검색 결과에 한해 후보를 확대하고 다시 검증한다. 운영 임계값을 전체적으로 낮추지는 않는다. |
| 항공권 질문에 명의 변경 수수료가 무료라는 FAQ를 잘못 선택함 | ID와 인용문 일치 외에 질문 핵심 어휘가 후보에 포함되는지 검사한다. |
| FAQ 답변이 주어를 생략해 올바른 비교 근거도 거절됨 | 대상 식별에는 FAQ 질문도 활용하되 사실 인용은 답변 원문에서만 허용한다. |
| 첫 문장만 남기면 비교 사실이 잘리고, 자유 생성하면 근거 없는 정책이나 추천이 추가됨 | 검증된 인용문을 포함한 FAQ 원문 문장으로 비교 답변을 구성한다. |
| `5G 라이트` 질문에 `5G 프리미엄` 근거도 대상명이 일부 겹쳐 통과할 수 있음 | 원문과 FAQ에서 대상 식별 단어가 모두 확인돼야 통과시킨다. |
| 판정 모델 호출 장애까지 근거 부족 안내로 바뀜 | 모델 장애는 실패 원인을 보존해 상위 실행 처리기로 전달한다. |

방법을 선택할 때 참고한 논문과 적용 지점은 다음과 같다. 아래 연구는 설계 근거이며 TEL-ME의 한국어 FAQ 성능을 직접 보증하지 않는다.

| 논문과 본문 위치 | 참고한 내용 | TEL-ME 적용 |
| --- | --- | --- |
| [Min 외, ACL 2019, 3.1절 및 표 2](https://aclanthology.org/P19-1613.pdf) | 복합 질문 분해와 비교 연산을 구분하는 구조 | 독립 FAQ는 각각 처리하고 비교 질문은 양쪽 속성의 근거를 연결한다. |
| [Yang 외, EMNLP 2018, 2절](https://aclanthology.org/D18-1259.pdf) | 비교 질문에 필요한 두 대상의 정보와 supporting facts | 한쪽 근거만으로 비교를 완성하지 않는다. |
| [Min 외, EMNLP 2023, 3.1절](https://aclanthology.org/2023.emnlp-main.741.pdf) | 답변을 사실 단위로 나누어 근거성을 평가 | 원문 인용을 검증하고 비교 답변의 추가 사실 생성을 제한한다. 원문 표시 정책은 프로젝트의 선택이다. |
| [Tang 외, EACL 2021, 1절 및 3절](https://aclanthology.org/2021.eacl-main.283.pdf) | 최종 답이 맞아 보여도 하위 질문 해결은 실패할 수 있음 | 각 하위 질문의 검색 근거와 답변을 따로 기록하고 대조한다. |

## 검증 결과

로컬 PostgreSQL의 활성 FAQ 1,152건과 기존 `bge-m3` 임베딩, Ollama `exaone3.5:7.8b`를 사용했다. 일반 검색은 이중 벡터, 답변 임계값 0.72, 질문 임계값 0.88, top-3이다. 정답 FAQ 직접 주입과 실제 검색을 별도로 실행했다.

라우팅 단독 평가에서는 EXAONE이 비교 요청 10건을 모두 여러 FAQ 질문으로 분리했다. `QueryRoutingService`의 비교 질문 보정 후에는 10건 모두 사용자 원문을 유지한 질문 하나가 됐다. 이 결과는 질문 구조만 검증하며 근거와 답변 품질은 아래 별도 실측으로 확인했다.

| 검증 | 결과 |
| --- | --- |
| 비교 질문 14건의 실제 검색 | 수정 전에는 5건, 최종 코드에서는 7건이 양쪽 비교 사실을 답했다. 나머지 7건은 근거 부족 또는 질문 조건의 모호함으로 보류했다. |
| 명의 변경과 번호 이동 서류 비교 | FAQ 65와 125의 양쪽 서류 정보가 최종 재검증 답변에 포함됐다. |
| 분실 신고와 일시 정지 비교 | FAQ 45와 637의 각 정보가 최종 답변에 포함됐다. |
| eSIM과 유심 개통 비교 | 전환과 재발급 FAQ를 개통 절차와 동일한 근거로 취급하지 않고 보류했다. |
| 독립 FAQ 복합 질문 4사례 | 두 질문 또는 세 질문을 순서대로 결합했다. 명의 변경 서류는 복구했고, 무료 항공권 질문만 근거 없음으로 남겼다. 결합 답변과 기록된 전송 내용이 일치했다. |
| 자동 테스트 | 최종 전체 빌드 성공. 테스트 1,580개 중 실패 0개, 제외 100개. 다른 상품 근거의 혼입, 판정 형식 오류, 모델 장애와 취소, 호출 기록의 하위 상담 연결을 포함한다. |
| 실제 채팅 API 7사례 | EXAONE과 별도 PostgreSQL 평가 DB로 세션 생성, 메시지 전송, 실제 라우팅과 검색, 답변 저장, 근거 조회 및 SSE 수신을 연결했다. 단일 FAQ, 복합 FAQ, 부분 근거 부족, 두 비교 질문, 전체 근거 부족 및 FAQ와 매장 복합 안내를 확인했다. |

실측 프로브는 Spring의 실제 검색 및 답변 생성 기능을 사용한다. 복합 질문 프로브의 라우팅 입력과 저장 및 전송 경계는 모의 객체다. 별도의 실제 HTTP 검증에서는 그 경계를 대체하지 않고 실행해 복합 답변이 하나만 저장되는지, 상담 요청이 모두 완료되는지, 저장된 답변과 SSE 토큰이 일치하는지 확인했다. SSE 완료 이벤트의 메시지 ID도 저장된 답변과 대조했다. 이 소규모 결과를 서비스 전체 정확도나 환각률로 해석하지 않는다.

실행 예: 필요한 환경 변수를 설정하고 `./gradlew test --tests com.telme.probe.ComparisonPolicyProbe`를 실행한다. DB의 FAQ와 임베딩, Ollama 모델이 준비돼 있어야 한다. 새 실행은 `runs/*-current.json`에 기록하며 보관된 실험 결과를 덮어쓰지 않는다. `TELME_COMPARISON_OUT`, `TELME_FORCED_EVIDENCE_OUT`, `TELME_LIVE_MULTI_FAQ_OUT`, `TELME_FORCED_MULTI_FAQ_OUT`으로 출력 경로를 지정할 수도 있다.

실제 HTTP 검증은 [run_live_api.py](../scripts/compound-faq-evaluation/run_live_api.py)로 재현한다. FAQ와 임베딩을 복제한 별도 평가 DB로 Spring 앱을 18089 포트에 실행한 뒤 `python scripts/compound-faq-evaluation/run_live_api.py --database telme_compound_pr_review_20261006`을 실행한다. 모델은 `LLM_PROVIDER=ollama`, `LLM_MODEL=exaone3.5:7.8b`이며 Docker의 `telme-postgres`에서 상담 상태를 대조한다. 서버와 검증 도구가 같은 평가 DB를 사용해야 한다.

## 한계

- 의미 적합성은 EXAONE 판정에 의존한다. 실제 FAQ 인용인지 확인해도 질문과 무관한 FAQ를 고르는 오류를 완전히 배제하지는 못한다.
- 핵심 어휘 검사는 잘못된 후보를 막는 대신 동의어나 오타로 표현된 올바른 근거도 거절할 수 있다.
- 후보 확대와 추가 판정에는 검색 및 LLM 호출 비용과 지연이 추가된다.
- 비교 답변은 FAQ 원문에 있는 정보만 표시하므로 자연스러운 설명이나 추가 추천보다 근거 보존을 우선한다.

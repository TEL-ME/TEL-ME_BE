# 채팅 답변 품질 평가 기준

Spring 채팅 API로 질문을 보내 생성, 저장, 조회까지 끝난 답변을 평가하는 기준이다. 실행 방법은 [측정 절차](SERVICE_EVALUATION.md), 평가셋 구성은 [README](README.md#평가셋), 사람이 정한 라벨 결정은 [라벨 검토 목록](LABEL_REVIEW.md)에 있다. TELME-100의 [500건 고정 검증셋](https://github.com/TEL-ME/TEL-ME_BE/blob/ae637974770f03fa8620c6b5540877becf1ff0c5/docs/chat-judge/experiments/V3-fixed-500-case-validation/20261001-validation-v2-results.md)은 사람이 구성한 답변으로 Judge 자체를 시험한 자료라 서비스 품질 점수로 쓰지 않는다.

## 1. 평가 단위와 라벨

기본 단위는 **고객 질문 한 턴**이다. 멀티턴은 앞선 턴과 함께 하나의 대화로 묶고, 집계에서는 대화 수와 턴 수를 함께 적는다. 질문을 실행하기 전에 다음을 라벨로 고정한다.

| 항목 | 라벨 |
| --- | --- |
| 기대 동작(`expectedBehavior`) | `ANSWER`(답변), `PARTIAL_ANSWER`(일부만 답할 수 있음), `ANSWER_OR_CLARIFY`(답하거나 조건을 되물어도 됨), `ABSTAIN`(답이 없어 보류), `OUT_OF_SCOPE`(범위 밖 안내), `STORE_LOOKUP`(매장 조회) |
| 질문 부분과 정답 근거(`qualityReferenceGroups`) | 질문 부분마다 인정할 대체 FAQ 답변 묶음. 묶음 안은 OR, 질문 부분 사이는 AND. 복합 질문의 질문 부분은 고객 문장에서 나눈 부분 질문이다 |
| 필수 사실(`requiredFacts`) | 정답에 반드시 들어가야 할 사실. 금액, 기간, 대상, 조건, 예외를 나눠 적고, 고객이 실제로 묻는 것만 적는다 |
| 답의 출처(`answerSources`) | `FAQ`, `PLAN_TABLE`(요금제 표), `MEMBER`(회원 계정 데이터), `STORE`(매장 조회) |
| 바로 답했을 때 필수 사실(`requiredFactsIfAnsweredDirectly`) | 고객 조건에 따라 답이 갈리는 질문에서, 앱이 되묻지 않고 바로 답했을 때 갈리는 경우를 모두 안내하는 사실 |
| 되묻기 고객 답변(`clarificationReplies`) | 흐름 평가셋에서 앱이 조건을 되물으면 보낼 고객 답변. 조건 이름(`whenKey`)으로 짝짓는다 |

유사도가 높다는 이유만으로 대체 정답을 인정하지 않는다. FAQ 답변 본문에 필수 사실이 모두 있는 FAQ만 인정한다. 평가 중 새 동등 FAQ가 발견되면 사람이 확인하고 라벨 버전을 올린 뒤, 비교할 두 대상을 같은 라벨로 다시 판정한다.

## 2. 세 축과 통과 조건

세 축을 따로 기록한다. 하나의 점수로 합쳐 원인을 숨기지 않는다.

| 축 | 라벨 |
| --- | --- |
| 근거성 | `SUPPORTED`: 모든 사실 주장이 근거에 부합. `UNSUPPORTED`: 한 주장 이상에 명백한 근거 부족 또는 모순. `NOT_APPLICABLE`: 사실 주장 없는 안내. `REVIEW`: 근거 관계가 애매함. `UNSCORED`: 추출 또는 출력 검증 실패 |
| 충족도 | 질문 부분마다 `COMPLETE`(필수 사실을 모두 처리), `PARTIAL`(일부만), `MISSED`(실질적인 답 없음), `NOT_APPLICABLE`(내용 답변이 기대되지 않음), `REVIEW` |
| 보류 | `APPROPRIATE`: 실제 근거 부족이나 범위 밖 질문을 적절히 보류. `OVER_REFUSAL`: 충분한 근거가 있는데 거절. `SHOULD_ABSTAIN`: 근거 없는 내용을 단정. `NOT_APPLICABLE`: 보류 판단이 필요 없는 정상 답변. `REVIEW` |

**한 턴의 통과:** 실행이 끝나 답변이 저장됐고, 근거성이 `UNSUPPORTED`가 아니며, 모든 질문 부분이 `COMPLETE`(범위 밖·보류 질문과 코드 규칙의 정상 처리는 `NOT_APPLICABLE`)이고, 보류가 `SHOULD_ABSTAIN`·`OVER_REFUSAL`·`REVIEW`가 아닐 때다. 미채점과 사람 검토는 통과로 넣지 않는다(미확정).

- `PARTIAL_ANSWER`는 답할 수 있는 부분을 정확히 답하고 나머지를 보류해야 통과다. 보류 사실은 "…은 제공된 FAQ에서 확인할 수 없다"는 필수 사실로 적는다.
- 답할 수 있는 내용을 말했더라도 근거 없는 사실이 하나라도 섞이면 근거성은 실패다.
- 복합 질문에서 한쪽만 답하면 근거성이 `SUPPORTED`여도 충족도는 `PARTIAL`이다.
- 고객이 물은 값은 답에 직접 있어야 충족이다. 답변의 숫자로 계산하면 나오는 값(예: 24개월 중 8개월 지남 → 16개월 남음)도 직접 말하지 않으면 부분 답이다(라벨 검토 D6).

## 3. 근거로 보는 것

근거성과 보류의 근거 충분성은 **실제로 생성에 전달된 근거**로 판정한다. 검색 후보 전체나 저장된 인용으로 대신하지 않는다.

| 근거 | 언제 | 판정 입력 |
| --- | --- | --- |
| FAQ 답변 본문 | RAG 입력(`ragInputs`)에 들어간 FAQ | 답변 본문만 넘긴다. FAQ 질문 문장은 넘기지 않는다 |
| `SERVICE:PLAN_TABLE` | 요금제 목록·추천 답변(`pipelineTrace.planAnswer`) | 캡처 당시 판매 중 요금제 표와 가입 연령 기준. 판매 중 요금제 전부라는 문장과 개수·최저가처럼 표에서 바로 나오는 값도 적는다 |
| `SERVICE:MEMBER_DATA` | 로그인 회원의 내 요금제·사용량·약정·위약금·추천 답변 | 대화 직전에 조회한 계정 데이터. 시각은 한국 시간, 데이터는 GB 환산을 함께 적는다 |
| `SERVICE:RECOMMENDATION_RULE` | 요금제 추천 답변 | 앱의 추천 규칙(제공량이 평균 사용량의 1.2배 이상이면 알맞다, 사용량을 모르면 50GB·3GB 기준)과, 회원이면 지금 요금제가 규칙상 알맞은지 |
| `SERVICE:STORE_RESULTS` | 매장 결과 | 보여 준 매장 목록과 각 매장의 취급 업무·영업시간 |

- FAQ 질문 문장은 정책 근거가 아니라서 Judge에 넘기지 않는다. 이 때문에 답 문장만으로는 어떤 상황에 대한 답인지 모호한 FAQ에서 Judge가 틀릴 수 있다. 예: "해지하는데 할부 한 번에 내는 게 나아요"에 대한 답 "부담되시면 나눠 내는 것도 됩니다"를 이번 달 요금 분할 납부의 근거로 읽었다(U041). 질문 문장을 상황 맥락으로 넘겨 봤지만 모델이 그 문장을 근거처럼 써서 사람 판정과의 일치가 떨어졌고, U041도 고쳐지지 않아 되돌렸다([시험 결과](results/20261017-situation-context/README.md)).
- 고객 질문과 확정된 상담 조건은 상황을 해석하는 맥락이며 정책의 증거가 아니다.
- 단어가 달라도 뜻, 대상, 조건, 부정, 금액, 기간, 예외가 같으면 지지됨이다. 조건이나 대상을 넓히거나 뒤집으면 근거 없음이다. 예: FAQ "미납 요금을 완납해야 명의 변경 가능"에 "미납 요금이 있으면 모두 납부하셔야 명의 변경할 수 있습니다"는 지지됨, "미납 요금이 있어도 명의 변경 가능"은 실패, "유심 재발급 비용 7,700원"으로 "택배비도 포함"을 확정하면 근거 부족이다.
- 답변의 주장은 답변 원문에서 그대로 추출해 위치를 검증한 뒤 의미를 비교한다. 답변에 없는 문구를 추출하면 미채점이다. 애매하면 `REVIEW`로 둔다.
- 서비스 통신사는 TELME다. LG U+, SKT, KT 같은 타사의 정책은 자사 FAQ로 뒷받침되지 않는다(Judge 프롬프트에 아직 반영 전, 라벨 검토 D7).

## 4. 코드가 정하는 판정

기대 동작과 실제 응답 유형만으로 정해지는 판정은 모델을 부르지 않고 코드가 정한다. 원시 기록에 `rule`로 남고, 저장한 판정을 다시 집계할 때(`rescore`, `combine_judges.py --capture`)도 지금 기준으로 다시 적용한다. 앱 고정 문구 목록은 [`service_data.py`](../../scripts/chat_judge/service_data.py)에 있고, 테스트가 Java 소스에 글자 그대로 있는지 확인한다.

| 규칙 | 조건 | 판정 |
| --- | --- | --- |
| `EMPTY_SOURCES` | 생성에 전달된 FAQ 근거와 서비스 데이터 근거가 모두 없음 | 근거 충분성은 모든 질문 부분이 `INSUFFICIENT`. 답변이 거절이면 보류는 `APPROPRIATE` |
| `SERVICE_GUIDANCE` | 근거성 주장 전체가 앱 고정 안내 문장(로그인 안내, 범위 안내, 인사 등) 안에 있음 | 그 주장은 정책 주장에서 뺀다(`IRRELEVANT`, 모델 판정은 `modelVerdict`) |
| `SYSTEM_FALLBACK` | 답변 전체가 처리 실패 대체 문구(질문 분리 실패, 질문 개수 초과, 분류 불가, 매장 조회 불가) | 기대 동작과 상관없이 충족도 `MISSED`. 보류·범위 밖 질문에서도 통과하지 않는다 |
| `OUT_OF_SCOPE_QUESTION` | 기대 동작이 `OUT_OF_SCOPE` | 충족도 `NOT_APPLICABLE`. 사실을 지어내면 근거성과 보류에서 걸린다 |
| `ABSTAIN_REFUSAL_TEMPLATE` | 답이 없는 질문(`ABSTAIN`)에 답변 전체가 앱의 거절 고정 문장(검색 결과 0건 안내, "지금 확인할 수 있는 정보만으로는 정확하게 안내드리기 어려워요") | 충족도 `NOT_APPLICABLE`(정상 보류). 모델에 맡기면 같은 문장을 턴마다 다르게 판정했다 |
| `NO_SEARCH_RESULT_FALLBACK` | 답이 없는 질문에 검색 결과 0건 고정 문구로 답함 | 보류로 인정하고 발견 사항으로 따로 센다(라벨 검토 D1). 답이 있는 질문에서 이 문구로 끝나면 충족도 실패다 |
| `LOGIN_GUIDANCE_ACCEPTED` | 답의 출처가 회원 정보뿐인 보류 질문에 답변 전체가 로그인 안내 | 충족도 `NOT_APPLICABLE`, 정상 처리(비로그인 실행) |
| `CLARIFICATION_ACCEPTED` | 기대 동작이 `ANSWER_OR_CLARIFY`이고 응답이 되묻기 | 충족도 `NOT_APPLICABLE`, 정상 처리 |
| `UNNECESSARY_CLARIFICATION` | 그 밖의 기대 동작에서 최종 응답이 되묻기(매장 조회 제외) | 충족도 `MISSED` |
| `STORE_RESULTS_RETURNED` / `STORE_SERVICE_MISMATCH` / `STORE_LOCATION_MISMATCH` / `STORE_NOT_RETURNED` | 기대 동작이 `STORE_LOOKUP` | 매장 목록을 보여 줬고, 고객이 말한 위치 기준(현재 위치 버튼이면 현재 위치, 지명이면 지명)이며, 고객이 말한 업무를 하는 매장만이면 `COMPLETE`, 아니면 `MISSED`. 거리와 영업 중 여부는 보지 않는다 |
| `REASKED_CONDITION` | 한 턴 안에서 이미 답한 조건을 다시 되물음 | 최종 답이 맞아도 통과로 보지 않는다 |
| `UNSCRIPTED_CLARIFICATION` | 앱이 평가셋에 고객 답변이 없는 조건을 되물음 | 사람 검토(미확정) |

## 5. 되묻기가 있는 흐름

- 앱이 조건을 되물으면 평가셋의 고객 답변을 보내 최종 응답까지 받고 그 응답을 판정한다. 판정에는 첫 질문, 되묻기, 고객 답변이 이전 대화로 들어가고, 현재 질문은 마지막 고객 발화다.
- 고객 조건에 따라 답이 갈리는 질문은, 앱이 되물어 고객이 조건을 말했으면 `requiredFacts`, 되묻지 않고 바로 답했으면 `requiredFactsIfAnsweredDirectly`로 충족도를 판정한다. 고객이 말하지 않은 조건을 전제한 사실은 요구하지 않는다.
- 의도 분류는 첫 질문 기준으로 비교한다. 되묻기 답변은 후속 분석으로 처리돼 라우팅 기록이 없다.

## 6. 보고할 지표

모든 지표는 전체와 묶음별로 `분자/분모`를 함께 보고하고, 비율에는 95% 신뢰구간(Wilson)을 붙인다. 한 줄 요약에는 턴 합산 통과율 대신 **묶음 평균 통과율**(흐름 회귀를 뺀 묶음별 통과율의 단순 평균, `suiteMacroPassPercent`)을 쓴다. 턴 합산은 평가셋의 묶음 크기 비율에 따라 바뀌기 때문이다. 운영 채팅 기록이 생기면 실제 유형 비율로 가중한다.

| 지표 | 계산 |
| --- | --- |
| 답변 품질 통과율 | 통과한 턴 / 품질이 확정된 턴. 실행 실패는 실패로 넣고, 미확정을 포함한 전체 분모의 최저·최고 범위를 함께 적는다 |
| 근거 없는 답 비율 | 근거 없는 주장이 하나 이상인 답변 / 유효한 근거성 판정을 받은 사실 답변. 거절 답변은 분모에 넣지 않는다 |
| 주장 단위 근거 부족률 | 근거 없는 주장 / `SUPPORTED` 또는 `UNSUPPORTED`로 판정된 주장 |
| 완전 답변율 | 모든 필수 사실과 질문 부분을 처리한 답변 / 답할 수 있는 턴 |
| 과도한 거절률 | `OVER_REFUSAL`인 턴 / 답할 수 있는 턴 |
| 검색 적중률 | 검색 후보, 실제 RAG 입력, 저장 근거 각각에서 인정 FAQ를 찾은 질문 부분 / 정답 묶음이 있는 질문 부분 |
| 정상 완료율, 라우팅 적중률 | 정상 완료·저장된 턴 / 실행한 턴, 기대 의도와 첫 질문의 분류 의도가 같은 턴 / 의도 라벨이 있는 턴 |
| Judge 채점률 | 세 축의 출력 검증을 모두 통과한 턴 / 판정한 턴 |

검색 후보 적중과 저장 근거 적중은 따로 본다. 정답 FAQ가 검색되지 않았으면 검색 단계의 실패이고, 검색됐지만 답변에 쓰이지 않았으면 선택이나 생성 단계의 실패다. 같은 질문을 여러 번 실행했으면 독립 질문 수와 반복 실행 수를 구별한다. 최종 SSE 내용은 점수에 넣지 않으므로 자동 품질 통과율을 종단 성공률이라고 부르지 않는다.

## 7. Judge 신뢰도와 사람 판정

- 자동 점수는 Judge 추정치로 표시하고 사람 확정 점수라고 하지 않는다.
- Judge에는 라우팅 정답, 기대 동작, 정답 FAQ ID, 필수 사실을 근거성이나 보류 판정의 힌트로 주지 않는다. 충족도 판정에만 질문 부분별 정답 FAQ 답변과 필수 사실을 준다.
- 원문 답변, 실제 RAG 입력, 저장 근거, 프롬프트, 원시 응답, 검증 실패 사유를 모두 보존한다.
- Judge 검증 보고에는 최종 판정 일치율과 함께 축별 일치율, 사람이 실패로 본 답을 통과시킨 수, 사람이 통과로 본 답을 실패시킨 수, 미확정 수를 싣는다. 층화 표본의 일치율을 서비스 전체 정확도로 일반화하지 않는다.
- Judge가 틀린 것으로 확인된 사례(라벨 검토 D7)는 Judge 검증셋 v2에 넣는다.

## 8. 비교 실행

1. 평가 대상 커밋, 활성 채팅 처리 구현, 앱 설정(`appConfig`), 평가 DB, FAQ와 임베딩, 생성 모델, Judge 모델과 코드 버전을 기록한다.
2. 같은 평가셋과 DB로 기준 버전과 변경 버전을 각각 캡처한다. Judge만 바꿔 비교할 때는 같은 캡처를 다시 판정한다.
3. 먼저 심각한 회귀를 본다. 근거 밖 금액·혜택·기간·정책, 고객 조건의 임의 추가, 근거 없는 단정이 새로 생기면 평균이 올라도 통과시키지 않는다.
4. 그다음 묶음별 전후 변화와 질문별 승패를 신뢰구간과 함께 본다. 미채점과 `REVIEW` 증가도 함께 보인다. 사람 라벨을 확보하기 전에는 목표 수치를 실측 성능처럼 선언하지 않는다.

# 실제 채팅 파이프라인 답변 품질 평가 기준

2026-10-02. 이 문서는 **Spring 채팅 API로 질문을 보내 생성, 저장, 조회까지 끝난 결과**를 평가한다. 실행 도구는 [`run_chat_pipeline_eval.py`](../../scripts/chat_judge/experiments/v6_live_chat_pipeline/run_chat_pipeline_eval.py)이며 판정은 vLLM Qwen3-14B-AWQ의 동시 요청 8개로 수행한다. [500건 고정 검증셋](experiments/V3-fixed-500-case-validation/20261001-validation-v2-results.md)은 사람이 구성한 답변으로 Judge 자체를 시험한 자료다. 그 점수를 실제 서비스의 답변 품질이나 환각률로 사용하지 않는다. 실제 파이프라인 평가 입력과 실행 방법은 [README](README.md)에 있다.

## 1. 평가 단위와 정답 기록

기본 단위는 **사용자 질문 한 턴**이다. 멀티턴은 앞선 턴과 함께 하나의 대화 사례로 묶고, 결과 집계에서는 대화 수와 턴 수를 각각 표시한다. 복합 질문은 턴 안의 하위 질문마다 답변 가능 여부, 필요한 사실, 정답 FAQ 묶음을 별도로 기록한다.

실행 전에 사람이 다음을 확정하고 고정한다.

| 항목 | 기록할 값 |
| --- | --- |
| 입력 | 사용자 원문, 이전 대화, 확정된 상담 조건 |
| 기대 동작 | FAQ 답변, 부분 답변, 근거 부족 안내, 범위 밖 안내, 되묻기, 매장 조회 중 하나 |
| 하위 질문 | 각각의 요구사항과 필수 답변 사실. 금액, 기간, 대상, 조건, 예외를 분리 |
| 근거 | 하위 질문마다 인정할 대체 FAQ ID 묶음. 묶음 안은 OR, 하위 질문 묶음 사이는 AND |
| 답변 불가 이유 | 카탈로그에 답이 없는지, 현재 검색에서 놓친 것인지, 필요한 사용자 조건이 없는지 구분 |

`goldSourceGroups`는 `[[첫 질문의 대체 FAQ들], [둘째 질문의 대체 FAQ들]]`로 기록한다. 유사도가 높다는 이유만으로 대체 정답을 확정하지 않는다. 현재 동등 FAQ 목록은 후보를 모델로 선별한 것이며 전체 1,150건의 완전한 사람 검토 결과가 아니다. 평가 중 새 동등 FAQ가 발견되면 사람이 확인하고 **라벨 버전을 올린 뒤 두 비교 대상을 같은 라벨로 재채점**한다.

## 2. 한 턴의 판정 순서

| 단계 | 합격 기준 | 실패 기록 |
| --- | --- | --- |
| 실행과 저장 | 실행이 종료되고 최종 답변 1건이 저장된다. 조회 내용과 사용자가 받은 최종 SSE 내용이 같다 | 실행 실패, 중복 저장, 최종 응답 불일치 |
| 라우팅과 조건 | 현재 질문의 의도와 모든 하위 질문을 보존한다. 원문이나 확인된 이전 맥락에 없는 지역, 상품, 금액, 조건을 보태지 않는다 | 오분류, 하위 질문 누락, 정제 질문 의미 변경 |
| 검색 | 답변 가능한 각 하위 질문의 Top-K 결과에 정답 FAQ 묶음 중 하나가 있다. 검색 결과와 최종 답변에 **저장된 근거**를 각각 검사한다 | 후보 누락, 후보는 있으나 최종 근거 누락, 부적합 근거 사용 |
| 근거성 | 최종 답변의 **모든 사실 주장**이 실제 전달된 FAQ 답변 본문 또는 확인된 상담 조건으로 뒷받침된다 | 근거 밖 주장, 근거와 모순, 조건 확대 |
| 질문 충족 | 답할 수 있는 필수 사실과 하위 질문을 빠뜨리지 않는다. 답할 수 없는 부분은 그 부분만 명확히 보류한다 | 일부 누락, 전체 미답변, 과도한 답변 |
| 답변 불가 | 충분한 근거가 없으면 추측하지 않고 보류한다. 충분한 근거가 있는데 거절하면 과도한 거절이다 | 부당한 단정, 과도한 거절, 모호하여 사람 검토 |

검색의 **후보 적중**과 **저장 근거 적중**은 별개다. 현재 `judge_chat_flow.py`의 `retrievalCoverage`는 최종 답변에 저장된 근거를 바탕으로 계산한다. 따라서 이 값 하나를 Top-K 검색 Recall로 부르지 않는다. 후보 적중은 캡처의 `searches[].results`로 따로 계산한다. 정답 FAQ가 검색되지 않았으면 검색 단계의 실패이고, 검색됐지만 답변에 쓰이지 않았으면 선택 또는 생성 단계의 실패다.

근거 판정에서는 FAQ의 **질문 문구**를 정책 근거로 사용하지 않는다. 사용자 질문에 적힌 수치도 서비스 정책으로 확인된 사실이 아니다. 답변 주장과 FAQ 답변의 단어가 달라도 뜻, 대상, 조건, 부정, 금액, 기간, 예외가 같으면 지지됨으로 본다. 답변의 주장은 답변 원문에서 그대로 추출해 위치를 검증한 뒤 의미를 비교한다. 답변에 없는 문구를 추출한 경우는 `UNSCORED`다. 근거가 명백히 반대인 경우와 근거가 모자란 경우를 검토 기록에서 구분하고, 의미 관계가 애매하면 `REVIEW`로 둔다.

예: FAQ가 “미납 요금을 완납해야 명의 변경 가능”이고 답변이 “미납 요금이 있으면 모두 납부하셔야 명의 변경할 수 있습니다”라면 지지됨이다. “미납 요금이 있어도 명의 변경 가능”은 조건을 뒤집었으므로 실패다. “유심 재발급 비용 7,700원”이라는 FAQ로 “택배비도 7,700원에 포함”을 확정한 답변은 근거 부족이다.

## 3. 최종 답변 라벨

세 축을 따로 기록한다. 하나의 종합 점수로 합쳐 원인을 숨기지 않는다.

| 축 | 라벨과 의미 |
| --- | --- |
| 근거성 | `SUPPORTED`: 모든 사실 주장이 근거에 부합. `UNSUPPORTED`: 한 주장 이상에 명백한 근거 부족 또는 모순. `NOT_APPLICABLE`: 사실 주장 없는 안내. `REVIEW`: 판단 근거가 모호함. `UNSCORED`: 추출 또는 출력 검증 실패 |
| 충족도 | `COMPLETE`: 답변 가능한 필수 사실과 하위 질문을 모두 처리. `PARTIAL`: 일부만 처리. `MISSED`: 실질적인 답변 없음. `NOT_APPLICABLE`: 범위 밖 질문 등에서 내용 답변 자체가 기대되지 않음 |
| 답변 불가 | `APPROPRIATE`: 실제 근거 부족이나 범위 밖 질문을 적절히 보류. `OVER_REFUSAL`: 충분한 근거가 있는데 답변을 거절. `SHOULD_ABSTAIN`: 근거 없는 내용을 단정. `NOT_APPLICABLE`: 답변 불가 판단이 필요 없는 정상 답변. `REVIEW`: 근거 충분성 판단이 애매함 |

`PARTIAL_ANSWER`는 답할 수 있는 부분을 정확히 답하고 나머지를 보류해야 합격이다. 답할 수 있는 내용을 말했더라도 **근거 없는 사실이 하나라도 섞이면 근거성은 실패**다. 복합 질문에서 첫째 질문만 답하면 근거성이 `SUPPORTED`여도 충족도는 `PARTIAL`이다. 매장 조회가 기대된 질문에서 “매장 기능을 사용할 수 없다”는 안내는 서비스가 정직하게 상태를 알린 것이지만 요청 충족도는 `MISSED`다. 미연결 기능은 FAQ 답변 품질의 분모에 섞지 않고 별도 기능 결함으로 보고한다.

## 4. 보고할 지표와 분모

모든 지표는 전체, 유형별, 실패 단계별로 `분자/분모`를 함께 보고한다. `UNSCORED`와 `REVIEW`를 성공으로 넣거나 조용히 제외하지 않는다.

| 지표 | 계산 |
| --- | --- |
| 정상 완료율 | 정상 완료 및 저장된 턴 / 실행한 전체 턴 |
| 라우팅 적중률 | 의도와 하위 질문이 모두 맞은 턴 / 라우팅 기대 라벨이 있는 턴 |
| 후보 검색 적중률 | Top-K에 인정 FAQ가 있는 답변 가능 하위 질문 / 답변 가능 하위 질문 |
| 저장 근거 적중률 | 최종 답변에 저장된 근거가 인정 FAQ를 포함한 하위 질문 / 답변 가능 하위 질문 |
| 답변 단위 근거 통과율 | 사실 주장이 모두 지지되는 채점 가능 답변 / 채점 가능하고 사실 주장이 있는 답변 |
| 근거 없는 답변 발생률 | 근거 밖 주장 또는 근거와 모순이 한 건 이상인 답변 / 유효한 근거성 판정을 받은 사실 답변. 자동 Judge 판정과 사람 확정 값을 구분 |
| 주장 단위 근거 부족률 | 근거가 없는 사실 주장 / `SUPPORTED` 또는 `UNSUPPORTED`로 판정된 사실 주장 |
| 답변 품질 통과율 | 정상 실행, 질문 충족, 근거성, 보류 적절성이 모두 합격인 턴 / 품질이 확정된 턴. 실행 실패는 실패로 포함하고 미확정 턴을 포함한 전체 분모의 최저 및 최고 범위를 함께 제시 |
| 완전 답변율 | 모든 필수 사실과 하위 질문을 처리한 답변 / 답변 가능한 턴 |
| 부당한 단정률 | `SHOULD_ABSTAIN`인 턴 / 답변 불가 판단 대상 턴 |
| 과도한 거절률 | `OVER_REFUSAL`인 턴 / 답변 가능한 턴 |
| Judge 채점률 | 세 축의 출력 검증을 모두 통과한 턴 / Judge에 넣은 턴 |
| 종단 성공률 | 실행, 라우팅, 검색 또는 적절한 보류, 근거성, 충족도, 저장과 최종 SSE 일치가 모두 합격인 턴 / 해당 기능의 평가 대상 턴 |

검색 결과가 있는데 답을 만들지 못한 사례와 애초에 정답이 카탈로그에 없는 사례를 분리한다. 응답 시간은 전체 턴의 중앙값 및 P95, 생성 호출 시간, Judge 시간으로 나눈다. 모델 실패와 시간 초과, 재시도, 취소도 별도 건수로 적는다. 같은 질문을 여러 번 실행했다면 독립 질문 수와 반복 실행 수를 구별한다.

현재 캡처에는 `route`, `searches`, `ragInputs`, `generatorCallRecords`, `executionStatus`, `outputMessage`, `savedSources`, `durationMs`가 있다. **근거성은 `ragInputs`에 포착한 실제 RAG 입력을 사용한다.** 저장 근거가 누락됐다고 생성에 없었던 근거로 판단하거나 검색 후보 전체를 자동으로 생성 근거라고 간주하지 않는다. 최종 SSE 내용은 이 캡처의 점수에 포함하지 않는다. 따라서 자동 품질 통과율을 위 표의 종단 성공률이라고 부르지 않는다.

## 5. Judge 신뢰도와 사람 판정

Qwen의 자동 점수는 실행 직후 계산한다. 이를 사람 확정 점수라고 표시하지 않는다. Judge에는 라우팅 정답, `requiredFacts`, 기대 행동, 정답 FAQ ID를 근거성 또는 답변 불가 판정의 힌트로 주지 않는다. 질문 충족도 요청에만 질문별 정답 FAQ 본문과 큐레이션된 `requiredFacts`를 전달해 정책상 정확한 답인지 판단한다. 원문 답변, 실제 RAG 입력, 저장 근거, 프롬프트, 원시 응답과 검증 실패 사유를 보존한다.

먼저 답변 생성 전에는 결과를 모르는 사람이 신규 대화 사례를 고정한다. 여러 표현의 같은 의미, 조건과 부정, 유사하지만 답이 없는 FAQ, 과도한 거절, 후속 질문, FAQ 복합 질문, 매장 질문을 포함한다. 기존 9건은 회귀 사례로 유지하고 신규 사례와 분리한다. [눈가림 40건 검토](experiments/V5-grounding-two-stage/20261002-grounding-human-review-method.md)는 완료됐고, 전체 판정 40건이 일치했다. 층화 표본이므로 [비교 보고서](experiments/V5-grounding-two-stage/20261005-grounding-human-judge-comparison.md)의 범위와 한계를 함께 보고, 실제 서비스 품질로 일반화하지 않는다. 신규 사례는 답변과 실제 근거만 보고 사람이 먼저 세 축을 판정하고, 의견이 다른 사례를 합의한 후 Judge 결과를 공개한다.

Judge 검증 보고에는 전체 일치율 외에 축별 일치율, `UNSUPPORTED`를 놓친 건수, 과도한 거절 오판, 답변에 없는 claim 추출 비율, 미채점 비율과 유형별 혼동표를 싣는다. `NAME_CHANGE-0038`과 `USIM-0011`처럼 **원문 claim 추출 오류**는 FAQ와 표현이 다른 정상적인 답변과 구분한다. 과거 500건의 채점 가능 465건 또는 35건 재시도 중 통과 34건은 출력 검증 결과이며 사람 판정과의 일치율이 아니다.

## 6. 비교 실행과 통과 판단

1. 평가 대상 브랜치와 활성 `ChatProcessingPort`, 기능 플래그, DB 스냅샷, FAQ 및 임베딩 버전, 모델 digest, 프롬프트, 검색 설정, Judge 버전을 기록한다. 현재 코드에는 조건부 파이프라인이 여러 개 있으므로 실제 실행된 구현체를 반드시 기록한다.
2. 동일한 고정 대화와 DB로 기준 버전과 변경 버전을 각각 Spring 채팅 API에서 실행한다. 생성 답변과 저장 근거를 그대로 보존하고, Judge 변경 비교를 할 때는 **같은 생성 기록**을 재사용한다.
3. 먼저 필수 사례에서 심각한 회귀를 본다. 근거 밖 금액, 혜택, 기간, 정책, 사용자 조건의 임의 추가, 근거가 없는데 단정, 최종 SSE와 저장 답변 불일치가 새로 생기면 평균 점수가 높아도 통과시키지 않는다.
4. 그다음 단계별 지표의 전후 변화와 질문별 승패를 보고, 사람 검토가 끝난 사례만 품질 결론에 사용한다. 미채점이나 `REVIEW` 비율 증가를 함께 보여 준다. 첫 실제 채팅 기준선과 독립 사람 라벨을 확보하기 전에는 95% 같은 수치 목표를 실측 성능처럼 선언하지 않는다.

근거성의 애매한 관계는 `REVIEW`로 기록하도록 프롬프트, JSON Schema와 코드 검증을 맞췄다. 새로운 실제 채팅 결과는 과거 합성 답변 실험 파일을 갱신하지 않고 별도 보고서로 저장한다. 정답에 없는 사실을 추정하는 모델의 오류 가능성 때문에 사람이 확인하지 않은 자동 수치는 항상 Judge 추정치로 표시한다.

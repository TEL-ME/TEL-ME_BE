# 실제 채팅 파이프라인 509개 질문 평가

2026-10-02. **실제 Spring 채팅 API에서 EXAONE 답변을 생성하고 저장한 뒤 vLLM Qwen3-14B-AWQ로 채점 완료했다.** 기존에 사람이 작성한 답변 500건의 Judge 검증 결과와 구분한다. 이 문서의 수치는 고정 평가 질문에서의 자동 Judge 추정값이며 실제 이용자 전체의 환각률이나 사람 확정 점수는 아니다.

품질 통과는 정상 실행, 질문에 대한 정확하고 충분한 답변 또는 적절한 보류, 근거성을 모두 만족해야 한다. 실행 실패 15개는 품질 실패로 포함한다. 미채점 16개와 검토 필요 7개는 품질을 확정하지 않고 범위로 표시한다.

근거 없는 답변 발생률은 **유효한 근거 판정이 있는 사실 답변**을 분모로 사용한다. 사실 주장 없는 거절 답변을 넣어 수치를 낮추지 않는다. 전체 509개 질문 중 근거 없는 답변이 확인된 비율은 별도로 113/509, 22.20%다. 이 두 비율의 분모는 다르다. 모든 자동 판정의 세부 근거는 원시 자료와 검토 문서에 있다.

## 어떤 흐름을 실행했나

- 고정 코드: `7ffece3b79cfbedf863257fa74a9a55a8d4d45cf`. 처음 실험한 기준 코드를 유지했으며 최신 develop을 섞지 않았다.
- 실제 활성 처리기: `com.telme.consult.service.ConsultChatProcessingService`.
- 생성: Ollama 0.34.0의 `exaone3.5:7.8b`. 모델 digest는 원시 캡처에 기록했다.
- 평가 DB: 개발 DB와 분리된 `telme_judge_eval`, FAQ 1,152개 및 임베딩 1,152개.
- 카탈로그 정답 기준: `faq_full_1150.json`의 1,150개 FAQ. `slotId`가 비어 있는 DB 결과는 질문과 답변 본문이 모두 완전히 일치할 때만 ID를 보충했다.
- 입력: 기존 500개 질문에 8개 회귀 대화를 더한 508개 대화, 509개 질문. 기존 합성 답변과 Judge 기대 판정은 생성 입력에서 제거했다.
- API 경로: 게스트 세션 생성, 메시지 전송, 실제 비동기 상담 처리 및 검색, EXAONE 생성, 실행 상태 확인, 저장된 대화 이력과 근거 조회.

Spring MockMvc에서 실제 컨트롤러와 서비스, PostgreSQL 및 Ollama를 호출했다. 브라우저와 공개 HTTP 포트의 통합 테스트는 아니며 최종 SSE 전송 내용의 일치 여부는 이번 점수에 포함하지 않는다. 공개 API와 DB 마이그레이션은 변경하지 않았다.

## 무엇과 비교해서 채점했나

| 판정 | 모델에 전달한 자료 | 정답 정보 전달 여부 |
| --- | --- | --- |
| 주장 추출 | 저장된 답변 원문만 | 질문, FAQ, 정답 라벨 모두 제외 |
| 근거성 | 검증된 답변 인용 구간과 실제 RAG 입력의 FAQ 답변, 확정 조건 | 정답 라벨 제외 |
| 질문 충족도 및 정확성 | 실제 질문과 답변, 해당 질문의 정답 FAQ | 충족도 비교에만 정답 FAQ 사용 |
| 답변 불가 판단 | 질문과 답변, 실제 RAG 입력의 FAQ | 정답 라벨 제외 |

의미가 같은 표현을 허용하며 조건, 부정, 대상, 금액, 기간 및 예외가 바뀌면 실패다. 코드의 문자열 검사는 인용 출처를 검증한다. 답변과 FAQ가 같은 문장이어야 한다는 검사가 아니다. 검색은 됐으나 실제로 생성에 전달되지 않은 FAQ를 근거로 인정하지 않는다.

복합 질문의 정답은 하위 질문별 대체 FAQ 묶음을 유지한다. 한 묶음 안에서는 하나만 맞으면 되고 모든 하위 질문 묶음이 충족돼야 전체 검색 성공이다. 질문 충족도 역시 하위 질문마다 판정한다.

## 실패 단계별 관찰

| 관찰 | 전체 509개 질문 |
| --- | --- |
| 근거 없는 주장 포함 답변 | 113 |
| 충족도 판정에서 불완전하거나 미답인 답변 | 111 |
| 정답 근거를 놓친 질문 | 99 |
| 기대 intent와 다른 라우팅 | 39 |
| 충분한 근거가 있는데 거절 | 12 |
| 실제 실행 실패 | 15 |
| 매장 조회 미연결 회귀 사례 | 1 |

각 항목은 서로 중복될 수 있다. 라우팅의 기대 intent는 평가 입력에서 정한 진단 기준이며 별도로 사람이 검증한 라우팅 전용 정답셋의 정확도로 표현하지 않는다.

하위 질문 기준 정답 근거 적중은 검색 후보 **384/507, 75.74%**, 실제 RAG 입력 **384/507, 75.74%**, 저장된 근거 **369/507, 72.78%**다. 507은 답변 가능한 정답 묶음의 수이며 질문 수 509와 다르다. 복합 질문 하나가 여러 묶음을 갖는다. 99개 질문에서 총 123개 정답 묶음을 놓쳤다.

실행 실패 15개 중 13개는 `LLM502-1`이며 생성 기록에 근거 없는 금액 또는 수치가 남아 있다. 2개는 `LLM502-2` 스트림 중단 코드다. 단순히 전부 모델 연결 장애로 묶지 않았다. 최종 답변이 없는 이 질문들은 사실 답변의 근거 부족률에 넣지 않고 서비스 처리 실패로 기록했다.

## 미채점과 검토 필요는 무엇인가

실행 완료 494개 질문에 각각 근거성, 충족도, 답변 불가 판정의 **1,482개 평가 작업**을 모두 실행했다. 근거성 작업은 주장 추출과 의미 판정의 두 모델 호출로 구성된다. 질문을 1,482개로 늘린 것은 아니다.

유효한 판정은 근거성 479개, 충족도 493개, 답변 불가 494개다. 출력 검증 실패는 다음 16개 질문이며 다른 축의 정상 판정은 유지했다.

- 주장 추출 원문 또는 순서 불일치: 12개
- 전체 근거성 판정과 개별 주장 판정의 모순: 3개
- 답했다고 판정했지만 답변 인용이 없는 충족도 결과: 1개

7개의 검토 필요 판정에는 근거 관계가 모호한 1개와 충족도상 사실을 답했는데 주장 추출이 비어 있는 6개의 축 간 불일치가 포함된다. 모두 정상 판정으로 강제 변환하지 않았다. **미채점 31개**라는 원시 집계에는 실행 실패 15개도 포함되므로 Judge 오류 16개와 혼동하지 않는다.

Qwen의 자동 판정 자체도 오판할 수 있다. 예를 들어 같은 의미의 조건 표현을 지나치게 엄격하게 읽거나 일반적인 안내를 정책 주장으로 볼 수 있다. 이런 가능성을 포함해 답변과 FAQ를 직접 대조할 수 있도록 검토 문서에 실제 원문과 Judge 이유를 남겼다. 이전의 40개 블라인드 검토는 아직 사람 판정이 없어 이번 Judge의 정확도 근거로 사용하지 않았다.

## 실행 환경 및 검증

Judge는 **vLLM 0.29.0, Qwen/Qwen3-14B-AWQ, 동시 작업 8개**다. temperature 0, thinking 비활성화, 최대 출력 2048토큰, 최대 문맥 4096을 사용했다. GPU는 RTX 5070 Ti 16GB이며 이전 Windows/WSL 호환 패치를 유지했다.

초기 자동 KV 캐시 예약 환경에서 지연이 발생해 일부 결과를 보존하고 재개했다. 예약률 0.80 시도는 시작에 실패했고 최종 환경은 FP16 KV 캐시 2GiB를 명시했다. 초기 환경의 557개 완료 작업과 재개 후 작업을 구분할 수 있도록 기록했으며 기존 결과를 덮어쓰지 않았다. 모델 가중치와 프롬프트 및 판정 기준은 같지만 이 실행을 하나의 독립적인 속도 벤치마크로 해석하지 않는다.

파이프라인 처리 시간은 P50 1,315ms, P95 2,328ms였다. 질문을 순차 전송한 이 실험의 값이며 동시 사용자 부하 성능은 아니다. 마지막 Judge 재개 구간은 764.781초였으며 앞선 실행, 중단 및 모델 준비 시간을 제외한 값이다.

실행 도중 메인 워크트리가 develop으로 전환되고 GitHub Desktop이 평가 작업을 stash로 보관했다. 고정 커밋의 별도 워크트리에 복원해 마무리했고 운영 코드의 해시가 캡처와 일치함을 확인했다. 이후 메인 워크트리가 원래 평가 브랜치로 돌아온 것을 확인해 이번 변경과 결과 파일을 `D:\finalproject\TEL-ME_BE`의 `feat/TELME-100-llm-judge-evaluation-system`으로 옮겼다. 원격 작업이나 커밋은 하지 않았다.

검증은 실제 PostgreSQL 및 EXAONE API 수집 테스트 1회로 509개 질문 전체를 실행했고, 평가 도구 Python 테스트 62개 및 `compileTestJava`를 통과했다. 재개 시 실패 기록 보존, 입력 변경 거부, 축별 실패 격리, 분모 및 누락 집계, 인용 출처와 병렬 호출을 확인했다.

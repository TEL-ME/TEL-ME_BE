# 멀티턴 문맥과 상담 요약

TELME-121은 고객 원문과 최신 조건으로 후속 질문의 대상을 찾는다. 요약은 필요한 원문 발언을 선택해 보존하고, 정책 답변은 이번에 검색한 FAQ에서 확인한다.

## 동작 기준

| 상황 | 처리 |
| --- | --- |
| “그건 얼마야?”, “그럼 신청 방법은?” | 관련 고객 발언 ID를 선택하고 현재 요구만 담은 검색 질문으로 복원 |
| 구체적인 새 주제 | 이전 문맥을 제외하고 현재 질문으로 처리 |
| “이전에 신청한 로밍 요금제를 해지하려면?” | 시간 표현이 있어도 대상이 명시된 독립 질문으로 처리 |
| 대상이 없거나 여러 대상 중 하나를 고를 수 없음 | 임의로 추측하지 않고 확인 안내 |
| 되묻기에 대한 조건 응답 | 기존 상담 질문과 확정 조건 사용 |
| 되묻기 대기 중 새 질문 | 문맥 복원 후 한 번 재라우팅. 기존 대기 상담 상태 유지 |
| 출처 없는 자유문장 요약 | 라우팅, 조건 검증과 RAG에서 제외. 최근 원문을 다시 조회 |
| 이전 AI 답변 | 새 정책 근거로 사용하지 않음 |
| 요약의 원문 변조, 다른 세션의 ID 또는 미래 발언 | 사용 차단 |

고객 원문은 그대로 저장한다. 공개 API, DB 스키마와 application.yml은 변경하지 않는다.

## 문맥과 요약 처리

### 후속 질문

1. ChatContextBuilder가 실행과 세션의 연결을 확인하고 완료된 대화를 예산 내에서 조회한다. 요약 출처는 DB의 원문, 화자와 순서에 대조한다.
2. ChatQuestionResolver가 관련 고객 발언 ID만 선택한다. 선택하지 않은 주제와 순수 인사 및 감사는 전달하지 않는다.
3. 라우터는 이전 발언을 대상 확인에만 쓰고 **현재 질문만 분류하고 분해**한다. 이전 질문의 답변 요구를 다시 추가하지 않는다.
4. 조건 검증을 거친 검색 질문으로 FAQ를 찾고, RAG와 Guard를 거친 최종 답변을 저장하고 전송한다. 원문, 복원 출처, 검색과 생성 입력은 실행 trace에 기록한다.

예: “로밍 요금제는 어떻게 골라요?” → “그럼 신청 방법은?”이면 **로밍 요금제 신청 방법 한 건**을 검색한다. 이전 선택 방법을 다시 답변하지 않는다.

“그때 요금은?”, “이전에 물어본 건?”처럼 대상이 빠진 질문은 출처가 없으면 확인 안내 대상이다. 시간 표현과 로밍, 유심, LTE 등 명확한 업무 대상이 함께 있고 과거 발언을 지칭하지 않으면 코드가 독립 질문으로 처리한다. 나머지 시간 표현은 모델이 대상을 판단하며, 잘못된 출력은 확인 안내로 처리한다. 정상 되묻기 응답에는 기존 상담 질문과 확정 조건을 사용하며, 다른 주제의 대화를 추가하지 않는다.

문맥 판정은 `chat.question-resolution.mode`로 선택한다. 기본값 `REGEX_GATED`는 정규식으로 LLM 호출 대상을 선별하는 기존 방식이다. `LLM_ALL`은 새 질문을 모두 LLM에 보내 독립 질문, 이전 대화 의존 질문, 확인이 필요한 질문으로 분류한다. 실행 환경에서 `CHAT_QUESTION_RESOLUTION_MODE=LLM_ALL`로 전환할 수 있으며 `application.yml`은 수정하지 않는다. 한 요청에는 선택한 방식만 실행하고 사용한 모드는 실행 trace의 `questionResolutionMode`에 남긴다. 두 방식 모두 모델이 고른 이전 고객 발언 ID를 검사하고, 잘못된 판정은 확인 안내로 처리한다. `LLM_ALL`의 Ollama 요청은 전용 JSON Schema를 사용하며 Qwen3나 EXAONE 4.0 모델일 때 이 요청의 사고 모드를 끈다.

문맥 복원 LLM 호출은 `CONTEXT_RESOLUTION`으로 기록해 의도 분류의 `ROUTING`과 호출 횟수, 처리 시간, 토큰 사용량을 구분한다. 관리자 LLM 오류 조회에서도 해당 유형으로 필터링할 수 있다. 과거 `ROUTING` 기록은 유지한다.

### 상담 요약

완료된 답변 뒤 ChatSummaryService가 요약할 원문을 준비한다. 모델은 보존할 messageIds만 반환하고 코드가 해당 원문을 저장한다.

- ID의 존재와 중복을 검사하고, 선택한 상담사 답변에는 연결된 고객 질문을 함께 보존한다.
- 기존 선택 원문과 새 원문을 함께 제공해 최신 정정, 부정과 상담 대상을 유지한다.
- chat_sessions.summary에 telme-summary-v1 JSON을 저장한다. 발언별 ID, 순번, 화자, 유형, 본문과 매장 결과를 포함한다.
- 요약과 summary_through_sequence_no를 조건부 갱신으로 함께 저장한다. 검증 실패 시 커서를 이동하지 않으며 늦은 작업이 최신 요약을 덮어쓰지 못한다.
- 고객 발언은 상담 상황이며 검증된 정책 사실이 아니다. 자유문장 요약과 legacySummary는 DB에 유지하지만 모델 입력에서 제외한다.

### 예산을 넘는 대화

| 초과 상황 | 처리 |
| --- | --- |
| 질문과 답변의 합계만 초과 | 배치를 나눠 순차 요약 |
| 상담사 답변만 너무 김 | 고객 질문과 필요한 앞선 대상을 보존 |
| 고객 질문 자체가 단독 입력 예산보다 큼 | 해당 질문과 답변을 기억에서 제외하고 커서 진행. 오래된 조건도 초기화 |
| 저장할 원문이 너무 많음 | 최신 발언부터 원문 전체와 의존 관계를 함께 보존 |
| 사용할 요약이 없음 | 요약 커서 앞까지 최근 원문을 다시 조회 |

원문을 문장 중간에서 자르지 않는다. 기억에서 제외한 범위와 이유는 WARN 로그로 남기며 DB 원문은 유지한다. **요약 커서는 처리 범위의 끝이며 모든 발언의 보존을 뜻하지 않는다.**

논문의 학습 방법 전체를 구현하거나 한국어 EXAONE에서 동일한 효과를 보장한다는 뜻은 아니다. 문구 보존과 답변 정확도는 별도로 평가한다.

## 검증 결과

### V1: 요약 원문 보존

Spring의 실제 LLM 클라이언트로 EXAONE 3.5 7.8B를 호출했다. temperature 0, 컨텍스트 8192, 출력 한도 512로 동일 입력을 비교했다.

| 구성 | 저장 검증 통과 | 지정 문구 모두 보존 | 추정 기억 토큰 중앙값 | 사례 시간 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| develop 자유문장 요약 | 60/60 | 19/60 | 78.5 | 447.5ms |
| 보존 규칙을 추가한 자유문장 요약 | 60/60 | 28/60 | 99 | 599.5ms |
| 원문 선택과 코드 검증 | 60/60 | 60/60 | 96 | 173ms |

60개 평가 행은 6개 유형의 변형과 반복이며 중복 제외 원본 대화는 24개다. 개발셋과 검증셋은 같은 유형을 공유하고, 6개 사례는 재요약 3회도 포함한다. **문구 보존 결과이며 의미 정확도나 환각률이 아니다.** 동의어 표현은 문구 검사에서 실패할 수 있다. 시간은 로컬 순차 실행의 사례 시간이며 서비스 P95가 아니다.

### V2: 요약 전후의 실제 채팅

독립 평가 DB의 FAQ 1150개와 기존 임베딩, PostgreSQL, EXAONE, bge-m3와 실제 Spring 채팅 파이프라인을 사용했다.

- 유심, 로밍, 명의변경과 해지의 요약 전후 후속 질문 8건: 실행 완료와 대상 복원 및 정답 FAQ 검색 8건.
- 경계 사례 3건: 여러 대상의 모호함은 확인 안내, 명확한 새 주제는 전환, “비용은?”은 기존 대상으로 복원.

### V3: 생략형과 주제 경계

같은 실제 Spring 채팅 경로에서 7개 유형을 반복 포함 10회 실행했다. 문맥 연결과 검색 경로 검증은 **10/10 통과**했다.

| 입력 상황 | 횟수 | 검증 결과 |
| --- | ---: | --- |
| 로밍 상담 → “그럼 신청 방법은?” | 3 | 신청 방법만 한 번 검색 |
| 명의변경 상담 → “필요한 서류는?” | 1 | 명의변경 서류 검색 |
| 유심 상담 → “기간은 얼마나 걸려?” | 1 | 유심 재발급 기간으로 복원. 검색 근거가 없어 안내 |
| 로밍 상담 → 독립적인 미성년자 가입 질문 | 2 | 로밍 문맥 제외, 신규 가입 조건으로 답변 |
| 유심 상담 → 독립적인 해지 질문 | 1 | 유심 문맥 제외, 해지 질문 검색 |
| 매장 되묻기 대기 중 로밍 후속 질문 | 1 | 문맥 복원 후 로밍 신청 검색, 매장 대기 상태 유지 |
| 자유문장 요약에 강남역과 39000원이 있음 | 1 | 미검증 조건 제외, 원래 유심 발언 복구 |

통과 기준은 대상 복원, 주제 격리, 검색과 실행 상태다. 최종 답변 정확도 점수로 사용하지 않는다.

### V4: 시간 표현과 실제 참조 구분

실제 Spring과 EXAONE에서 시간 표현이 있는 독립 질문 4건, 대상이 빠진 질문 2건, 기존 대상으로 복원하는 질문 1건을 실행해 **7/7 통과**했다. 같은 실행에서 V3의 문맥 연결 회귀 사례도 **10/10 통과**했다. 독립 질문은 불필요한 확인 없이 FAQ 검색으로 진행하며, 검색 근거가 없는 질문은 답변 불가로 안내한다.

### 자동 테스트

독립 PostgreSQL DB에서 clean test build --build-cache 실행: **전체 1961건, 통과 1853건, 조건부 제외 108건, 실패와 오류 0건**. 실제 모델 실행은 별도 검증이다.

테스트는 원문과 정정 보존, 출처와 실행 무결성, 요약 및 커서의 원자적 저장, 장문 예산 처리, 주제 격리, 되묻기 중 재라우팅과 과거 지시어를 포함한다.

## 설정과 한계

| 설정 | 기본값 |
| --- | --- |
| chat.summary.grounded-output | true |
| 요약 시작 | 16개 메시지 또는 추정 2048토큰 |
| 요약 뒤 최근 이력 | 8개 메시지, 추정 1024토큰 |
| 요약 입력 / 출력 | 추정 3072 / 512토큰 |
| 기억 저장 | 최대 16개 발언, 추정 512토큰 |
| 상담 분석 Context | 추정 1024토큰 |
| RAG 이력 예산 | 모델 창에서 시스템, FAQ, 질문, 출력 1024와 여유 256을 제외한 범위 |

토큰 수는 추정치이며 기본값의 최적성을 주장하지 않는다.

- 원문 선택 모델의 누락과 잘못된 대상 연결은 가능하다. 예산 때문에 제외한 아주 오래된 정보를 DB 전체에서 다시 검색하는 기능은 없다.
- 이전 AI 답변에서만 찾을 수 있는 “두 번째 상품”, 표의 항목 등은 복원 대상에 포함하지 않는다.
- 최종 답변의 내용 누락과 숫자의 관계 해석은 남아 있다. V3 로밍 신청 4건은 홈페이지와 고객센터 경로를 누락했다. V2에서는 명의변경의 인감증명서 누락, 일 요금을 추가 금액처럼 표현한 사례가 있었다. 문맥 복원 성공과 답변 정확도를 구분해야 한다.

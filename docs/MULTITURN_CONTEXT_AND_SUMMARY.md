# 멀티턴 문맥과 상담 요약 개선

TELME-121은 이전 대화의 **원문, 화자, 순서**를 보존해 후속 질문을 이해하고, 정책 답변은 이번에 검색한 FAQ에서 다시 확인하도록 연결한다. 상담 요약은 모델이 새 문장을 쓰는 방식에서 **다음 상담에 필요한 원문 발언을 선택하는 방식**으로 바꾼다.

## 무엇을 고쳤나

| 기존 문제 | 적용한 처리 |
| --- | --- |
| 요약 문장이 부정, 명의자, 미완료 상태를 바꿀 수 있음 | 모델은 발언 ID만 선택하고 코드가 해당 원문을 저장 |
| 이전 요약을 다시 요약하면서 상담 주제나 정정 내용이 사라짐 | 이전에 선택한 원문과 새 원문을 함께 선택 후보로 사용 |
| “지역은 바꿀게요”, “그 비용”만 남겨 원래 대상을 잃음 | 생략된 대상을 가진 선택 발언에는 앞선 고객 원문도 함께 보존 |
| “그건 얼마야?”를 그대로 검색해 다른 FAQ가 먼저 검색됨 | 고객 원문 ID를 선택해 현재 질문과 함께 검색 입력으로 전달 |
| 이전 잘못된 AI 답변이 새 답변의 정책 근거처럼 사용될 수 있음 | RAG에 이전 AI 답변 본문을 넣지 않고 이번 FAQ 답변만 정책 근거로 사용 |
| 요약을 예산 때문에 제외해도 커서 앞 원문을 조회하지 않음 | 요약을 사용할 수 없으면 커서 제한을 풀어 최근 원문을 다시 조회 |

공개 채팅 API와 DB 스키마는 그대로다. `application.yml`도 수정하지 않는다. 변경은 내부 Context, 상담 어댑터, 검색 입력, RAG 입력과 요약 저장 방식에 적용한다.

## 실제 처리 흐름

### 후속 질문

1. `ChatContextBuilder`가 실행, 세션, 현재 입력 메시지의 관계를 확인한다. 완료된 질문과 답변을 짝으로 읽고 예산 내에서 최근 대화를 구성한다.
2. 새 요약의 발언 ID, 본문, 화자, 순서를 DB 원문과 대조한다. 다른 세션, 현재 질문 이후 발언, 변조된 본문은 사용하지 않는다.
3. `ChatQuestionResolver`가 지시어 또는 생략된 대상이 있는 질문에서 관련 **고객 발언의 ID만** 선택한다. 순수 인사와 감사는 후보에서 제외한다.
4. 고객 원문과 현재 질문을 구분해 `resolvedQuery`를 만든다. 현재 질문을 모델이 자유롭게 재작성하거나 새 지역, 상품, 금액을 추가하지 않는다.
5. 문맥을 연결한 질문으로 검색하고 원문, 검색 질문, 검색 근거, RAG 입력을 실행 trace에 남긴다.
6. RAG가 이번 FAQ와 고객 문맥으로 답변한다. 기존 Guard를 통과한 최종 답변을 기존 저장과 전송 경로로 전달한다.

예를 들어 고객이 “유심 재발급 비용이 얼마예요?”라고 말한 뒤 “그건 비용이 얼마야?”라고 하면, DB에는 두 번째 질문을 그대로 저장하고 검색 입력은 다음처럼 구성한다.

```text
[대상을 확인할 이전 고객 발언]
유심 재발급 비용이 얼마예요?
[현재 후속 질문]
그건 비용이 얼마야?
```

대상이 없는 질문, 잘못된 선택 결과, 선택 호출 실패는 확인 안내로 처리한다. 여러 대상 중 하나를 정할 수 없는 경우도 확인 안내 대상이다. 명확한 새 주제는 추가 선택 호출 없이 기존 원문 경로를 사용한다. 진행 중인 되묻기 상담은 기존 조건 확정 로직을 유지한다.

### 상담 요약

`ChatSummaryService`가 기존과 같이 완료된 답변의 후속 작업으로 실행된다. 예전 요약이 선택한 발언과 새로 요약할 발언을 모델에 제공하고 다음처럼 보존할 ID를 받는다.

```json
{"messageIds": [101, 105]}
```

코드는 ID가 실제 후보에 있는지, 중복이 없는지 검사한다. 선택한 상담사 답변에는 연결된 고객 질문도 보존한다. 모델이 만든 설명 문장, 가격, 변경 완료 여부를 요약 사실로 저장하지 않는다. 유효한 원문 선택이 저장 예산을 넘으면 최신 발언부터 원문 전체를 보존하며, 연결된 질문이나 생략된 상담 대상이 없는 발언만 남기지 않는다.

기존 `chat_sessions.summary` TEXT에 `telme-summary-v1` 형식의 JSON을 저장한다. 각 발언에는 `messageId`, `sequenceNo`, `role`, `messageType`, `content`, `storeResults`가 있다. **고객이 말한 내용과 검증된 정책은 별개**이며, 고객 원문을 보존했다고 그 주장을 정책 사실로 인정하는 것은 아니다.

요약 본문과 `summary_through_sequence_no`는 기존 조건부 갱신으로 함께 저장한다. 출력 형식이나 ID 검증이 실패하면 커서를 옮기지 않는다. 늦게 끝난 작업이 더 최신 요약을 덮어쓰는 것도 기존 커서 비교로 막는다. 순수 인사만 있는 구간은 새 사실을 만들거나 모델을 호출하지 않고 빈 기억으로 처리한다.

### 장문으로 인한 반복 실패 방지

입력 예산은 시스템 프롬프트와 실제 발언 표시 형식을 포함해 계산한다. 개별 질문과 답변이 예산 안에 들어가지만 합계만 넘으면, 현재 배치를 저장하고 나머지는 다음 요약에서 처리한다.

- 상담사 답변만 너무 길면 답변을 제외하고 고객 질문의 원문 전체를 유지한다. 이전 상담 대상도 입력 예산 내에서 함께 유지한다.
- 고객 질문 자체가 단독 입력 예산보다 길면 해당 질문과 답변을 기억에서 제외하고 처리 커서를 진행시킨다. 생략된 질문이 정정일 수 있어 그보다 오래된 기억도 비운 뒤 이후 구간을 처리한다. 제외 범위와 이유는 WARN 로그에 기록하며 DB의 메시지 원문은 삭제하지 않는다.
- 모델이 너무 많은 발언을 선택하면 최신 발언부터 저장 예산 안에 맞춘다. 긴 상담사 답변은 고객 질문으로 대체할 수 있지만, 고객 원문을 문장 중간에서 자르지는 않는다. 최신 정정이나 그 상담 대상이 함께 들어가지 않으면 더 오래된 선택도 중단해 옛 조건만 복원되는 것을 피한다.
- 남길 원문이 없으면 빈 기억과 커서를 함께 저장하며, 빈 대화에 대한 모델 호출은 생략한다. 형식 오류, 존재하지 않는 ID, 중복 ID는 이 처리로 우회하지 않는다.

따라서 `summary_through_sequence_no`는 처리한 범위의 끝이며, 그 이전의 모든 발언을 기억에 보존했다는 의미는 아니다. 예산에 들어가지 않는 정보의 손실을 로그로 드러내면서 이후 요약이 같은 장문에서 계속 막히는 것을 방지하는 절충이다.

기존 일반 문장 요약은 삭제하지 않고 미검증 이전 요약으로 구분해 유지한다. 출처가 확인되지 않은 일반 요약은 RAG의 정책 입력으로 전달하지 않는다.

## 검증 결과

### 요약 방식 비교

같은 EXAONE 3.5 7.8B, temperature 0, 컨텍스트 8192, 출력 한도 512로 비교했다. Python은 입력 생성과 집계에만 사용했다. **모델 호출은 Spring 평가 테스트의 실제 LLM 클라이언트**를 사용했다.

입력은 정정, 부정과 미완료 상태, 대상 분리, 미해결 질문, 이전 잘못된 안내, 주제 전환의 6개 유형이다. 60개 평가 행 중 중복을 제외한 원본 대화는 **24개**다. `development`와 `validation`은 같은 유형을 공유하므로 독립 블라인드 검증셋으로 해석하지 않는다. 6개 사례는 세 번의 재요약도 포함했다.

| 구성 | 저장 검증 통과 | 지정 문구 모두 보존 | 기억의 추정 토큰 중앙값 | 사례 처리 시간 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| develop 원래 자유 문장 요약 | 60/60 | 19/60 | 78.5 | 447.5ms |
| 보존 규칙을 추가한 자유 문장 요약 | 60/60 | 28/60 | 99 | 599.5ms |
| 적용안: 원문 선택과 코드 검증 | 60/60 | 60/60 | 96 | 173ms |

적용안은 지정한 필수 원문 ID도 60/60 사례에서 보존했다. **문구가 동일하게 남았는지 확인한 결과이지 의미 평가나 환각률 수치가 아니다.** 자유 요약의 동의어 표현도 문구 검사에서는 실패할 수 있다. 처리 시간은 같은 로컬 환경에서 순차 실행한 사례 시간이며 서비스의 P95, 병렬 처리 성능이나 일반적인 모델 속도 비교가 아니다.

### 실제 채팅 API

개발 DB의 FAQ 1150개와 기존 임베딩만 독립 평가 DB에 복사했다. PostgreSQL, 실제 EXAONE, bge-m3, Spring 채팅 API와 상담 파이프라인을 연결했고 모델과 검색 결과를 대역으로 바꾸지 않았다.

| 항목 | 결과 |
| --- | --- |
| 유심, 로밍, 명의변경, 해지의 요약 전후 후속 질문 8건 | 실행 완료 8건. 대상 복원 및 해당 정답 FAQ 검색 8건 |
| 유심과 로밍을 함께 언급한 뒤 “그건 얼마인가요?” | 대상을 임의로 확정하지 않고 확인 안내. 검색과 생성 생략 |
| 유심 상담 이후 명확하게 로밍 요금을 질문 | 새 로밍 질문으로 검색. 기존 유심 대상 유지하지 않음 |
| 유심 상담 이후 “비용은 얼마인가요?” | 생략된 대상을 기존 유심 발언에 연결해 검색 |

원문과 FAQ를 대조하면 문맥 연결과 별개로 아래 답변 문제는 남아 있다.

- 명의변경 2건: 한 명만 방문하는 경우 FAQ의 `위임장 + 인감증명서` 중 **인감증명서를 누락**했다.
- 명확한 주제 전환 사례: 하루 12100원인 무제한 요금을 **“추가로 12100원”**이라고 표현했다. 기존 Guard는 근거에 있는 숫자여서 차단하지 않았다.
- 일부 답변에 불필요한 후속 안내가 붙었다.

이 결과는 Context 전달과 기억 보존이 동작함을 보여준다. **최종 답변 11건이 모두 정확하다는 뜻은 아니다.** 필수 내용 누락과 금액의 관계 해석은 RAG 답변 품질과 의미 검증의 후속 대상으로 기록한다. 이 대조는 코드 작성 도구의 검토이며 사람이 채점한 기록으로 표시하지 않는다.

### 자동 테스트

실제 DB를 사용하는 API와 요약 저장 테스트 및 단위 테스트로 다음을 검증한다.

- 원문 발언과 순서, 부정, 명의자, 최신 정정 보존.
- 존재하지 않는 ID, 중복 ID, 형식 오류, 변조된 기억과 다른 세션의 원문 사용 차단.
- 요약 출력 검증 실패 시 저장하지 않음, 커서 조건부 갱신, 요약 제외 시 최근 원문 복구.
- 실제 저장된 요약과 커서에서 Context 재구성, 순수 인사 구간 처리.
- 장문 고객 질문 이후 커서 진행과 오래된 조건 제외, 긴 상담사 답변에서 고객 질문 및 이전 대상 보존.
- 입력 합계 초과 시 질문과 답변 단위 배치 분리, 저장 예산 초과 시 원문과 의존 관계 보존, 빈 배치의 모델 호출 생략.
- 질문과 답변 짝을 유지한 예산 제한, 이전 AI 답변 본문을 RAG에서 제외.
- 원문 질문 저장 유지, 문맥을 반영한 검색, 실제 Guard 차단과 최종 답변 저장.

초기 구현의 `clean test build --build-cache`는 전체 1582건 중 1484건 통과, 98건은 실행 조건이 있는 테스트라 제외됐다. 실측 테스트는 별도로 실행했다. 당시 집계는 [verification.json](../scripts/multiturn-evaluation/results/verification.json)에 보존한다.

장문 예산 처리 보완 후 같은 명령으로 전체 1592건 중 1494건 통과, 98건 조건부 제외, 실패 0건을 확인했다. 요약 Converter, Service, PostgreSQL Store의 관련 테스트 32건도 모두 통과했다. 이번 회귀 검증의 모델은 대역이며 EXAONE 실측을 새로 실행한 결과가 아니다. 명령, 테스트 목록과 코드 SHA256은 [장문 처리 검증 결과](../scripts/multiturn-evaluation/results/summary-budget-verification.json)에 기록했다.

## 설정과 남은 한계

| 설정 | 현재 기본값 | 의미 |
| --- | ---: | --- |
| `chat.summary.grounded-output` | `true` | 선택한 원문으로 요약 기억 구성 |
| 요약 시작 기준 | 16개 메시지 또는 추정 2048토큰 | 최근 대화가 기준에 도달하면 오래된 구간 요약 |
| 요약 뒤 최근 이력 | 8개 메시지, 추정 1024토큰 | 질문과 답변 짝을 유지한 원문 버퍼 |
| 요약 입력 / 출력 한도 | 추정 3072 / 512토큰 | 선택 입력과 모델 응답의 상한 |
| 저장하는 기억 | 최대 16개 발언, 추정 512토큰 | 선택한 원문과 매장 결과의 보존 예산 |
| 상담 분석 Context | 추정 1024토큰 | 현재 질문, 기억, 최근 대화의 합계 |
| RAG 입력 | 모델 창에서 출력 1024와 여유 256을 제외한 예산 | 시스템 프롬프트, FAQ, 질문을 먼저 확보하고 남는 범위에 이력 제공 |

토큰 수는 기존 추정기를 사용하며 모델 토크나이저의 정확한 수치가 아니다. 위 숫자는 실측을 시작할 운영 설정이며 최적값이라고 주장하지 않는다.

원문 선택은 모델이 어떤 발언을 남길지 판단하는 과정이다. 중요한 발언의 누락, 서로 다른 대상의 잘못된 연결, 최신 정정의 잘못된 해석을 완전히 없애지는 못한다. 단독 입력 예산보다 긴 고객 발언은 요약 기억에서 제외되고 이전 기억도 초기화될 수 있다. 저장 예산에 맞추는 과정에서도 오래된 선택이 빠질 수 있다. 원문은 DB에서 조회할 수 있지만 기억에서 빠진 정보를 다음 상담에 모두 복구하는 기능은 없다. 모델 호출 실패나 잘못된 선택 형식은 커서를 이동하지 않고 다음 완료 답변에서 재시도한다.

고객 발언에 없는 추천 상품명이나 목록의 “두 번째 것”처럼 **이전 AI 답변 본문에서만 대상을 찾을 수 있는 질문**은 이번 구현의 제한이다. 과거 AI 정책을 재사용하지 않으면서 필요한 대상만 검증해 꺼내는 방식은 별도 설계가 필요하다. 이미 선택에서 빠진 아주 오래된 정보를 DB 전체에서 다시 검색하는 기억 검색도 구현 범위가 아니다.

| `scripts/multiturn-evaluation/export_results.py` | 원시 자료 압축 보존과 문구 보존 지표 집계 |

| `results/V1-summary-comparison/raw/` 및 `results/V2-live-api/raw/` | 이전 실행을 포함한 입력, 모델 요청과 원본 출력, 검색 근거, 저장 답변 |

개발 DB를 대상으로 아래 명령을 실행하지 않는다. `telme_121_verification`은 실측용, `telme_121_fullchecks`는 자동 테스트용 독립 DB다. FAQ 복사 전에 대상 DB에 해당 코드의 Flyway 마이그레이션을 적용해야 하며, 복사 스크립트는 대상에 FAQ가 이미 적재돼 있으면 중단한다.

```powershell
$env:POSTGRES_PORT = '5440'
$env:POSTGRES_DB = 'telme_121_verification'
$env:RUN_TELME121_LIVE = 'true'
./gradlew.bat test --tests '*ChatSummaryLiveEvaluationTest' --rerun-tasks
./gradlew.bat test --tests '*MultiturnLiveApiEvaluationTest' --rerun-tasks

Remove-Item Env:RUN_TELME121_LIVE
$env:POSTGRES_DB = 'telme_121_fullchecks'
./gradlew.bat clean test build --build-cache
```

모델 요청과 원본 답변은 `.measure/telme121/`에 실행별로 저장된다. `export_results.py`에 최종 요약 파일, API 파일, 경계 사례 파일과 성공한 빌드 로그를 지정하면 위 결과 폴더로 보존한다. 기존 실패 실행을 새 성공 결과로 덮어쓰지 않는다.

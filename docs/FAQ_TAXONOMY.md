# FAQ 분류 체계

FAQ를 생성할 때 쓰는 세 축(카테고리 · 질문유형 · 페르소나)을 정의합니다.
사실 관계는 [`POLICY.md`](POLICY.md)를 따르고, 이 문서는 무엇을 몇 건 만들지만 정합니다.

## 세 축

```
카테고리 10종  ×  질문유형 5종  ×  페르소나 3종  =  150개 조합
```

조합마다 목표 건수를 배분해 합계 **1,150건**을 만듭니다. 최종 목표는 1,000건 이상인데 **중복 제거로 줄어들 것을 감안해 15%를 더 생성**합니다(자세한 계산은 4절).

조합을 나누는 이유는 두 가지입니다.

- **표현이 겹치지 않게 하려고**: 같은 정책을 다루더라도 질문유형과 페르소나가 다르면 문장이 달라집니다. 중복 제거(유사도 0.95) 통과율이 올라갑니다
- **검색 품질을 카테고리별로 측정하려고**: 2주차 과업인 "카테고리별 Recall 편차 분석"이 이 분류를 기준으로 합니다

## 1. 카테고리 10종

`faqs.category` 컬럼에 저장합니다. 컬럼이 `VARCHAR(30)`이라 코드는 30자 이내여야 합니다.

| 코드 | 한글명 | 범위 | 매장 업무 연계 |
| --- | --- | --- | --- |
| `BILLING` | 요금·청구 | 청구서, 납부, 미납, 소액결제 한도 | — |
| `PLAN` | 요금제 | 요금제 종류와 월정액, 기본 데이터 제공량, 이월·선물, 자격 | — |
| `USIM` | 유심 | 재발급, eSIM, 분실 처리 | `USIM_REISSUE` |
| `SUBSCRIBE` | 가입·개통 | 신규 가입, 구비 서류, 미성년자, 회선 한도 | `NEW_LINE` |
| `PORTING` | 번호이동 | 소요 시간, 구비 서류, 제한 조건, 철회 | `PORT_IN` |
| `NAME_CHANGE` | 명의변경 | 구비 서류, 처리 시간, 제한 조건 | `NAME_CHANGE` |
| `TERMINATE` | 해지·위약금 | 해지 방법, 약정 위약금, 할부 정산, 일시정지 | — |
| `DEVICE` | 단말·할부 | 할부 조건, 기기변경, 분실·파손, 반품 | — |
| `ROAMING` | 로밍·해외 | 로밍 요금제, 신청, 자동 차단 | — |
| `SERVICE` | 부가서비스·기타 | 부가서비스, 멤버십, 매장 안내, 명의도용 | — |

`USIM`, `SUBSCRIBE`, `PORTING`, `NAME_CHANGE` 네 개는 `store_service_types` 테이블의 업무 코드와 1:1로 대응합니다. 상담 중 "이 업무 되는 매장" 질문이 들어오면 카테고리로 매장을 필터할 수 있습니다.

기존 시드 데이터(`V2__seed_sample_data.sql`)가 쓰던 `BILLING`, `USIM`을 그대로 포함했습니다.

### 경계 사례

카테고리가 겹쳐 보이는 질문의 소속을 미리 정해둡니다. 생성할 때와 검수할 때 같은 기준을 씁니다.

| 질문 | 소속 | 이유 |
| --- | --- | --- |
| "요금제 바꾸면 요금이 어떻게 청구되나요?" | `BILLING` | 변경 절차가 아니라 청구 방식을 묻고 있음 |
| "요금제 언제 바꿀 수 있나요?" | `PLAN` | 요금제 자체의 변경 조건 |
| "해지하면 할부금 어떻게 되나요?" | `TERMINATE` | 해지가 주된 맥락 |
| "기기 바꾸면 할부금 어떻게 되나요?" | `DEVICE` | 기기변경이 주된 맥락 |
| "유심 잃어버렸는데 정지되나요?" | `USIM` | 유심 분실 처리 |
| "폰 잃어버렸는데 정지되나요?" | `DEVICE` | 단말 분실 처리 |
| "미성년자도 번호이동 되나요?" | `PORTING` | 번호이동 조건을 묻고 있음 |
| "미성년자 가입 서류가 뭔가요?" | `SUBSCRIBE` | 가입 서류 |
| "로밍 요금 안 내려면요?" | `ROAMING` | 로밍 맥락 유지 |
| "매장 몇 시까지 해요?" | `SERVICE` | 매장 운영 정보 |

## 2. 질문유형 5종

같은 정책이라도 묻는 방식이 다르면 검색 난이도가 달라집니다. 다섯 유형을 고르게 섞습니다.

| 코드 | 이름 | 특징 | 예시 |
| --- | --- | --- | --- |
| `FACT` | 단순 사실 | 값 하나를 묻는다. 짧다 | "유심 재발급 얼마예요?" |
| `PROCEDURE` | 절차 | 어떻게 하는지 순서를 묻는다 | "번호이동 어떻게 신청해요?" |
| `CONDITION` | 자격·조건 | 되는지 안 되는지를 묻는다 | "미성년자도 가입할 수 있나요?" |
| `TROUBLE` | 문제 상황 | 상황을 서술하고 해결을 요청한다 | "유심을 잃어버렸는데 어떡하죠?" |
| `COMPARE` | 비교·선택 | 둘 이상을 견주거나 추천을 요청한다 | "24개월이랑 30개월 할부 중 뭐가 나아요?" |

`TROUBLE`은 질문에 정책 용어가 거의 등장하지 않아 검색이 가장 어렵습니다. 검색 실패 사례가 여기 몰릴 가능성이 높아, 2주차 실패 케이스 분류에서 이 유형을 따로 봅니다.

`COMPARE`는 답변이 두 개 이상의 정책 항목을 인용하므로 `policy_ref`에 대표 항목 하나를 적고 답변 본문에 나머지를 함께 서술합니다.

## 3. 페르소나 3종

같은 질문을 누가 하느냐에 따라 어휘와 문장 길이가 달라집니다.

| 코드 | 이름 | 말투 | 예시 |
| --- | --- | --- | --- |
| `NOVICE` | 초심자 | 정확한 용어를 모른다. 구어체, 에두른 표현 | "그 칩 같은 거 새로 받으려면 돈 드나요?" |
| `EXPERIENCED` | 경험자 | 용어를 정확히 쓴다. 간결하고 조건이 구체적 | "유심 재발급 수수료와 소요 시간 알려주세요" |
| `SENIOR` | 고령층 | 문장이 짧고 단정적. 존댓말, 핵심만 반복 | "유심 바꾸는 거 얼마요" |

**답변 문체는 페르소나와 무관하게 통일합니다.** 질문만 페르소나에 따라 달라지고, 답변은 정중하고 간결한 상담 문체로 고정합니다. 답변까지 달라지면 같은 정책에 서로 다른 답변이 여러 개 생겨 검색 결과가 흔들립니다.

`NOVICE`는 정책 용어가 질문에 안 나오는 경우가 많아 `TROUBLE`과 함께 검색 난이도를 높이는 축입니다. 임계값 결정에 영향을 주므로 충분히 포함합니다.

## 4. 카테고리별 목표 건수

### 왜 1,150건인가

과제 조건은 **1,000건 이상**이지만, 생성 이후 공정이 건수를 줄입니다.

```
생성 1,150건 → 중복 제거(유사도 0.95) → 정책 대조 → 샘플 검수 → 최종 1,000건 이상
                        ↑ 여기서 줄어든다
```

정확히 1,000건을 생성하면 중복이 한 건만 걸려도 조건에 미달합니다. 

다시 생성해서 채우면 그 건도 다시 중복 검사를 거쳐야 해서 왕복이 생깁니다. 

**15% 여유를 두면 중복률 13%까지 재생성 없이 버팁니다.**

남는 건수는 버리지 않고 둡니다. 조건이 "이상"이므로 1,050건이 최종으로 남아도 문제없습니다.

### 배분

실제 통신사 상담에서 자주 나오는 순서를 반영해 가중치를 뒀습니다.

| 카테고리 | 목표 건수 | 조합당(÷15) | 비중 |
| --- | ---: | ---: | ---: |
| `BILLING` | 160 | 10~11 | 13.9% |
| `PLAN` | 150 | 10 | 13.0% |
| `SUBSCRIBE` | 130 | 8~9 | 11.3% |
| `DEVICE` | 130 | 8~9 | 11.3% |
| `USIM` | 115 | 7~8 | 10.0% |
| `PORTING` | 115 | 7~8 | 10.0% |
| `TERMINATE` | 115 | 7~8 | 10.0% |
| `NAME_CHANGE` | 90 | 6 | 7.8% |
| `ROAMING` | 80 | 5~6 | 7.0% |
| `SERVICE` | 65 | 4~5 | 5.7% |
| **합계** | **1,150** | | **100%** |

조합당 건수는 `목표 건수 ÷ 15`(질문유형 5 × 페르소나 3)입니다. 나누어떨어지지 않는 몫은 `FACT`와 `PROCEDURE`에 더 배분합니다. 실제 상담에서 이 두 유형의 비중이 가장 높습니다.

### 카테고리당 정책 항목 수

`POLICY.md`의 항목 수와 목표 건수를 함께 보면 항목당 몇 건을 만들어야 하는지 나옵니다.

| 카테고리 | 정책 항목 | 목표 건수 | 항목당 |
| --- | ---: | ---: | ---: |
| `BILLING` | 7 | 160 | 23 |
| `PLAN` | 5 | 150 | 30 |
| `SUBSCRIBE` | 4 | 130 | 33 |
| `DEVICE` | 4 | 130 | 33 |
| `USIM` | 4 | 115 | 29 |
| `PORTING` | 4 | 115 | 29 |
| `TERMINATE` | 4 | 115 | 29 |
| `NAME_CHANGE` | 3 | 90 | 30 |
| `ROAMING` | 5 | 80 | 16 |
| `SERVICE` | 5 | 65 | 13 |

항목 하나로 **13~33건**을 만들어야 하므로 **중복이 생기기 가장 쉬운 지점**입니다. 질문유형 5종과 페르소나 3종을 모두 쓰면 조합 15개가 나오고, 조합 하나당 1~3건이 됩니다. 같은 조합에서 여러 건을 만들 때는 묻는 대상(비용/시간/서류처럼 항목 안의 세부 값)과 사유(5절 ③)를 다르게 잡습니다.

`SUBSCRIBE`와 `DEVICE`가 항목당 33건으로 가장 빡빡합니다. `BILLING`·`ROAMING`·`SERVICE`·`PLAN`은 실제 FAQ에서 문의가 확인된 주제로 정책 항목을 보강해(`BILLING-05~07`, `ROAMING-04~05`, `SERVICE-05`, `PLAN-05`) 항목당 23·16·13·30건까지 낮췄습니다. 두 카테고리도 생성 중 중복이 몰리면 같은 방식으로 항목을 늘립니다.

## 5. 질문 표현 참고 출처

답변의 **사실**은 `POLICY.md`만 따릅니다. 다만 **사용자가 실제로 어떻게 묻는지**는 실제 통신사 FAQ를 참고합니다. 과제 Q&A에서 기존 통신사 FAQ 활용이 허용됐습니다.

- LG유플러스 자주하는 질문 — <https://www.lguplus.com/support/online/faq>

### 실제 FAQ 분류와의 대조

LG유플러스가 쓰는 분류와 우리 10종을 맞춰봤습니다. 

우리 분류가 자의적이지 않다는 근거이자, 뺀 영역을 왜 뺐는지 남겨두는 기록입니다.

| LG유플러스 분류 | 우리 카테고리 | 비고 |
| --- | --- | --- |
| 유심(USIM) 업데이트 · 교체 | `USIM` | 실제로도 최상위 독립 분류. 문의량이 많다는 신호 |
| 가입 및 변경 | `SUBSCRIBE` `PORTING` `NAME_CHANGE` `TERMINATE` | **우리가 4개로 세분화** |
| 요금 및 납부 | `BILLING` | |
| 해외로밍 | `ROAMING` | |
| 서비스안내 · 혜택 | `SERVICE` | 멤버십은 `SERVICE-02` |
| 모바일 | `PLAN` `DEVICE` | 상품군 축이라 업무 축으로 분해 |
| TOP10 | — | 분류가 아니라 조회수 집계 뷰 |
| 인터넷/IPTV · 전화 · U+스마트홈 | — | **모바일 전용이라 제외** |
| 결합 할인 | — | 상품군이 둘 이상일 때 생기는 개념이라 제외 |
| 소상공인 · 유독 · 공식온라인스토어 · 심플랩 | — | 브랜드·판매채널 특화라 제외 |

**"가입 및 변경"을 4개로 나눈 이유**는 두 가지입니다. 카테고리별 Recall 편차를 볼 때 어느 업무에서 검색이 약한지 분리해서 보려는 것이 하나이고, `store_service_types`의 업무 코드와 1:1로 맞춰 "이 업무 되는 매장" 필터에 바로 쓰려는 것이 다른 하나입니다. 대신 경계가 흐려지므로 1절의 경계 사례 표로 기준을 고정했습니다.

**모바일 외 상품군을 뺀 근거**는 과제 Q&A입니다. 범주는 각자 적당한 선에서 정하면 되고, 데이터에 없는 질문은 답변할 수 없다고 안내하면 됩니다. 인터넷·IPTV 질문이 들어오면 `OUT_OF_SCOPE`로 처리합니다.

참고하는 것은 **질문 문장의 어휘와 말투**까지입니다. 답변 수치를 그대로 가져오면 `POLICY.md`와 어긋나 `check_policy.py`에서 걸립니다.

특히 `NOVICE` × `TROUBLE` 조합은 정책 용어가 거의 등장하지 않아 표현을 지어내기 어렵습니다. 실제 FAQ에서 사용자가 쓰는 표현("그 칩", "폰이 안 터져요")을 가져오면 검색 난이도가 현실에 가까워집니다.

> 이 페이지는 JavaScript로 목록을 그리는 구조라 HTTP 요청만으로는 본문이 받아지지 않습니다. 브라우저에서 열어 필요한 만큼 복사해 쓰거나, 카테고리별로 질문 제목만 모아 별도 파일로 두고 참고합니다.

### 실제 FAQ에서 확인한 질문 형태

LG유플러스 FAQ 질문 50건(유심 10 / 가입 및 변경 10 / 요금 및 납부 10 / 해외로밍 10 / 부가서비스 10)을 분석한 결과입니다.
유심 10건은 실제 IMSI 보안 조치 관련이고 부가서비스 10건은 LG유플러스 고유 상품이라 우리 정책에 대응 항목이 없습니다. 두 묶음은 표현 패턴 추출에만 썼습니다.

**① 절반 가까이가 물음표가 아닌 요청문입니다.**

```
~ 방법을 알려주세요.        ~ 하고 싶어요.
~ 궁금해요.                ~ 하고 싶습니다.
```

질문유형 `FACT`·`PROCEDURE`를 만들 때 의문형만 쓰지 않습니다. 검색 대상이 되는 실제 입력은 요청문이 섞여 있습니다.

**② `TROUBLE`은 "상황 + 질문" 2단 구조입니다.**

```
[상황 서술] + ~는데 / ~습니다  →  [질문]

핸드폰을 분실했는데               일시정지를 어떻게 하나요?
미납요금으로 인해 정지된 상태입니다.  요금을 납부하면 바로 이용할 수 있나요?
요금이 이중 납부되었습니다.         환불은 어떻게 받나요?
```

**③ 사유(trigger)가 질문을 갈라놓습니다 - 중복 회피의 핵심 장치**

같은 정책 항목이라도 **왜 그 상황이 생겼는지**를 바꾸면 자연스럽게 다른 질문이 됩니다.

```
TERMINATE-04 일시정지 하나로
  군입대로 정지하고 싶은데 …
  장기 해외출장이라 정지가 필요한데 …
  핸드폰을 분실했는데 정지하려면 …
  당분간 안 쓸 건데 정지되나요?
```

항목당 13~33건을 만들어야 하는 상황에서 **같은 조합(질문유형 × 페르소나) 안의 건수를 벌리는 주된 수단**입니다. 축으로 추가하면 조합이 150개에서 수백 개로 늘어나므로, 축이 아니라 변형 장치로 씁니다.

카테고리별로 자주 쓰이는 사유를 미리 정해두고 순환시킵니다.

| 카테고리 | 사유 예시 |
| --- | --- |
| `TERMINATE` | 군입대, 장기 해외체류, 분실, 장기 미사용, 요금 부담 |
| `SUBSCRIBE` | 첫 개통, 자녀 명의, 외국인 등록, 법인 명의, 세컨드폰 |
| `PORTING` | 요금 불만, 결합 해지, 단말 구매, 통화 품질 |
| `NAME_CHANGE` | 가족 간 양도, 이직·퇴사, 명의자 사망, 미성년 → 성인 |
| `DEVICE` | 분실, 액정 파손, 침수, 배터리 노후, 기기변경 희망 |
| `BILLING` | 이중 납부, 미납 정지, 청구서 미수신, 요금 급증 |
| `USIM` | 분실, 파손, 인식 불량, 기기변경, 해외 유심 교체 |
| `ROAMING` | 출장, 여행, 장기 체류, 요금 폭탄 우려 |
| `PLAN` | 데이터 부족, 요금 절감, 가족 결합, 연령 변경 |
| `SERVICE` | 자동 결제 해지, 멤버십 등급 확인, 명의도용 의심 |

**④ `TROUBLE`에는 한 줄짜리 최소 형태도 있습니다.**

```
휴대폰결제 이용이 안돼요
월요일마다 자동으로 변경이 안 돼요
```

상황 서술 없이 `~이 안돼요` 하나로 끝납니다. 정책 용어가 거의 없어 **검색이 가장 어려운 형태**입니다. `SENIOR` 페르소나와 잘 맞습니다. 임계값 결정에 영향을 주므로 일정 비율을 반드시 포함합니다.

**⑤ 완곡한 가능 질문이 쓰입니다.** `~할 수 있을까요?`, `~가능한가요?`. `CONDITION` 유형의 실제 어미입니다.

**⑥ 기기·OS가 질문에 들어갑니다.** "아이폰은 벨소리 구매를 어디서", "워치/패드도 로밍을 별도로 신청". `DEVICE`와 `ROAMING`에서 질문을 벌리는 데 쓸 수 있는 축입니다(아이폰/안드로이드, 워치/태블릿).

**⑦ 브랜드명이 질문에 등장합니다.** "U+ 모바일(휴대폰)", "U+휴대폰" 처럼 씁니다. 우리는 "텔미"를 쓰되 대부분은 생략하는 쪽이 자연스럽습니다. 검색 대상 어휘가 브랜드명으로 쏠리면 변별력이 떨어집니다.

**⑧ 공식 FAQ에는 `NOVICE` 표현이 없습니다.** 정제된 문장만 있어서 "그 칩 같은 거" 류는 나오지 않습니다. 이 페르소나는 참고 없이 작성해야 합니다.

### 따라 하면 안 되는 패턴

실제 FAQ에서 **같은 질문 문장이 여러 항목에 반복**됩니다.

```
[번호변경안내(무료)]  어떤 서비스인가요?
[듀얼넘버]           어떤 서비스인가요?
[벨링모아A]          어떤 서비스인가요?
[번호변경안내(유료)]  어떤 서비스인가요?
[플레이스]           어떤 서비스인가요?
```

FAQ 사이트는 소분류가 문맥을 주므로 이게 성립하지만, **우리 검색은 질문 텍스트만 임베딩합니다.** 이런 질문 5건은 임베딩이 거의 동일해져서 중복 제거(0.95)에 걸리고, 걸러지지 않더라도 검색이 그중 무엇을 골라야 할지 알 수 없습니다.

**질문 문장 안에 대상이 드러나야 합니다.** "어떤 서비스인가요?"가 아니라 "듀얼넘버가 어떤 서비스인가요?"로 씁니다.

## 6. 생성 규칙

- **답변은 `POLICY.md`에 있는 수치만 인용합니다.** 문서에 없는 값을 지어내면 `scripts/check_policy.py`에서 걸립니다
- FAQ 한 건에는 근거가 된 `policy_ref`를 정확히 하나 기록합니다
- 질문은 한 문장, 답변은 2~4문장을 기본으로 합니다. 답변이 길면 임베딩에서 핵심이 희석됩니다
- 답변에 "자세한 내용은 고객센터로 문의하세요" 같은 맺음말을 반복해서 넣지 않습니다. 모든 답변에 같은 문장이 들어가면 유사도가 전체적으로 올라가 검색 변별력이 떨어집니다
- 질문에 카테고리명을 그대로 넣지 않습니다("요금·청구 관련해서 문의드립니다"). 실제 사용자는 그렇게 묻지 않습니다

## 7. 산출물 형식

`scripts/data/faq_*.json` — 배열 안에 다음 형태의 객체를 담습니다.

```json
{
  "category": "USIM",
  "question": "유심 재발급 비용이 얼마인가요?",
  "answer": "유심 재발급 비용은 7,700원(부가세 포함)입니다. 매장을 방문하시면 즉시 발급되며, 온라인으로 신청해 택배로 받으시면 2~3 영업일이 걸립니다.",
  "policy_ref": "USIM-01",
  "question_type": "FACT",
  "persona": "EXPERIENCED"
}
```

`question_type`과 `persona`는 **생성·검증용 메타데이터라 `faqs` 테이블에는 넣지 않습니다.** 적재 시점에 제외합니다. 카테고리별 Recall 편차를 분석할 때 필요하면 JSON 쪽을 참조합니다.

`version`은 적재 시 `1`, `content_hash`는 `question + answer`의 SHA-256으로 적재 스크립트에서 계산합니다.
